# 前端开发

先找到本次界面对应的真实页面、组件（Component）、主题和交互来源，再决定复用、扩展或新增。遵循项目技术栈和目录约定，不要求引入 Buildr Web 的框架或重构整个前端。

## 按实际职责开发

- 页面负责装配完整业务场景；组件（Component）承接可独立理解的展示与交互，相关输入、等待、成功和失败反馈保持在一起。
- 优先复用已有组件（Component）、主题变量和完整交互；有意改变已有行为时明确原因并修改共同来源，不能默默复制近似实现。复用范围包含产品导航与页面框架；修改或模拟局部内容不授权重画外围界面。
- 局部实现先留在所属功能，真实跨功能复用再提升到公共位置。不要为每个元素拆文件，也不要求所有组件（Component）无状态。
- 确需两种运行入口时，由入口接入数据、导航和业务操作，共享界面不直接绑定真实写入。保留正式入口的保存时机、错误反馈和版本校验。
- 样式延续当前主题与局部作用范围；新增颜色、间距或交互前先检查已有语义。让相关示例就近说明输入、操作结果及关键状态，不另建组件登记平台。

## 原型选择与授权

识别新增关键页面、主要布局或核心功能交互变化；这类变化存在实质设计选择且用户尚未表达偏好时，先询问是否需要界面原型（UI Prototype）。只有用户明确同意，才使用原型技能（UI Prototype Skill）。识别为“大改动”本身不是制作授权。

普通小改动、已明确的局部文案、样式和交互修复直接实现，不默认生成原型。只说“继续开发”不构成原型授权；同一任务已有明确授权或拒绝继续适用，不逐轮重复询问。此技能（Skill）可以持续指导开发，但不自动触发原型技能（UI Prototype Skill）。

用户决定按已有原型实施时，先核对确认版本与保存位置；尚未归入任务或仅留在临时预览位置时，在正式前端编辑前接续 `ui-prototype` 的“成果保存与接续”，由它保全成果、更新引用并验证适用的任务内展示，不重新询问是否制作原型。没有原型的普通局部修复仍直接实施。

已有原型时先核对它与当前设计及源码的差异；以当前已确认设计和行为规范为准，不让演示中的临时操作覆盖真实业务语义。

## 已授权原型与正式页面的共同来源

需要原型时，两种入口导入同一份相关界面与主题源码。原型入口只提供模拟数据（Mock Data）、内存操作和受控导航，不导入真实会话、请求初始化或业务写入。仅替换数据不够：保存、跳转、上传等副作用也必须可替换。

例如现有下拉选择是“选中即保存”，正式入口传入已有保存能力，演示入口传入本地保存；不改成另一套多选确认流程。需要侧边说明时，复用已有侧边阅读容器与交互，只替换内容。

无可用来源或无法隔离真实操作时说明具体限制，不用手写近似冒充共同源码。新界面可以在已授权的隔离位置先形成候选组件（Component），审看后完善同一来源。

## 完成判断

指出本次复用或扩展的源文件，核对调用方、样式和副作用归属。按影响验证真实交互及必要状态；存在模拟入口时对照两种入口，说明模拟边界和未覆盖范围。共同源码变化后重建受影响原型并重新验证，不把旧画面的验证当成当前结果。

代码结构取舍沿用适用的代码架构技能（Code Architecture Skill）；体验设计取舍沿用适用的体验设计技能（UX Design Skill）。不要求一次普通开发完整执行所有相关技能（Skill），不创建额外审批或验证状态。
