# 成果种类、组织与来源

## 共同说明

每份受维护成果能回答四个问题：覆盖哪个项目（Project）、服务（Service）、模块、流程或视角；依据哪些规范、代码路径、必要符号与配置；包含和不包含什么；关联哪些地图、技术图和解释文档。

优先使用文件开头的短说明、图源现有来源字段或就近导航。导航集中说明多个文件时明确覆盖成员；单纯写“参见源码”不足以定位。已有具体文件直接读取，只有位置未知时才在相应范围查找。来源版本可辅助判断漂移，不要求每次提交都更新所有成果的版本号。

## 代码地图（Code Map）

按目标表达目录、模块、主要对象、代表方法、调用关系、数据归属与副作用，帮助从功能定位真实实现。使用可点击的路径和准确符号，标注源码、生成结果与外部依赖的区别。只展开有助于理解的调用链，不复制代码全文，不建设逐行索引。

可以按系统、服务、功能或技术视角组织多张地图，同一事实可以出现在不同视角，但必须共同指向真实来源。发现规范与实现不一致时显式标注双方来源及未决点。

## 技术图（Technical Diagram）

选择系统组成、调用顺序、数据流、部署或其他实际有价值的关系。保存可维护图源和可打开的展示成果，节点、连线与说明均有事实来源；标明视角与未覆盖内容。固定图源到展示的渲染可以程序化。使用 Archify 时遵从其图源、校验、交付与视觉检查要求；其他已选图工具按其适用保证执行，不把特定工具设为所有知识工作的通用前置。

图可以直接依据代码、规范和配置，也可复用已核验地图中的定位信息。来源相关关系变化时判断是否需要改图；图源变化后生成并检查对应展示，不能手改展示造成两者分离。

## 解释文档（Explanatory Documentation）

综合、面向人地说明产品与技术。以下是推荐的内容种类，不是必须填满的文件清单：

| 文档 | 回答的问题与内容边界 | 建议位置 |
|---|---|---|
| 产品概览 | 为谁解决什么问题、主要能力、边界、协作方式与阅读入口；不罗列全部实现细节 | `docs/overview.md` |
| 核心概念与术语表 | 名称、定义、区别、作用域、来源与容易混淆的表达；复杂概念关系在相关解释中展开并链接术语表 | `docs/glossary.md`，按需另写概念专题 |
| 产品架构 | 用户、角色、业务能力、领域模块、产品边界与信息组织 | `docs/architecture/product.md` |
| 技术架构 | 系统、服务、模块组成，依赖、数据归属、接口与运行约束；引用详细地图和图表 | `docs/architecture/technical.md` 及有价值的专题 |
| 关键业务流程 | 一个目标的起点、参与者、关键顺序与状态、异常和结果；跨服务完整流程只在一处维护 | `docs/flows/<flow>.md` |
| 服务或重要模块说明 | 具体职责、能力、输入输出、数据、依赖、边界及实现入口；按阅读价值决定拆分 | `docs/services/<service>.md`，模块专题也可就近归入架构 |
| 使用指南 | 人如何表达目标、参与判断、查看与接续成果，必要手动操作 | `docs/guides/usage.md` 或已有同职责文件 |
| 开发与运行指南 | 如何开始开发、选择验证、配置、部署、排障和恢复；按实际需要拆篇，具体命令指向当前参考 | `docs/guides/` 或唯一的服务内分发文档 |

产品概览讲清当前定位。设计理由在相关内容旁明确其来源与适用条件；未来方向明确标注，较大规划留在规划区。历史审计、历史记录、对外文章按各自用途保留，不随实现自动重写。示例不是规范承诺，解释不能覆盖规范或实际代码。

解释文档可以引用代码地图、技术图或直接引用规范、代码、配置与已确认材料，没有固定生成次序。链接通常已经足够；必要摘录必须保留来源及片段更新关系，避免复制出无人维护的第二份正文。

## 推荐目录与迁移

以项目现有根为准；Buildr Product 使用：

```text
knowledge/
├── README.md
├── code-map/
├── archify/
└── docs/
    ├── overview.md
    ├── glossary.md
    ├── architecture/
    ├── flows/
    ├── services/
    └── guides/       # 有实际内容才建立
```

先按正文语义分类，再移动或合并；同一份当前说明只有一个维护位置。根导航可以保留。服务内需要随包分发的参考文档保留唯一正文并链接，不为了目录外观复制内容。

迁移前识别当前入口、相对链接、图源、测试、脚本与配置等实际消费者。迁移后更新这些依赖，记录有价值的旧位置到新位置导航；历史材料原文保留，历史链接可通过迁移导航找回，不全局替换历史正文。保留用户修改；合并时核对原文各段的去向，不能因重复标题丢失事实、理由或未来规划。

`brief.md` 属于对应 OpenSpec 变更，只解释该次变化，不放到长期知识目录，也不成为独立知识建设的前置。
