# 当前认知维护

## Purpose

根据正式 Change 或已确认当前事实的真实影响，评估、收敛、检查或独立维护 Project 当前认知，使人类知识入口与 canonical specs、实现和 registries 对齐。

## Consumer Obligations

consumer 必须提供 operation（`assess`、`reconcile`、`inspect` 或 `maintain`）、Workspace/Project identity、当前候选 tree 范围、允许的写入阶段和已有 evidence。Change lifecycle operations 还必须提供 change identity 与 artifact paths；`maintain` 必须提供 target assets、fact sources 和明确的 knowledge 写入授权，且不得伪造 Change identity 或 sidecar。多Project Task的Development consumer必须分别取得每个有效Project的Result，再以精确Project集合提交最小dispositions；provider不得把单Project Result声明为整个Task已对齐。

consumer 必须在可能修改 delivery content 的 `reconcile` 或 `maintain` 后重新建立验证 evidence，并不得在 archive 后请求当前知识写入。

## Minimum Guarantees

`assess`必须按真实影响分类目标和理由，不得生成空文档任务；`reconcile`必须以canonical specs、当前实现与registries为首要事实，更新或确认真正受影响的Brief/current knowledge，并处理terminology result；`inspect`必须核对全部已评估影响、Brief一致性、当前tree identity和unresolved terms，并按当前Task完成结论影响区分`aligned|not-applicable|attention|blocked`。只有会导致handoff遗漏必要行为、风险、兼容性或验收事实的冲突可以`blocked`；解释性漂移或无关历史债务必须`attention`。

`maintain` 必须只处理已由 canonical specs、当前实现、registries 或已确认决定证明的既有事实，只更新真实受影响的 current knowledge，不创建 Brief 或 Change sidecar。若候选内容需要新的业务决定或改变 canonical behavior，必须返回 `change-required`；authority 冲突必须返回 `unresolved`。

Provider 必须保持 README、docs、knowledge、specs、active Change 与 archive 的权威边界，并 required 使用 selected `buildr.terminology-governance/v1` provider 处理适用术语。

## Effects and Authorization

`assess` 和 `inspect` 默认只读，但可以在 Change 内维护明确授权的 workflow evidence。`reconcile` 只有在 consumer 已授权当前 Change 范围实现写入时，才能创建或更新 Brief、Project knowledge 和 sidecar。

`maintain` 只有在 consumer 已授权明确 targets，且 fact sources 足以证明当前事实时才能创建或更新 Project knowledge；不得改变 specs、实现或 registries，不得机械创建空文件、扩大到无关历史知识债务、修改 archived Change 或建立 Change-local evidence。

## Result Evidence

provider必须返回`operation`、`status: aligned|updated|unresolved|not-applicable|change-required|attention|blocked`、`project`、`impacts`、`changedAssets`、`unresolvedItems`、`sourceIdentities`和`treeIdentity`。Change lifecycle operation还必须返回`change`；`maintain`必须返回`change: none`与实际targets。Development consumer只聚合`aligned|not-applicable|attention|blocked`最小disposition，其他状态必须先根据是否改变bytes或完成结论收敛，不得伪装ready。

使用 `.buildr/knowledge-impact.yml` 时，它必须是版本化 Change workflow evidence，记录目标、理由、状态与来源，不得成为当前事实源；`maintain` 不得创建该 sidecar。

## Decision Points

当specs、实现、registries、Brief或current knowledge存在无法在当前授权内解决的冲突，impact evidence缺失/陈旧，terminology unresolved，或候选tree identity无法匹配时，provider必须返回`unresolved`；若该问题会造成当前Task错误完成结论，最终disposition必须为`blocked`，否则为`attention`并允许无关开发、Verification与handoff继续。`maintain`发现候选事实改变长期产品/业务语义时必须返回`change-required`并回到Change flow。任何knowledge写入改变delivery bytes时必须重新观察Content Target并使旧Candidate/evidence失效。

## Allowed Variations

provider 可以调整调查工具、文档排版、impact sidecar 的非规范字段和 follow-up 记录方式；必须保持四种 operation、按影响维护、事实权威顺序、无空文档、归档后无写入、`maintain` 无 Change 副作用和结构化 result evidence。
