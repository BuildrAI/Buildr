# Task Development

## Purpose

在 ready Task Environment 中把已完成的内容、Task context、verification policy 和专业 Result 收敛为稳定 Content Target、Task Candidate generation、推进决定与不可变 Development handoff。Task Development 是这些事实的唯一 Application writer/reader；它不是 Task Core、测试执行器、Git 交付器或通用状态机。

## Consumer Obligations

consumer 必须提供 active Task ID、canonical Workspace、matching ready Environment、完整 Change disposition，以及 Planning target identity。code-only Task 显式提供空 Change 列表。consumer 必须先完成实现、测试开发、current knowledge 与所有关联 Change 的最终处置，再观察稳定 Content Target；OpenSpec 是可选的 `0..N` 关联，不能成为 schema 或流程前提。

verification policy 必须来自当前 Task scope 和 Task Verification Application 返回的 declaration observations。consumer 只能选择已声明 capability，或记录明确的 Project/Service coverage gap；applicability override 必须绑定 Project、capability、required decision、范围、依据与来源。正式 Verification 必须在 Candidate freeze 前针对 Content Target 完成，Result 只能由 `buildr.task-verification@3` provider 记录。

Completion Review 必须由 `buildr.task-review@1` provider 绑定 current Candidate identity。`passed` 不自动代表业务验收通过；Verification `not-passed`、coverage gap 或 Completion `changes-required` 可以在用户作出明确、范围受限、绑定精确 Result digest 的风险接受后形成 `proceed`。没有该决定时记录 `blocked`，不得修改 Task 顶层状态。

consumer 不得直接读写 `.buildr/tasks/<task-id>/development.yml`，不得伪造 Result digest/applicability、Content Target、Candidate generation、decision 或 handoff，也不得把 Git HEAD、branch、worktree、Environment path、Agent session 或时间当 Candidate identity。

## Minimum Guarantees

- Development Application 只能通过 Task Record、Task Environment、Task Review 与 Task Verification Applications/ports 取得事实；不得直接读取 Review/Verification Result store。
- Development Receipt 使用 `buildr.task-development-receipt/v1` closed schema，保存 Task ID、Environment Receipt 逻辑引用、最小 Task context、Change dispositions、verification policy、Content Target、current Candidate/generation、最小 gates、decision 与正式 handoff snapshots。
- Receipt 不保存开发日志、diff、stdout/stderr、timing、临时 evidence path、本机 Environment 资源、完整 Result 正文、完整 Candidate history、revision、CAS、lock、lease 或跨记录事务。
- repository 必须完整 normalize、serialization round-trip，并用同目录临时文件和 atomic replace 写入；未知、损坏、不兼容或任一写入阶段失败时不得覆盖 current，也不得影响 Task sibling records。
- Content Target 由 Environment scopes 的内容 bytes 形成，可使用 Git 或 filesystem observer port；identity 不依赖绝对路径、Git tracking/staging/commit 载体、Node、npm、OpenSpec、测试框架或 Buildr 自身 registry。
- policy identity 只绑定 current declarations、selected capabilities、coverage gaps 与明确 overrides。Task Verification 不拥有或改写 policy。
- Verification applicability 必须经同一 Task Verification Application 检查 target 与 declarations；policy 要求的 capability 必须有明确 passed/failed fact，policy gap 必须有对应 Result coverage gap。结论可以是 `not-passed`，但事实必须完整。
- Candidate identity 只绑定 Content Target identity、Task Intent/scope/Change context identity、policy identity 与正整数 generation；不得包含 Planning、Verification 或 Completion Result identity。Candidate freeze 是纯身份写入，不运行生成器、Verification、Review、Change convergence、runtime sync、Git commit 或交付。
- Content、Task context 或 policy 变化使 current Candidate 失效；下一次成功 freeze 递增 generation。只替换仍适用于同一输入的 Result 不递增 generation。
- handoff snapshot 绑定 Candidate、Change dispositions、三个 current gate 的最小引用、proceed decision 和用户风险决定。已正式写入的 snapshot 是 append-only immutable；Result 替换或下一 generation 不得改写或删除旧 snapshot。
- Finish carrier equivalence 是只读检查。Finish consumer 不得借此修改 Development Receipt。

## Effects and Authorization

普通 Development 授权只覆盖 current Development Receipt 的整值写入和读取。实现、测试开发、current knowledge、Change sync/archive、专业 Result record、外部副作用、Git carrier/target transition 与 Environment cleanup 分别由对应能力授权。风险接受必须来自用户或具备明确业务授权的来源，并限制到精确 Candidate、Result digest 和 scope。

## Result Evidence

Application operation result 使用 `buildr.task-development-operation-result/v1`，返回 operation、status、taskId、Receipt read model、response-only receipt digest、派生 applicability、精确 effects、diagnostic 与 next actions。Receipt 中的 Result gate 只保存 `resultDigest`、target identity、最小 conclusion 与 `current` snapshot，不复制 Result 正文。

正式 handoff snapshot 至少保存 Candidate identity/generation 及其三个 input identities、Change dispositions、Planning/Verification/Completion gate digest/target/outcome、proceed decision、风险来源/范围和 snapshot identity/time。

## Decision Points

Task/Environment 非 current、Planning 非 ready、Change 仍 pending、declaration/policy stale、Verification 缺失或事实不完整时不得 freeze。Completion 缺失时不得 proceed。风险 gate 不为正向且缺少精确 risk acceptance 时不得 proceed 或 handoff。carrier内容不等价、Task Contribution漂移/冲突、handoff stale或Finish无法证明target transition时必须返回Task Development；单纯Delivery Baseline前进不得使Candidate失效，Finish可在确定性证明最新基线上的贡献identity等价时复用同一Candidate/generation与既有gates，但不得修改Candidate或补跑Verification/Completion Review。

## Allowed Variations

Project 可以使用任意技术栈、声明 command/Agent/external capability，并采用 Git commit、branch、tarball、安装包或其他 Delivery Carrier。Content observer 与 Finish adapter 可以按 Project 能力替换；Development schema、Candidate identity 和 authority ordering 不得硬编码 Product/buildr、dev、origin/dev、Git/worktree、OpenSpec、Node/npm 或特定测试 registry。
