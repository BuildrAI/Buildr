# 任务收尾

## Purpose

通过持久化、可恢复的 finish run 安全编排完整收尾，不接管 provider 专属的验证、Git 或 worktree 策略。

## Consumer Obligations

consumer 必须明确 task/change、请求的收尾范围、验证证据、目标分支、远端，以及所有明确排除的动作。普通“收尾”只授权已披露的delivery closeout，不授权修改候选实现以修复formal assurance发现的缺陷。需要修复时，consumer必须提供绑定task/change、failure identity与allowed scopes的版本化repair authorization；scope扩大或failure identity变化必须重新决策。

## Minimum Guarantees

provider 必须建立独立 finish run，并确保 run id 不能逃逸 canonical runs root。每个步骤持久化 `pending|running|passed|blocked|stale`、非空 input fingerprint、稳定 evidence/effect identity、invalidation dependencies、retry policy、全部 attempt timing 与可选 execution plan；缺少这些完成证据不得进入 `passed`。execution plan 必须在动作前核对 allowed cwd、绝对 executable、npm script 和 verification selector，并纳入 fingerprint。预检不得表述为 Buildr 已执行 provider action。同一 attempt 的重复完成只有 identity 完全一致时才幂等返回。run 绑定 task/change 而不绑定单个 session；resume 只重跑 blocked/stale 及其下游。正式 assurance 位于 canonical、target 与 runtime convergence 后。

多个 run 不使用 Workspace 全局锁，只为真实共享写临界区取得带 holder、token 与 expiry fencing 的短 lease；当前未过期 holder 可以使用相同 fencing identity 显式 renew，过期或失去 lease 的旧 holder不得续租、提交成功或删除接管者 lease。running step失效时必须原子终结attempt并释放仍由它持有的lease，complete run不得残留running attempt、lease或未处理stale/blocked step。

`integration-push` 必须记录push前后expected/observed target ref transition；只有push前外部漂移才阻塞并失效真实受影响下游，自身成功推进和远端已等于candidate必须幂等通过。默认push只覆盖已集成目标分支。

provider必须支持`buildr.task-finish-recovery/v1`，一次消费environment、candidate、target、runtime、change与assurance的before/after identities、effective fingerprints、transition evidence与execution plans。在同一原子checkpoint mutation中计算最早失效边界、终结受影响running attempt/lease并保留identity未变的passed evidence；随后复用safe executor推进到formal assurance或真实边界。未知或证明不完整的transition按`implementation-changed` fail closed；`runtime-projection-only`必须同时证明source/projection digests和changed paths属于provider允许集合。formal assurance失败时provider必须返回结构化repair decision并停止，不得静默修改delivery tree。只有匹配当前failure identity且所有changed paths位于allowed scopes内的`buildr.task-finish-repair-authorization/v1`，才允许`implementation-changed` recovery进入re-verification；不完整、越界或陈旧授权一律fail closed。

包含delta specs的Change必须由产品application service聚合compatibility findings、运行隔离archive rehearsal、pre-sync、deterministic plan/apply、strict validation与post-sync，并把change、delta/baseline/canonical digest、OpenSpec executable/version组成convergence receipt；全部阶段只能消费同一identity。planner只有在结构与baseline证明唯一结果时才能写入；歧义必须整批零写入并返回Agent fallback。provider通过单一identity-bound handler消费结果，不得以单个退出码替代中间契约。首次asset review后产生新的observation revision时，provider必须在cleanup前再次调用selected asset-review provider；没有revision变化时记录not-applicable。

cleanup readiness与真实completion必须分离：provider先在environment内把prepared completion receipt写入canonical Workspace，实际删除或明确保留task-owned资源后再由retained checkout finalize。prepare不得把run标记complete。

## Effects and Authorization

当前轮次的收尾授权覆盖已披露的常规归档、任务提交、集成、目标分支推送和安全本地清理。formal assurance发现的候选缺陷修复不属于上述授权。创建、推送或删除远端任务分支、强制推送、丢弃改动、改写共享历史和语义冲突决策仍明确排除。

## Result Evidence

默认返回compact checkpoint delta、next action、blocked、repair decision与timing summary；结构化child failure必须优先保留primary failed step/stage/check、exit、code/status、bounded findings/nextActions与digest绑定diagnostic，budget warning等次级信息不得覆盖主失败，非结构化失败保留exit、raw byte count、failure excerpt、preview与digest。最终evidence包含run/task/change identity、provider identities、正式验证、repair authorization与recovery、归档、提交/集成/push、完整ref transition、runtime/doctor、清理、canonical completion receipt和未触碰并发环境。run-local append-only observation ledger记录Buildr-owned command、handler、stage与recovery的identity、cwd、timing、exit和raw output bytes。completion metrics必须声明`product-complete|product-partial|external-unobserved` coverage，保留end-to-end wall-clock，并分别报告initial verification、repair、re-verification、最后有效assurance之后的closeout-only、product execution、orchestration gap与unobserved intervals；不得把测试或返工统称为收尾，也不得把部分计数表述为全部tool round trips或token消耗。

## Decision Points

遇到 required capability 被阻断、范围或目标不明确、验证不可信、语义冲突、检查失败、远端写入被拒绝、同端口 Local App 交接失败或无法安全清理时，必须停止。

## Allowed Variations

provider 可以按 Project policy 扩充 action payload，但必须保持持久化状态语义，并把验证、Git 集成、worktree、current knowledge 与资产审查策略交给各自 selected provider。
