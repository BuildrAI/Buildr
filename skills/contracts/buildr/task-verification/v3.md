# Task Verification

## Purpose

针对正式 Task 的明确交付目标，选择并执行 Project 已声明的适用验证能力，或为真正仅工作区Task记录明确的workspace coverage gap，从 transient Execution Evidence 或完整缺口事实提炼一份可移植值语义、Workspace本地持久化的 current Task Verification Result。

## Consumer Obligations

consumer必须提供active Task ID、canonical Workspace、稳定target identity和current Candidate identity/generation；正式执行能力时还必须使用Task Environment允许的execution root。`reconcile`目标中的declaration bytes尚未进入canonical Workspace时，consumer可以提交matching ready Task Environment根作为只读declaration source；Application必须验证ownership，且不得把该本机路径写入Result。`inspect`不得提交路径或要求Application重新观察声明，只能提交显式Candidate/target/declaration identity做纯值比较。consumer只能提交Execution Record identities与coverage gaps，不得提交capability outcome/facts、evidence digest、declaration identity、applicability、Result digest、Task状态或风险proceed/blocked决定。仅工作区`record`兼容入口只接受Candidate、target、唯一workspace gap和`not-passed`。

consumer必须区分四种动作：`inspect`只读取current Result并派生适用性；`verification run`绑定Candidate lease执行能力并在正式Task context中保留独立execution record，Task外run仍为transient-only；`reconcile`从matching terminal authorities派生并完整替换current Result；`record`只兼容真正仅工作区coverage gap。中断、authority不匹配、正文不完整或写入失败时不得覆盖current。

consumer与Application必须以Task显式Project、Service所属Project和Change所属Project的去重排序并集作为有效Project集合。并集非空时必须观察并保存全部非空Project declarations；只有并集为空时才是仅工作区Task，不得通过省略`scope.projects`绕过Service或Change所属Project。

## Minimum Guarantees

- Project `verification.yml` 只接受 `buildr.project-verification/v3`，声明既有 capability family 的 scope、proves、evidence、usable targets、discovery、affected/full/provider invocation及必要执行边界；旧声明不兼容读取。
- Application必须从closed Verification Request与current declarations/provider生成内容寻址Plan。正式execution和Execution Record必须绑定matching request/plan/provider/declaration/execution unit identities；preview不得充当evidence，不同Plan的records不得混合reconcile。
- capability可选通过`environment.preparation`引用同Project已登记Preparation Recipe。Formal command execution必须先纯读合并selected capability requirements，绑定capability/declaration、closure、Environment Plan/Receipt与runtime invocation identities；只有admission current且ready后才能open Execution Record或启动target/process/Browser/resource副作用。首次副作用前必须按相同expected identities重验，漂移时fail closed且record不得open。
- 只有可由声明Recipe恢复的preparation gap可以返回closed supplemental Plan Request，并且只能交给Task Environment唯一writer幂等prepare后重跑admission。辅助Service不得进入Task scope、Change、Content Target、allowed execution roots或源码写入authority。Verification不得自行安装依赖、设置`BUILDR_NODE`/PATH、猜cwd或复制Environment facts进Result。
- Formal admission只门禁正式execution、current Result与完成声明。provider/Receipt/preflight暂不可用时，无关开发、只读调查和明确非正式的有界检查不受阻塞，但不得产生Formal Result或完成声明。coverage、declaration invalid、authorization与external-system/resource gap必须保持各自owner，不得伪装成preparation recovery。
- Buildr 不开发测试。声明或适用能力不存在时只形成 coverage gap；不得在 Verification 中创建测试、框架、CI、通用 DAG、调度器或资源平台。
- command capability可以由`buildr verification run`执行；Agent capability必须作为有界Agent operation执行。正式Task run必须在首次target/process/resource副作用前要求Development consumer提供Candidate identity/generation，把Candidate与target加入invocation identity、Execution Record metadata和summary，并取得Execution Record容量；runner不得反向依赖或写Task Development。`effects.authorization: explicit`和explicit resource分别要求精确capability/resource授权。相同Task、owner、kind与exact invocation identity已有record且未显式`--retry`时，Application必须在同一原子transaction中先选择active、否则选择terminal，并在对应集合按`opened_at DESC, record_id DESC`复用latest record；不得取得resource、观察target、启动process、创建transient evidence或新record。只有显式`--retry`可以为同一identity创建独立run/record；identity输入变化仍创建首次执行。失败、重试、中断与target drift不得互相覆盖。Task外execution不接受Candidate lease、仍为transient-only且不提供caller-managed output writer。
- active只允许`running/open`。terminal outcome固定为`passed|failed|blocked|cancelled`，terminal lifecycle固定为`retained|cleanup_pending|cleaned|attention`；`attention`是lifecycle而不是outcome。terminal复用必须返回`not-started-existing-terminal`非执行evidence并保留原outcome/lifecycle；只有非attention的passed可返回成功，负向outcome或任意attention必须非零退出。Execution Record readback不得创建、替换或充当current Verification Result。
- 正式record正文只允许保存可移植摘要、受控stdout/stderr、闭合timeline与diagnostics，并受统一脱敏、截断、配额和retention约束；不得保存本机root、executable path、resource token、Environment handle或完整敏感argv。seal成功后才精确清理transient evidence；seal失败必须保留恢复现场。
- 同一 coordinated resource 的有效 waiter 必须按确定的等待顺序取得可用容量；新 waiter 不得越过仍有效的更早 waiter。等待 ticket 与执行 lease 必须保持分离，取消、timeout、崩溃或过期 ticket 只能按匹配 owner/token 或已证明过期的事实精确清理，并且不得进入 Project declaration 或 current Result。
- Workspace SQLite中的Task-scoped row是唯一current slot；current writer只写`buildr.task-verification-result/v2`，reader dual-read合法v1但将其标记为`legacy-result-candidate-unbound`且不能用于新Candidate gate。只有Task Verification Application可以解释、读取或事务整值写入该Result。
- current Result不进入Git或跨机器同步；旧`.buildr/tasks/<task-id>/verification.yml`不读取、不迁移、不双写。Execution Record、transient Execution Evidence、log、resource、Environment、runtime 与 response-only digest仍不属于current Result。
- Application从当前Task有效Project集合和Project declaration bytes生成declaration identity，并独立读取matching terminal Execution Record metadata与受控summary，核验body integrity、Task、Candidate、generation、target、Project、declaration、selected capability、target stability与outcome后派生facts；调用方不得伪造。v2 Result绑定Candidate、target identity和全部有效Project declaration identities。真正仅工作区Task保存Candidate、空declarations、空capabilities、唯一`workspace` coverage gap与`not-passed`，不得自动passed；repository新写入必须拒绝Task scope与declarations不匹配。
- reader只对调用方显式提供的Candidate identity/generation、target/declaration identity与保存值派生applicability：v2全部相等为`current`，任一不等为`stale`，未提供的axis为`unknown`；v1 Candidate axis始终legacy-unbound。不得在读取时打开路径、registry或声明文件。applicability与Result digest不持久化。
- repository 必须在 closed-schema normalization 和 serialization round-trip 后，通过单一SQLite transaction精确替换current row并在提交前重读验证；任何失败都rollback并保留旧current value。
- v2 Result只允许Candidate、target、declarations、从authority派生的capabilities/facts及closed record/run/invocation/body identities、coverage gaps、`passed|not-passed` conclusion和completed time。不得保存stdout/stderr、临时evidence path、Environment Receipt、history、revision、CAS、局部patch、assurance level、proceed/blocked或Task progression。
- Task Development 是 lifecycle consumer：它形成独立 verification policy，并通过本 Application 检查 Result target/declarations applicability 与 required facts。Task Finish 不解释、补跑或记录 Verification Result，只消费已经引用该 Result 的 formal Development handoff。

## Effects and Authorization

声明为本地、临时且 `authorization: implicit` 的已有命令可按当前任务执行。访问外部系统、持久业务数据、共享状态或显式授权资源前必须取得对应授权。Result 写入只影响当前 Task 的固定 current slot；正式execution record在SQLite与owned body目录中持久化，transient evidence只在record retained后精确清理。

## Result Evidence

`inspect`、`reconcile`与仅工作区`record`返回`buildr.task-verification-operation-result/v1`，至少包含operation、status、taskId、current slot、Result digest、派生applicability、effects、diagnostic和next actions。

closed `buildr.task-verification-result/v2`包含：

- `taskId`；
- Candidate identity、generation与contentTargetIdentity；
- `target.identity` 与可移植 summary；
- Task scope 内每份 declaration 的 Project、Workspace 相对 path 与 `sha256-*|absent` identity；
- 实际capability的Project、id、`passed|failed`、非空portable facts与closed Execution Record evidence identity；
- Project/Service scoped coverage gaps；仅工作区模式使用唯一`workspace` gap；
- `passed|not-passed` conclusion；
- `completedAt`。

Candidate content target必须等于Result target。存在failed capability或coverage gap时conclusion不得为passed。Result至少包含一个实际capability或coverage gap。空declarations只允许与空capabilities、唯一`workspace` gap和`not-passed`组合；合法v1 Result继续兼容读取但不迁移、回填Candidate/evidence或伪造历史事实。

## Decision Points

Task 非 active、target identity 不稳定、declaration 无效、capability 不在 Task/Service scope、外部副作用未授权、执行仍在进行、证据不完整或无法形成完整 Task 结论时必须停止且不得覆盖 current。测试命令完整失败可以形成 `not-passed` Result；是否带风险继续或阻塞由用户通过 Task Development 决定。

## Allowed Variations

Project 可以使用 command、CI wrapper 或有界 Agent operation，也可以声明确有需要的 coordinated/external resource。Product 自身可在测试实现内部使用专用 DAG；Project declaration、Task Result 和本 contract 不提供通用依赖图或 assurance 层级。
