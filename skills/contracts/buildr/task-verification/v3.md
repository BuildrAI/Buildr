# Task Verification

## Purpose

针对正式 Task 的明确交付目标，选择并执行 Project 已声明的适用验证能力，从 transient Execution Evidence 提炼一份可移植值语义、Workspace本地持久化的 current Task Verification Result。

## Consumer Obligations

consumer 必须提供 active Task ID、canonical Workspace 和稳定 target identity；执行能力时还必须使用 Task Environment 允许的 execution root。`record`目标中的 declaration bytes 尚未进入 canonical Workspace 时，consumer 可以提交 matching ready Task Environment 根作为只读 declaration source；Application 必须验证其 ownership，且不得把该本机路径写入 Result。`inspect`不得提交路径或要求Application重新观察声明，只能提交显式identity值做纯值比较。consumer 可以提交实际 capability facts、coverage gaps 和整体验证结论，但不得提交 declaration identity、applicability、Result digest、Task 状态、风险 proceed/blocked 决定或 Candidate generation。

consumer 必须区分三种动作：`inspect` 只读取 current Result 并派生适用性；`verification run` 只产生 transient execution evidence；`record` 只在完整结果已经形成后完整替换 current Result。中断、执行证据不完整或写入失败时不得覆盖 current。

## Minimum Guarantees

- Project `verification.yml` 使用 `buildr.project-verification/v2`，只声明既有 capability identity、Project/Service scope、invocation、applicability、proves、`requiredForDelivery`，以及确有需要的 environment/effects/resource claims。
- Buildr 不开发测试。声明或适用能力不存在时只形成 coverage gap；不得在 Verification 中创建测试、框架、CI、通用 DAG、调度器或资源平台。
- command capability 可以由 `buildr verification run` 执行；Agent capability 必须作为有界 Agent operation 执行。`effects.authorization: explicit` 和 explicit resource 分别要求精确 capability/resource 授权。完整 stdout/stderr、耗时、临时路径、Environment Receipt 和资源诊断只属于 provider-owned transient Execution Evidence，不提供 caller-managed output writer。
- 同一 coordinated resource 的有效 waiter 必须按确定的等待顺序取得可用容量；新 waiter 不得越过仍有效的更早 waiter。等待 ticket 与执行 lease 必须保持分离，取消、timeout、崩溃或过期 ticket 只能按匹配 owner/token 或已证明过期的事实精确清理，并且不得进入 Project declaration 或 current Result。
- Workspace SQLite中的Task-scoped row是唯一current slot，schema 为 `buildr.task-verification-result/v1`。只有Task Verification Application可以解释、读取或事务整值写入该Result。
- current Result不进入Git或跨机器同步；旧`.buildr/tasks/<task-id>/verification.yml`不读取、不迁移、不双写。transient Execution Evidence、log、resource、Environment、runtime 与 response-only digest仍不属于current Result。
- Application 从当前 Task scope 和 Project declaration bytes 生成 declaration identity；调用方不得伪造。Result 绑定 target identity 和全部 Task-scoped declaration identities。
- reader 只对调用方显式提供的target/declaration identity与保存值派生applicability：相等为`current`，不等为`stale`，未提供的axis为`unknown`；不得在读取时打开路径、registry或声明文件。applicability与Result digest不持久化。
- repository 必须在 closed-schema normalization 和 serialization round-trip 后，通过单一SQLite transaction精确替换current row并在提交前重读验证；任何失败都rollback并保留旧current value。
- Result 只允许 target、declarations、实际 capabilities/facts、coverage gaps、`passed|not-passed` conclusion 和 completed time。不得保存 stdout/stderr、临时 evidence reference、Environment Receipt、history、revision、CAS、局部 patch、assurance level、proceed/blocked 或 Task progression。
- Task Development 是 lifecycle consumer：它形成独立 verification policy，并通过本 Application 检查 Result target/declarations applicability 与 required facts。Task Finish 不解释、补跑或记录 Verification Result，只消费已经引用该 Result 的 formal Development handoff。

## Effects and Authorization

声明为本地、临时且 `authorization: implicit` 的已有命令可按当前任务执行。访问外部系统、持久业务数据、共享状态或显式授权资源前必须取得对应授权。Result 写入只影响当前 Task 的固定 current slot；transient evidence 使用完毕后按其 lifecycle 精确清理。

## Result Evidence

`inspect` 与 `record` 返回 `buildr.task-verification-operation-result/v1`，至少包含 operation、status、taskId、current slot、Result digest、派生 applicability、effects、diagnostic 和 next actions。

closed `buildr.task-verification-result/v1` 包含：

- `taskId`；
- `target.identity` 与可移植 summary；
- Task scope 内每份 declaration 的 Project、Workspace 相对 path 与 `sha256-*|absent` identity；
- 实际 capability 的 Project、id、`passed|failed` 和非空事实；
- Project/Service scoped coverage gaps；
- `passed|not-passed` conclusion；
- `completedAt`。

存在 failed capability 或 coverage gap 时 conclusion 不得为 passed。Result 至少包含一个实际 capability 或 coverage gap。

## Decision Points

Task 非 active、target identity 不稳定、declaration 无效、capability 不在 Task/Service scope、外部副作用未授权、执行仍在进行、证据不完整或无法形成完整 Task 结论时必须停止且不得覆盖 current。测试命令完整失败可以形成 `not-passed` Result；是否带风险继续或阻塞由用户通过 Task Development 决定。

## Allowed Variations

Project 可以使用 command、CI wrapper 或有界 Agent operation，也可以声明确有需要的 coordinated/external resource。Product 自身可在测试实现内部使用专用 DAG；Project declaration、Task Result 和本 contract 不提供通用依赖图或 assurance 层级。
