# Task Verification

## Purpose

针对正式 Task 的明确交付目标，选择并执行 Project 已声明的适用验证能力，或为真正仅工作区Task记录明确的workspace coverage gap，从 transient Execution Evidence 或完整缺口事实提炼一份可移植值语义、Workspace本地持久化的 current Task Verification Result。

## Consumer Obligations

consumer 必须提供 active Task ID、canonical Workspace 和稳定 target identity；执行能力时还必须使用 Task Environment 允许的 execution root。`record`目标中的 declaration bytes 尚未进入 canonical Workspace 时，consumer 可以提交 matching ready Task Environment 根作为只读 declaration source；Application 必须验证其 ownership，且不得把该本机路径写入 Result。`inspect`不得提交路径或要求Application重新观察声明，只能提交显式identity值做纯值比较。consumer 可以提交实际 capability facts、coverage gaps 和整体验证结论，但不得提交 declaration identity、applicability、Result digest、Task 状态、风险 proceed/blocked 决定或 Candidate generation。

consumer 必须区分三种动作：`inspect` 只读取 current Result 并派生适用性；`verification run` 执行能力并在正式 Task context 中保留独立 execution record，Task外run仍为transient-only；`record` 只在完整结果已经形成后完整替换 current Result。中断、执行证据不完整或写入失败时不得覆盖 current。

consumer与Application必须以Task显式Project、Service所属Project和Change所属Project的去重排序并集作为有效Project集合。并集非空时必须观察并保存全部非空Project declarations；只有并集为空时才是仅工作区Task，不得通过省略`scope.projects`绕过Service或Change所属Project。

## Minimum Guarantees

- Project `verification.yml` 使用 `buildr.project-verification/v2`，只声明既有 capability identity、Project/Service scope、invocation、applicability、proves、`requiredForDelivery`，以及确有需要的 environment/effects/resource claims。
- Buildr 不开发测试。声明或适用能力不存在时只形成 coverage gap；不得在 Verification 中创建测试、框架、CI、通用 DAG、调度器或资源平台。
- command capability 可以由 `buildr verification run` 执行；Agent capability 必须作为有界 Agent operation 执行。`effects.authorization: explicit` 和 explicit resource 分别要求精确 capability/resource 授权。正式Task command execution必须在首次target/process/resource副作用前取得Execution Record容量。相同Task、owner、kind与exact invocation identity已有record且未显式`--retry`时，Application必须在同一原子transaction中先选择active、否则选择terminal，并在对应集合按`opened_at DESC, record_id DESC`复用latest record；不得取得resource、观察target、启动process、创建transient evidence或新record。只有显式`--retry`可以为同一identity创建独立run/record；identity输入变化仍创建首次执行。失败、重试、中断与target drift不得互相覆盖。Task外execution仍为transient-only，不提供caller-managed output writer。
- active只允许`running/open`。terminal outcome固定为`passed|failed|blocked|cancelled`，terminal lifecycle固定为`retained|cleanup_pending|cleaned|attention`；`attention`是lifecycle而不是outcome。terminal复用必须返回`not-started-existing-terminal`非执行evidence并保留原outcome/lifecycle；只有非attention的passed可返回成功，负向outcome或任意attention必须非零退出。Execution Record readback不得创建、替换或充当current Verification Result。
- 正式record正文只允许保存可移植摘要、受控stdout/stderr、闭合timeline与diagnostics，并受统一脱敏、截断、配额和retention约束；不得保存本机root、executable path、resource token、Environment handle或完整敏感argv。seal成功后才精确清理transient evidence；seal失败必须保留恢复现场。
- 同一 coordinated resource 的有效 waiter 必须按确定的等待顺序取得可用容量；新 waiter 不得越过仍有效的更早 waiter。等待 ticket 与执行 lease 必须保持分离，取消、timeout、崩溃或过期 ticket 只能按匹配 owner/token 或已证明过期的事实精确清理，并且不得进入 Project declaration 或 current Result。
- Workspace SQLite中的Task-scoped row是唯一current slot，schema 为 `buildr.task-verification-result/v1`。只有Task Verification Application可以解释、读取或事务整值写入该Result。
- current Result不进入Git或跨机器同步；旧`.buildr/tasks/<task-id>/verification.yml`不读取、不迁移、不双写。Execution Record、transient Execution Evidence、log、resource、Environment、runtime 与 response-only digest仍不属于current Result。
- Application 从当前 Task有效Project集合和 Project declaration bytes 生成 declaration identity；调用方不得伪造。Result 绑定 target identity 和全部有效Project declaration identities。真正仅工作区Task保存空declarations、空capabilities、唯一`workspace` coverage gap与`not-passed`，不得自动passed；repository新写入必须拒绝Task scope与declarations不匹配。
- reader 只对调用方显式提供的target/declaration identity与保存值派生applicability：相等为`current`，不等为`stale`，未提供的axis为`unknown`；不得在读取时打开路径、registry或声明文件。applicability与Result digest不持久化。
- repository 必须在 closed-schema normalization 和 serialization round-trip 后，通过单一SQLite transaction精确替换current row并在提交前重读验证；任何失败都rollback并保留旧current value。
- Result 只允许 target、declarations、实际 capabilities/facts、coverage gaps、`passed|not-passed` conclusion 和 completed time。不得保存 stdout/stderr、临时 evidence reference、Environment Receipt、history、revision、CAS、局部 patch、assurance level、proceed/blocked 或 Task progression。
- Task Development 是 lifecycle consumer：它形成独立 verification policy，并通过本 Application 检查 Result target/declarations applicability 与 required facts。Task Finish 不解释、补跑或记录 Verification Result，只消费已经引用该 Result 的 formal Development handoff。

## Effects and Authorization

声明为本地、临时且 `authorization: implicit` 的已有命令可按当前任务执行。访问外部系统、持久业务数据、共享状态或显式授权资源前必须取得对应授权。Result 写入只影响当前 Task 的固定 current slot；正式execution record在SQLite与owned body目录中持久化，transient evidence只在record retained后精确清理。

## Result Evidence

`inspect` 与 `record` 返回 `buildr.task-verification-operation-result/v1`，至少包含 operation、status、taskId、current slot、Result digest、派生 applicability、effects、diagnostic 和 next actions。

closed `buildr.task-verification-result/v1` 包含：

- `taskId`；
- `target.identity` 与可移植 summary；
- Task scope 内每份 declaration 的 Project、Workspace 相对 path 与 `sha256-*|absent` identity；
- 实际 capability 的 Project、id、`passed|failed` 和非空事实；
- Project/Service scoped coverage gaps；仅工作区模式使用唯一`workspace` gap；
- `passed|not-passed` conclusion；
- `completedAt`。

存在 failed capability 或 coverage gap 时 conclusion 不得为 passed。Result 至少包含一个实际 capability 或 coverage gap。空declarations只允许与空capabilities、唯一`workspace` gap和`not-passed`组合；既有Result继续兼容读取，不迁移、回填或伪造历史workspace事实。

## Decision Points

Task 非 active、target identity 不稳定、declaration 无效、capability 不在 Task/Service scope、外部副作用未授权、执行仍在进行、证据不完整或无法形成完整 Task 结论时必须停止且不得覆盖 current。测试命令完整失败可以形成 `not-passed` Result；是否带风险继续或阻塞由用户通过 Task Development 决定。

## Allowed Variations

Project 可以使用 command、CI wrapper 或有界 Agent operation，也可以声明确有需要的 coordinated/external resource。Product 自身可在测试实现内部使用专用 DAG；Project declaration、Task Result 和本 contract 不提供通用依赖图或 assurance 层级。
