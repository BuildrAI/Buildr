# 对话交接内容定义与方案审查

本文保留原型阶段的交接信息审查。用户已确认第七版原型并授权实施；当前实现方案与检查以 `projects/product/openspec/changes/conversation-handoff/` 及任务的验证结果为准。原型使用模拟数据，不能以原型发送成功证明真实账号验收。

## 三类内容的准确含义

- 用户要求：本段对话中用户的原始输入，包括目标、补充、纠正、选择及本次新要求；用户对问题的回答和授权决定也须保留来源与范围。必要的关联回复单独标为已有决定，不冒充用户原话。附件内容与用户指令区分。
- 工作记录：各执行方在本段工作中的动作和结果，包括读取、搜索、修改、运行、检查、失败及结果未确认的操作。全部原始记录保留；直接交接的是有来源的精简动作记录，可合并重复读取和中间日志，但不能丢失失败、未完成及可能已生效的副作用。文件全文、巨大脚本和完整命令输出改为按需读取，不把已读文件正文再次塞入交接材料。
- 已有成果：当前成果索引，包括新增、修改、删除的文件、文档、生成物、检查证据，以及已经生效的外部结果。每项说明实际对象、位置、主要变化、当前版本或观察时点和验证状态；不是所有改动说明的同义词，也不把计划中的产物列为已完成。

## 新执行方继续工作所需的完整材料

1. 整体交接提示词（Prompt）：说明同一目标继续、资料来源、历史不能自动重放、继续前核对当前现场，以及原有授权按原范围有效。
2. 用户原始表达和必要关联决定，按顺序保存，保留后续纠正与撤回；有缺口就明确说明，不能声称已经完整交付。
3. 当前工作位置与身份：所属对话、任务（如有）、项目、服务、准确目录及成果引用的解析基准。没有正式任务的普通对话也能工作，不为交接强造任务。
4. 有效目标与边界：当前目标、有效约束和授权范围、尚需用户判断的事项；摘要不能扩大授权。
5. 当前进展与未完成事项：已完成、待完成、失败和未知分别列出；检查成功不等于实际服务验证或业务完成。
6. 精简执行记录与成果索引。外部操作保留准确对象、操作编号、是否确认生效；未知结果先查询，防止重复执行。
7. 可读取的证据和附件。必要图片按接收能力实际交付；不能把不可读路径或文件名当作已交付完整内容。不可重新取得的错误片段和结果编号须保留。
8. 可用摘要及其来源范围、当前记录边界、本次新要求。摘要只是本地资料的派生辅助，不能覆盖原始记录或嵌套上一份交接包。

每次从同一份本地对话、执行记录和当前成果组织。通常由 Buildr 直接组织本地记录，不调用原模型（Model）。仅当必要交接材料超出目标接收预算时，才尝试请原模型按专门提示词（Prompt）精简；额度耗尽或整理失败时，使用本地记录的必要索引与按需读取入口。不能将完整记录强塞入接收容量，也不能静默丢弃必要信息。能准确恢复原生会话（Session）时，只补其尚未收到的变化；新建执行上下文（Context）时提供相应必要材料。没有可靠摘要导出能力时不得假装迁移原生压缩结果。

## 已发现的实现落差

- 受审源码的 `ConversationApplication.prepare` 排除了 `status === 'failed'` 的记录；这会漏掉失败线索，不能直接复用于新方案。
- `ConversationApplication.reply` 将回答交给原生执行方后清除待回应项，没有显式把回答和问题身份追加到统一可见历史。新方案必须补足可恢复的用户决定来源。
- 旧版原型的成果只显示路径，整体材料缺少工作位置、有效边界和准确执行状态。第四版已在示例交接正文补入这些信息，并演示先失败、后复查通过的记录；正式实现仍待进行。

## 按轮次组织与专门提示词（Prompt）

按本地已保存的执行轮次身份组织，用户对执行中问题的答复仍归属原轮次，不把每条用户角色消息机械分成新一轮。每轮包含：用户输入、必要助手说明、执行概况、能确认的成果及最后答复；没有最终答复时明确标示中断或未完成。

执行概况说明“做了什么、结果怎样、到哪里查”。不复制工具参数中的大脚本、文件正文或完整日志，但保留不可重取的关键错误和操作编号。成果必须有本轮证据，标明位置、变化与验证状态；读取不是成果，执行了修改命令也不能自动视为修改成功。无法确认归属和状态时明示未知，不推断补齐。

`handoff-prompts.ts` 提供两份独立规则：接收提示词（Prompt）说明继续同一目标、来源与授权范围、按需查阅和核对当前现场；精简提示词（Prompt）仅在过长时供原模型整理，保留轮次与来源、失败未知及用户纠正，不继续执行工作。摘要只是辅助资料，不能替代本地原始记录，也不能成为下一次交接的唯一来源。

## 大小限制与自动回退

接收预算由目标接入的请求大小限制和上下文可用容量共同决定，并为本次用户输入、固定指令及回复预留空间；字节限制与词元（Token）限制分别计量，不能把 64 KiB 当成 64K 词元。正常先去掉文件、脚本和日志正文，按本地规则组织；仍过长才尝试模型精简。精简后仍过长，改为携带必要目标、有效边界、待办、风险和可读取的分轮索引，具体记录按需读取。没有可读取入口或必要信息仍无法容纳时，明确说明缺口，保留草稿并提供更大容量模型选择，不声称完整交接。原型中的过长状态为模拟，不证明真实接入容量。

## 界面调整

移除常驻“先整理再交接”选项。正常只显示接下来由谁、使用什么模型，以及“交接内容”入口；只显示实际改变的维度。材料较长时才简短说明将尝试精简，旧模型不可用也无需用户手写总结。

交接详情先用一句话说明“已有对话、工作记录和成果会一并交接。你可以补充要求后发送。”，已接收时改为对应完成时态。默认按轮次折叠，展开后查看五类内容。底部“查看完整交接内容”默认收起，并在展开前说明“这是发送给新执行方的完整内容，无需逐项确认。”。轮次使用紧凑分隔列表，以用户输入摘录帮助定位。完整入口展开后只显示独立框中的实际发送原文，页面解释和技术元信息不混入正文；来源范围、当前要求等只有本来属于发送正文时才随正文出现。不额外展示精简提示词（Prompt）或重复的操作提示。关闭后重新打开恢复收起。需处理的决定仍独立显明。说明从对话所在的一侧展开。

为提示统一定义浅色背景、边框及文字色：进度与一般提醒使用灰绿色 `#f0f5f3` / `#dbe6e0` / `#496258`，需要处理使用暖灰色 `#f6f3ed` / `#e6ddcd` / `#796747`。取代纯白卡片和偏橙色块，正文继续沿用系统文字色。需处理提示只突出一个必要决定和直接操作。此轮仅在原型定义，尚未修改正式主题。

## 审查结论与后续证明

补足上述信息后，方案具备让新执行方独立理解并重新核对现场的信息基础；界面无需把所有字段默认铺开。此结论仅接受修订后的方案范围，不证明真实模型调用或正式交接已经通过。

正式实现至少验证：额度用尽与摘要失败后仍可继续；用户回答、失败及未知操作不丢失；“第二个方案”等关联表达可解释；引用、成果版本和附件可读取；重复切换不嵌套旧交接包；送达未知不重发；摘要生成期间发生变化时重新核对材料边界。厂商摘要导出、原生恢复及实际容量仍需对应接入证明。
