# 在 DSH 中加入 Buildr 入口

用户想在 DSH 里直接打开 Buildr，而不是切到浏览器或桌面启动器时，使用本技能。执行者是智能体（Agent），用户只需要表达目标并确认结果。

## 用户要什么

用户要的是“在 DSH 侧栏有一个按钮，点开就是我的 Buildr”。他不应该被要求选择渠道、填写路径、理解插件机制，也不需要执行任何准备命令。

## 前置事实

- 这台机器上已经安装了 Buildr。正式版插件只打开正式版 Buildr，不涉及开发版。
- DSH 的桌面版提供侧栏底部席位；非桌面版没有这个位置，不要承诺按钮会出现。
- 插件自己会发现本机 Buildr 的位置，所以**没有单独的登记步骤**。

## 流程

1. 把插件装进 DSH，使用 DSH 自己的插件管理能力（`plugin_manager` 的 `install_bundle`）。插件来源可以是 npm 包名、代码仓库地址或本地归档。不要手工改 DSH 配置文件。

2. 告诉用户需要**重启 DSH** 才能看到入口。

3. 重启后确认入口出现、点击能打开 Buildr。这一步必须在真实桌面版确认，不能用“安装成功”代替。

## 已经装好了 Buildr 时

插件第一次被点击时会自己找到 Buildr。找不到时入口会说明“没有检测到 Buildr”，这是明确提示，不是故障：

- 用户确实还没装 Buildr → 先装 Buildr，然后重启 DSH；
- 用户已经装了却仍提示 → 核对上面的“前置事实”，把实际情况报告给用户，不要猜测路径或手工改配置。

## 开发版入口（只在开发者机器上）

开发者在同一台机器上还有一份 Buildr 开发版源码、需要单独入口时，用开发版变体：它由源码工作空间单独构建（`--dev`），装进开发者自己的 DSH profile，**不随正式发布提供**。两个入口互不影响：一个只开正式版，一个只开开发版。

用户没有开发版源码时不要提供开发版入口。

## 边界

- 不修改 DSH 的配置文件，不使用 `link:` 方式安装未打包目录（那会缺依赖）。
- 不替用户决定绑定哪个渠道；正式版插件只服务正式版 Buildr。
- 不声称已经验收：真实入口位置、点击行为与对话保留需要在桌面版实际确认一次。
- 安装失败或用户不再需要时，如实告知可以卸载，并给出卸载动作。
