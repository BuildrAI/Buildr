# 浏览器验证工具的发现与准备

需要真实页面验证而缺少浏览器操作（Browser Use）工具时，由智能体（Agent）在当前任务授权内检查、准备并验证现成工具。Buildr 不维护工具市场、统一安装目录或插件管理窗口；电脑操作（Computer Use）不属于本版交付。

## 先发现，再安装

1. 检查当前 `PATH`、项目依赖与已有浏览器技能（Skill）。Buildr 内部接入的 `HOME` 是独立账号目录；`BUILDR_HOST_HOME` 只提供原用户目录的路径线索，可据此检查已有启动器（例如 `.local/bin`）和官方安装位置，不能据此复制或继承厂家账号。优先复用实际可用的工具，不因独立 `HOME` 误判本机没有安装。
2. 已有 Tabbit 等浏览器及配套工具时，先读取其实际技能或帮助并在自己新建的页签验证。Chromium 内核相同不能证明兼容；不改变用户浏览器、共享设置或其他页签来绕过连接失败。
3. 缺少工具时，优先采用微软官方 [Playwright CLI](https://github.com/microsoft/playwright-cli)。先确认 Node.js、npm 与官方当前说明；按用户已有的项目依赖、全局 npm 安装或 `npm exec` 方式准备。必要时可选独立安装位置，但不强制建立 Buildr 工具目录。不使用其他实验目录里的临时程序，不修改全局 shell 配置，不为安装绕过系统权限。
4. 使用实际工具的 `--help` 与对应版本的浏览器安装命令。工具包和浏览器二进制分别检查；匹配的浏览器由 Playwright 下载与维护，不要求额外安装 Chrome。缺系统依赖或需要系统权限时说明准确缺口，只暂停该操作。

## 安装位置与调用

npm 的项目安装使用项目 `node_modules`；全局位置以 `npm config get prefix` 为准，缓存以 `npm config get cache` 为准。不要假定所有机器都安装在同一路径。私有任务不应仅为工具准备而修改业务依赖；已有项目工具不兼容时可选 npm 的临时执行方式或经授权的独立位置。

Playwright 的[官方浏览器缓存](https://playwright.dev/docs/browsers#managing-browser-binaries)默认在 macOS `~/Library/Caches/ms-playwright`、Linux `${XDG_CACHE_HOME:-~/.cache}/ms-playwright`、Windows `%LOCALAPPDATA%/ms-playwright`。Buildr 原生进程保留明确的 `PLAYWRIGHT_BROWSERS_PATH`；未指定时将其解析到原用户的官方默认缓存，使三家接入可以复用同一工具缓存。显式值 `0` 仍使用 Playwright 的包内安装语义。安装和运行须使用一致的路径；某个版本已存在不等于当前工具需要的版本可用。

无窗口模式（Headless）适合自动验证；需要人观察或接手时使用工具支持的可见窗口模式（Headed）。依据实际已安装浏览器与工具帮助选择配置，不把默认 Chrome 通道误当作系统已经安装 Chrome。已有浏览器必须经过实际启动和页面操作才算可用。

## 验证与释放

使用任务独占的浏览器会话（Session），只操作目标页面及自己创建的页签。先重新观察页面，再定位并完成必要点击、输入、状态断言和截图；页面验证与 HTTP 健康检查分别报告。真实登录、外部写入或业务提交继续受用户授权约束，不能注入模拟页面或拦截响应冒充真实完成。

没有图片查看能力时，明确区分页面结构与状态断言、截图生成和视觉审查（Visual Review），不能把未查看的截图称为已完成视觉验收。

报告实际工具及版本、安装或复用位置、浏览器及模式、目标地址、操作与断言、截图及未覆盖项。任务结束只关闭本次会话并清理自己生成的临时输出；不使用全局关闭或清空命令，不删除仍在使用的工具、官方共享缓存、登录资料或他人页面。长期可复用的工具不因由本次智能体安装就成为待删实验资源。
