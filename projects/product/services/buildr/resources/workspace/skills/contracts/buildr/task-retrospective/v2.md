# 任务复盘

## Purpose

按需记录 terminal Task 的 Agent 执行效率复盘，并把 pending 复盘基于当前项目事实转化为明确丢弃结论或由 todo/active Task 承接的后续改进。

## Consumer Obligations

consumer 必须提供 canonical Workspace 与 terminal Task ID。记录报告时只使用当前可见证据，并按需提供Task Record时点、专业current摘要、相关Execution Record/Finish timing、工具结果与已有current复盘；处理报告时必须先 inspect 并向用户提供原始正文或 current digest 不可变引用，再调查当前 specs、实现、knowledge 和 active Tasks。

“处理、检查、查看、分析复盘”等未指定 mutation 的宽泛请求只授权只读阶段：consumer 必须展示拟 disposition、理由、目标 Task IDs 和完整 Task effects，不得调用 Task Record create/update 或 Task Retrospective handle。只有用户直接指定完整 mutation，或明确接受刚展示且未发生实质变化的完整方案后，才能执行精确写入；完整动作本身已构成授权时不得要求重复确认。只有全部有效方向已关联承接 Task、全部丢弃方向已有理由时才可提交 handled；没有有效方向使用 no-action。

## Minimum Guarantees

provider 必须通过 Task Retrospective Application 维护单一 current Markdown Result 与 `pending|handled|no-action` disposition，并提供有默认值和硬上限的有界批量只读结果。批量读取默认只返回 pending 摘要，报告正文必须显式请求；它不得建立新存储、缓存或历史，也不得自动分析、评分或处置。

provider 必须从当前可见的任务执行过程事实与已有current复盘中主动探索确定性流程候选。可信候选必须说明重复或单次高成本/高风险证据、closed输入、Owner、停止条件、结果证据、可恢复性、预期收益、仍由人和Agent保留的判断与Rule/Skill/Application/CLI/checker/test建议落点；没有可信候选时如实说明。候选不得把推荐路径变成唯一合法路径、通用许可层或lifecycle gate，不得自动替代专业判断、修改工作资产或创建承接Task，也不得建立审批、事件、history或workflow registry。

处理单份或多份复盘时，provider必须先使用有界摘要收窄对象，再对必要来源逐项inspect，基于当前事实语义聚类、合并或丢弃候选。它不得按关键词自动聚类或把旧候选视为current事实；Application的list/inspect仍只返回事实，不执行分析。

provider 通过 selected `buildr.task-record/v2` provider 复用已有 todo/active Task 或创建 data-only todo，再写 source Task 关系。provider 必须允许多方向合并到一个 Task及一个来源关联多个 Task；不得创建 action item ID、通用 relation、第二 backlog 或自动生成 Change/Environment/artifacts。

## Effects and Authorization

inspect、list 与 current facts 调查零写入。record/handle 只写 Retrospective current row；后续承接只通过 Task Record provider 写 Task-owned rows。Agent mutation 授权必须覆盖拟 disposition、处置理由、确定性流程候选和全部 Task 创建/关联 effects；未提及的 effects 不得推断为已授权。一人或多人仍在讨论、意见不一致或没有明确接受时保持只读，不建立approval状态。候选确认只授权承接Task effects，不授权直接修改其建议落点。执行前重新 inspect 发现 current digest、拟 disposition、理由、目标 Task 或关系 effects 发生实质变化时，旧授权失效；候选边界发生实质变化时同样失效。provider 必须停止后续写入、保持 current disposition，并重新展示完整方案取得新授权；已有部分已授权 effects 只能按实际结果报告，不得冒充完整处置。

处理流程不得修改原始报告、自动激活 Task、执行研发或成为 lifecycle gate。Buildr Web 的明确按钮动作可以维护 disposition 并只读展示当前承接 Task，但不生成报告或创建 Task。

## Result Evidence

记录/单份读取返回 operation、current Result/digests、disposition、effects 与承接 Task current summaries。批量读取返回过滤条件、匹配数、返回数、截断状态、稳定排序的摘要与逐项诊断，并保持 `effects: []`；正文只在显式请求时 additive 返回。处理报告必须包含原始报告或引用、当前有效性证据、重新拆分方向、可信确定性流程候选或无候选结论、哲学护栏判断、丢弃理由、实际 target Task IDs、关系 effects 和最终 disposition。

## Decision Points

Task 未终态、报告/当前事实不可得、用户是否授权具体 disposition 或 Task effects 不明、用户仍在讨论或提出异议、Task Record provider blocked、任一关系写入失败、current digest 冲突或已授权方案发生实质变化时必须停止；保持 current disposition，不用旧授权继续写入，也不把部分落地冒充 handled。

## Allowed Variations

Agent 可以使用自由 Markdown、不同调查顺序、候选表达与目标 Task 聚合方式；不得强制固定候选列表或评分，不得估算不可得 token、跟踪 action item、自动修改 Rule/Skill/workflow、建立 history 或阻塞 Task lifecycle。
