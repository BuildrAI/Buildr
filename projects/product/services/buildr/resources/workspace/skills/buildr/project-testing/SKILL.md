# 项目测试建设

本技能（Skill）负责项目（Project）与服务（Service）的测试建设，以及 `projects/<project>/verification.yml` 测试登记的维护。测试代码、替身、项目执行入口和测试登记由这里一并维护；不再经由独立的声明接入技能转交。选择与实际执行已有检查、交付验证证据及可选任务报告由 `project-verification` 负责。

## 1. 核对真实项目

先核对用户目标、实际服务根、适用规则、现有测试代码、依赖、命令、持续集成（CI）和测试登记。目录名称与命令名称只是线索，不证明成本和覆盖；分析请求只交付方案，已有实施授权内才修改测试与登记。只读取本次相关范围，不要求正式任务（Task）、比较基线或新建计划后才能理解和运行检查。

需要分类或调整框架时读取[四类测试定义](references/testing-model-v1.md)。只使用静态检查（Static Check）、单元测试（Unit Test）、集成测试（Integration Test）、端到端测试（End-to-End Test，E2E）四类；按实际证明边界归类，不另设并列执行体系。

## 2. 建设最低充分的检查

从待证明的公共结果选择正常、失败和必要边界案例，再选择能区分正确与错误实现的最低充分检查。单元测试（Unit Test）可覆盖完整内部功能，保留真实业务判断，替换数据库、网络、文件存储和外部程序等协作者；不要求一个函数或一个类一条检查，也不为目录整齐引入额外层级。

真实数据库、HTTP、Git、文件系统协议或子进程边界使用集成测试（Integration Test）；实际入口下的完整使用流程使用端到端测试（End-to-End Test，E2E）。类型、源码依赖、声明和交付结构使用静态检查（Static Check）。同一文件混合边界时按实际检查拆分，保留断言和原有证明，不把所有旧目录机械映射为一个新类型。

单元测试（Unit Test）整套须易准备、低成本、不依赖真实账号或外部服务，不为等待状态使用真实长时间休眠。检查实际耗时、峰值资源和工作进程数量；发现成本失配时优化依赖、准备和检查本身，不为隐藏耗时改名，也不设未经项目和用户确认的统一秒数门槛。测试运行器的文件读取与工作进程启动不等于被测业务穿过真实外部边界。

替身仅隔离协作者，不复制被测算法或替换关键判断；断言公开结果与必要副作用。缺陷回归应能捕获旧错误；安全低成本可复现时核对修复前或受控错误行为，否则说明反例依据和缺口。具有状态或外部副作用时检查必要隔离、幂等、清理及重复运行。纯文档只验证真实链接、引用、渲染或结构，不测试固定措辞、标题和任意数字。

## 3. 维护登记与发现

`verification.yml` 只登记少量稳定能力、真实范围、完整入口与环境要求，不逐项维护测试文件清单。按[声明字段](references/project-verification-v4.md)与[地图写入方法](references/maintain-map.md)读取当前身份、形成完整候选、验证差异、按已观察版本更新并回读。这里是测试登记内容的唯一维护者；应用（Application）继续提供既有 `project verification inspect|validate|update` 安全写入能力。

新增或修改测试同时接入项目实际发现与相关选择，不复制第二份测试成员清单。完整入口必须覆盖该类或该族的全部检查；辅助覆盖允许重叠，主要归属不能漏项。外部根、命令、依赖或证明范围变化时同步真实登记；普通已确认事实维护在现有授权内连续完成。业务取舍、授权缺失或未获授权的范围扩大才反馈用户决定，不因内部登记步骤逐项确认。

## 4. 交接验证

向 `project-verification` 提供已存在的入口、相关选择方法、准备要求、覆盖范围与具体缺口。用户可要求任意已存在的具体检查、某类全量或相关范围，不把正式任务或比较基线作为运行前提。自动选择漏项时修正项目映射；测试不足时在授权范围内补齐。

推送前是否强制执行完整集合由具体项目政策决定；Buildr 产品明确要求四服务全部静态检查（Static Check）与单元测试（Unit Test）。这不扩大为所有用户项目的默认政策。发布仍核对准确交付物与真实平台差异，验证成功不授予公开发布或远端写入授权。

## 输出

报告实际改动、测试登记差异、发现及选择覆盖、实际成本与未覆盖项。相关检查由 `project-verification` 实际执行；本技能（Skill）不另建结果状态、统一计划或第二份报告。
