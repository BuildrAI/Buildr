# 代码架构

已有结构能承载局部修改，就在原位置扩展。只有职责归属、依赖方向或维护成本确实要变，才提出结构调整；先读相关实现、调用方和测试，不先画理想目录树。

## 决定归属和拆并

- 找到谁拥有数据、谁负责业务判断、谁执行外部副作用。保持唯一的业务写入责任；协议转换和技术适配不接管业务规则。不为目录整齐预建层级或复制相同字段的类型。
- 同一功能总是一起理解和修改时，就近放置方法、局部类型和组件。如果几个文件只做转发，考虑合并；如果某项能力需要独立保护、独立演进，或当前复杂度已妨碍修改且有清楚分界，再拆。行数本身不是依据。
- 复用须有真实调用方和一致语义。以表单为例，字段、状态和提交只属于该表单时可以放在一起，不默认拆成多套文件。需要比较具体布局、映射类型或依赖方向时，查[分层与拆并案例](references/examples.md)；以项目约定为准。

## 说明影响并验证

局部修改只说明相关位置和影响。结构设计、跨模块重构或明确要求地图时，用真实目录、职责、主要对象、代表方法及关键调用链区分现状和拟议结构，说明改动解决哪个维护问题。需要地图时使用 `code-map`；已有知识受影响时说明要校准什么，按已有授权通过 `current-knowledge-maintenance` 就地维护，不因重排目录强建规范变更。

实施后核对调用方、数据归属、副作用和已有地图，运行相应类型、编译与行为检查。目录更整齐、文件更短或编译成功，都不能替代行为正确的证据。
