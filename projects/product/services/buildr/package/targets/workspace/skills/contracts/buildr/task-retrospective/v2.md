# 任务复盘

## Purpose

按需记录 terminal Task 的 Agent 执行效率复盘，并把 pending 复盘基于当前项目事实转化为明确丢弃结论或由 todo/active Task 承接的后续改进。

## Consumer Obligations

consumer 必须提供 canonical Workspace 与 terminal Task ID。记录报告时只使用当前可见证据；处理报告时必须先 inspect 并向用户提供原始正文或 current digest 不可变引用，再调查当前 specs、实现、knowledge 和 active Tasks。只有全部有效方向已关联承接 Task、全部丢弃方向已有理由时才可提交 handled；没有有效方向使用 no-action。

## Minimum Guarantees

provider 必须通过 Task Retrospective Application 维护单一 current Markdown Result 与 `pending|handled|no-action` disposition，并通过 selected `buildr.task-record/v2` provider 复用已有 todo/active Task 或创建 data-only todo，再写 source Task 关系。provider 必须允许多方向合并到一个 Task及一个来源关联多个 Task；不得创建 action item ID、通用 relation、第二 backlog 或自动生成 Change/Environment/artifacts。

## Effects and Authorization

record/handle 只写 Retrospective current row；后续承接只通过 Task Record provider 写 Task-owned rows。处理流程不得修改原始报告、自动激活 Task、执行研发或成为 lifecycle gate。Local App 可以维护 disposition 并只读展示当前承接 Task，但不生成报告或创建 Task。

## Result Evidence

记录/读取返回 operation、current Result/digests、disposition、effects 与承接 Task current summaries。处理报告必须包含原始报告或引用、当前有效性证据、重新拆分方向、丢弃理由、实际 target Task IDs、关系 effects 和最终 disposition。

## Decision Points

Task 未终态、报告/当前事实不可得、用户是否保留意向不明、Task Record provider blocked、任一关系写入失败或 current digest 冲突时必须停止；保持或恢复 pending，不把部分落地冒充 handled。

## Allowed Variations

Agent 可以使用自由 Markdown、不同调查顺序和目标 Task 聚合方式；不得估算不可得 token、跟踪 action item、自动修改 Rule/Skill/workflow、建立 history 或阻塞 Task lifecycle。
