# Task Finish Handoff Consumer

## Purpose

消费 current formal Development handoff，准备与 Task Candidate Content Target 可证明等价的交付载体（Delivery Carrier），推进目标、按需render Workspace runtime并把 cleanup eligibility 交给 Task Environment。Task Finish 是窄交付 adapter，不是 Development、Change、Review 或 Verification authority。

## Consumer Obligations

consumer 必须提供正式 Task ID、canonical Workspace、matching ready Environment、由 `buildr.task-development@2` Application 读取的 current handoff，以及首次run所需的完整语义化commit message。仅工作区Task与Project/Service Task使用同一handoff入口；Finish不解释其中的空declarations、workspace gap、负向Result或风险授权。Agent负责根据最终内容和Workspace、Project、Service、repository约定确定subject与可选body；产品只规范化、校验、冻结和机械使用，不得根据Task ID、Change、diff或路径推断语义。不得用 Project/Change 参数、Git HEAD、branch、worktree、时间或调用方摘要代替 handoff。retained metadata-only Git handoff 仍须证明 exact paths、验证 identity、目标 branch/remote 和 selected `buildr.git-operations@1` provider ready，并由 Task Finish 分别选择 commit 与 push operation。

Git-backed Product adapter 必须把 run 绑定到 retained checkout 当前符号分支；显式 target branch 必须与当前分支一致。Environment checkout `startPoint` 只描述候选来源，不得充当交付分支 identity；detached retained checkout、显式不一致或不可解析的 local branch 必须在创建 run 前停止。Product adapter 还必须绑定 retained checkout 中真实配置的 delivery remote。Environment 对 workspace source 没有 remote 时，consumer 可以依赖 target branch upstream 或唯一配置 remote；没有可用 remote、多个 remote 无法消歧或用户指定值未配置时必须停止，不得接受本地-only delivery 冒充远端交付。

consumer除首次run的commit message外，不得提交caller evidence、Candidate、generation、risk acceptance、Result、claimed semantic equivalence或recovery manifest让产品解释。已有run与resume不得接受message覆盖。新Development handoff必须创建独立run并重新提交commit message，不能继承旧run的message identity。只有Development Application报告handoff/Candidate applicability stale时返回Task Development；Finish机械应用冲突只返回Delivery Adaptation facts。

唯一例外是用户单独明确授权的existing-run `--bootstrap-recovery`：它不接收source/module/tarball/manifest，仍进入完整retained registry与Application；Execution Record成功open后，retained Application才可从current ready Environment与current Development handoff共同确认的clean committed checkout派生run-owned capsule，并只加载Task Finish Product phase provider。candidate只获得closed allowlist runtime façade；retained Application、Structured Store runtime、Execution Record、run state machine和Environment cleanup仍是canonical owner。初始failure必须是preflight/prepare的确定provider exception origin，且无carrier、lease、delivery、retained、prepared completion或cleanup事实；否则零capsule副作用fail closed。

另一existing-run例外是 `--release-occupancy`：仅当 Task Record 当前为 `abandoned`、指定 run 绑定同一 Task 与 canonical Workspace、且从未形成成功交付时，Finish 才删除可证明属于该 run 的隔离载体。它不 push、不 complete Task Record、不把 abandoned 改成 completed，也不进入五阶段。已交付、Task 仍 active、或 carrier 所有权不可证明时 fail closed 并保留现场。

Task Finish current run、target lease与compact terminal Result MUST由canonical Workspace SQLite structured store统一持久化。每次真正执行的Finish invocation MUST在任何current/Carrier/target/recovery副作用前open独立`task-finish/finish-diagnostics` Execution Record，并把完整stdout/stderr、timeline与命令诊断先写入invocation-owned transient；只有record retained后才能精确清理该diagnostics transient。Delivery Carrier、lease、resume和其他恢复材料继续只由Finish owner管理，不得被record cleanup删除或延长。`task_finish_current`不得保存record identity/status/history或正文；`.buildr/task-finish/` MUST NOT作为新runtime的输入、authority、reader或双写目标。

## Minimum Guarantees

- canonical首次入口`buildr task finish run --task <id> --commit-message <message>`仍顺序执行`preflight → prepare → verify → deliver → cleanup`，但五阶段只覆盖handoff/current environment检查、carrier preparation、内容等价检查、交付和cleanup。新run在所有Finish副作用前规范化LF、校验非空subject、拒绝精确“交付 + 当前Task ID”占位主题，并确定性加入`Buildr-Task: <task-id>` trailer；已有run的resume只复用冻结message。
- 调用前参数、Task/Environment/handoff、target/remote、resume token与complete/no-op校验完成后，产品必须先取得execution record固定reservation；backpressure不得创建或改变Finish current、Carrier、target、lease、resume或恢复资源。首次run和每次resume使用不同invocation identity，且同一逻辑Finish run的旧record不得被覆盖。
- `preflight` 只能读取 Development handoff、Environment、当前 adapter carrier与retained target readiness；preflight、prepare、verify、deliver及复用这些阶段输出的resume都必须通过Development Application精确核对run冻结的handoff、Candidate、generation与Content Target identity，不得自行遍历历史handoffs；不得检查或解释Project activation配置、Change/current knowledge/Review/Verification store。
- `prepare`可以改变隔离carrier的commit identity，但不得改变Candidate内容或原Task worktree/index/branch。Git adapter从原任务基线到冻结source snapshot计算Task Contribution，在最新Delivery Baseline的run-owned detached worktree中机械应用，并用run-owned完整message创建commit、回读实际`%B`校验identity；clean apply记录`deterministic-reuse`，conflict保留baseline carrier并blocked返回`delivery-adaptation-required`。不执行OpenSpec convergence/archive、runtime generation、target rebase、Candidate freeze或自动冲突解决。
- Agent只可在run-owned carrier完成Delivery Adaptation。最终carrier HEAD的完整message必须保持冻结identity，否则blocked且不得deliver。resume必须核验ownership、baseline ancestry、source/handoff current、cleanliness、message identity及Project policy要求的bounded compatibility checks；resume动作或调用方boolean不得充当semantic equivalence evidence。
- `verify`调用Development Application只读确认applicability，并复核Task Contribution/Delivery Baseline/carrier identities与compatibility evidence；clean apply记录`deterministic-reuse`，适配记录`agent-reviewed-delivery-adaptation`并明确Buildr未证明语义等价。formal Verification executions必须为`0`，不得record Verification Result或执行Completion Review。
- `deliver` 继续使用短 target lease/fencing、fast-forward target transition与普通push，再按冻结 plan执行`none | render-runtime`并运行通用Workspace inventory Doctor。Doctor仍严格要求`health.ready: true`，但不选择Agent adapter把待post-Finish专属激活的Product runtime drift升级为Finish失败。Workspace根runtime source只render，其他变化none；plan不得读取Project/Service声明，也不得包含sync、Buildr development CLI/Buildr Web安装、任意command、args、env或shell。
- `render-runtime`后任何tracked/staged delta都必须blocked。普通路径的`remoteAfterRef`与`finalRemoteRef`必须都等于carrier；只有确定性证明最新target包含carrier ancestry及全部changed-path after mode/blob/删除状态时，才可记录`targetDisposition: already-contained`并以该后代ref进入cleanup。这些动作不取得Development writer authority。
- `cleanup` 先写已有 Finish delivery/completion facts，再将 delivery identities 交给 `buildr.task-environment@1`。Environment 独占资源停止、provider cleanup、共享根解除占用和 cleanup result。
- `cleanup` 必须先持久化 delivery 与 `cleanup_pending` 边界，再幂等消费 Environment cleanup；只有 Environment cleanup、Finish transient cleanup、lease释放和compact terminal Result 写后读取全部完成，Task Record 才能进入 `completed`。若进程在 Environment 已清理后崩溃，resume 只能重试 Finish-owned cleanup 与 terminal transition，不得重跑 delivery。
- invocation结束后必须独立seal受控summary、固定phase timeline、diagnostics与output；record retained后只清理该invocation diagnostics transient。seal、metadata确认或diagnostics cleanup失败只进入公开`executionRecord` operation summary，不得回滚、改写或重放remote delivery、Environment/Carrier cleanup、Task terminal或Finish current。不可捕获死亡保持record open。
- Finish不创建、递增、回退或删除Task Candidate/generation，也不拥有Candidate applicability。clean apply与Agent-reviewed Delivery Adaptation均复用同一Candidate/generation、Verification、Completion Review、decision与handoff；Finish不执行Completion Review，不决定proceed/blocked，不接受用户风险，也不修改Development Receipt。
- `task finish` 是交付收尾入口；`task complete` 只表达上述所有 gates 通过后的 Task Record terminal status。Task Finish 不建立第二套 Task complete authority。
- blocked resume token只能由产品绑定run/phase/carrier/failure生成。Development Application报告handoff/Content Target stale时，无carrier、lease、delivery、retained或cleanup事实的preflight-only旧run可以保留Execution Record后安全失效；已有任一恢复或副作用事实的旧run必须保留现场并返回`task_finish.current_run_identity_conflict`，不得自动删除、终结或换绑。已持久化delivery事实后的cleanup仍按原run完成必要清理。Delivery Adaptation、target-race、compatibility、retained与cleanup阻塞只返回相应facts与exact token。
- 明确授权的bootstrap recovery MAY在同一run重置无副作用的terminal failed preflight/prepare phase，并把原status/failure保存到bootstrap provenance；blocked run及后续阶段继续使用Product token。每个run只能绑定一个source commit/tree/provider digest/capsule identity；cleanup phase必须先持久化passed，再由retained finalizer原子移出精确可执行source并写revocation tombstone，最后执行terminal SQLite finalize。撤销中断保留可判定的source或quarantine供same-run恢复；terminal finalize失败只运行retained shell，不重新导入provider；撤销后的残留回收失败只记attention且不得重放成功phase。Candidate/generation、handoff、formal Verification和Completion Review不得变化。

## Effects and Authorization

普通“收尾”授权run-owned carrier机械准备、Agent在该carrier中的Delivery Adaptation、适用bounded compatibility checks、目标分支fast-forward/push、Workspace根runtime render、retained Doctor和Task-owned cleanup。它不授权bootstrap recovery；后者需要单独明确授权。两种授权均不允许sync、Buildr development CLI或Buildr Web安装、任意shell、Change convergence/archive、原Candidate或Task worktree修改、target rebase、正式Verification Result写入、Review、风险接受、force push、共享历史改写或丢弃用户改动。Bootstrap授权也不允许candidate canonical writer、任意provider path、npm tarball runtime或递归恢复Task。

## Result Evidence

canonical产品结果使用`buildr.task-finish-result/v2`，包含run identity、Development handoff、Task Candidate/generation、Content Target、Task Contribution、Delivery Baseline、Delivery Carrier及其activation plan、冻结提交的subject与message identity、五阶段状态、`deterministic-reuse|agent-reviewed-delivery-adaptation`、只读equivalence/adaptation facts、delivery、cleanup/completion、primary failure、可选resume token与效率指标。Bootstrap适用时additive记录retained writer mode、原failure、source commit/tree、provider digest、capsule identity/revocation与`bootstrapRecoveryExecutions: 1`；`manualRecoveryManifests`和`formalVerificationExecutions`仍为0。CLI JSON缺省或显式`--detail compact`从同一canonical Result生成closed `buildr.task-finish-compact-result/v1`，只保留状态、关键identity、current phase、主失败、next action、matching resume、关键refs、timing与portable Execution Record摘要；显式`--detail full`原样返回v2。detail不得改变执行、持久化或恢复authority。完整message只由Task Finish current run owner和实际Git commit持有，不得复制到Task Record、Development/Environment Receipt、terminal Result或Execution Record；公开投影只含subject与identity。`run`结果另外以additive portable`executionRecord`表达`not-opened|blocked|retained|attention`、record identity/outcome/body摘要与diagnostics cleanup，不得暴露SQLite、body/transient locator、Carrier绝对路径或Execution Record resource token；`inspect`保持pure Finish read model且不枚举records。record attention不得改变Finish status；complete result的`nextAction`仍按终态提供非阻塞“任务复盘”建议，blocked result继续优先提供确定性恢复动作。Git-backed普通路径的`observedTargetRef`、`carrierRef`、`remoteAfterRef`与`finalRemoteRef`必须分别来自push前观察、carrier、carrier push后回读和通用activation最终回读；`already-contained`路径还必须报告原carrier、ancestor/path-state proof与最新后代ref。所有路径必须报告`formalVerificationExecutions: 0`。兼容字段`runtimeInstall`与`localAppDelivery`可以保留为deprecated `not-applicable`，但不得参与delivered门禁；Workspace专属post-Finish evidence不得写回本Result或复制到其他authority。

## Decision Points

handoff非current、同Task current run identity冲突、Environment漂移、retained target branch detached/不一致、delivery remote缺失/歧义、carrier ownership/baseline/source/cleanliness无法证明、compatibility checks失败、push后远端ref不等于预期、retained checkout含无关dirty或cleanup不安全时停止并按失败类型返回。run factory只有请求与existing run normalized identity digest完全一致时才能幂等复用；不同identity必须抛出`task_finish.current_run_identity_conflict`。carrier准备后target ref前进时先检查精确包含；证明成立则跳过重复transition并继续，证明失败或不可得才blocked并生成精确token，从最新Delivery Baseline恢复`prepare → verify → deliver → cleanup`。Candidate/generation与既有gates保持不变。Git conflict进入Delivery Adaptation；只有Development Application报告applicability stale才返回Development rebuild。路径不重叠、clean apply或Agent resume不得被表述为语义安全。

## Allowed Variations

current Product 只提供一个直接接线的 Git carrier adapter，不建立 adapter registry、选择层或未来 adapter 占位。只有第二个真实交付 adapter 已有实现、调用方与可验证契约时，后续窄 Change 才 MAY 引入选择机制；每个 adapter 都必须证明与 handoff Content Target 等价，且不得把 adapter-specific Git/OpenSpec/Node/npm/Buildr registry 约束写回 Development schema，或恢复旧 Candidate/Verification writer。
