# Task Finish Handoff Consumer

## Purpose

消费 current formal Development handoff，准备与 Task Candidate Content Target 可证明等价的交付载体（Delivery Carrier），推进目标、按需render Workspace runtime并把 cleanup eligibility 交给 Task Environment。Task Finish 是窄交付 adapter，不是 Development、Change、Review 或 Verification authority。

## Consumer Obligations

consumer 必须提供正式 Task ID、canonical Workspace、matching ready Environment 和由 `buildr.task-development@2` Application 读取的 current handoff。不得用 Project/Change 参数、Git HEAD、branch、worktree、时间或调用方摘要代替 handoff。retained metadata-only Git handoff 仍须证明 exact paths、验证 identity、目标 branch/remote 和 selected `buildr.git-operations@1` provider ready，并由 Task Finish 分别选择 commit 与 push operation。

Git-backed Product adapter 必须把 run 绑定到 retained checkout 当前符号分支；显式 target branch 必须与当前分支一致。Environment checkout `startPoint` 只描述候选来源，不得充当交付分支 identity；detached retained checkout、显式不一致或不可解析的 local branch 必须在创建 run 前停止。Product adapter 还必须绑定 retained checkout 中真实配置的 delivery remote。Environment 对 workspace source 没有 remote 时，consumer 可以依赖 target branch upstream 或唯一配置 remote；没有可用 remote、多个 remote 无法消歧或用户指定值未配置时必须停止，不得接受本地-only delivery 冒充远端交付。

consumer不得提交caller evidence、Candidate、generation、risk acceptance、Result、claimed semantic equivalence或recovery manifest让产品解释。只有Development Application报告handoff/Candidate applicability stale时返回Task Development；Finish机械应用冲突只返回Delivery Adaptation facts。

## Minimum Guarantees

- canonical `buildr task finish run --task <id>` 仍顺序执行 `preflight → prepare → verify → deliver → cleanup`，但五阶段只覆盖 handoff/current environment 检查、carrier preparation、内容等价检查、交付和 cleanup。
- `preflight` 只能读取 Development handoff、Environment、当前 adapter carrier与retained target readiness；不得检查或解释Project activation配置、Change/current knowledge/Review/Verification store。
- `prepare`可以改变隔离carrier的commit identity，但不得改变Candidate内容或原Task worktree/index/branch。Git adapter从原任务基线到冻结source snapshot计算Task Contribution，在最新Delivery Baseline的run-owned detached worktree中机械应用；clean apply记录`deterministic-reuse`，conflict保留baseline carrier并blocked返回`delivery-adaptation-required`。不执行OpenSpec convergence/archive、runtime generation、target rebase、Candidate freeze或自动冲突解决。
- Agent只可在run-owned carrier完成Delivery Adaptation。resume必须核验ownership、baseline ancestry、source/handoff current、cleanliness及Project policy要求的bounded compatibility checks；resume动作或调用方boolean不得充当semantic equivalence evidence。
- `verify`调用Development Application只读确认applicability，并复核Task Contribution/Delivery Baseline/carrier identities与compatibility evidence；clean apply记录`deterministic-reuse`，适配记录`agent-reviewed-delivery-adaptation`并明确Buildr未证明语义等价。formal Verification executions必须为`0`，不得record Verification Result或执行Completion Review。
- `deliver` 继续使用短 target lease/fencing、fast-forward target transition与普通push，再按冻结 plan执行`none | render-runtime`并运行通用Workspace inventory Doctor。Doctor仍严格要求`health.ready: true`，但不选择Agent adapter把待post-Finish专属激活的Product runtime drift升级为Finish失败。Workspace根runtime source只render，其他变化none；plan不得读取Project/Service声明，也不得包含sync、Buildr development CLI/Local App安装、任意command、args、env或shell。
- `render-runtime`后任何tracked/staged delta都必须blocked。普通路径的`remoteAfterRef`与`finalRemoteRef`必须都等于carrier；只有确定性证明最新target包含carrier ancestry及全部changed-path after mode/blob/删除状态时，才可记录`targetDisposition: already-contained`并以该后代ref进入cleanup。这些动作不取得Development writer authority。
- `cleanup` 先写已有 Finish delivery/completion facts，再将 delivery identities 交给 `buildr.task-environment@1`。Environment 独占资源停止、provider cleanup、共享根解除占用和 cleanup result。
- Finish不创建、递增、回退或删除Task Candidate/generation，也不拥有Candidate applicability。clean apply与Agent-reviewed Delivery Adaptation均复用同一Candidate/generation、Verification、Completion Review、decision与handoff；Finish不执行Completion Review，不决定proceed/blocked，不接受用户风险，也不修改Development Receipt。
- blocked resume token只能由产品绑定run/phase/carrier/failure生成。Development Application报告handoff/Content Target stale时返回`nextWorkflow: task-development`；Delivery Adaptation、target-race、compatibility、retained与cleanup阻塞只返回相应facts与exact token。

## Effects and Authorization

普通“收尾”授权run-owned carrier机械准备、Agent在该carrier中的Delivery Adaptation、适用bounded compatibility checks、目标分支fast-forward/push、Workspace根runtime render、retained Doctor和Task-owned cleanup。它不授权sync、Buildr development CLI或Local App安装、任意shell、Change convergence/archive、原Candidate或Task worktree修改、target rebase、正式Verification Result写入、Review、风险接受、force push、共享历史改写或丢弃用户改动。

## Result Evidence

产品结果使用`buildr.task-finish-result/v2`，包含run identity、Development handoff、Task Candidate/generation、Content Target、Task Contribution、Delivery Baseline、Delivery Carrier及其activation plan、五阶段状态、`deterministic-reuse|agent-reviewed-delivery-adaptation`、只读equivalence/adaptation facts、delivery、cleanup/completion、primary failure、可选resume token与效率指标。Git-backed普通路径的`observedTargetRef`、`carrierRef`、`remoteAfterRef`与`finalRemoteRef`必须分别来自push前观察、carrier、carrier push后回读和通用activation最终回读；`already-contained`路径还必须报告原carrier、ancestor/path-state proof与最新后代ref。所有路径必须报告`formalVerificationExecutions: 0`。兼容字段`runtimeInstall`与`localAppDelivery`可以保留为deprecated `not-applicable`，但不得参与delivered门禁；Workspace专属post-Finish evidence不得写回本Result或复制到其他authority。

## Decision Points

handoff非current、Environment/Workspace Node漂移、retained target branch detached/不一致、delivery remote缺失/歧义、carrier ownership/baseline/source/cleanliness无法证明、compatibility checks失败、push后远端ref不等于预期、retained checkout含无关dirty或cleanup不安全时停止并按失败类型返回。carrier准备后target ref前进时先检查精确包含；证明成立则跳过重复transition并继续，证明失败或不可得才blocked并生成精确token，从最新Delivery Baseline恢复`prepare → verify → deliver → cleanup`。Candidate/generation与既有gates保持不变。Git conflict进入Delivery Adaptation；只有Development Application报告applicability stale才返回Development rebuild。路径不重叠、clean apply或Agent resume不得被表述为语义安全。

## Allowed Variations

current Product 只提供一个直接接线的 Git carrier adapter，不建立 adapter registry、选择层或未来 adapter 占位。只有第二个真实交付 adapter 已有实现、调用方与可验证契约时，后续窄 Change 才 MAY 引入选择机制；每个 adapter 都必须证明与 handoff Content Target 等价，且不得把 adapter-specific Git/OpenSpec/Node/npm/Buildr registry 约束写回 Development schema，或恢复旧 Candidate/Verification writer。
