# Buildr Service

## 职责

Buildr Service 是 Product Project 的可执行应用实现，负责 CLI、Workspace/Project/Service/Task Record/Task Environment/Task Review/Task Retrospective/Task Verification/Task Development/Parent Coordination/Task Finish domain、Skill-only Git Operations、Project Testing 指导、Local App HTTP/runtime 与 session 同源托管、runtime adapters、受管资产与 Component 生命周期、capability graph、验证执行、package 和发布。Local App React/Vite 权威前端源码与构建属于 sibling Service `buildr-web`；本 Service 在构建/打包时消费其产物到 `src/interfaces/local-app/web-dist/`，运行时不依赖 `buildr-web` 源码或 Vite。

## 接口与入口

- CLI：`projects/product/buildr`（开发 checkout）及 npm `buildr` 命令。
- Local App：loopback HTTP 与浏览器界面；Workspace 是全局目录，Project、Service、Task Record、Change 使用稳定详情路由。Task 列表/详情首屏使用 SQLite stored-state query projection，列表默认 active 并支持封闭过滤，复盘处置过滤只消费已保存的状态列；详情按需读取 Parent 候选。正式 Task 只由 Agent/Task Manager 创建，Local App 只编辑或结束已有 active Task。Task 详情固定为“概览、研发、证据、复盘、环境”五个一级视图及 Task-scoped Change route；研发只读调用 Task Development `inspect`，reviews 与 verification 分别只读调用自身 Review/Verification `inspect`，三个专业视图只附加读取 Task Record 与 Finish 已写入的 terminal delivery association，不依赖完整 terminal 聚合投影或其他专业 reader；复盘只读渲染 Retrospective current Result 或空态，但可在非空时通过Application所有的处置PATCH标记已处理、无需处理或重新打开。Development/Environment mutation 和专业 Result CRUD 都不进入 UI，复盘处置是唯一额外专业 mutation。全局 Change 详情的 Task 关联面板按用户动作读取 active Task stored-state projection，使用既有 Task Record PATCH 与 `recordDigest`，不增加首屏 Task/Environment/Git 读取；Task-scoped Change 仍由共享 Resolver 提供只读详情。Local App 另提供独立的“文章”入口，通过 Publication Application 只读投影已登记 Workspace 中 Product Project 的 `docs/publications/` Markdown、发布目标元数据和固定目录内的本地图片；不提供文章 writer、平台发布 adapter、数据库副本或任意文件路径读取。
- Package：`services/buildr/package/manifest.yml` 定义发布边界、workspace/project baseline、builtins、contracts、bindings 和 Components；Component definition 同时拥有 Skill fragments 与其引入的结构化 capability dependencies，package builtin descriptor 不重复维护 Component-owned `requires`。
- Runtime Skill renderer统一组合package产品入口与Workspace Skills。产品入口不接收完整capability routing dump；每个consumer只获得自身`requires`的紧凑binding block。Doctor full输出全局capability graph，destination-aware `.buildr/agent-runtime/` receipt保存受管文件identity和consumer-local contract digest/provenance快照，runtime目录不承担机器证据authority。

## Launcher 与发布运行时

- Release launcher 由 `package/launchers/build.mjs` 构建为自包含平台入口，内置 Node、Buildr application、Web 资源、依赖、图标和 macOS 动态库，用户不需要安装 Node、配置 PATH 或保留 Buildr checkout。Development launcher 同样由当前 checkout 构建，但只包含图标、identity 和平台启动脚本，绑定当前 Service source root 与 Workspace Node executable/version，不复制 Node、dylib、Buildr source、package 或 `node_modules`。
- Development 启动脚本只使用 identity 中记录的绝对 source/runtime 路径，校验 `bin/buildr.mjs`、Node version 和路径含空格等边界后固定启动 `app --port 4317`。source root、CLI 或 Node 不可用时 fail closed，status/日志返回重新安装 launcher、`buildr sync` 等恢复动作；不从 PATH 或另一个 checkout 静默回退。源码变化在重启服务后由当前 checkout 读取。
- `app launcher install` 只更新目标 channel，先 staging/verify，再停止同 channel 实例并原子替换，保留 previous rollback；Release 与 `Buildr Dev` 的安装、运行身份、诊断和卸载互不覆盖。`launcher-status/v1` 继续公开平台、channel、目标、identity 和 running instance，并为 Development 附带 source/runtime diagnostics。

## 数据与依赖

- Workspace/Project/Service、Rules、Skills、Commands 和 Components 使用 YAML manifests/registries。
- Workspace Structured Store使用每个Workspace root自身的`.buildr/local/workspace.sqlite`，由随npm package交付的连续SQL migrations、checksum ledger和Doctor管理。它是Buildr Local单机数据，不进入Git或同步；未来Server/Cloud不复用数据库文件作为共享协议。Local App registry已解析root后的read-only Application path只读取该root，不执行Git/worktree provenance观察或`git rev-parse`；writable、migration和mutation path仍执行writer guard。自举 candidate runtime 在与 retained Workspace 共享 Git common-dir 时，只能写入自己的 linked Task Validation Workspace store；写 retained canonical store 或 peer checkout 会在创建目录、SQLite、WAL/SHM、ledger 或业务 row 前被 provenance guard 拒绝。验证 store 从完整 migration chain 建立，数据不回灌主库；最终集成后的 retained runtime 才能升级主库。
- Task Record 使用Workspace Structured Store中的规范化`tasks`、Project/Service/Change关系表及closed `buildr.task-record/v1` schema；nullable `tasks.parent_task_id` self-reference foreign key直接表达单Parent/多直接Child，并由主表索引支持Children查询，不建立独立关系表。repository以单transaction维护，并按Git topology拒绝linked-worktree authority。关系拒绝不存在/terminal Parent、自引用与祖先循环，但不传播生命周期或专业动作。旧`task.yml`不读取、不迁移、不双写、不删除；同目录其他专业模块文件继续保留。Task Record只保存最小顶层事实，不保存Task Environment或其他专业模块字段。
- Task Review 使用 Workspace SQLite 中的`(task_id, planning|completion)`两个可选current slots与统一closed `buildr.task-review-result/v1` schema。同类型事务原子保存完整Result及`target_identity`、`outcome`、`updated_at`查询字段，跨类型隔离；inspect只比较调用方显式提供的保存identity，未提供时返回`unknown`。Task Review Application仍是唯一writer。
- Task Retrospective使用Workspace SQLite中按Task ID唯一的closed `buildr.task-retrospective-result/v1` current row，只允许terminal Task写入固定执行效率focus与自由Markdown。Task Record terminal result与Task Finish complete result通过既有next-action字段返回非阻塞“任务复盘”建议，随包Skills只在用户同意后路由复盘；Token按可信可得、部分可得或缺失记录来源与覆盖范围，不为补齐数值新增采集或估算。重复复盘整值替换并原子重置处置状态为`pending`；同一row另存`handled|no-action`、非空处置说明与系统时间。Skill/internal driver 与Local App通过同一Application `inspect|handle`和current digest共用处置语义，Markdown Result保持只读。它不提供公共CLI、history、评分、跨任务聚合或lifecycle gate，旧`.buildr/asset-review/`保持inert。
- Task Verification 使用 Workspace SQLite 中按Task ID唯一的closed `buildr.task-verification-result/v1` current row。record action绑定opaque Content Target identity和由Application观察的Project declaration identities，并在同一transaction保存完整Result及`target_identity`、`outcome`、`updated_at`查询字段；inspect不接受declaration root或重新读取声明，只比较调用方显式提供的保存identity。持久模型不含Candidate/generation、execution stdout/stderr、Environment Receipt、revision/history、风险或推进决定；Task Verification Application仍是唯一writer/reader。
- Task Development使用Workspace SQLite中按Task ID唯一的closed`buildr.task-development-receipt/v3` current row，不读取旧YAML，v1/v2 JSON只读归一化为Parent facts absent且不backfill。每个合法action先形成Receipt与正式applicability observation，再由唯一repository在同一transaction保存`record_json`、`applicability_status`、`applicability_json`和`observed_at`；inspect只返回这些保存事实，不重新观察Environment、Content Target或declaration。Receipt增加可选closed Parent Plan、Child planned Contribution binding、Parent final acceptance，并让既有append-only handoff可选携带Contribution Handoff；仍保存Environment逻辑引用、Task context、最小planning nodes/dispositions、可空Content Target、verification policy、current Candidate/generation、最小gate或waiver refs和decision，不保存Child状态、专业artifact/Result正文、execution evidence、Git carrier、绝对路径或完整history。`pending`允许专业Change继续演进；`converged`必须由Task Record的Task-scoped Change read model证明当前working copy为available且archived。
- Parent Coordination Domain/Application不拥有repository。它通过Task Record取得直接关系，通过Development取得Parent Plan/binding/current handoff，通过Review取得Plan identity applicability，通过Terminal Delivery只接受matching Finish association证明Child delivery，动态返回Contribution disposition与最终验收前置条件。CLI、Local App与Agent共用该Application；Child状态不回写Parent，Child completed无matching handoff为`unproven`，Parent final acceptance和completed均为显式独立动作。没有Parent Plan的历史Task保持`legacy`；不扫描、迁移、推断或改写旧Parent Change/checkbox。
- Task Execution Record使用单张SQLite`task_execution_records`表保存closed metadata，并由唯一Application组合`.buildr/local/task-execution-records/<owner>/<record-id>/`受限正文Store。v1开放Verification execution与Finish diagnostics两组owner/kind，提供open、seal、inspect/list、failure resolution和单记录cleanup；正式Task command Verification与每次真正执行的Finish invocation均已接入producer，Task外Verification run仍为transient-only。open先预留固定record quota，正文先版本化脱敏与安全截断，再通过staging/manifest原子publish，retained后才精确清理producer-owned transient evidence。retention、attention恢复、CAS cleanup与cleaned tombstone均由该authority维护。本阶段仍不注册CLI、Local App、Doctor或批量GC，不建立Consumer/Adoption、通用payload/history、execution resource writer或lifecycle聚合。

Task Record与各专业模块共用`.buildr/local/workspace.sqlite`，但不合并Domain、Application、writer或状态机。已退役的`task_lifecycle_current`不再复制跨专业事实；Task Overview与Parent Coordination只组合各owner已保存事实，不新增store、cache、view、progress/lifecycle/event/history表或writer。Task current records不发布、不进入Git、不进行本地多机同步；Task Metadata Publication、静态Task Board与旧Task Asset Review生成链均已清退。既有静态页面与`.buildr/asset-review/`只作为历史数据保留，不由Service读取或维护。Environment与Finish继续拥有各自本机运行/交付事实，Buildr Server/Cloud只作为未来团队协作方向。
- OpenSpec 依赖 `@fission-ai/openspec` 1.6.0；apply 前使用上游 strict validation 与 current Planning Review，Buildr 补充跨 Change conflict evidence、文件事实驱动的确定性收敛事务和 runtime contributions。`baseline create`、阶段型 `check`、`sync-plan`、`sync-apply` 公开 CLI 已删除，deterministic primitive 只在 `converge` 事务内部组合；历史 archive bytes 保持 inert，不作为当前授权。
- Local App Task API 先把已登记 `workspaceId` 解析为 canonical root。Overview endpoint调用Task Overview Application，用一次参数化SQLite联表查询返回Task与各专业current的最小摘要；Development、Environment、Review、Verification与Retrospective GET调用各自Application `inspect`并使用`no-store`。专业endpoint不接受任意root/path；唯一额外writer是受同源、session、JSON白名单与current digest保护的Retrospective处置PATCH，它只调用Application `handle`。Finish的唯一`task_finish_current`行保存current或compact terminal及本次采用的handoff、Candidate与三个gate最小关联；Terminal Delivery从terminal payload读取并与Development handoff确定性匹配，不用后续current Result重新证明历史关联。Change全局collection保持retained-only，Task关联详情通过共享Resolver从matching Environment execution root或retained Project读取。
- Local App 的四个 Task 只读操作通过固定容量 bounded read executor 执行，默认 2 个 long-lived Worker、32 个 FIFO queued slots；Worker 只接受 overview/development/reviews/verification operation 并在自身 runtime 中读取既有 Application read model。队列满返回 `local_app_read_queue_full`，请求取消不重试且运行中结果丢弃，Worker failure 只结算当前请求并恢复容量；server close 释放 pool。该 executor 不承载 mutation、Environment、worktree、Finish 或 Doctor，也不重新执行已解析 root 的 Git/worktree provenance 或 `git rev-parse`。
- Project根可选`preparation.yml`使用closed`buildr.project-environment-preparation/v1`长期声明Project-wide或Service-scoped Recipe。Agent按Task Record完整Project/Service scope提交Plan Request；Task Environment Application从Task execution root解析Declaration与Recipe identity，保存Plan v2和closedReceipt v5到Workspace SQLite唯一`task_environment_current`。Receipt分层保存Declaration/Scope/Recipe/Step current与prepared identity、executed、inputs/outputs/required/status/diagnostic，以及既有scope/root、Runtime/CLI/projection、provider、资源和cleanup facts。Application不扫描仓库manifest或实现技术栈适配器；任一required Recipe/Step缺失、漂移或失败时整体blocked。`inspect`只读live observation且不升级Plan，Local App GET只读saved current；旧Receipt只读兼容，只有显式Plan Request升级。
- Git worktree provider 只在 Git common-dir 保存 `buildr.git-worktree-evidence/v1`，包含 repository plan、checkout/branch/HEAD/clean/registration 和 Git effects。`worktree create|inspect|cleanup` 不返回 Environment ready、Runtime/CLI/依赖、资源、恢复或总 cleanup 结论。
- Git Operations 只由 `git-operations` Skill 和 `buildr.git-operations/v1` contract 表达调用期行为，不新增 Application、CLI、Receipt 或 store。consumer 提供 repository/operation/ref/scope/授权；Result 只返回适用的前后 identity、完整 push range、变化维度和实际 effects。
- 普通 Rule/Skill 内容修改不要求新 session、reload、re-enter 或 activation evidence。候选 CLI/runtime 可以在自身 Task Validation Workspace 验证；只有集成到 retained source 后正式 runtime 才同步生效。bounded Agent capability 必须由 Agent 形成事实，文件投射或 Environment ready 本身不等于验证通过；Result 不复制 Environment Receipt。

Workspace Node identity 进入 Environment Receipt 的 Runtime probe 与 execution binding，并绑定verification execution evidence/record及Finish本机run/resume判断，但不进入Content Target或Task Candidate identity。Agent runtime 只能消费该 identity，不能选择或保存 Node version；验证 executor 为 node、npm、测试和子进程统一注入受管环境。portable Task Verification Result 只绑定调用方Content Target和Project declarations，不复制Node/Environment事实。

## 运行与验证

Task Record以Domain/Application/SQLite repository构成独立writer；Task Environment、Task Review、Task Retrospective、Task Verification与Task Development继续使用各自Domain/Application/repository。它们只共享Task ID，Task Record不再以Task目录或文件存在作为authority。Task Development只通过bundled Skill和internal driver的`begin|planning|observe|policy|gate|freeze|decide|handoff|carrier` actions写入；Task Retrospective通过Skill/internal driver的`record|inspect|handle`工作，Local App只新增同一Application所有的处置mutation；二者都不注册公共CLI。`git-operations`、`task-environment`、`task-review`、`task-retrospective`、`task-verification`、`task-development`与窄`task-worktree`分别提供对应独立capability。

Service 使用 Node.js ESM并要求Node 24.15+，开发依赖通过lockfile与`npm ci`收敛。Workspace 在 `.buildr/workspace.yml` 维护精确 `runtime.node.version`；`init` 采用当前受支持 CLI Node 并准备本机受管 runtime，`sync` 按声明恢复且不改版本，`doctor` 只读核对声明、Node/npm/CLI/验证环境及SQLite schema/integrity并建议恢复动作。开发与安装入口的普通命令固定使用该 runtime；仅 `init`、`doctor`、`sync` 可在 runtime 缺失时使用兼容 bootstrap Node。npm package 的 `engines.node` 最低为`>=24.15.0`。`task verification record` 的 `--declaration-root` 只用于正式写入前观察声明，`task verification inspect` 不接受该参数；Browser changed dispatcher 优先消费 `BUILDR_CHANGED_PATHS_JSON`，否则从 execution root 的 Git base 推导，无法解析时返回明确的 capability input error；run 的 target drift 以 added/removed paths 和 status change 单独报告。

Project `verification.yml` 使用 closed v2 declaration，只描述少量稳定、可独立选择的已有 capability；测试意图、执行边界、成本、范围、验证目标和目标耗时保留在 Project Testing 或项目 registry。Buildr 的唯一 verification registry 为每个 step 保存 owner、测试意图、执行边界、证明范围、目标耗时、主要证据 owner、环境足迹、隔离方式和重置负担；`fast` profile 表达低成本 Quick，inputs 表达 affected owner，`candidate` profile 表达显式核心完整回归，三者不再复制为混合编排场景分类。Planner 在启动 verifier 前拒绝穿过真实 filesystem、CLI、Git、网络或 Workspace 生命周期的 Component，也拒绝需要重复 cleanup 或完整生命周期的 Quick；低成本 Integration 只有在有界、可测、隔离且无重置负担时才可例外进入。`test:contract` 只保留 Static Conformance 与只读 Product tree 检查；真实开发入口、Git、临时目录和 cleanup case 由 `test:integration` 的 affected/focus/Candidate owner 承担。完整 CLI、Git、Workspace 生命周期由唯一 `test:system` 入口承载，旧 `test:integration:fast` 不再保留。System 的 Task lifecycle 测试在一次运行内共享 `task-lifecycle/v1` 不可变基线，每个 case 使用独立 sandbox；初始化、Git/Task Environment、安装、迁移与 Finish owner 保持完整隔离。OpenSpec contract/recovery cases 在 Candidate 中互斥，package parity 只持有代表输出和一次 init mutation，安装后 sync/doctor/uninstall 由 release tarball smoke 独占。默认 local/CI 允许两个使用不同临时 root 的 `workspace-saturating` verifier 有界并行，资源受限 CI 保持单路。正式交付只有一个 required `product.delivery`，在冻结 Candidate 上由 changed planner 选择 affected；registry/planner/runner、声明或 timing 等全局 owner 变化时同一 plan 扩展为 full。`product.full-regression` / `test:candidate` 保留为显式完整回归；Browser 由独立、条件化必需 capability 持有，Release 专项保持独立。上述能力和 Product-only runner 不构成通用 assurance 层级。`buildr verification run --project <code> --capability <id> ... --target-identity <identity>` 随npm runtime发布，只执行显式command capabilities；Task外run输出provider-owned transient evidence，正式Task run则在启动前open execution record，seal成功后清理transient evidence。公开JSON只返回portable executionRecord摘要，不暴露SQLite或body locator。`effects.authorization: explicit`与explicit resource分别要求精确capability/resource授权；被真实claim的`coordinated`资源才通过Git common-dir lease协调。该机制不调度Agent或任务，也不写current Result。

Product `test:candidate` 额外执行 `concurrent-task-acceptance` 组合验收：在单一临时多仓 Workspace 创建两个正式 Task，并发 prepare 两个真实 Environment，从不同 cwd 按 Task ID 调用 Receipt 返回的绝对 CLI invocation，再并发执行显式 `verification run`、记录两个不同 Task-scoped current Verification Result，并启动随机端口 Preview。验收按 fixture、environment prepare、Task invocation、verification、verification result、resource coordination、preview、failure diagnostics 与 cleanup 输出阶段 timing，并核对多仓 scope、allowed roots、共享容量等待与释放、不同 Result path/digest/current applicability、非空 execution identity、错误 Task 无法停止对方 Preview、异常子进程诊断、顺序 Environment 清理保持另一 Task 及 retained doctor。独立 invocation、Preview stop 与 Task abandon 可以并发；只有证明 peer preservation 的 Environment cleanup 保持顺序。该步骤使用本地临时 Git 与进程，不访问外部系统。

Task Finish是`buildr.task-finish/v1`的固定五阶段窄adapter。CLI只公开`task finish run|inspect`，首次run只接受Task ID和可选target branch/remote参数，从Task Development Application取得current研发交接（Development Handoff）；不接受Project/Change、Candidate/generation、Verification或caller-authored authority。current Product只有一个直接接线的Git carrier adapter，不建立adapter registry或未来路径占位；target branch来自retained canonical Workspace当前符号分支，Environment `startPoint`不提供交付branch authority。`preflight → prepare → verify → deliver → cleanup`保持不变：prepare在最新交付基线（Delivery Baseline）的run-owned detached worktree机械应用任务贡献（Task Contribution）；clean apply记录`deterministic-reuse`，Git conflict保留baseline carrier并返回交付适配（Delivery Adaptation）。Agent只编辑该carrier，Buildr恢复时核验ownership、baseline、source/handoff、cleanliness、path/mode/blob/tree/head与Project policy要求的compatibility checks；verify对适配只记录`agent-reviewed-delivery-adaptation`，`formalVerificationExecutions`固定为0。

Finish不解析或收敛Change/current knowledge，不执行target rebase、formal Verification Result写入、Completion Review、Candidate generation、`proceed / blocked`或风险接受。deliver普通路径只允许已核验carrier的fast-forward、普通push与远端ref回读；target前进时仅在carrier ancestor及全部changed-path after mode/blob/删除状态精确保持时记录`already-contained`、跳过重复transition并保留原carrier与最新后代ref。随后执行类型化retained runtime activation与通用Workspace inventory Doctor，不安装Buildr development CLI或Local App。Doctor仍要求Workspace health ready，但不选择Agent adapter把待post-Finish专属激活的Product runtime drift升级为Finish失败。activation只按冻结Task Contribution选择`none | render-runtime`：Workspace根Rule、Skill、Component、Command等runtime source选择render，其他变化none；不读取Project/Service配置，不执行sync，也不接受任意executable/args/env/shell。render产生tracked delta即fail closed；无法证明包含时target race凭exact token从最新Delivery Baseline重做carrier phases；Git conflict进入同一run的Delivery Adaptation，不宣称Candidate stale。只有Development Application报告原Task source/context/policy/gate/handoff stale才返回Development rebuild。cleanup在durable final delivery后先把delivery facts写入SQLite cleanup-pending边界，再幂等清理Task Environment、Carrier、transient与lease，最后由Task Record Application提交顶层`completed/noChange=false`并保留compact terminal Result；Environment已清理后的恢复不重跑delivery。Formal Finish成功后，Buildr自举Workspace专属`buildr-self-bootstrap` Component只按Result绑定的冻结Task Contribution paths去重执行package sync、development CLI/Local App install与selected-Agent最终Doctor；失败不回写Finish或上游facts。普通Workspace、通用Skill和executor不获得该能力。路径不重叠、clean apply或resume动作不构成语义安全判断。

当前run/result为`buildr.task-finish-run/v2`与`buildr.task-finish-result/v2`。Workspace SQLite按Task唯一保存一行`task_finish_current`：状态、当前阶段、关键identity、失败、resume、cleanup、target/token/expiry lease与时间为普通列，固定五阶段只保存status/timing/current failure等compact恢复事实；run与prepared completion使用有界payload，完成时原位替换为compact terminal payload。调用前invalid/no-op先结束；每次真正执行的首次run或resume在任何Finish owner副作用前open独立`task-finish/finish-diagnostics` record，backpressure保持Finish current、Carrier、target与恢复资源零变化。完整stdout/stderr、timeline和命令诊断先进入invocation-owned transient，再由record正文Store脱敏、截断和retained，随后只清理该diagnostics transient；seal或cleanup attention不改写或重放Finish delivery、Environment/Carrier cleanup与Task terminal。公开`executionRecord`只给portable operation summary，`task finish inspect`不读取或枚举records。Delivery Carrier、target、lease、resume与其他恢复资源继续只由Finish owner管理。拒绝旧v1 run；`.buildr/task-finish`不被新runtime读取或扫描，启用SQLite-only前由受控步骤直接清理。Environment已清理后的恢复只重试Finish cleanup与terminal transition，不重跑delivery；`task complete`只表达Task Record completed终态。

retained canonical Workspace 中明确的 metadata-only候选不进入产品执行器，因为无关dirty state无法形成隔离交付载体。Task Finish Skill只有在任务paths、当前研发交接、目标branch/remote与retained context都可证明时，才选择精确commit与push的目标和顺序，并分别交接给optional selected`buildr.git-operations/v1` provider；provider只能stage任务paths、检查完整push range并保留无关改动，返回两项各自适用的最小Result。任一事实或provider readiness不可证明时正式blocked，不使用`git add -A`、stash、reset、rebase、merge、force push、虚假Change或手写Git回退。

Task Environment 候选集成后，主 Workspace runtime 仍从 retained checkout sync/doctor；未合并 task checkout 不更新主 runtime。sync 只维护当前 SQLite authority 与 runtime assets，不扫描旧 Task Environment receipt 或 `.buildr/tasks/`；Git provider evidence 继续由窄 provider authority 维护。


## 与 buildr-web 的交接

- `buildr-web` 拥有前端源码；`npm run build:web` / `dev:web` 委托 sibling `../buildr-web`。
- `buildr/package.json`中的`build:web`委托和Task Verification所选前端能力，是Agent判断当前Task需要同时准备`buildr`与`buildr-web`的正式源码事实；Agent把该判断登记到Task专属Environment Plan，静态Project配置不充当routing authority。
- 正式静态资产落在本 Service 的 `web-dist`；checkout、npm package 与 launcher 三入口只打包/服务该 dist。
- Local App HTTP 继续从 `web-dist` 同源 loopback 托管并注入 session，不改为独立前端端口。
