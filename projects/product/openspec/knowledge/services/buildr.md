# Buildr Service

## 职责

Buildr Service 是 Product Project 的可执行应用实现，负责 Bootstrap composition与公共CLI Host、System Installation、Workspace/Project/Service/Task Record/Task Environment/Task Review/Task Retrospective/Task Verification/Task Development/Parent Coordination/Task Finish/项目每日演进 domain、Skill-only Git Operations、Project Testing 指导、Buildr Web Runtime 与 session 同源托管、runtime adapters、受管资产与 Component 生命周期、capability graph、验证执行、package 和发布。Buildr Web React/Vite 权威前端源码与构建属于 sibling Buildr Web Frontend Service `buildr-web`；本 Service 在构建/打包时消费其产物到顶层 `web-dist/`，运行时不依赖 `buildr-web` 源码或 Vite。

## 接口与入口

- 发布身份链固定为 `dev baseline → ordered selection chain → release HEAD/tree → Product Candidate generation → frozen tarball manifest/integrity → main tree → post-publish dev convergence → transaction evidence`。current Product已经实现selection、Candidate/artifact、Task correlation、shared readiness/protected transaction与Git convergence五类owner；任一owner无法回读current fact时仍返回`release-model-implementation-incomplete`。已成立的Publication与后续`published-but-dev-convergence-blocked`维护失败保持正交。
- p1c 的 release task evidence correlation 只读取 Task/Environment/Development/Finish/Execution Record 与 matching self-bootstrap 的 current read model，生成 portable carrier/context identity；不复制专业 Result、不扩展 Task Record/SQLite writer，也不把 Activation、Cleanup 或 Diagnostics 失败改写为 Delivery 失败。

- Release transaction runner从selection、Candidate aggregate/唯一artifact、Task correlation、Task Environment/exact Node与Git/GitHub readback构造`buildr.release-context/v1`。默认readiness按阶段collect-all且`effects: []`；只有维护者对current frozen digest明确授权后，显式dispatch才调用一次受保护`publish.yml`。Hosted workflow从matching Candidate run下载同一aggregate/tarball供所有consumer复用，不build payload、不重新pack；terminal evidence保存run/attempt逐步事实与恢复分类。`release-transaction-evidence.mjs inspect-run`按publish run校验artifact identity与GitHub source/attempt，返回portable关联，不扩张Task Record、Task Execution Record或SQLite schema。
- `release-git-convergence.mjs`分别拥有release→main、Publication后main→dev与remote release cleanup的窄动作。release→main只使用冻结release HEAD/tree并确保唯一受保护PR；main→dev只消费passed transaction evidence，在隔离临时worktree执行普通merge并以普通fast-forward push保留current dev新内容。冲突、remote race或identity漂移返回`published-but-dev-convergence-blocked`且不撤销Publication；远端release branch删除展示精确ref/commit与公开事实后仍要求独立授权。
- CLI：`projects/product/buildr`是Buildr checkout唯一开发入口；PATH默认`buildr`只代表npm installation。两者身份和更新责任隔离。`bin/buildr.mjs`只委托`src/bootstrap/cli/main.mjs`；Bootstrap创建同一Runtime/module set并合并唯一command catalog。Task Record/Task Review commands来自Task module contributions；`project daily-progress record|inspect|list` 来自Workspace module contribution；`update`、`installation status`与`web launcher install|status|repair|uninstall`只来自System Installation module contribution，其余命令保持在公共Host与未迁移Adapter边界。每日演进 `record` 校验 closed v2 payload 后原子覆盖 `.buildr/daily-progress/<project-code>/<YYYY-MM-DD>.yml`；Task 关联可选，他人提交禁止挂 Task，存在的 Task ID 仍须本机已有。`inspect`/`list` 只读。JSON 使用 `buildr.project-daily-progress-*-result/v1`。Application 不扫描 Git、不写 Task SQLite、不提供 cron；收集 Git 由产品 Skill 在写入前完成。
- Release Awareness Application一次读取npm的`latest`与`next`，分别投影GA正式版和RC候选版。`buildr update check [--json]`同时展示两个版本；`buildr update --track stable|candidate`只在用户显式选择后更新精确版本，不自动切轨或降级。
- Buildr Web：loopback HTTP 与浏览器界面。Task 列表默认 `open` (todo + active)，可分别过滤 todo、active 和终态；Task 详情展示复盘来源，复盘 Tab 展示后续 Task 与当前状态。正式 Task 只由 Agent/Task Manager 创建或激活，Buildr Web 只编辑/结束已有 Task 并维护复盘处置。六个 Task 一级视图包含独立“原型”Tab；Change Application 只在 Task 已有关联 Change 内有界发现全部带 `buildr:ui-prototype` 标记的自包含 HTML，`/ui-prototypes` 列表 JSON 只返回 portable metadata，具体内容只由 Task 与不透明页面 ID 的专用只读响应返回并强制 opaque-origin CSP sandbox。变更前的标记与接口不兼容。Runtime 不接受文件路径、不提供任意 HTML route、不扫描无关联 Workspace 路径，也不取得 UI Prototype writer；Task-scoped Change route、其他专业只读边界、复盘处置 PATCH 与文章入口语义保持不变。
- Project Document Application 为 Buildr Web 提供 Project-root 内受限 `.md` 读取。Task Intent 中的 Workspace 相对文档链接由前端先根据 Task scope 和 Project registry `source.path` 定位 Project，再复用 `GET /api/v1/projects/:project/documents/<path>` 只读展示；不扩展 Task Record schema，不引入附件表或第二文档 writer。
- Daily Progress 是 Workspace module 中的 Project-scoped 纵向切片。`src/workspace/module.mjs` 私有组装唯一 YAML Repository/Application 并贡献 CLI/HTTP Adapter；公共 Bootstrap/HTTP Host 不直接实现其业务路由。Application 拥有本机每日演进 YAML 的唯一 writer/reader。HTTP 只开放 `GET /api/v1/workspaces/:workspaceId/projects/:project/daily-progress[/:date]` 与 `GET /api/v1/workspaces/:workspaceId/tasks/:taskId/daily-progress`；不接受 `target`/`path`/`root`，不提供 POST 写入，也不在 GET 时执行 `git log`。读取时解析本机 Task 标题与状态，消失的 Task 标 unresolved 且不改文件；v1 文件返回 incompatible。
- Resources：`services/buildr/resources/manifest.yml` 定义发布边界、可安装产品内容、builtins、contracts、bindings 和 Components；`resources/workspace/` 是受管 Workspace 内容的 source authority，不携带 `.buildr/workspace.yml`、Workspace 根 Registry、Project capabilities/commands 或 Service Registry 等用户持久化配置源。`init`、Project create 与 `sync` 使用 canonical Domain renderer/writer 生成缺失 Registry并保留已有用户内容，再从资源声明收敛 Builtins/Components。Component definition 同时拥有 Skill fragments 与其引入的结构化 capability dependencies，builtin descriptor 不重复维护 Component-owned `requires`。
- Workspace module 的 source-root Domain 统一解析 Project/Service Managed Root 与 Attached Root。`project add --attach`、`service add --attach` 只登记已存在的独立 Git top-level；Application 在写 registry 前核对绝对 realpath、remote、branch、Workspace 包含关系和重复来源，且不修改外部 repository 的内容、HEAD 或配置。Project/Service detail 暴露 root kind、实际位置、ownership 与 Git identity；Change/OpenSpec、Publication、Verification、Task Verification 和 Doctor scope 通过同一 resolver 消费实际来源。Service registry 始终属于实际 Project root；需要 Workspace ownership 的 action 不因 attach 自动取得外部 writer authority。
- Runtime Skill renderer统一组合package产品入口与Workspace Skills。产品入口不接收完整capability routing dump；每个consumer只获得自身`requires`的紧凑binding block。Doctor full输出全局capability graph，destination-aware `.buildr/agent-runtime/` receipt保存受管文件identity和consumer-local contract digest/provenance快照，runtime目录不承担机器证据authority。
- Agent Assets 平台实现已迁入`src/agent-assets/`：Rule、Skill、Command、Component、Builtin/package maintenance与runtime projection位于`application/`，Agent adapter、Capability Binding、render、projection和receipt位于`infrastructure/runtime/`，并只由`agent-assets/module.mjs`向Bootstrap注册。旧`application/domains`资产入口、`application/package-maintenance*`、`application/runtime.mjs`和全局`infrastructure/runtime/`已退出。Workspace manifests与内容仍是源资产，Agent原生文件和`.buildr/agent-runtime/` receipt仍是可重建投射；产品入口Buildr Skill、Workspace Builtin与package runtime source的长期合并关系继续待后续产品决策。

## 应用负载、Launcher 与发布运行时

- `tools/release/application-payload.mjs`把同一runtime CJS bundle、read Worker bundle、Web dist、migrations、resources、deferred package runtime、生产依赖、图标与许可证冻结为`buildr.application-payload/v1`；npm staging消费同一`applicationPayloadDigest`。resource resolver只从摘要验证payload或canonical development root解析资源，正式runtime不依赖cwd、PATH、`buildr-web`源码或Vite。`tools/`与`test/`不进入npm tarball或Application Payload，产品runtime也不得导入它们。
- Candidate packaging 在唯一 `release-artifact.json` 中额外绑定 source commit、source tree 与 Candidate generation；`candidate-ci` 的每个 shard、Host Node tuple、Windows/Launcher consumer 和 publish smoke 都只接受 matching identity，失配时在任何公共 mutation 前 fail closed，不重新 `npm pack`。
- npm installation identity、origin/registry、CLI update、installation status、npm lifecycle enrollment、Launcher binding 与正式 npm Launcher install/status/repair/uninstall 由 `src/system/installation/{domain,application,infrastructure,interfaces}` 及唯一 `module.mjs` 拥有；`domain/release-version.mjs` 是 Release Awareness 与 release tools 共用的 SemVer/track authority。Bootstrap、Application Payload、Web 与 Doctor 通过公开模块入口或注入的 identity/binding/Application/Diagnostic ports 消费同一实现；旧 application、product-identity、product-launcher 与 CLI Launcher 入口已删除。通用 Product Data Root、filesystem、process 与 product-resource 机制仍归全局 Infrastructure。

- Buildr Web Runtime Host 已收敛到 `src/web/`：实例生命周期位于 `application/`，PID、锁、端口、进程和目录选择适配位于 `infrastructure/`，CLI 位于 `interfaces/cli/`。`http/server.mjs` 只拥有 loopback/listen/close 与资源生命周期，`router.mjs`、`session.mjs`、`static-files.mjs`、`responses.mjs` 分别拥有路由、安全请求、静态托管和响应映射，bounded read executor 保持独立。公共 Host 只分发各模块提供的 HTTP contribution，不实现 Workspace、Task、Change、Publication 或 Installation 业务路由。System Doctor 的 CLI、Application、结果模型和诊断位于 `src/system/doctor/`，并在 Bootstrap 末端聚合各模块 Diagnostic/Read Model contribution；它保持只读且不取得业务 writer authority。公开 CLI、HTTP、JSON、SQLite schema、migration、Session/Origin/Secret、实例复用与 Preview 行为不变。
- Public JSON identity/envelope 与 Declaration Intake next-action contract 由 `src/infrastructure/contracts/` 拥有；同目录的 `json-schema-validator.mjs` 只提供通用 strict Draft 2020-12 Ajv 编译/复用机制，不拥有业务字段语义。Task list/detail/update/complete/abandon 已作为首个 HTTP 契约参考切片：Schema 与 operation catalog 位于 Task HTTP Interfaces，校验后的 DTO 显式映射到既有 Application，构建工具从同一 authority 生成两端 tracked TypeScript DTO并检查 drift，真实 HTTP Contract Test校验成功/错误响应。其余 route 仍按模块逐步迁移，未覆盖只形成非阻塞诊断。Task internal workflow catalog/router 位于 `src/task/contracts/` 与 `src/task/interfaces/internal/`，由 `task/module.mjs` 注入 runner 后供 Bootstrap 调用。Git Worktree CLI Adapter 同样归入 `src/task/interfaces/cli/`。顶层 `src/application`、`src/domain`、`src/interfaces` 已无生产文件。
- Task professional HTTP 已沿同一 authority 扩展到 Task Overview、Environment、Development、Review、Verification、Parent Coordination、Execution Record 与 Retrospective 的 detail/list/update/prompt 操作。Task HTTP Interfaces 持有 operation catalog、strict Ajv validator、显式 DTO-to-Application mapping 与真实 Buildr Web Contract Test；Buildr Web 只消费同一 Schema 生成的 tracked DTO 与 capability-level typed client。既有 security、session、digest/conflict、terminal/domain error precedence 保持不变；未覆盖 route 只生成 non-blocking coverage diagnostic，不形成全局迁移门禁。
- Runtime/System HTTP Schema authority 分属 `src/web/http`、`src/system/installation/interfaces/http` 与 `src/system/publication/interfaces/http`：health、两种 quit、release-awareness、Publication JSON 与 binary asset 均有稳定 operation metadata、strict validator、真实 HTTP Contract Test 和统一错误契约。构建期从同一 Schema 生成 Buildr/Buildr Web tracked DTO并检查 drift；全局 coverage 保存 migrated JSON、binary、deferred 与 non-HTTP disposition，离线暴露未知/重复 operation但不参与Runtime启动。Publication binary bytes/MIME/path安全、session/Origin/instance secret、shutdown顺序以及 Doctor/Launcher/release writer ownership保持不变。
- npm package是唯一正式产品安装。`buildr web launcher install`只在显式请求后生成本机macOS `.app`或Windows Start Menu shortcut，v2 closed binding精确记录formal npm origin、Host Node、package entry、prefix、payload/protocol、target与`webPort`策略；默认首选`4457`，install/repair可指定`0..65535`，`0`直接随机。macOS wrapper同步校验后向用户launchd提交一次性runner并退出，bundle identifier由Launcher ownership派生；launchd后代从binding的绝对Host Node重建PATH首项，并把实际executable、version与PATH head写入Launcher log。默认release smoke使用隔离Root直接执行无界面入口，强制no-open/no-notify并清理owned进程；真实平台启动入口集成仅由显式专项运行，不进入affected/full/Candidate。每次Launcher startup使用15秒独立readiness budget；失败时先保留脱敏诊断，再清理owned进程与临时安装根。真实用户未设置no-notify时仍保留可见失败诊断。wrapper与runner不复制Node、Buildr package或payload，也不形成独立更新渠道。
- Development Launcher继续由当前checkout的`package/launchers`内部manager构建为thin入口，只包含图标、identity与启动脚本，绑定Service source root、精确development Node与固定端口`4458`，不复制payload或npm安装。`npm run install:development`和self-bootstrap activation都直接调用manager，不经过npm-owned公开`buildr web launcher`命令。同profile健康实例按单实例语义复用；foreign进程占用`4458`时明确失败，不随机回退、不停止占用者。Development Launcher与formal npm Launcher在名称、target、identity和lifecycle上隔离。
- 普通 Web Runtime 由 installation channel 与 runtime role 唯一解析 released/development Web profile。两者分别拥有默认 Web Data Root、Workspace registry、instance/start lock和日志，可并行运行且不跨 profile 复用或停止；Development Launcher固定使用`4458`，直接CLI与Task Preview仍可使用显式或随机loopback端口。released由正式Launcher启动时读取binding策略，非零首选端口因`EADDRINUSE`失败只在同一start lock内随机回退一次。其他单实例、ownership、profile隔离、receipt清理、Product Data Root与Frontend标题语义保持不变；旧 released Root 中的 development instance 仍以 profile conflict 报告并保留。
- Workspace 注册、`web --target`、Launcher 与 central Structured Store open 共用 Workspace management fence：先核对 real root、Workspace UUID、对侧 registry 和 `.buildr/local/web-management.json`，再允许任何 SQLite 创建、migration 或写入。错误 channel 条目只能从当前 registry 精确移除；该动作不打开/删除 SQLite，且无 force/adopt。Preview 保持按实例名隔离的 Root，不取得普通 management claim，并把子进程输出写入自己的启动日志。
- `installation status --json`、Doctor和Web health/instance分别展示receipt证明的npm、development、Launcher与current instance identity；`update`按同一receipt路由npm package或development checkout，并只原子刷新同slot已有Launcher，不扫描PATH、文件名或目录形状。
- Doctor通过独立`releaseAwareness`/`notices`投影版本提示，查询失败不进入Workspace findings、repair plan或readiness；Buildr Web Runtime只开放全局只读`GET /api/v1/release-awareness`，不提供网页npm更新mutation。每轨道的seen/notified/check时间只保存在用户级Buildr Data Root，不写Workspace。
- Doctor finding 以 `domain`、`scope`、`affectedActions`、`ownershipUnit` 表达局部影响，JSON 额外输出 `domainHealth`；兼容 `health` 明确以 `generalWorkPermitted: null` 拒绝成为通用许可。sync source plan 只把 required Component conflict 作为当前受管 mutation 的 blocker，optional/foreign-owner unit 保留 warning 并跳过其独立写入；Capability route 与其他 consumer 继续按各自 required/optional contract 判断，不从聚合 Doctor readiness 扩张授权。

## 数据与依赖

- Workspace/Project/Service、Rules、Skills、Commands 和 Components 使用 YAML manifests/registries。
- Workspace Structured Store使用每个Workspace root自身的`.buildr/local/workspace.sqlite`，由随npm package交付的连续SQL migrations、checksum ledger和Doctor管理。它是Buildr Local单机数据，不进入Git或同步；未来Server/Cloud不复用数据库文件作为共享协议。Buildr Web registry已解析root后的read-only Application path只读取该root，不执行Git/worktree provenance观察或`git rev-parse`；writable、migration和mutation path仍执行writer guard。自举 candidate runtime 在与 retained Workspace 共享 Git common-dir 时，只能写入自己的 linked Task Validation Workspace store；写 retained canonical store 或 peer checkout 会在创建目录、SQLite、WAL/SHM、ledger 或业务 row 前被 provenance guard 拒绝。验证 store 从完整 migration chain 建立，数据不回灌主库；最终集成后的 retained runtime 才能升级主库。
- Task Record 使用 closed `buildr.task-record/v2`，由`src/task/module.mjs`显式接收Structured Workspace Store、Project/Service Reader、Change Resolver、operation memoizer和Parent Coordination Reader，在私有组装对象中创建唯一Repository/Application，并贡献自身CLI/HTTP Adapter。Bootstrap兼容Facade只让既有消费者继续访问同一Application与窄Persistence读取面，不复制数据库或writer；其owner、冻结调用者和`legacy-exit-and-conformance`退出条件由架构验证约束。状态、todo规则、复盘信源、Parent/Child、scope/Change、单事务writer、linked-worktree guard和旧`task.yml` inert边界保持不变。
- Task Review 使用 Workspace SQLite 中的`(task_id, planning|completion)`两个可选current slots与统一closed `buildr.task-review-result/v1` schema。同类型事务原子保存完整Result及`target_identity`、`outcome`、`updated_at`查询字段，跨类型隔离；inspect只比较调用方显式提供的保存identity，未提供时返回`unknown`。Task Review Application仍是唯一writer。
- Task Development仍以`task_development_current`保存normal Receipt、Candidate、gate与immutable handoff。严格终态异常恢复由Task Development Application唯一写入按Child唯一的`terminal_contribution_reconciliations` closed evidence：只接受completed非no-change Child、active Parent、current Plan、matching handoff/Finish、archived Change与无owner冲突的显式Contribution Handoff；相同identity幂等，不改写旧Receipt、handoff、Finish、Task或Parent Plan。Parent Coordination固定两条查询联表读取该可选proof，优先原生handoff并显式返回`native-handoff|terminal-reconciliation`；该表不保存progress/history，normal Child仍必须先binding并在同一handoff中提交Contribution Handoff。
- Task Retrospective 仍以单一 SQLite current row 保存原始 Markdown 与 `pending|handled|no-action`。处理流程必须先返回原文/current digest，再基于当前项目事实重新拆分方向；有效方向全部关联已有 todo/active Task 或新 data-only todo 后才 handled，全部失效才 no-action。Application 只返回反向后续 Task read model，不保存分析中间项或 action item ID。
- Task Verification使用Workspace SQLite中按Task ID唯一的current row；current writer只写closed`buildr.task-verification-result/v2`，reader兼容v1但标记legacy-unbound。`reconcile`只接受matching terminal Execution Record IDs，并独立核验metadata、受控summary、body integrity、Task、Candidate/generation、Content Target、Project/declaration、selected checks与target stability，再派生portable capability facts和closed evidence identities。Project/Service record claims、外部URL/Git ref/文件/聊天摘要均不能成为Result；仅工作区gap保留受控record兼容入口。inspect只比较调用方显式Candidate/target/declaration identities，不重新读取路径。
- Formal Verification runner在Execution Record open之前要求Development consumer提交Candidate identity/generation lease，并把Candidate与target加入invocation identity和summary；runner不反向读取或写Development。随后对selected capability执行纯读准备准入，把`verification.yml`中的Recipe引用与Environment Plan/Receipt、runtime invocation组成稳定闭包；可恢复缺口只返回Task Environment closed恢复请求。Task外transient run不接受Candidate lease，不能用于formal reconciliation。
- Task Development使用Workspace SQLite中按Task ID唯一的closed`buildr.task-development-receipt/v3` current row。Content Target与policy current后即可freeze Candidate；Verification、Completion与Current Knowledge不进入Candidate identity，也不阻止首次freeze。`knowledge` action保存current tree与`aligned|not-applicable|attention|blocked`最小disposition，只有blocked阻止proceed/handoff，attention进入immutable handoff但保持可交付。operation/compact Result派生`not-applicable|blocked|ready` Formal Verification Readiness；ready时consumer交接Candidate lease。Receipt继续保存Parent coordination、Content Target、policy、Candidate/generation、Knowledge、最小gates/decision与append-only handoff，不保存专业正文或raw evidence。
- Parent Coordination Domain/Application不拥有持久化authority或writer；专用只读repository在同一read-only SQLite connection内以固定2条参数化查询组合当前Task、直接Parent/Children及Development、Planning Review、Environment和Finish saved current，查询次数不随Child数量增长。Parent Plan新writer只接受v2结构；旧v1按原identity只读兼容并只允许显式reconcile升级，不迁移SQLite或backfill。Application从该projection取得Task关系、Plan/binding/current handoff、Plan identity applicability与Environment saved readiness，并只接受matching compact Finish terminal association证明Child delivery，分别动态返回预期`expected|none`、可执行`eligible|waiting-dependency|not-eligible`和实际`unassigned|bound|active|delivered|residual|superseded|unproven`三轴，以及最终验收前置条件、启动checks、blockers与next。公开`buildr.parent-coordination-result/v3`只保留紧凑Plan/Planning Review/Child delivery摘要和唯一顶层Contribution Map：不复制raw Parent Plan、完整Review/Handoff Result、work item、Child binding alias或下一步alias；独立startup v2仍保留专用dependency blockers。CLI、Buildr Web与Agent共用该Application；GET/inspect不调用live Environment provider或逐Child专业Application。`task parent refresh-planning`只复用saved Plan、matching planning snapshot与current ready Review刷新既有Development gate，Plan/Review drift或changes-required时零写入；record/reconcile公开closed schema/example。Child状态不回写Parent，Child completed无matching handoff为`unproven`，Parent final acceptance和completed均为显式独立动作。没有Plan的独立Task为`ordinary`，已有Child关系的旧Parent为`legacy`；不扫描、迁移、推断或改写旧Parent Change/checkbox。
- Task Execution Record使用单张SQLite`task_execution_records`表保存closed metadata，并由唯一Application组合`.buildr/local/task-execution-records/<owner>/<record-id>/`受限正文Store。v1开放Verification execution与Finish diagnostics两组owner/kind，提供open、seal、inspect/list、failure resolution、单记录cleanup与Workspace级ExecRecord GC；正式Task command Verification与每次真正执行的Finish invocation均已接入producer，Task外Verification run仍为transient-only。open先预留固定record quota，正文先版本化脱敏与安全截断，再通过staging/manifest原子publish，retained后才精确清理producer-owned transient evidence。Buildr Web通过同一Application开放Task-scoped `all|verification|finish` portable列表、详情和closed filename正文读取；正文必须先验证manifest/digest/size且单次响应限量512 KiB，不暴露locator或本机路径。GC只从同一SQLite authority选择bounded candidates，优先恢复`cleanup_pending`、复用retention/resolution/recent-count与单记录cleanup，并在cleaned满90天且超出同类最近20条后条件删除tombstone metadata。`buildr task execution-record gc`提供手动/headless dry-run与执行入口；正式Local HTTP Server从下一本地整点调度，Task Preview Server在scheduler factory前禁用全部scheduled maintenance。GC不接入Workspace Doctor或Buildr Web mutation/UI，不扫描文件系统、不自动处置失败记录、不管理execution resources，也不建立Consumer/Adoption、通用payload/history、第二GC store或lifecycle聚合。
- Verification invocation identity只绑定Task、target、Project/declaration与规范化capability集合，并保存在同一`task_execution_records` authority。open事务对相同Task/owner/kind/exact identity默认active优先、随后terminal，并在对应集合按`opened_at DESC, record_id DESC`复用latest record，零执行返回原record/run identity；`passed|failed|blocked|cancelled` outcome与`retained|cleanup_pending|cleaned|attention` lifecycle均保留原事实，负向或attention不改写为通过。只有显式`--retry`创建同identity独立run；identity输入变化仍创建首次执行。`cleaned` tombstone在row存在时参与复用，被既有GC合法purge后不再存在authority，本语义不以内存或CLI输出补造永久幂等。Agent使用`task execution-record list/inspect`从同一authority回读portable lifecycle/outcome、timing、failure与evidence摘要；session或PTY句柄不再是终态authority，CLI不暴露SQLite/body locator，也不建立第二份执行状态。open Verification record若已有matching provider-owned terminal summary，Agent可用`task execution-record recover --summary`校验Task/record/run/invocation/target、完成事实与推导outcome后补seal原record，且不重跑capability；证据不可用时先返回authorization-required，只有用户明确接受未知结果后才能用`--authorize-unknown-outcome`保存`unknown`、`retained`与`acknowledged`。unknown record继续可读并按失败类固定retention保留，但不参与terminal duplicate复用，后续普通invocation可创建新run；recover不提供timeout、进程探测、自动retry、目录扫描或第二状态authority。
- Buildr Product 的 changed-test planner 通过 `npm run test:changed -- --base <ref> --json`（或显式paths加`--json`）只返回计划且不执行测试。计划以closed `affected|full|explicit|not-applicable` scope和结构化reason说明选择结果；未知Product路径或缺少直接生产owner的路径保守回退完整Candidate，同时保留`unmapped`或`productionOwnerGaps`供registry coverage审计，不以无映射错误阻塞验证。仅经base/current JSON证明的`package.json`与`package-lock.json`版本字段变化可以免于全量触发，任意其他路径不能借通用exemption降级。Agent在追加broad transient verification前用它核对scope、selected owners、coverage gap与成本，再结合任务风险决定补充范围；该preview不能替代正式 Verification evidence、Project declaration、Execution Record或current Result，通用Task Verification Skill也不硬编码此Product专用入口。

Task Record与各专业模块共用`.buildr/local/workspace.sqlite`，但不合并Domain、Application、writer或状态机。已退役的`task_lifecycle_current`不再复制跨专业事实；Task Overview与Parent Coordination只组合各owner已保存事实，不新增store、cache、view、progress/lifecycle/event/history表或writer。项目每日演进不进入该 SQLite，只使用 ignored YAML。Task current records不发布、不进入Git、不进行本地多机同步；Task Metadata Publication、静态Task Board与旧Task Asset Review生成链均已清退。既有静态页面与`.buildr/asset-review/`只作为历史数据保留，不由Service读取或维护。Environment与Finish继续拥有各自本机运行/交付事实，Buildr Server/Cloud只作为未来团队协作方向。
- OpenSpec 依赖 `@fission-ai/openspec` 1.6.0；apply 前使用上游 strict validation 与 current Planning Review，Buildr 补充跨 Change conflict evidence、文件事实驱动的确定性收敛事务和 runtime contributions。`baseline create`、阶段型 `check`、`sync-plan`、`sync-apply` 公开 CLI 已删除，deterministic primitive 只在 `converge` 事务内部组合；历史 archive bytes 保持 inert，不作为当前授权。完整`MODIFIED`省略既有唯一Scenario identity时，planner继续整批零写入返回`semantic-resolution-required`，并以`scenario-identities-omitted`和确定排序的`omittedScenarioIdentities`给Agent最小可移植上下文；Buildr不复制正文、不自动补回或决定删除。
- Buildr Web Task API 先把已登记 `workspaceId` 解析为 canonical root。Overview endpoint调用Task Overview Application，用一次参数化SQLite联表查询返回Task与各专业current的最小摘要；Coordination endpoint调用Parent Coordination Application，以同一只读connection上的固定2条参数化查询返回Task关系与协调所需saved facts，不执行live Environment解析或逐Child N+1；Development、Environment、Review、Verification、Retrospective与Execution Record GET调用各自Application并使用`no-store`。Execution Record routes只接受Task ID、closed view、record identity与closed filename，返回登记的portable JSON；专业endpoint不接受任意root/path。唯一额外writer是受同源、session、JSON白名单与current digest保护的Retrospective处置PATCH，它只调用Application `handle`。Finish的唯一`task_finish_current`行保存current或compact terminal及本次采用的handoff、Candidate与三个gate最小关联；Terminal Delivery从terminal payload读取并与Development handoff确定性匹配，不用后续current Result重新证明历史关联。Change全局collection保持retained-only；Task关联详情通过共享Resolver读取Environment saved current，`ready`或`blocked` Receipt只要仍能证明matching Project scope、source path与execution root归属且目录当前可读，就使用task-environment candidate，否则回退retained Project。Runtime、CLI、依赖或projection readiness阻塞继续作为Environment诊断，不隐藏可读Change，也不授予任何执行能力。
- Buildr Web 的专业Task只读操作通过固定容量 bounded read executor 执行，默认2个long-lived Worker、32个FIFO queued slots；Worker只接受overview、development、reviews、verification、coordination及execution-record list/detail/body-file closed operation，并在自身runtime中读取既有Application read model。队列满返回`local_app_read_queue_full`；queued请求取消时直接移除，running请求取消时立即停止交付、终止占用的Worker并补充固定容量，且不重试或复制operation；Worker failure只结算当前请求并恢复容量，server close释放pool。该executor不承载mutation、Environment、worktree、Finish current/terminal Application、execution record cleanup/GC或Doctor，也不重新执行已解析root的Git/worktree provenance或`git rev-parse`。
- Buildr Web 实例生命周期是独立后端模块：`src/web/application` 编排默认实例、Preview、Launcher handoff、maintenance和清理，`src/web/infrastructure` 管理Web专属receipt、启动锁、健康探测与认证退出，`src/web/interfaces/cli` 通过 `src/web/module.mjs` 向统一CLI Host贡献commands。模块内技术层默认扁平，不为默认实例、Preview或maintenance建立单文件能力目录。HTTP Router、Session、安全边界和`web-dist`托管暂留既有HTTP Host并通过server factory接入，不由本切片改写；React/Vite源码和正式前端构建继续归`buildr-web` Service。
- Project根可选`preparation.yml`使用closed`buildr.project-environment-preparation/v1`长期声明Project-wide或Service-scoped Recipe。Task Environment只约束实际消费Buildr-managed checkout、Preparation、runtime projection、Task-owned资源、正式环境证据或cleanup的动作，不把Formal Task或普通编辑/构建/有界测试变成通用许可。Agent选择受管路径时按Task scope提交Plan Request；`task environment prepare`必须带`--agent <adapter>`，省略失败且不默认为Codex。Application保存Plan v3与Receipt v6；required Recipe/Step缺失、漂移或失败只阻塞相应受管动作。
- Git worktree provider 只在 Git common-dir 保存 `buildr.git-worktree-evidence/v1`，包含 repository plan、checkout/branch/HEAD/clean/registration 和 Git effects。`worktree create|inspect|cleanup` 不返回 Environment ready、Runtime/CLI/依赖、资源、恢复或总 cleanup 结论。
- Git Operations 只由 `git-operations` Skill 和 `buildr.git-operations/v1` contract 表达调用期行为，不新增 Application、CLI、Receipt 或 store。默认提交语言由随包 workspace `AGENTS.md` 提供，Project、Service、repository 更具体约定优先；Git Operations 与 Task Finish 只消费该规则，不复制 Core 语言契约。consumer 提供 repository/operation/ref/scope/授权；Result 只返回适用的前后 identity、完整 push range、变化维度和实际 effects。
- 普通 Rule/Skill 内容修改不要求新 session、reload、re-enter 或 activation evidence。候选 CLI/runtime 可以在自身 Task Validation Workspace 验证；只有集成到 retained source 后正式 runtime 才同步生效。bounded Agent capability 必须由 Agent 形成事实，文件投射或 Environment ready 本身不等于验证通过；Result 不复制 Environment Receipt。

Task Environment不再建立Workspace级Node probe或execution binding；`workspace-foundation`仅从当前执行环境解析Preparation Step明确命名的命令并记录executable identity，Project/Service executable继续按既有scope约束解析。Verification直接执行Project declaration中的argv，不替换node/npm/npx，也不把Node事实写入execution evidence、record或public JSON。Task Finish不再冻结、核验或投影Workspace Node identity。portable Task Verification Result仍只绑定调用方Content Target和Project declarations，不复制Environment事实。

## 运行与验证

本 Service 的通用技术机制由 `src/infrastructure/index.mjs` 统一组装；`src/infrastructure/filesystem/product-data-root.mjs` 统一解析跨平台 Product Data Root，`src/infrastructure/sqlite/workspace-sqlite.mjs` 是 SQLite connection、operation scope、全局 migration、锁与事务的唯一 owner。Task Environment、Task Review、Task Retrospective、Task Verification、Task Development、Task Finish、Task Overview、Task Execution Record 与 Parent Coordination 的业务 Persistence 统一位于 `src/task/persistence/`，由各自 Task descriptor 在私有 composition 中注册，不存在聚合 `registerTaskPersistence` 或第二套 connection/transaction入口；Infrastructure 不解释这些业务事实，也不取得业务 writer authority。

只读Task Entry Snapshot Application通过`buildr task next`组合Task、Environment与Development compact facts。active Task尚无Development且Environment Plan/Receipt缺失时返回整体ready、空blocker与recommended prepare；Development已绑定Environment后发生漂移，或实际owner请求受管checkout、正式证据、资源、自动Finish或cleanup时仍required fail closed。Snapshot不把recommended解释为Environment或正式Result成功，也不展开完整graph或自动执行。

随包`task-manager`只在Task Record Application成功创建active Parent后按用户的创建/准备/拆分意图交接`task-development`，不调用Environment、Development或Review writer。`task-development`持有Child前准备循环：先消费current `task next`的prepare/begin，尚无Plan时只根据同一次明确Parent交接和充分规划输入执行`task parent record`，随后按typed next完成Planning Review与refresh；每个owner动作后重读next。只有真实业务/授权blocker或`start-child-contribution`停止，后者只报告eligible Contributions，不自动创建Child、observe、Verification、Candidate或Finish。Task Record result与CLI schema不增加handoff字段，也不从intent文本推断Parent专业状态。

Task Record以Domain/Application/SQLite repository构成独立writer；Task Environment、Task Review、Task Retrospective、Task Verification与Task Development继续使用各自Domain/Application/repository。它们只共享Task ID，Task Record不再以Task目录或文件存在作为authority。Task Development只通过bundled Skill和matching retained controller的`__internal task-development` route执行`begin|planning|observe|policy|gate|freeze|decide|handoff|carrier` actions；同一runner另外提供无需Task/Workspace且不compose runtime的全局/action `--help`、action `--schema`与`--example`，其closed顶层输入字段来自同一action contract，运行态合法性仍由Application判断。`begin|planning`的required fields由Application从该contract执行写前校验，省略完整`planning`整值会在写入前失败，显式空snapshot仍合法；其他action保留既有Application/Domain诊断顺序。普通action可opt-in `--compact`，从同一次完整operation result投影current identities/applicability、effects、diagnostic与建议性next actions，不追加观察、不形成第二authority，也不根据效率指标自动推进。Task Retrospective通过同一retained invocation的`__internal task-retrospective` route执行`record|inspect|list|handle`；Task Planning Identity通过只读`__internal task-planning-identity` route解析语义target。统一route inventory由package static validation与Doctor检查runner、source wrapper和全部受管consumer闭环，npm installed-layout tests在无checkout source和空`NODE_PATH`下真实启动三个route。`list`复用Task Record current query与单份inspect语义，按处置状态或显式Task集合返回有上限的稳定摘要，只有显式请求才包含报告正文，且不建立缓存、分析聚合或mutation。Agent收到宽泛处理请求时只读inspect并展示拟disposition、理由和Task effects，只有用户直接指定完整mutation或明确接受未变化方案后才执行Task关系与handle写入；Buildr Web只新增同一Application所有的处置mutation。三者都不注册公共CLI。`git-operations`、`task-environment`、`task-review`、`task-retrospective`、`task-verification`、`task-development`与窄`task-worktree`分别提供对应独立capability。

Service source使用Node.js ESM并支持`>=24.15.0 <25`；Product checkout以`.node-version`锁定精确development Node `24.15.0`，development CLI、npm wrapper、验证、安装与self-bootstrap入口对其他兼容版本也fail closed。后端TypeScript只在受约束的渐进切片中采用：锁定`typescript`与`@types/node`开发依赖，`strict`、`NodeNext`、`verbatimModuleSyntax`、`erasableSyntaxOnly`和`noEmit`由稳定typecheck覆盖，Node直接执行`.mjs`与`.ts`混合模块图，不引入tsx、ts-node、path alias或第二运行入口。CLI identity是首个真实`.ts`切片；Fast、affected和Candidate preflight都把`.ts`与`tsconfig.json`映射给静态owner。发布时锁定bundler吸收同一模块图并形成npm package消费的单一CommonJS runtime payload，正式tarball不携带或运行`.ts`、compiler或开发类型依赖；开发依赖通过lockfile与`npm ci`收敛。npm entry只接受兼容Host Node。Application Payload root只负责逻辑资源定位，Workspace SQLite writable/migration入口独立绑定实际controller source root；候选源码即使借用installed payload identity，也必须在创建SQLite、WAL或本机目录前被writer provenance拒绝。Workspace canonical manifest不含runtime；reader忽略旧`runtime.node`，sync重写时移除该字段但不删除本机已有runtime文件，Doctor不因此产生finding。正式`verification run`从Development consumer接受Candidate lease，`task verification reconcile`只从matching terminal Execution Records派生Result；`task verification inspect`只比较传入identity，workspace-only `record`不接受capability claims。Browser changed dispatcher 优先消费 `BUILDR_CHANGED_PATHS_JSON`，否则从 execution root 的 Git base 推导，无法解析时返回明确的 capability input error。dispatcher 对适用输入只返回至少一个selector的`selected`或明确`not-applicable`，Browser-owned但零selector时以coverage gap阻塞；selected执行先把Buildr Web构建到临时staging，再与tracked `web-dist`做路径、类型和bytes精确比较，验证过程不改写冻结Content Target。run 的 target drift 以 added/removed paths 和 status change 单独报告。

Project `verification.yml` 使用 closed v2 declaration，只描述少量稳定、可独立选择的已有 capability；测试意图、执行边界、成本、范围、验证目标和目标耗时保留在 Project Testing 或项目 registry。Buildr 的唯一 verification registry 为每个 step 保存 owner、测试意图、执行边界、证明范围、目标耗时、主要证据 owner、环境足迹、隔离方式和重置负担；`fast` profile 表达低成本 Quick，inputs 表达 affected owner，`candidate` profile 表达显式核心完整回归，三者不再复制为混合编排场景分类。Planner 在启动 verifier 前拒绝穿过真实 filesystem、CLI、Git、网络或 Workspace 生命周期的 Component，也拒绝需要重复 cleanup 或完整生命周期的 Quick；低成本 Integration 只有在有界、可测、隔离且无重置负担时才可例外进入。`test:contract` 只保留 Static Conformance 与只读 Product tree 检查；真实开发入口、Git、临时目录和 cleanup case 由 `test:integration` 的 affected/focus/Candidate owner 承担。完整 CLI、Git、Workspace 生命周期由唯一 `test:system` 入口承载，旧 `test:integration:fast` 不再保留。System 的 Task lifecycle 测试在一次运行内共享 `task-lifecycle/v1` 不可变基线，每个 case 使用独立 sandbox；初始化、Git/Task Environment、安装、迁移与 Finish owner 保持完整隔离。OpenSpec contract/recovery cases 在 Candidate 中互斥，package parity 只持有代表输出和一次 init mutation，安装后 sync/doctor/uninstall 由 release tarball smoke 独占。默认 local/CI 允许两个使用不同临时 root 的 `workspace-saturating` verifier 有界并行，资源受限 CI 保持单路。正式交付只有一个 required `product.delivery`，在冻结 Candidate 上由 changed planner 选择 affected；registry/planner/runner、声明或 timing 等全局 owner 变化时同一 plan 扩展为 full。`product.full-regression` / `test:candidate` 保留为显式完整回归；Browser 由独立、条件化必需 capability 持有，Release 专项保持独立。上述能力和 Product-only runner 不构成通用 assurance 层级。`buildr verification run --project <code> --capability <id> ... --target-identity <identity>` 随npm runtime发布，只执行显式command capabilities；Task外run输出不含stdout/stderr的compact checks与固定有界失败摘要，正式Task run则在启动前open execution record，把完整脱敏输出保存在正文后seal并清理transient evidence。公开JSON只返回portable check与executionRecord摘要，不暴露raw output、SQLite或body locator。Task Verification inspect没有current identity输入时分别返回`target-identity-not-provided`与`declaration-identities-not-provided`，且不自行读取source。`effects.authorization: explicit`与explicit resource分别要求精确capability/resource授权；被真实claim的`coordinated`资源才通过Git common-dir lease协调。该机制不调度Agent或任务，也不写current Result。

执行 profile 同时拥有适用 `node-test` owner 的内部并发预算。Task Finish delivery 在 local/CI 使用两路、资源受限 CI 使用单路；静态参数与 profile 同时声明时失败关闭，避免两个配置源产生不可解释的实际并发。

Verification resource claim 必须匹配 registry 资源契约要求的 footprint、`unique-temporary-root` 隔离和 lifecycle cleanup；只使用独立临时 Git/CLI fixture 的 owner 不占用 Workspace lifecycle 压力容量。`runtime-adapter-contract` 的所有投射归属一个 run-unique 临时根，并在进程退出时只清理该根。

Product verification DAG 默认使用按近期成功样本校准的粗粒度成本调度；资源或 concurrency class 暂不可用时继续选择其他 ready step，不为高优先级 owner 空置全局容量。`critical-path` 模式使用自身成本与最长后续依赖链排序，同分时优先 fan-out producer、自身成本与 registry 声明顺序；它与`declaration`模式仅用于同一计划的受控对照。timing evidence 保留实际调度模式与每步估算优先级，不改变 owner、选择范围或证据要求。planner判定为`full`的计划在启动DAG前通过Git common-dir共享的`product-full-execution`容量一lease跨Task排队，affected与其他非full计划不占用该容量；等待期间每15秒输出心跳，最长等待30分钟，完成、失败或取消后按owner精确释放。`system-fresh-build`在独立临时Workspace内复用prepared controller，使用`workspace-saturating`与`task-lifecycle-heavy`资源而非全局`exclusive`；其余长尾 owner的调度成本同样按多次成功样本中位数粗粒度校准，成本不替代target duration或超时。

Package metadata changed planning只在拥有Git base与current内容时豁免`package.json.version`、`package-lock.json.version`和lockfile根package version；依赖、scripts、engines、其他lockfile结构、解析失败或显式paths-only调用仍保守full。registry `node-test`和受管glob在启动前解析真实文件并拒绝空集合。Release专项保持独立诊断入口，不应与普通delivery自动叠加。

生产`src/*/application/**/*.mjs`与`src/infrastructure/**/*.mjs`必须命中非broad领域Integration/System owner，或进入带owner/reason的闭合精确allowlist；仓库完整源码集合与每次changed path都在进程启动前审计。声明、OpenSpec、验证编排、Runtime、发布、数据存储、Task Environment/self-bootstrap以及Task read-model、coordination、execution-record、Development与Finish Integration文件由同一primary slice registry持有，general exclusions从该registry派生；66个Integration文件由14个领域slice、4个general文件和2个外部primary owner互斥持有。28个System文件由13个primary owner互斥持有，Verification的admission/编排/公共JSON/OpenSpec audit、Workspace的Project/Service/Task/Worktree以及Task Finish CLI/Product Journey分别选择。changed-path与verification run CLI两个入口文件由独立`system-verification-admission`持有。本地非空changed与Candidate计划把完整Quick及适用canary合成一次去重admission DAG；所有非admission步骤等待准入通过，同一次execution和timing evidence中每个step最多执行一次。领域owner的target duration与调度成本只依据同一内容树的成功focused采样校准；历史budget warning必须逐项区分结构性重复与完整生命周期波动，不统一倍增。

目标为`dev`的PR由macOS运行主要changed/affected admission与适用Browser验证；Windows并行只消费registry step的显式`developmentRunners: [windows]`投影，空投影不安装依赖也不附加Fast admission，因此不重复执行普通跨平台owner，且不声明为完整Candidate。Formal Finish和self-bootstrap successor直接推送`dev`不自动启动GitHub Product verification，其证据分别由current Task Verification、Finish remote readback以及self-bootstrap runner的精确delta、push readback、development identity和最终Doctor持有。发布集合不再从最新`dev`冻结：`release-<version>`在精确release HEAD/tree上运行同一verification registry的分布式Candidate投影，形成唯一tarball后经受保护release→main PR收敛；普通`dev`可继续前进。Publication成功后，Git convergence owner消费passed transaction evidence，在隔离临时worktree把current `main`普通merge到current `dev`，只允许普通fast-forward push；冲突、remote race或identity漂移保留Publication并返回`published-but-dev-convergence-blocked`，不使用`ours`、reset或force push。单个macOS bootstrap使用Product锁定Node并复用checkout与依赖，先形成独立`preflight-macos` evidence，再构建唯一candidate tarball与`artifact-macos` evidence；随后并行运行macOS core、唯一消费artifact的Windows runtime/Launcher、Windows fresh build、无artifact的Windows Workspace lifecycle、Task/worktree recovery、Task Finish与Task Development四个有界shard，以及macOS/Windows最低/当前Node 24 Host Node tuple。内部shard identity与primary step集合可以随资源压力和语义owner重新分片；workflow matrix与registry必须由contract test保持一致，runner、phase、artifact依赖、Windows平台owner和稳定gate identity不变。稳定`Candidate gate`继续在macOS checkout上不安装npm依赖，直接以Node内置能力聚合closed evidence，检查source SHA、registry identity、artifact identity、primary coverage和结果完整性；branch protection不依赖内部shard名。Candidate内置`release-tarball-smoke`仍是发布冒烟owner，CI不建立重复的独立release smoke job。本地admission依赖不投射为跨shard dependency，GitHub继续由既有phase与job `needs`表达分布式短路边界。

Product `test:candidate` 额外执行 `concurrent-task-acceptance` 组合验收：在单一临时多仓 Workspace 创建两个正式 Task，并发 prepare 两个真实 Environment，从不同 cwd 按 Task ID 调用 Receipt 返回的绝对 CLI invocation，再并发执行显式 `verification run`、记录两个不同 Task-scoped current Verification Result，并启动随机端口 Preview。验收按 fixture、environment prepare、Task invocation、verification、verification result、resource coordination、preview、failure diagnostics 与 cleanup 输出阶段 timing，并核对多仓 scope、allowed roots、共享容量等待与释放、不同 Result path/digest/current applicability、非空 execution identity、错误 Task 无法停止对方 Preview、异常子进程诊断、顺序 Environment 清理保持另一 Task 及 retained doctor。独立 invocation、Preview stop 与 Task abandon 可以并发；只有证明 peer preservation 的 Environment cleanup 保持顺序。该步骤使用本地临时 Git 与进程，不访问外部系统。

Task Finish Application保留`run|reconcile|inspect`三个入口。Finish 的私有交付、恢复、维护与诊断协作者位于`src/task/application/finish/`，单文件Repository位于`src/task/persistence/task-finish-repository.mjs`，CLI/internal drivers位于`src/task/interfaces/`；`src/task/module.mjs`以独立`task-finish`和`task-terminal-delivery` descriptor唯一装配Application、窄Persistence Read/Internal port与四条CLI contribution。`legacy-runtime-module.mjs`不再直接注册Finish Repository/Application，旧全局路径不保留转发实现；轻量inspect仍组合同一新路径实现。`run`是可选五阶段Git自动化；`reconcile`在Agent直接Git或PR交付后读取current Development handoff、完整repository set、冻结Task Contribution与真实remote target，逐repository登记Delivery，不创建carrier、不push，也不接受caller提交success或proof。若旧current run绑定不同Handoff且只在prepare阶段terminal failed并遗留run-owned carrier，显式`reconcile`以selector、source path、retained/task roots、Environment/target branch、remote与disposition精确相等证明repository topology未变，不要求包含Task Contribution的`repositorySetIdentity`跨Handoff相等；随后只在current Handoff全部repository已由真实远端包含、旧run没有lease/delivery/retained/completion/cleanup/resume或后续phase事实且carrier可按ownership安全清理时，才清理旧occupancy并形成current terminal association。新terminal persistence以旧failed current run ID与精确serialized digest作为Product-owned transaction fence，任一row/kind/status/identity/digest漂移均零写入；普通finalize仍只允许同run原地终结。任一topology或证明缺口保持旧current run，普通`run`的carrier identity conflict边界不放宽。Agent拥有交付、冲突与恢复策略，Buildr只保护remote containment、identity、共享历史与ownership边界。

自动deliver在remote仍等于carrier时保持`targetDisposition: carrier`与空containment；只有remote后继可证明包含carrier时才保存`already-contained`与完整proof，relation/proof必须同一checkpoint写入。历史already-contained缺proof会重新fetch并重建，不直接复用。Doctor、runtime render和retained controller失败保存Activation attention，deliver phase仍passed；Execution Record、Task terminal登记、Environment cleanup或carrier cleanup失败同样只写所属attention，不撤销已确认Delivery。

Task交付终态先于维护收敛：全部适用repository的Delivery成立后，Task Record Application尝试写`completed/noChange=false`，summary只声明任务贡献已验证交付；失败由后续`task finish reconcile`幂等修复，不重复业务push。Environment Cleanup独立消费持久化Delivery evidence，为carrier、exact Task Contribution containment或no-contribution proof重新核验source与target后才删除worktree。公开compact/terminal结果正交投影Delivery、Activation、Environment Cleanup与Diagnostics。

Buildr自举Workspace的Activation继续由workspace-only `buildr-self-bootstrap-sync`唯一runner负责，但输入扩大为自动Finish或reconciliation形成的matching delivery result。reconciliation可没有Delivery Carrier；Product self-bootstrap projector从已验证containment evidence投影activation paths。runner失败只形成Activation attention，不改写Task Delivery，Environment Cleanup由Task Environment独立处理。

Self-bootstrap runner仍在任何retained mutation前核验Workspace、Node、remote/branch、delivered ref、clean tree与存在的carrier inventory，并取得matching Task/run target lease；没有carrier的reconciliation结果不是错误。它只允许fetch与fast-forward，不merge、rebase、stash、reset、force push或修改foreign carrier；latest target、lease或identity不可证明时只停止Activation。

Runner用Environment retained Node显式验证retained `projects/product/buildr`的development channel、source commit、CLI entry与package/version，再尝试最终Doctor。入口或Doctor失败返回结构化Activation attention；新Delivery不会再进入retained Doctor blocked终态，旧doctor-blocked run只保留兼容恢复。

远端协作者提交使canonical `dev`前进、但当前会话没有与该更新匹配的Formal Finish Result/run时，Agent把它视为普通Workspace update；本地没有协作者Task是正常事实，不得从commit author、HEAD、dirty tree或Doctor drift反推self-bootstrap activation。Git transition后运行Doctor；若唯一问题是受管投影过期，则按既有授权执行Buildr workspace sync并复核Doctor，其他并存blocker保持显式。只有matching Finish才进入`buildr-self-bootstrap-sync`，普通sync不创建Task、Finish或新的lifecycle authority。

Development Launcher安装前，self-bootstrap runner的continuity helper只读取Development Web Data Root并用instance secret认证health；只有健康development实例才冻结当前端口与旧PID，绝不读取、停止或清理released实例。manager原子更新Launcher后，helper通过retained `projects/product/buildr web --port 4458 --no-open`、Environment retained Node与新Launcher identity恢复服务，并记录previous/current端口、新旧PID及retained source/HEAD/Node；历史随机端口实例因此迁移到`4458`。原本未运行、stale或其他channel保持按需启动。恢复失败只回收本次启动且PID可证明的进程，保留代码交付与新Launcher，并以自举激活注意（Activation Attention）停止后续gate/finalize，不回滚交付、不停止foreign占用者。

同一carrier根存在多个run时，runner只隔离可证明ownership、路径和identity的foreign carrier；不得修改或删除仍代表repository carrier的内容。历史Result已由Product明确声明全部carrier为`cleaned/root: null`时，runner只有在精确run container真实、非symlink、未越界且完全为空的情况下，才以`stale-empty-container`兼容分类执行非递归空目录删除；非空、identity不匹配或删除失败继续阻断且不递归清理。已交付但cleanup pending的owner仍由Agent通过Task Environment独立处理，不成为其他Delivery或Activation的全局前置条件。

多个自动Finish run只在相同repository-scoped target mutation窗口竞争短lease；多repository不构成跨remote原子事务。逐repository push/readback后立即checkpoint，部分成功必须保留，恢复或reconciliation不重复push已交付repository。

retained canonical Workspace存在metadata-only或其他自动adapter不适用情形时，Agent仍可选择精确Git Operations或PR交付；每次operation保持独立Result，完成后由reconciliation登记Task Delivery。无法证明repository/ref/scope或完整push range时停止，不使用`git add -A`、stash、reset、隐式rebase/merge或force push。

Task Environment 候选集成后，主 Workspace runtime 仍从 retained checkout sync/doctor；未合并 task checkout 不更新主 runtime。sync 只维护当前 SQLite authority 与 runtime assets，不扫描旧 Task Environment receipt 或 `.buildr/tasks/`；Git provider evidence 继续由窄 provider authority 维护。


## 与 buildr-web 的交接

- `buildr-web` 拥有前端源码；`npm run build:web` / `dev:web` 委托 sibling `../buildr-web`。
- `buildr/package.json`中的`build:web`委托和Task Verification所选前端能力，是Agent判断当前Task需要同时准备`buildr`与`buildr-web`的正式源码事实；Agent把该判断登记到Task专属Environment Plan，静态Project配置不充当routing authority。
- 正式静态资产落在本 Service 的`web-dist`；公共application payload只消费已提交dist，npm package不携带`buildr-web`源码或Vite toolchain。
- Buildr Web Runtime 继续从 `web-dist` 同源 loopback 托管并注入 session，不改为独立前端端口。
