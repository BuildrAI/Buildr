# Buildr Service

## 职责

Buildr Service 是 Product Project 的可执行应用实现，负责 CLI、Workspace/Project/Service/Task Record/Task Environment/Task Review/Task Retrospective/Task Verification/Task Development/Parent Coordination/Task Finish domain、Skill-only Git Operations、Project Testing 指导、Buildr Web Runtime 与 session 同源托管、runtime adapters、受管资产与 Component 生命周期、capability graph、验证执行、package 和发布。Buildr Web React/Vite 权威前端源码与构建属于 sibling Buildr Web Frontend Service `buildr-web`；本 Service 在构建/打包时消费其产物到内部 `src/interfaces/local-app/web-dist/`，运行时不依赖 `buildr-web` 源码或 Vite。

## 接口与入口

- CLI：`projects/product/buildr`是Buildr checkout唯一开发入口；PATH默认`buildr`只代表npm installation。两者身份和更新责任隔离。
- Buildr Web：loopback HTTP 与浏览器界面。Task 列表默认 `open` (todo + active)，可分别过滤 todo、active 和终态；Task 详情展示复盘来源，复盘 Tab 展示后续 Task 与当前状态。正式 Task 只由 Agent/Task Manager 创建或激活，Buildr Web 只编辑/结束已有 Task 并维护复盘处置。五个 Task 一级视图、Task-scoped Change route、专业只读边界、复盘处置 PATCH 与文章入口其余语义保持不变。
- Package：`services/buildr/package/manifest.yml` 定义发布边界、workspace/project baseline、builtins、contracts、bindings 和 Components；Component definition 同时拥有 Skill fragments 与其引入的结构化 capability dependencies，package builtin descriptor 不重复维护 Component-owned `requires`。
- Runtime Skill renderer统一组合package产品入口与Workspace Skills。产品入口不接收完整capability routing dump；每个consumer只获得自身`requires`的紧凑binding block。Doctor full输出全局capability graph，destination-aware `.buildr/agent-runtime/` receipt保存受管文件identity和consumer-local contract digest/provenance快照，runtime目录不承担机器证据authority。

## 应用负载、Launcher 与发布运行时

- `scripts/release/application-payload.mjs`把同一runtime CJS bundle、read Worker bundle、Web dist、migrations、package baseline、生产依赖、图标与许可证冻结为`buildr.application-payload/v1`；npm staging消费同一`applicationPayloadDigest`。resource resolver只从摘要验证payload或canonical development root解析资源，正式runtime不依赖cwd、PATH、`buildr-web`源码或Vite。
- npm package是唯一正式产品安装。`buildr web launcher install`只在显式请求后生成本机macOS `.app`或Windows Start Menu shortcut，closed binding精确记录formal npm origin、Host Node、package entry、prefix、payload/protocol与target；wrapper不复制Node、Buildr package或payload，也不形成独立更新渠道。
- Development Launcher继续由当前checkout的`package/launchers`内部manager构建为thin入口，只包含图标、identity与启动脚本，绑定Service source root和独立development host Node，不使用Workspace Node、不复制payload或npm安装。`npm run install:development`和self-bootstrap activation都用绑定的development/retained Node直接调用该manager；它们不经过npm-owned公开`buildr web launcher`命令。Development Launcher与formal npm Launcher在名称、target、identity和lifecycle上隔离。
- `installation status --json`、Doctor和Web health/instance分别展示receipt证明的npm、development、Launcher与current instance identity；`update`按同一receipt路由npm package或development checkout，并只原子刷新同slot已有Launcher，不扫描PATH、文件名或目录形状。

## 数据与依赖

- Workspace/Project/Service、Rules、Skills、Commands 和 Components 使用 YAML manifests/registries。
- Workspace Structured Store使用每个Workspace root自身的`.buildr/local/workspace.sqlite`，由随npm package交付的连续SQL migrations、checksum ledger和Doctor管理。它是Buildr Local单机数据，不进入Git或同步；未来Server/Cloud不复用数据库文件作为共享协议。Buildr Web registry已解析root后的read-only Application path只读取该root，不执行Git/worktree provenance观察或`git rev-parse`；writable、migration和mutation path仍执行writer guard。自举 candidate runtime 在与 retained Workspace 共享 Git common-dir 时，只能写入自己的 linked Task Validation Workspace store；写 retained canonical store 或 peer checkout 会在创建目录、SQLite、WAL/SHM、ledger 或业务 row 前被 provenance guard 拒绝。验证 store 从完整 migration chain 建立，数据不回灌主库；最终集成后的 retained runtime 才能升级主库。
- Task Record 使用 closed `buildr.task-record/v2`，状态为 `todo|active|completed|abandoned`，`open` 只是 todo + active 的查询语义。todo 只保存意向，不得关联 Change；activate 只转状态。`task_retrospective_sources`以 source/target Task ID 表达多对多复盘信源，新关系要求来源 Task 终态且有 current 复盘。它不保存 action item 或复盘正文。Parent/Child、scope/Change 关系、单事务 writer、linked-worktree guard 和旧`task.yml` inert 边界保持不变。
- Task Review 使用 Workspace SQLite 中的`(task_id, planning|completion)`两个可选current slots与统一closed `buildr.task-review-result/v1` schema。同类型事务原子保存完整Result及`target_identity`、`outcome`、`updated_at`查询字段，跨类型隔离；inspect只比较调用方显式提供的保存identity，未提供时返回`unknown`。Task Review Application仍是唯一writer。
- Task Retrospective 仍以单一 SQLite current row 保存原始 Markdown 与 `pending|handled|no-action`。处理流程必须先返回原文/current digest，再基于当前项目事实重新拆分方向；有效方向全部关联已有 todo/active Task 或新 data-only todo 后才 handled，全部失效才 no-action。Application 只返回反向后续 Task read model，不保存分析中间项或 action item ID。
- Task Verification 使用 Workspace SQLite 中按Task ID唯一的closed `buildr.task-verification-result/v1` current row。record action绑定opaque Content Target identity和由Application观察的Project declaration identities，并在同一transaction保存完整Result及`target_identity`、`outcome`、`updated_at`查询字段；inspect不接受declaration root或重新读取声明，只比较调用方显式提供的保存identity。Application从Task显式Project、Service所属Project与Change所属Project派生有效Project集合；集合为空时只允许空declarations、空capabilities、唯一workspace gap与`not-passed`，集合非空时继续要求完整非空declarations并拒绝workspace gap。repository只在新写入时绑定current Task scope，reader保持旧row与自描述workspace row可读以派生stale；不迁移、回填或自动passed。持久模型不含Candidate/generation、execution stdout/stderr、Environment Receipt、revision/history、风险或推进决定；Task Verification Application仍是唯一writer/reader。
- Task Development使用Workspace SQLite中按Task ID唯一的closed`buildr.task-development-receipt/v3` current row，不读取旧YAML，v1/v2 JSON只读归一化为Parent facts absent且不backfill。每个合法action先形成Receipt与正式applicability observation，再由唯一repository在同一transaction保存`record_json`、`applicability_status`、`applicability_json`和`observed_at`；inspect只返回这些保存事实，不重新观察Environment、Content Target或declaration。仅工作区policy以空declarations、空capabilities、唯一workspace gap与空overrides形成稳定identity，Content Target或有效Project集合变化后stale；gap未进入matching current Result时不能freeze，负向Result进入后仍要求明确风险授权才能proceed/handoff。Receipt继续保存可选Parent Plan、planned Contribution binding、final acceptance、Content Target、policy、current Candidate/generation、最小gates/decision与append-only handoff，不保存专业正文、execution evidence、Git carrier、绝对路径或完整history；carrier operation要求handoff、Candidate、generation与Content Target四项冻结identity，只有全部等于`observed.currentHandoff`才返回equivalent，不能从历史handoffs选择旧identity；Project/Service既有门禁不放宽。
- Parent Coordination Domain/Application不拥有repository。它通过Task Record取得直接关系，通过Development取得Parent Plan/binding/current handoff，通过Review取得Plan identity applicability，通过Terminal Delivery只接受matching Finish association证明Child delivery，动态返回Contribution disposition与最终验收前置条件。CLI、Buildr Web与Agent共用该Application；Child状态不回写Parent，Child completed无matching handoff为`unproven`，Parent final acceptance和completed均为显式独立动作。没有Parent Plan的历史Task保持`legacy`；不扫描、迁移、推断或改写旧Parent Change/checkbox。
- Task Execution Record使用单张SQLite`task_execution_records`表保存closed metadata，并由唯一Application组合`.buildr/local/task-execution-records/<owner>/<record-id>/`受限正文Store。v1开放Verification execution与Finish diagnostics两组owner/kind，提供open、seal、inspect/list、failure resolution、单记录cleanup与Workspace级ExecRecord GC；正式Task command Verification与每次真正执行的Finish invocation均已接入producer，Task外Verification run仍为transient-only。open先预留固定record quota，正文先版本化脱敏与安全截断，再通过staging/manifest原子publish，retained后才精确清理producer-owned transient evidence。Buildr Web通过同一Application开放Task-scoped `all|verification|finish` portable列表、详情和closed filename正文读取；正文必须先验证manifest/digest/size且单次响应限量512 KiB，不暴露locator或本机路径。GC只从同一SQLite authority选择bounded candidates，优先恢复`cleanup_pending`、复用retention/resolution/recent-count与单记录cleanup，并在cleaned满90天且超出同类最近20条后条件删除tombstone metadata。`buildr task execution-record gc`提供手动/headless dry-run与执行入口；正式Local HTTP Server从下一本地整点调度，Task Preview Server在scheduler factory前禁用全部scheduled maintenance。GC不接入Workspace Doctor或Buildr Web mutation/UI，不扫描文件系统、不自动处置失败记录、不管理execution resources，也不建立Consumer/Adoption、通用payload/history、第二GC store或lifecycle聚合。
- Verification invocation identity只绑定Task、target、Project/declaration与规范化capability集合，并保存在同一`task_execution_records` authority。open事务默认复用相同identity的active record并零执行返回原record/run identity；只有显式`--retry`创建独立run，`attention`等terminal history不阻塞。Agent使用`task execution-record list/inspect`从同一authority回读portable lifecycle/outcome、timing、failure与evidence摘要；session或PTY句柄不再是终态authority，CLI不暴露SQLite/body locator，也不建立第二份执行状态。

Task Record与各专业模块共用`.buildr/local/workspace.sqlite`，但不合并Domain、Application、writer或状态机。已退役的`task_lifecycle_current`不再复制跨专业事实；Task Overview与Parent Coordination只组合各owner已保存事实，不新增store、cache、view、progress/lifecycle/event/history表或writer。Task current records不发布、不进入Git、不进行本地多机同步；Task Metadata Publication、静态Task Board与旧Task Asset Review生成链均已清退。既有静态页面与`.buildr/asset-review/`只作为历史数据保留，不由Service读取或维护。Environment与Finish继续拥有各自本机运行/交付事实，Buildr Server/Cloud只作为未来团队协作方向。
- OpenSpec 依赖 `@fission-ai/openspec` 1.6.0；apply 前使用上游 strict validation 与 current Planning Review，Buildr 补充跨 Change conflict evidence、文件事实驱动的确定性收敛事务和 runtime contributions。`baseline create`、阶段型 `check`、`sync-plan`、`sync-apply` 公开 CLI 已删除，deterministic primitive 只在 `converge` 事务内部组合；历史 archive bytes 保持 inert，不作为当前授权。
- Buildr Web Task API 先把已登记 `workspaceId` 解析为 canonical root。Overview endpoint调用Task Overview Application，用一次参数化SQLite联表查询返回Task与各专业current的最小摘要；Development、Environment、Review、Verification、Retrospective与Execution Record GET调用各自Application并使用`no-store`。Execution Record routes只接受Task ID、closed view、record identity与closed filename，返回登记的portable JSON；专业endpoint不接受任意root/path。唯一额外writer是受同源、session、JSON白名单与current digest保护的Retrospective处置PATCH，它只调用Application `handle`。Finish的唯一`task_finish_current`行保存current或compact terminal及本次采用的handoff、Candidate与三个gate最小关联；Terminal Delivery从terminal payload读取并与Development handoff确定性匹配，不用后续current Result重新证明历史关联。Change全局collection保持retained-only；Task关联详情通过共享Resolver读取Environment saved current，`ready`或`blocked` Receipt只要仍能证明matching Project scope、source path与execution root归属且目录当前可读，就使用task-environment candidate，否则回退retained Project。Runtime、CLI、依赖或projection readiness阻塞继续作为Environment诊断，不隐藏可读Change，也不授予任何执行能力。
- Buildr Web 的专业Task只读操作通过固定容量 bounded read executor 执行，默认2个long-lived Worker、32个FIFO queued slots；Worker只接受overview、development、reviews、verification、coordination及execution-record list/detail/body-file closed operation，并在自身runtime中读取既有Application read model。队列满返回`local_app_read_queue_full`，请求取消不重试且运行中结果丢弃，Worker failure只结算当前请求并恢复容量；server close释放pool。该executor不承载mutation、Environment、worktree、Finish current/terminal Application、execution record cleanup/GC或Doctor，也不重新执行已解析root的Git/worktree provenance或`git rev-parse`。
- Project根可选`preparation.yml`使用closed`buildr.project-environment-preparation/v1`长期声明Project-wide或Service-scoped Recipe。Agent按Task Record完整Project/Service scope提交Plan Request；Task Environment Application从Task execution root解析Declaration与Recipe identity，保存Plan v2和closedReceipt v5到Workspace SQLite唯一`task_environment_current`。Receipt分层保存Declaration/Scope/Recipe/Step current与prepared identity、executed、inputs/outputs/required/status/diagnostic，以及既有scope/root、Runtime/CLI/projection、provider、资源和cleanup facts。Application不扫描仓库manifest或实现技术栈适配器；任一required Recipe/Step缺失、漂移或失败时整体blocked。`inspect`只读live observation且不升级Plan，Buildr Web GET只读saved current；旧Receipt只读兼容，只有显式Plan Request升级。
- Git worktree provider 只在 Git common-dir 保存 `buildr.git-worktree-evidence/v1`，包含 repository plan、checkout/branch/HEAD/clean/registration 和 Git effects。`worktree create|inspect|cleanup` 不返回 Environment ready、Runtime/CLI/依赖、资源、恢复或总 cleanup 结论。
- Git Operations 只由 `git-operations` Skill 和 `buildr.git-operations/v1` contract 表达调用期行为，不新增 Application、CLI、Receipt 或 store。consumer 提供 repository/operation/ref/scope/授权；Result 只返回适用的前后 identity、完整 push range、变化维度和实际 effects。
- 普通 Rule/Skill 内容修改不要求新 session、reload、re-enter 或 activation evidence。候选 CLI/runtime 可以在自身 Task Validation Workspace 验证；只有集成到 retained source 后正式 runtime 才同步生效。bounded Agent capability 必须由 Agent 形成事实，文件投射或 Environment ready 本身不等于验证通过；Result 不复制 Environment Receipt。

Workspace Node identity进入Environment Receipt的Runtime probe与Workspace-owned execution binding，并绑定Verification execution evidence/record及Finish adapter本机run/resume判断，但不进入Content Target或Task Candidate identity。它不充当平台、npm或development main process runtime，也不因版本相同而与Product/Host/development Node合并。portable Task Verification Result只绑定调用方Content Target和Project declarations，不复制Node/Environment事实。

## 运行与验证

Task Record以Domain/Application/SQLite repository构成独立writer；Task Environment、Task Review、Task Retrospective、Task Verification与Task Development继续使用各自Domain/Application/repository。它们只共享Task ID，Task Record不再以Task目录或文件存在作为authority。Task Development只通过bundled Skill和internal driver的`begin|planning|observe|policy|gate|freeze|decide|handoff|carrier` actions写入；该driver另外提供无需Task/Workspace且不compose runtime的全局/action `--help`、action `--schema`与`--example`，其closed顶层输入字段与Application校验消费同一action contract，但运行态合法性仍由Application判断。Task Retrospective通过Skill/internal driver的`record|inspect|handle`工作，Agent收到宽泛处理请求时只读inspect并展示拟disposition、理由和Task effects，只有用户直接指定完整mutation或明确接受未变化方案后才执行Task关系与handle写入；Buildr Web只新增同一Application所有的处置mutation。二者都不注册公共CLI。`git-operations`、`task-environment`、`task-review`、`task-retrospective`、`task-verification`、`task-development`与窄`task-worktree`分别提供对应独立capability。

Service source使用Node.js ESM并支持`>=24.15.0 <25`，发布时由锁定bundler形成npm package消费的单一CommonJS runtime payload；开发依赖通过lockfile与`npm ci`收敛。npm entry只接受兼容Host Node，development launcher绑定兼容development host；二者都不被Workspace声明替换。Workspace在`.buildr/workspace.yml`维护精确`runtime.node.version`，`init`准备、`sync`只按声明恢复、`doctor`只读核对；只有Workspace-owned subprocess使用该runtime。未来Node主版本升级必须经Host/Workspace独立验证后显式修改对应authority。`task verification record` 的 `--declaration-root` 只用于正式写入前观察声明，`task verification inspect` 不接受该参数；Browser changed dispatcher 优先消费 `BUILDR_CHANGED_PATHS_JSON`，否则从 execution root 的 Git base 推导，无法解析时返回明确的 capability input error；run 的 target drift 以 added/removed paths 和 status change 单独报告。

Project `verification.yml` 使用 closed v2 declaration，只描述少量稳定、可独立选择的已有 capability；测试意图、执行边界、成本、范围、验证目标和目标耗时保留在 Project Testing 或项目 registry。Buildr 的唯一 verification registry 为每个 step 保存 owner、测试意图、执行边界、证明范围、目标耗时、主要证据 owner、环境足迹、隔离方式和重置负担；`fast` profile 表达低成本 Quick，inputs 表达 affected owner，`candidate` profile 表达显式核心完整回归，三者不再复制为混合编排场景分类。Planner 在启动 verifier 前拒绝穿过真实 filesystem、CLI、Git、网络或 Workspace 生命周期的 Component，也拒绝需要重复 cleanup 或完整生命周期的 Quick；低成本 Integration 只有在有界、可测、隔离且无重置负担时才可例外进入。`test:contract` 只保留 Static Conformance 与只读 Product tree 检查；真实开发入口、Git、临时目录和 cleanup case 由 `test:integration` 的 affected/focus/Candidate owner 承担。完整 CLI、Git、Workspace 生命周期由唯一 `test:system` 入口承载，旧 `test:integration:fast` 不再保留。System 的 Task lifecycle 测试在一次运行内共享 `task-lifecycle/v1` 不可变基线，每个 case 使用独立 sandbox；初始化、Git/Task Environment、安装、迁移与 Finish owner 保持完整隔离。OpenSpec contract/recovery cases 在 Candidate 中互斥，package parity 只持有代表输出和一次 init mutation，安装后 sync/doctor/uninstall 由 release tarball smoke 独占。默认 local/CI 允许两个使用不同临时 root 的 `workspace-saturating` verifier 有界并行，资源受限 CI 保持单路。正式交付只有一个 required `product.delivery`，在冻结 Candidate 上由 changed planner 选择 affected；registry/planner/runner、声明或 timing 等全局 owner 变化时同一 plan 扩展为 full。`product.full-regression` / `test:candidate` 保留为显式完整回归；Browser 由独立、条件化必需 capability 持有，Release 专项保持独立。上述能力和 Product-only runner 不构成通用 assurance 层级。`buildr verification run --project <code> --capability <id> ... --target-identity <identity>` 随npm runtime发布，只执行显式command capabilities；Task外run输出provider-owned transient evidence，正式Task run则在启动前open execution record，seal成功后清理transient evidence。公开JSON只返回portable executionRecord摘要，不暴露SQLite或body locator。`effects.authorization: explicit`与explicit resource分别要求精确capability/resource授权；被真实claim的`coordinated`资源才通过Git common-dir lease协调。该机制不调度Agent或任务，也不写current Result。

目标为`dev`的任务分支只在Windows Node 24.15.0/当前24.x运行`windows-npm-preflight`定向组，集中覆盖npm Host Node、Launcher、Integration、System、并发Task、runtime parity、Workspace lifecycle与release tarball smoke且禁用fail-fast；`dev -> main`、手工最终候选和`main` push才在macOS/Windows × Node 24.15.0/当前24.x运行四个完整`test:candidate`。Candidate内置`release-tarball-smoke`是最终发布冒烟owner，CI不建立重复的独立release smoke job。

Product `test:candidate` 额外执行 `concurrent-task-acceptance` 组合验收：在单一临时多仓 Workspace 创建两个正式 Task，并发 prepare 两个真实 Environment，从不同 cwd 按 Task ID 调用 Receipt 返回的绝对 CLI invocation，再并发执行显式 `verification run`、记录两个不同 Task-scoped current Verification Result，并启动随机端口 Preview。验收按 fixture、environment prepare、Task invocation、verification、verification result、resource coordination、preview、failure diagnostics 与 cleanup 输出阶段 timing，并核对多仓 scope、allowed roots、共享容量等待与释放、不同 Result path/digest/current applicability、非空 execution identity、错误 Task 无法停止对方 Preview、异常子进程诊断、顺序 Environment 清理保持另一 Task 及 retained doctor。独立 invocation、Preview stop 与 Task abandon 可以并发；只有证明 peer preservation 的 Environment cleanup 保持顺序。该步骤使用本地临时 Git 与进程，不访问外部系统。

Task Finish是`buildr.task-finish/v1`的固定五阶段窄adapter。仅工作区与Project/Service Task都必须先形成current Development handoff；Finish不解释workspace gap、负向Result或风险授权，也不补跑Verification/Review。CLI只公开`task finish run|inspect`；首次run接受Task ID、必需的`--commit-message`和可选target branch/remote参数，从Task Development Application取得current研发交接并冻结完整handoff snapshot。Agent根据最终内容与仓库约定确定语义化subject和可选body；产品冻结message identity，不从Task/Change/diff或路径推断语义。preflight、prepare、verify、deliver及复用这些输出的resume都通过Development carrier operation精确核对冻结identity。handoff变化后，无carrier/lease/delivery/retained/cleanup事实的preflight-only旧run，以及可证明在carrier ownership形成前以`carrier-preparation` terminal failed、无resume且后续阶段未开始的prepare旧run，可安全失效并要求新message；blocked prepare、未知阶段状态或已有owner/recovery事实时保留现场并返回identity conflict。current Product只有一个直接接线的Git carrier adapter；`preflight → prepare → verify → deliver → cleanup`保持不变，prepare在最新Delivery Baseline的run-owned carrier机械应用Task Contribution，verify只证明carrier等价，deliver完成target/remote readback，cleanup以冻结handoff和已持久化delivery facts交给Environment；`formalVerificationExecutions`固定为0。

Finish不解析或收敛Change/current knowledge，不执行target rebase、formal Verification Result写入、Completion Review、Candidate generation、`proceed / blocked`或风险接受。deliver普通路径只允许已核验carrier的fast-forward、普通push与远端ref回读；target前进时仅在carrier ancestor及全部changed-path after mode/blob/删除状态精确保持时记录`already-contained`、跳过重复transition并保留原carrier与最新后代ref。`adaptation-required` run另可在matching token与`--accept-zero-delta-adaptation`下采用Agent审查的clean baseline carrier：actual delta为空、不创建commit，stable baseline以`already-contained`零推送继续；deliver与retained cleanup调用同一专用观察器，确定性复核registered clean carrier、baseline HEAD/tree、空delta、target ref和zero-delta proof identity，cleanup只在重建proof与saved proof整值一致时继续。target再次前进则重新产生target race。随后执行类型化retained runtime activation与通用Workspace inventory Doctor，不安装Buildr development CLI或Buildr Web。Doctor仍要求Workspace health ready，但不选择Agent adapter把待post-Finish专属激活的Product runtime drift升级为Finish失败。activation只按冻结Task Contribution派生的additive activation paths选择`none | render-runtime`，而不把零差异carrier的空`changedPaths`误作无影响：Workspace根Rule、Skill、Component、Command等runtime source选择render，其他变化none；旧Result没有该字段时回退`changedPaths`。不读取Project/Service配置，不执行sync，也不接受任意executable/args/env/shell。render产生tracked delta即fail closed；无法证明包含时target race凭exact token从最新Delivery Result；Environment已清理后的恢复不重跑delivery。Formal Finish成功后，Buildr自举Workspace专属`buildr-self-bootstrap` Component只按Result绑定的冻结Task Contribution activation paths去重执行package sync、development Buildr Web install、retained `projects/product/buildr` identity gate与selected-Agent最终Doctor；PATH默认`buildr`只属于npm installation，不由self-bootstrap安装、删除、覆盖或验证，最终Doctor或same-run resume必须通过已验证的retained Project bridge执行。失败不回写Finish或上游facts。普通Workspace、通用Skill和executor不获得该能力。路径不重叠、clean apply或resume动作不构成语义安全判断。

当前run/canonical result为`buildr.task-finish-run/v2`与`buildr.task-finish-result/v2`。CLI JSON缺省或显式`--detail compact`在Application输出边界生成closed `buildr.task-finish-compact-result/v1`，显式`--detail full`原样返回canonical v2；detail不读第二authority、不写SQLite，也不改变五阶段、resume、Carrier、Execution Record或Task terminal。compact仅保留Task/run/status、current phase、handoff/Candidate/Content Target、主失败、next action、matching resume、关键refs、delivery/completion disposition、timing和portable Execution Record摘要，完整diagnostics只属于full。Task Finish current run payload是规范化完整message的唯一恢复owner，并以message identity绑定run identity；已有缺少该字段的legacy current run保持可恢复，新run不得fallback。实际Git commit持有同一正文，公开Result与Execution Record只投影`deliveryCommit: { subject, identity }`，Task Record、Development/Environment Receipt与其他authority不复制正文。Result additive返回只读`resolvedContext`：固定报告`buildr.task-finish/v1` capability、Task/handoff/Candidate/Content Target、Agent、target branch/remote、Workspace Node及其确定性identity；这些值只从run identity投影，不接受caller输入，不增加execution capsule、列、Receipt或第二authority。旧terminal v2缺少该字段时reader返回null且不迁移。Workspace SQLite按Task唯一保存一行`task_finish_current`：状态、当前阶段、关键identity、失败、resume、cleanup、target/token/expiry lease与时间为普通列，固定五阶段只保存status/timing/current failure等compact恢复事实；run与prepared completion使用有界payload，完成时原位替换为compact terminal payload。调用前invalid/no-op先结束；每次真正执行的首次run或resume在任何Finish owner副作用前open独立`task-finish/finish-diagnostics` record，backpressure保持Finish current、Carrier、target与恢复资源零变化。完整stdout/stderr、timeline和命令诊断先进入invocation-owned transient，再由record正文Store脱敏、截断和retained，随后只清理该diagnostics transient；seal或cleanup attention不改写或重放Finish delivery、Environment/Carrier cleanup与Task terminal。公开`executionRecord`只给portable operation summary，`task finish inspect`不读取或枚举records。Delivery Carrier、target、lease、resume与其他恢复资源继续只由Finish owner管理。拒绝旧v1 run；`.buildr/task-finish`不被新runtime读取或扫描，启用SQLite-only前由受控步骤直接清理。Environment已清理后的恢复只重试Finish cleanup与terminal transition，不重跑delivery；`task complete`只表达Task Record completed终态。

Buildr自举Workspace的post-Finish activation仍在Formal Finish五阶段之外。已安装的Workspace Component只调用一次`buildr-self-bootstrap-sync` Skill自身携带的`scripts/closeout.mjs`；脚本通过retained Product CLI按run id只读取得同一Finish Result与`resolvedContext`，优先按carrier `activationPaths`、对旧Result回退`changedPaths`形成无持久状态的确定性plan，并把sync、精确successor commit、普通push/readback、development Buildr Web安装、retained development entry gate与最终Doctor或same-run resume表达为独立阶段。Gate直接执行retained `projects/product/buildr`，注入Environment retained Node，先通过closed development identity核对launcher、CLI entry与Node，再执行`version --json`核对development channel、source commit和retained package/version；它不解析或改变PATH默认`buildr`。Project bridge缺失、入口链漂移、Node/channel/source/version不一致或启动失败均停止finalize。修复该链自身的Task必须在交付前覆盖显式Project bridge、Development Launcher、sync、Doctor与doctor-blocked same-run resume；无关新问题保持原Task blocked并停止，不再逐症状递归创建修复Task。complete只通过已验证入口执行一次最终Doctor；doctor-blocked只通过同一入口恢复原run，Doctor仍只存在于resume内。Plan的`baseRef`始终冻结为当前Result的Finish final ref；runner另从真实Git选择`activationBaseRef`，只接受base到HEAD无merge、每个first-parent commit带`Buildr-Task`或成对`Buildr-Finish-Run`/`Buildr-Closeout-Plan` provenance、clean tree且remote精确对齐的Buildr-owned descendant。HEAD若是当前run/plan successor，则其parent为activation base且remote只可等于parent或HEAD；否则已push的当前HEAD为activation base，新sync successor直接以它为parent。这样多个已完成Finish可顺序激活而无需第二个queue/store；任一未知commit、merge或remote drift仍fail closed。`doctor-blocked`时仅从untracked observation排除由同一Result、Workspace和run identity精确证明的当前Delivery Carrier，其他tracked、staged或untracked差异仍然fail closed。证明不了就停止，不stash、reset、rebase、merge、amend或force push。该脚本不位于Product `src/`、npm package或`package/targets/**`；结构化`buildr.self-bootstrap-closeout-result/v1`additive返回frozen ref、actual activation base与当前调用的development entry identity evidence，不写Task、Development、Finish或新store。普通Workspace没有该Component或Skill，因而不获得此能力。

同一固定carrier根存在多个run时，bundled runner先枚举直接子项，并仍只用上述Product inspect入口核验各foreign Result。可证明的`cleanup_pending` run进入`buildr.self-bootstrap-recovery-plan/v1`，按owner Task/run稳定排序原Finish owner cleanup，最后列当前runner重试；不支持状态标记`manual-owner-review`，symlink、越界、inspect失败或identity/token漂移标记`unprovable`。只要foreign carrier仍存在，当前调用便在任何Git、sync、安装、Doctor或resume前blocked；计划只表达授权点、原owner命令和effects，协调器没有foreign cleanup/delete能力，也不保存聚合状态。

retained canonical Workspace 中明确的 metadata-only候选不进入产品执行器，因为无关dirty state无法形成隔离交付载体。Task Finish Skill只有在任务paths、当前研发交接、目标branch/remote与retained context都可证明时，才选择精确commit与push的目标和顺序，并分别交接给optional selected`buildr.git-operations/v1` provider；provider只能stage任务paths、检查完整push range并保留无关改动，返回两项各自适用的最小Result。任一事实或provider readiness不可证明时正式blocked，不使用`git add -A`、stash、reset、rebase、merge、force push、虚假Change或手写Git回退。

Task Environment 候选集成后，主 Workspace runtime 仍从 retained checkout sync/doctor；未合并 task checkout 不更新主 runtime。sync 只维护当前 SQLite authority 与 runtime assets，不扫描旧 Task Environment receipt 或 `.buildr/tasks/`；Git provider evidence 继续由窄 provider authority 维护。


## 与 buildr-web 的交接

- `buildr-web` 拥有前端源码；`npm run build:web` / `dev:web` 委托 sibling `../buildr-web`。
- `buildr/package.json`中的`build:web`委托和Task Verification所选前端能力，是Agent判断当前Task需要同时准备`buildr`与`buildr-web`的正式源码事实；Agent把该判断登记到Task专属Environment Plan，静态Project配置不充当routing authority。
- 正式静态资产落在本 Service 的`web-dist`；公共application payload只消费已提交dist，npm package不携带`buildr-web`源码或Vite toolchain。
- Buildr Web Runtime 继续从 `web-dist` 同源 loopback 托管并注入 session，不改为独立前端端口。
