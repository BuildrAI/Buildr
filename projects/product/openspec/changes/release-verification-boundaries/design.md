## Context

见 [proposal.md](proposal.md)。当前六个发布工具检查在两系统重复，Windows 拥有大量通用生命周期；源码和原包消费混在同一分片，阻碍整分片跳过。输入识别遇到动态导入或无文件的执行器时保守匹配整仓，导致局部修复传播。

## Goals / Non-Goals

以完整、可核验的行为覆盖为目标，减少重复执行和准备；本机成功只能证明其实际范围。保留原包、来源、失败及清理事实。不新增验证平台、不改变公开发布授权、不宣称本轮完成真实 Windows 验收。

## Decisions

1. 通用源码检查集中在 macOS 声明的主证明分片；本机入口包含原 Windows 的任务、工作目录、恢复、适配器与并发检查。六组发布工具保留单一主证明。它们可被定向诊断在 Windows 执行，但不再默认重复。
2. Windows 源码差异由独立检查文件证明真实命令 shim/PATH、真实路径别名与目录链接、进程终止和资源释放。登记同时携带系统依赖、故障、实现输入和复用条件；开发选择使用同一清单。字符串生成和业务规则继续由通用检查覆盖。
3. 原包在 macOS/Windows 保留真实平台启动器消费，宿主最低/当前 Node 保留轻量 CLI、Web、退出证明。两版本与两系统只组合这一小链路，不扩展为全量测试矩阵。无实际原生依赖的新平台项不凭名称增加。
4. 源码与原包分片彻底分开。受控本机结果有效时，源码分片及其依赖准备全部跳过；需要原包的检查不接受源码结果替代。缺项在本机入口可提前看见，不能把本机验证完成等同发布成功。
5. 结果输入按执行器真实文件、发现集合和模块依赖闭包识别。发现新增/删除测试必须使相应证明失效；其他测试文件内容变化不影响已证明的独立集合。可解析的字面量 URL 导入精确追踪；未知读取继续保守处理，不以选择路径当完整输入。

本机参数回归还发现并修复现有 Windows 命令拼接缺陷：命令脚本路径含空格、参数含命令解释器控制字符时补齐引号；非 Windows 和原生可执行程序保持原调用。此修复改变产品输入，因此新的完整候选须使用修复后的包；旧包继续作为原来源的历史事实。

## Risks / Trade-offs

- 真实系统行为遗漏 → 独立最小用例覆盖实际 OS 调用，原包启动及清理仍在目标系统证明；通用检查完整保留。
- 旧候选结构不同 → 新登记身份不接受旧汇总冒充新验收，既有发布和原包记录保持历史事实。
- 依赖范围不明 → 继续保守失效并报告，不能为减少数量静默忽略依赖。
- 本机工作量增加 → 原先远端独占的通用检查回到本机准备，日常仍按改动选择；成功结果按内容复用。

## Migration Plan

先落地登记、用例及选择/覆盖回归，再检查完整计划和本机结果复用，更新发布与验证说明。此轮不派发远端；后续独立验收只补真实 Windows 与 GitHub 边界。回退按原登记和对应版本执行，不混合不同登记的汇总。
