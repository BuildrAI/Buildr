## Context

同步（Sync）现在是单个工作树（Worktree）级能力：前端 `useSourceControlSync.run(repository, worktree)` 先读取同步上下文（sync-context）核对来源、分支、上游与已观察版本，再发起 `sync` 写入；结果通过 `notifySourceControlChange` 广播，由 `SourceControlOperationNotices` 以短时通知浮窗逐条表达，成功后触发受影响代码库的局部重新观察。目录标题的操作菜单目前只有“全部获取远程”。动机见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 目录菜单提供“全部同步”，一次点击按已观察目标依次完成全部可同步工作树的同步，用户不再逐行点击。
- 复用现有单条同步的上下文核对、写入、结果广播与局部重新观察，不引入第二套同步语义。

**Non-Goals:**

- 不新增服务端批量接口，不改变 `sync-context` / `sync` 请求形状。
- 不并行同步、不自动重试、不新增定时或自动同步。
- 不改变单条同步、全部获取远程与只读刷新的既有行为。

## Decisions

- **顺序执行而非并行。** 逐个工作树 await 单条 `run`；同一真实 Git 公共目录内应用层写入互斥既有保护继续生效，顺序执行天然避免与在途写入交错，也让逐条结果顺序稳定可读。考虑过并发上限（如全部获取远程的批量去重），但同步包含整合与推送写入，串行更简单且不扩大失败影响面。
- **批次目标取发起时已观察清单。** 在菜单点击处由当前 `observation.repositories` 快照生成目标集合：按目录顺序遍历每个代码库的工作树，过滤满足既有可同步条件（已就绪、非离线、有 `gitId`/`checkoutId`、有本地分支、有提交、已确认远端跟踪分支）的对象。不满足条件的对象保留原行内菜单给出的真实原因，在批次结果中以跳过原因表达，不猜测上游。
- **批次状态复用现有逐键 pending。** `runAll` 在 `useSourceControlSync` 内实现为顺序调用内部执行体并维护一个 `allRunning` 批次标记，供目录按钮显示等待；每个工作树仍登记自己的 pending 键，行内同步图标与行级菜单行为不变。`inFlight` 按代码库去重的既有保护保留：批次内同一仓库已在途的写入被跳过。
- **跳过原因与未发起区分。** 批次开始前已知不可同步的对象写入本地结果条目（状态不可用＋真实原因），不发起上下文请求；上下文核对阶段才发现漂移的对象沿用单条同步的失败路径。

## Risks / Trade-offs

- 逐条串行在多库、多工作树时总耗时累加 → 可接受：同步是显式低频动作，串行保证失败隔离与结果可读，页面有真实等待状态。
- 批次期间来源漂移（分支切换、上游改变）→ 单条同步的上下文核对与版本校验原样生效，漂移对象按既有语义拒绝。
- 通知浮窗逐条更新可能频繁变化 → 沿用现有按工作区聚合的通知键与 6 秒驻留语义，不新增视觉通道。
