现有工作空间（Workspace）、项目（Project）和两个服务（Service）同属一个 Git 仓库。初始基线为 `677ec0f361b6127f7d1e50adce2fccef01a00e1e`，随后接入其他任务已交付的 OpenSpec 1.13 更新；接入后的工作基线为 `ec7b92dd`。保留已有提交和工作，不改写他人历史。OpenSpec 当前没有其他活跃变更。

已核对源技能、两个版本的协作约定、资源清单、OpenSpec 组件贡献和测试：v1 仍要求辅助影响记录缺失时停止验证、归档与收尾；v2 与正文已局部允许提醒，但仍存在“交付内容变化就重建验证依据”的宽泛表达。地图和技术图已有成果，但维护入口只枚举解释文档；术语依赖被声明为必需。当前说明分布在 `docs/` 与 `knowledge/`。

## Goals / Non-Goals

目标：让人在明确范围内获得可读、可核验、能接续的代码地图（Code Map）、技术图（Technical Diagram）和解释文档（Explanatory Documentation）；让智能体（Agent）按目标发现、建设、维护并检查它们。

非目标：全产品知识普查、逐行索引、自动生成全部模块文档、独立知识数据库、后台监听、自动唤醒、发布新版软件。示范不改变现有技能投射行为。

## Decisions

### 成果与事实来源

规范描述承诺，代码描述实际行为，登记配置描述身份与选择，已确认决定描述已获授权的取舍。来源之间冲突时分别报告承诺和实际行为，交还相应修改责任；不能通过改写解释内容消除真实冲突。

代码地图表达实现定位、主要符号、调用、数据与副作用；技术图选择有用视角表达关系并保存可维护图源和可查看成果；解释文档综合说明产品与技术。三者可以直接依据原始事实，按目标组合，没有固定生成次序。版本变化触发影响判断，相关语义未变就保留现有成果。

### 解释文档的具体种类

推荐而非强制逐项建文件：产品概览；核心概念与术语表；产品架构和技术架构；关键业务流程；服务或重要模块说明；使用、开发、运行与排障指南。术语表负责稳定名称与定义，较复杂概念的关系在相关正文解释。设计理由跟随被解释对象；较大的规划独立保存并标明未来，历史审计和文章保持各自用途。

### 目录与迁移

`knowledge/README.md` 为统一入口；`code-map/`、`archify/`、`docs/` 分别保存三类成果。现有概览、术语、架构、流程和服务说明迁入 `knowledge/docs/`。`docs/buildr-product.md` 的当前产品解释与已有概览按内容合并，未来方向保留明确规划入口；当前架构说明和操作手册归入 `knowledge/docs/architecture/` 与 `knowledge/docs/guides/`。仅作导航的文件可以保留。历史审计、历史归档、未来规划和对外文章原地保留；仍作导航的规划链接只修目标，不改写论述。

迁移按语义逐份决定，记录旧位置、新位置与处理理由；当前消费者、规范、入口、相对链接、可执行检查同步更新。历史引用用迁移导航说明去向，历史材料不因当前路径变化被改写。服务内随包参考文档有其分发边界，保留唯一正文并从统一入口引用，不复制到项目目录。

### 最小发现与追溯

每份受维护成果在自身或明确的导航说明覆盖范围、来源路径及必要符号、表达边界和相关成果。已知目标直接读取；未知时只在当前模块、相关导航与来源路径中定位。使用路径和符号链接，摘录需标识来源与适用范围；来源相关片段变化时核对摘录。不实现文档嵌入系统或全局清单。

### 执行与授权

主技能按范围、发现、判断、执行、验证和报告组织，具体成果的编写与检查放入按需参考。明确建设授权可以覆盖一组具体成果；智能体据授权推导文件，不逐文件确认。范围外值得补建的成果列出覆盖、文件、视角、来源和用途，等待该建设授权时继续无关工作。持续维护授权只能作用于用户明确指定的范围与期限。

### 协作迁移

统一提供 `buildr.current-knowledge-maintenance/v3`，保留 `assess|reconcile|inspect|maintain` 操作并明确逐项结果、建设建议和验证影响。默认包不再声明或绑定 v1/v2；内置 OpenSpec 组件与任务分流同步迁移。旧版本包含更宽停止承诺，因此不继续以旧身份声称兼容；用户自有依赖不静默改绑，诊断仅影响相应分支。

术语治理改为可选依赖，有新术语、歧义或定义变化才使用已绑定提供者；缺少术语能力仅影响需该结果的术语结论。单次变更仍维护 `brief.md`；独立知识建设不创建变更说明或辅助记录。归档本身不触发知识写入；归档后独立的、已授权维护仍可以更新当前成果。

### 代表模块

选择 `src/modules/agent-assets/` 中技能源资产经过组合和投射、成为可发现入口的路径。覆盖主要调用、来源文件、投射输出和所有权保护，复用现有技能体系解释，补一份有界代码地图和技术图。排除所有运行时适配器的完整内部实现、组件安装全部分支及外部宿主的实际会话加载证明。

### 验证

复用并调整现有资源与协作测试；增加有实际输入/失败检查的目录、来源与消费者一致性验证，不用仅检查关键词的测试冒充智能体行为验证。七个代表场景通过当前技能、返回结果和实际成果逐项走查并记录依据。地图核对真实路径、符号和调用，技术图验证图源并实际检查截图与交互，解释文档检查关键陈述与链接。只改解释时执行文档检查；原代码测试仍适用就保留。未完成项必须局部报告，不把整体目标伪装完成。

## Risks / Trade-offs

- 旧路径可能被脚本或打包文档引用：读取实际消费者，更新当前依赖并提供轻量迁移导航，历史正文保持原样。
- 协作版本升级可能暴露用户自有旧依赖：如实诊断，不自动选择替代提供者；内置消费者必须全部可解析。
- 既有解释混入旧设计或规划：只迁移可确认当前内容，保留原有有价值材料，标清不确定性与来源，不在本次开展无界修订。
- 技术图依赖外部 Archify 技能：交付完整图源与自包含展示文件，保留验证说明，不将该技能变成所有知识维护的强制依赖。

## Migration Plan

先完成规划严格检查；在独立工作目录修改源资产与当前说明；通过定向检查和代表成果验收后收敛规范；按精确范围交付。正式自举仅使用既有唯一执行器。失败保留工作目录、已交付事实和具体诊断，不自动覆盖用户修改。目录回退如有必要只能对本次已确认改动执行新的明确恢复操作。
