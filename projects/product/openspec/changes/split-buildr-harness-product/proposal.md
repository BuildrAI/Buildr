## Why

Buildr 已有独立执行后台和可替换宿主契约，但对话界面、HTTP 映射、程序凭据管理及发行仍依赖 Development，无法作为独立 Harness 产品使用。现在以同一运行时和数据域支撑两个产品入口，可以独立演进智能体接入能力，同时让 Development 聚焦工作空间、任务、知识及工程现场，而不复制账号、对话和执行实现。

本次按“通用 Harness 产品＋软件工程工作环境产品”厘清能力归属，先交付两个独立产品。总体区分三种装配：本次的独立 Development＋Harness；后续不加载 Harness、采用 DSH 原生执行的 Development 插件；以及后续 DSH 插件框架＋Buildr Harness＋Development 的完整组合。第三种由 DSH 提供插件底座，Harness 统一不同执行程序、模型来源、对话、交互和编排，Development 提供工程环境；将 Development 换成营销等专业环境，仍可消费同一 Harness 能力。这是依赖方向的设计依据，不是本次插件交付承诺或前置验证要求。

拆分采用三个依次消费前置能力、分别验收的变更，由[同一拆分任务](@task/harness-product-split-plan)跟踪整体目标：

| 变更 | 唯一负责范围 | 独立完成依据 |
| --- | --- | --- |
| 本变更 `split-buildr-harness-product` | 目录宿主、通用启动激活、来源授权、唯一 API 与凭据维护 | 不加载 Development 业务即可准备并运行目录工作；Development 通过兼容代理回接 |
| [extract-harness-web](../archive/2026-11-16-extract-harness-web/proposal.md) | 完整对话功能包、三种承载、独立网页监听与换代 | 独立网页、专注、内嵌共用实现；同源认证及网页交接通过 |
| [distribute-harness-products](../distribute-harness-products/proposal.md) | 独立安装、两产品启动器、安装身份及发行边界 | 两个真实启动器可独立点击使用；安装共存、升级和卸载保全资料 |

三个变更不相互重复写同一规范条款；技术变更完成不代表已获得供应商许可、跨平台支持证明或公开发布授权。

## What Changes

- 明确两个产品：Buildr Harness 拥有厂家内核适配、订阅与自带密钥（BYOK）模型来源、统一对话、控制恢复、私有交互数据和独立 Harness Web；Buildr Development 保留工作资产及专业业务能力，通过公开契约与同一套 Harness 界面集成。
- 将 Development 的工程业务与 Harness 接入装配分开：任务、知识、仓库和验证能力保持自身模型与公开操作，只有接入层依赖 Harness 客户端、对话及运行协议。当前独立产品默认组合 Harness，不因此把工程能力永久绑定到它或 DSH。
- 同一操作系统用户、同一配置域共享一个逻辑 Harness 服务及一份对话库，不按产品启动两套后台。稳态只有一个接收新工作的协调后台；保留已有兼容升级时旧代次完成原工作的机制，以及正式版、开发版、预览间隔离。厂家子进程不计作第二个产品后台。
- 先提供只认目录的本地宿主，保留旧 `sourceId=buildr`、`@default`、对话身份及数据路径。目录宿主不创建任务或工作空间登记，业务宿主的对象核验与参与观察是可选能力。
- 显式区分调用入口身份与工作来源身份。同用户同配置域、通过本机认证的两个第一方完整用户入口默认可查看全部来源对话，并对既有执行进行准确控制；界面筛选不改变权限。程序凭据仍按明确范围授权，新执行仍须核验原宿主。恢复策略按来源隔离。
- 将运行单元准备、实例发现、兼容激活和就绪观察的通用编排归入 Harness 公共能力，复用已有 `prepareAgentRuntime/connectAgentProcess`；Development 专用来源、默认工作空间探针留在其适配层。目录宿主必须能在没有 Development 时启动后台。
- Harness 拥有唯一 HTTP/SSE 映射、协议 Schema 和客户端；Development 经同源认证代理接入，保留现有网页与程序接口。代理不变成通用转发器，不复制业务状态，不把内部后台令牌交给浏览器。
- 同一 Development 工作空间继续管理、开发和验证两个产品，沿用同一仓库及按职责登记的服务；不因产品拆分强制拆工作空间、复制任务系统或隔离成两套源码。
- **BREAKING**：多来源授权和可选宿主能力采用新版握手；首个拆分版本同时实现 v1 同来源与 v2 协商，不能只替换契约标识导致旧发现和激活失败。旧用户 URL、原生绑定和数据在声明窗口内保留。运行负载继续随 Development 提供，本变更不要求用户独立安装，也不新增用户网页端口。
- 完整 UI、可选独立网页和两个启动器由后两项变更交付，不是缩减整体目标。许可事实从本阶段并行核对，产品/发行负责人作使用与分发决定；相关流程见[发行设计](../distribute-harness-products/design.md)。

## Capabilities

### New Capabilities

- `harness-product`: 双产品职责、工程业务与执行接入分离、同域共享服务与资料、通用启动激活及目录工作闭环；不包含独立安装承诺。
- `harness-host-integration`: 目录型宿主、来源/调用者和默认权限、策略、工作对象引用、唯一 API/SSE、Development 同源代理与兼容映射。

### Modified Capabilities

- `agent-runtime-connections`: 修改宿主边界、通用协议与跨入口控制，保留随 Development 交付、独立进程、准确持有及兼容更新语义；独立产品发行另由第三变更约束。
- `programmatic-agent-access`: 修改程序凭据与能力发现条款，支持来源化执行范围并保持旧工作空间授权、旧 URL 和既有本机调用方；不把已有第三方本机调用能力删除成“仅第一方可用”。

## Impact

- `services/buildr-harness/`：公开契约、通用启动激活、来源授权和策略、宿主注册、目录提供者、通用工作对象关联、程序凭据唯一维护及共享 HTTP/SSE。
- `services/buildr/src/modules/agent-service/`：保留 Development 宿主与受认证代理，迁出通用协议和程序凭据维护；旧接口仅映射到唯一能力，不保留第二套业务处理器。
- Development 工程业务模块与应用装配：收口对话、生成和执行服务依赖，验证不加载 Harness 接入时已有非执行业务仍可独立使用；不另造通用插件框架或所有厂家统一 SDK。
- 协议 Schema、生成类型、程序帮助和验证入口迁到唯一所有者；Harness 测试不依赖 `buildr/test` 私有工具。现有 UI 本阶段只通过兼容接口回归，抽包属于第二变更。
- 知识与智能体使用指引：实施后按真实结果校准产品概览、接入/数据/技术架构、代码地图、系统图、术语及安装说明；本轮只在计划中列出影响，不把未来能力写成当前事实。
- 与 `agent-process-isolation`、`programmatic-full-access` 各两个需求存在交叠。核对其已交付实现、任务状态及剩余规范责任，按准确授权衔接条款；旧任务已结束但变更未归档时，不把它误报为仍需等待功能开发完成。对应规范同步前须解除重复写入归属，不以无关平台/账号验收阻塞独立切片，也不代验收或擅自归档旧变更。尤其必须区分 start/send 省略模式的 default 与 `/messages` 继承最近轮次，不能套用旧增量的笼统默认值。
- 正式实现前核对任务工作树与当前主线的相关差异，保全规划并纳入已交付的执行释放、退役接续和界面反馈修复；不以最初调研基线覆盖后续修复。
- 不包含拆仓库、自研推理循环、云端多租户、第三方宿主 SDK、插件市场或真实运行资料改名迁移。模型支持、额度、原生恢复等既有规范继续适用，不在此复制一份同义要求。实施与退出条件见 [design.md](design.md) 和 [tasks.md](tasks.md)。
- DSH 插件制作、DSH 执行层扩展、依赖/不依赖 Harness 的 Development 插件版本、其他行业工作台，以及新工作概览/摘要和交互重设计均不进入本次清单。既有 DSH 执行器继续按实际能力使用，不把“DSH 作为执行器”与“DSH 作为未来插件宿主”混为一事。
