## Context

动机及三个变更的关系见 [proposal.md](proposal.md)。本变更只建立可由目录客户端独立使用的核心、启动编排及 API；独立网页与安装分别由后续变更负责。

| 当前证据 | 对设计的影响 |
| --- | --- |
| [`process/server.ts`](../../../services/buildr-harness/src/process/server.ts) 已有独立后台、兼容并行激活；`operationScopes` 限同来源，`ownsPolicy` 仍由旧来源独占 | 复用运行机制，分离调用者、目标来源和来源策略 |
| [`activate-runtime.ts`](../../../services/buildr/src/modules/agent-service/application/activate-runtime.ts) 在 Development 编排准备/激活并用 `buildr/@default` 探测 | 底层能力已在公共包，缺的是产品无关的统一启动编排，不能机械搬业务特例 |
| [`host-channel.ts`](../../../services/buildr-harness/src/process/host-channel.ts) 支持多宿主注册；任务字段及映射仍在核心 | 多连接不是跨来源授权；可选工作对象能力和旧字段必须兼容 |
| HTTP/SSE、Schema 和 [`programmatic-credentials.ts`](../../../services/buildr/src/modules/agent-service/persistence/programmatic-credentials.ts) 仍在 Development | 迁移闭环所有者，凭据路径继续保留，不只搬路由文件 |
| [`programmatic-http.ts`](../../../services/buildr/src/modules/agent-service/interfaces/http/programmatic-http.ts) 区分显式发送和 `/messages` 省略模式 | 保留当前主规范与实现，不能照抄活跃旧增量的概括 |
| [`process/client.ts`](../../../services/buildr-harness/src/process/client.ts) 的 `matches` 与 [`runtime-unit.ts`](../../../services/buildr-harness/src/process/runtime-unit.ts) 精确比较三组 v1 契约 | v2 不能只替换常量；发现、协议协商和运行负载兼容必须分别保留 |
| [`execution-contracts.ts`](../../../services/buildr-harness/src/execution-contracts.ts) 的旧范围解码依赖 `legacySourceId`，进程启动再把它传入核心 | 历史来源解码必须固定，不得由首先连接的产品决定 |

以下均为拟议设计，不把尚未抽取的包或能力登记成当前事实。

## Goals / Non-Goals

目标是目录宿主无需加载 Development 即可启动并完成一次工作，Development 保持兼容接入。仓库、数据根、原生 home 和旧公共标识保持；本变更不做 UI 抽包、独立安装、启动器或公开发布。不引入自研推理循环、通用工具市场或第三方 Host SDK。

整体拆分仍以两个独立产品为交付目标。DSH 插件及其执行层/界面扩展留待后续，不先做 DSH 可行性验证，也不增加工作概览、自动摘要或行业工作台。未来插件方向只用于检验此次依赖边界是否合理。

## Decisions

### D0. 区分产品能力、接入装配与交付宿主

| 边界 | 本次归属与约束 |
| --- | --- |
| Harness 产品核心 | 原生执行器、模型来源、统一对话、确定性执行编排与完整交互；原生推理循环仍归对应内核 |
| Development 工程业务 | 工作空间、任务、知识、仓库/工作树、验证和交付；业务模型和操作不依赖某一对话 UI、运行代次或厂家 SDK |
| Development–Harness 接入 | 当前 `agent-service` 宿主及相关装配，调用双方公开能力，连接工作范围、外部工作对象、单次生成和对话界面 |
| 独立产品壳与安装 | 本次装配以上能力，交付两个启动器；后续插件宿主的装配不进入通用业务模块 |

当前 [`agent-service/module.ts`](../../../services/buildr/src/modules/agent-service/module.ts) 同时消费 Harness 公共包及工作空间/任务查询能力，已是可收口的接入位置；应用根也有运行单元装配。保留并完善这一边界，不让执行类型、账号配置或后台启动前置扩散到工程领域和持久层。需要执行的功能经接入层调用；无可用执行提供方时只报告该功能不可用，既有任务、知识和仓库等非执行操作仍可使用，不隐式切换执行内核。

独立 Development 默认组合 Buildr Harness，是本次发行选择，不是工程业务不可替换的依赖。本次只验证业务可独立装配、当前 Harness 集成完整，以及边界依赖方向；不为尚未实施的第二提供方新造通用 SDK、插件注册中心或动态装载机制，也不额外拆 npm 包来证明解耦。

产品能力与宿主组合明确区分三条路线，而不是只区分“有无 Harness”：

| 路线 | 装配关系 | 对话、交互与执行编排 | 范围 |
| --- | --- | --- | --- |
| 独立产品 | 独立产品壳＋Buildr Harness＋Development | Buildr Harness；Development 提供工程能力 | 本次交付；Harness 也可不带 Development 单独使用 |
| DSH 原生组合 | DSH 框架/原生执行＋Development 插件，不加载 Buildr Harness | DSH 原生能力及相应模型插件 | 后续交付 |
| DSH 生态完整组合 | DSH Plugin framework＋Buildr Harness 插件＋Development 插件 | Buildr Harness 统一执行程序、模型、对话和交互；DSH 提供插件装载底座 | 后续交付 |

第三条不等于把 Development 接到固定的 `dsh cli`：DSH 的插件框架身份与执行器身份分开，原生执行只是可接入路径之一，不能被当作调用其他执行程序的必经代理。具体插件机制及执行层扩展以后按实际宿主能力实现，本次不承诺已经可用。

第三条中，Development 是可替换的专业工作环境，而非 Harness 的必需底座；将其替换为营销等工作环境，Harness 的内核/模型接入、统一对话、交互及编排能力仍应可复用。行业对象、业务状态和专业操作由对应环境维护，不进入 Harness 核心。本次用目录宿主及 Development 两个已有范围证明解耦，不增加营销插件或通用工作台实现。

三条路线复用相应的产品能力与同一 Development 工程代码，不复制业务实现。DSH 原生组合不因此获得 Harness 多内核管理、共同 UI 或同一对话库，届时由相应接入定义来源和记录权威；本次不承诺两种会话库的合并与迁移。DSH 原生执行器适配可以保留其 SDK 依赖，但通用业务/交互模块不反向依赖 DSH 插件宿主的装载和生命周期。

### D1. 单例是逻辑数据域，不是全机唯一 PID

本次两个独立产品中由 Buildr Harness 承载的对话，在同一操作系统用户、准确 `dataRoot` 和 `profileId` 下复用一个逻辑 Harness 服务、一份对话库及账号配置。稳态一个协调后台接收新工作，共享配置单写，每轮一个持有者。兼容更新保留旧代次完成原轮；厂家工具进程不属于复制产品后台。不同用户、渠道与预览继续隔离；该承诺不要求未来不加载 Harness 的外部原生对话也迁入此库。

选择保留现有并行兼容升级，而不是为品牌拆分退回“旧工作结束后才能使用新版”。普通页面关闭或宿主退出只断连接；共享后台退出使用已有准确生命周期能力，不新增“无页面即关机”策略。

### D2. Harness 负责通用准备、发现和激活

在 `buildr-harness` 公开包边界内组合已有 `prepareAgentRuntime`、异步准备、`connectAgentProcess` 和生命周期观察，形成唯一通用启动编排。输入是已核验数据域、候选负载和连接/明确激活意图；输出是准确 runtime digest、instance、generation、受理状态及局部失败。

- 普通连接优先采用现有兼容后台，安装另一产品不自动选择“更高版本”。
- 明确激活复用现有准备锁、兼容判断、精确采用与有界失败恢复；启动了进程不等于目标 ready。
- 探针使用产品无关的身份、契约及受理状态，不查询 `buildr/@default`。
- Development 只装配自己的来源、工作空间解析和必要兼容探针；其专用错误恢复留在适配层。
- 后续 Harness CLI 和启动器只消费该公共能力。第三变更负责将必要负载打包，不能重新实现一份启动器内的激活逻辑。

第一切片即用只带 Harness 负载的干净测试环境验证冷启动，避免把“谁启动后台”拖到发行阶段。

通用化不删除历史解码责任：现有数据域的旧裸范围 ID 及 `@default` 继续按 `legacySourceId=buildr` 解释，不能取当前调用者、产品名或“第一个启动者”的来源。首个拆分版本保留这一兼容映射；新目录范围始终以显式 `harness-local` 引用保存。它属于旧存储格式的兼容解码，不要求加载 Development 模块。未知或冲突的历史来源证据应拒绝错误重解释，而非改名或搬迁记录。

### D3. 最小目录宿主与可选业务能力

目录宿主内置于 Harness，无第二个常驻 Host 进程。新来源固定为 `harness-local`；每段新对话选一个初始目录，产品可管理多个目录的多段对话。保存稳定引用、真实路径和观察身份，重新执行前核验目录未被替换。

`buildr` 和 `@default` 保持旧义，不按路径相同重归属旧对话。CWD 是起点，不是文件沙箱。程序凭据只能使用已登记和授权的目录引用，不能直接提供任意路径扩大范围。

宿主必需提供来源身份、版本协商及范围解析；工作对象核验、描述和参与观察可选。Development 的规则/技能投射、任务授权、Git、连接及专业工具留在 Development；独立 Harness 使用目录本地规则与原生能力，不自动获得业务工具。

### D4. 默认跨来源可见，执行权威不迁移

| 身份 | 负责什么 |
| --- | --- |
| 认证调用者/入口 | 请求者及实际操作权限 |
| `ExecutionScopeRef {sourceId,id}` | 工作范围的权威解释者 |
| conversation/run/participant/generation | 准确对话与执行持有者 |
| 来源策略及版本 | 本来源系统中断接续策略 |

首版是同一操作系统用户的本机产品，不另建一套按产品分割的用户身份。两个第一方完整用户页面经本机认证后，默认可读取同数据域全部来源对话、附件和运行观察，并停止或答复准确既有执行。Harness 默认列表包含 Development 对话并显示来源；Development 工作空间视图可筛选，全局对话入口可查看全部。该默认值不扩展到 v1 客户端、普通宿主注册或程序凭据。

请求体来源不是认证证明。新版握手分离 `caller`、`targetScope` 与 `authoritySources`，注册只允许提供自身被授予的权威回调。来源策略按版本保存，不以连接先后覆盖全局值。v1 保留同来源语义；改变安全含义的 operations/host 使用 v2，生命周期只在语义确有变化时升级。

#### 发现与协议兼容不能混为一个版本号

首个拆分版本采用真实双栈支持：保留旧发现入口、`contracts` 中实际仍支持的 v1 标识及旧运行描述的可读投影，另以支持集合/显式协商公布 v2。旧客户端读取的身份和新客户端选择的操作协议分开；不能把原 `AGENT_EXECUTION_CONTRACTS` 全量改成 v2，也不能只伪造 v1 元数据却不实现 v1 行为。

| 调用方与服务 | 允许的行为 | 必须验证 |
| --- | --- | --- |
| 未修改的 v1 客户端 → 新双栈服务 | 原同来源发现、注册、读取与准确控制 | 使用真实旧客户端构建；不能只用新代码的 v1 参数模拟 |
| 新客户端 → 旧 v1 服务 | 仅复用可声明兼容的同来源能力；跨来源/新目录能力明确不可用 | 不因功能缺失在同数据根另起后台，不静默扩大来源 |
| 新客户端 → 新双栈服务 | 经认证和协商后使用 v2 来源/可选能力 | 仍可通过 v1 路径回归旧调用，权限边界不混用 |
| 新旧后台并存 | 双方控制协议、持久格式及并行条件全部满足才允许 | 旧轮准确控制、配置单写、未知字段保全；否则受保护交接 |

运行描述的契约兼容、`storageVersion` 与并行兼容声明仍分别校验。协议能双栈不证明数据库可并行写入；旧代次不能保全新字段时提高相应兼容边界并等待受保护交接，不为通过旧校验伪装存储版本或复用不成立的并行标记。该矩阵是本次必要兼容层，不开放通用第三方 Host SDK。

| 原宿主不可达时的动作 | 行为 |
| --- | --- |
| 历史、保存附件、运行观察 | 按页面权限读取，来源快照标记不可达 |
| 停止原轮，回答/审批仍有效的请求 | 根据原执行身份、操作权限及通道继续，不依赖任务查询 |
| 新发送、派生、新关联或目录改绑 | 重新核验原宿主；不可达则保留输入并局部拒绝 |

不把 Development 对话改成目录对话来绕过核验，也不因另一个入口能查看历史就假定原宿主授权仍有效。

### D5. 通用工作对象引用与数据兼容

核心只存 `workObjectLinks` 引用：`sourceId/scopeId/kind/id`，可附核验版本和非权威显示快照。首期只适配 Development 的 `work-item`。`taskLinks/taskIds/taskId` 与 `link-task` 是同一关系集合的兼容投影；旧写入只修改其能表达的子集，保留未知关系，不改变任务状态或发送工作。

按完整四元组去重，标题不是权威。旧代次若不能保全新增格式，先沿现有保护机制交接写入权再启用格式，不能让旧写入者覆盖新字段。共享路径不变不等于任意旧版本都可降级。

### D6. 唯一 API、协议与凭据所有者

Harness 统一拥有路由语义、Schema、公开 DTO/客户端、输入输出校验、SSE、附件、活动投影、OpenAPI 和程序帮助。Development 保留页面认证、固定目标代理及旧 URL 映射，服务器使用有限宿主身份，不让浏览器选择目标地址或内部令牌。本变更不新增用户网页监听，后续独立网页消费同一映射。

`/api/v1/app/agent-service`、旧工作空间对话与 `/api/v1/programmatic/workspaces/...` 保留。来源化路径是新增能力；旧 `workspaceIds` 仅投影 Development 范围，不能授予目录或账号管理权限。聚合、统计、事件、附件和原生详情均执行相同范围检查。

凭据唯一写入者从 Development 转给 Harness，但继续使用 `dataRoot/programmatic-access/`，保留 ID、摘要、安全令牌文件、撤销和回推配置。先证明旧直接写入宿主不再写或不在支持共存集合内，再接管。目录范围需先经本机用户登记，程序 token 不成为网页或生命周期管理凭据。

SSE 保留首片、游标、增量、代次和有界恢复，代理不缓冲成整块。上传、幂等 ID、错误与取消语义透传；断订阅不停止执行。既有未知结果不重发等主规范直接复用，以双入口测试证明迁移没有破坏，不复制第二份同义要求。

### D7. 权限默认值按操作保持，不在拆分中重定义

| 操作 | 省略 `permissionMode` | 显式模式 |
| --- | --- | --- |
| start/send | 按现有契约 default | 校验连接能力及凭据 `allowFullAccess` |
| `/messages` 单步续聊 | 继承最近轮次，无最近模式才 default | 按主规范校验显式 full-access |

以[主规范](../../specs/programmatic-agent-access/spec.md)“单步续聊”及当前实现为依据。`allowFullAccess` 开关不是模式选择，也不合并 read/execute/answer/approve。旧活跃变更将全部操作写成省略即 default，应由原负责者在收敛前校准；本变更不越权修改它，也不以“已完整保留”掩盖冲突。

模型路径、额度、原生恢复、进程持有和未知结果继续引用主规范，只验证抽取后的回归，不创建同义新规则。

## Risks / Trade-offs

- 来源字符串冒充身份 → 新握手、第一方页面默认权限与程序窄权限分别测试；缓存包含数据域和来源。
- 仅迁路由遗漏凭据/生成类型 → 以完整调用闭环和无相邻源码消费验证，单一写入者接管前保护旧写入路径。
- 旧格式与兼容代次冲突 → 独占迁移只在准确释放后进行，保全原资料；新存储不允许不理解它的旧程序写入。
- 先有 UI、后发现无法冷启动 → 通用激活属于本变更第一切片，干净目录先验收。

## Migration Plan

1. 先核对实际实施基线，保全当前规划并纳入主线已交付的相关修复，尤其原生资源释放、退役后的未知/可接续状态及界面提示；用对应现有回归防止抽取时回退。这不改变既有退休策略，也不把未知状态当成完成或自动重发依据。
2. 核对本变更涉及的旧条款归属，随后迁通用启动、稳定历史来源解码、目录宿主和双栈契约。
3. 切换策略/关联的唯一写入者，迁协议及程序凭据，Development 立即经兼容路径回接。
4. 用真实本机传输与替身执行器完成以下退出验证；真实供应商和平台发行证明不混入本变更完成条件。

| 验证组 | 退出证据 |
| --- | --- |
| 核心 | 无 Development 冷启动、目录创建/发送/回应/停止/重启接续；目录替换拒绝 |
| 工程解耦 | 不装配 Harness 接入的组件夹具仍能使用已有工程业务；依赖检查证明执行客户端只从接入/装配层进入，无 DSH 插件运行前置 |
| 共享 | 两调用者并发启动同域复用，异渠道隔离，默认跨来源读取及程序越权拒绝 |
| 持有 | 旧轮仍执行时激活兼容新版；来源离线下读/控制可用、新执行拒绝 |
| 兼容 | 旧任务字段保全、凭据 ID/撤销/回推保全；start/send 与 messages 的不同省略规则 |
| 版本与冷启 | 未修改的 v1 客户端与新服务、新客户端与旧服务；Harness 首先启动既有资料仍保持旧来源与准确控制 |
| 协议 | Development 代理流式、附件、丢回执和并发答复；独立公开包不读取 Development 私有文件 |
