# 补齐任务过程材料覆盖

## 一句话摘要

让 Buildr 任务页面上的"任务需求、方案审查、实现审查、开发验证"不再大面积空白：需求默认展示任务目标，变更路径任务默认留下两次审查记录，收尾前补登已发生的验证与审查证据。

## 背景与问题

任务详情页设计了完整的工作路径节点，但实际使用中多数任务只有标题和完成摘要：自举 workspace 36 个任务没有任何审查记录，约一半完成任务没有验证报告，未关联变更的任务需求节点为空。原因是衔接缺口而非门禁：任务级需求没有明确承载与展示位；审查触发完全靠 Agent 逐任务自觉；验证/审查只能在任务进行中写入，完成登记前没有提醒，窗口一过就永远补不上；变更 `brief.md` 缺校验。

## 目标与非目标

目标：每个任务的需求节点始终有正文；变更路径任务默认产生方案审查和实现审查；已发生的验证与审查在任务完成前被登记；`propose` 在声明完成前能发现 `brief.md` 缺失。

非目标：不把审查、验证或 Brief 变成完成门禁；不给历史任务补数据；不改变"用户确认"节点的机制（它仍由验收待办事项填充）。

## 受影响用户或角色

使用 Buildr 任务页面跟进和验收工作的人；以及按技能指引执行任务的智能体（Agent）。

## 核心流程

1. 创建任务时，`intent` 写成简洁清晰的任务需求；页面需求节点默认展示它，变更 `brief.md` 作为补充需求可切换。
2. 走变更流程的任务：规划材料齐备 → 默认方案审查（核对需求与方案一致、方案完整合理）→ 实现与验证 → 默认实现审查（以需求和已审方案为基线核对真实改动）。
3. 收尾登记完成前：若实际跑过检查或审查但还没保存报告/结果，先在任务进行中登记，再完成。
4. `propose` 声明规划完成前自查 `brief.md` 存在。

## 关键变化

- `intent` 被明确定位为任务级需求说明，并落实写法指引。
- 审查触发从"逐任务判断"改为"绑定变更路径默认执行"，审查缺失变得可解释；其他路径仍按需。
- 收尾核对加入"补登已发生证据"一步。
- 前端需求节点目录新增任务目标条目并默认选中。

## 影响、风险与兼容性

影响工作空间技能文本（task-manager、task-review、task-triage、task-finish 与 OpenSpec 增强片段）、任务详情前端展示和一篇架构说明文档。不改应用、数据模型或契约，无迁移。风险：默认审查多为自审、独立性有限——如实标注审查方式，重要变更仍可要求独立审查。

## 验收摘要

- 无变更的任务：需求节点显示任务目标正文而非空态。
- 变更任务：技能指引明确两次默认审查与收尾前补登证据要求。
- `openspec validate --strict` 与收敛预检通过；受影响前端测试更新后通过。

## 技术材料入口
