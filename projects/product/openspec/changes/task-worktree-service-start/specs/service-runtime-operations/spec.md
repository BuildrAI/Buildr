# service-runtime-operations 规范增量

## REMOVED Requirements

### Requirement: 任务范围单项与组合启动
**Reason**: 任务范围按项目登记，公共服务（如 `business-common`）未必出现在每个项目里；按范围过滤会挡住任务工作树里实际存在的服务。
**Migration**: 服务选择改由本任务工作树证据决定；范围声明保留在任务记录中，不参与本地运行判定，历史任务无需迁移。

## ADDED Requirements

### Requirement: 任务工作树单项与组合启动

Buildr MUST 从属于该任务的已观察工作树提供服务选择，支持单个或多个服务；MUST NOT 按任务范围声明或项目归属过滤。

工作树归属 MUST 由提供者证据与当前 Git 观察共同证明：同一仓库公共目录、同一检出目录、同一分支。目录存在但无本任务证据、或身份不一致时 MUST NOT 视为覆盖。

没有本任务工作树证据的服务 MUST 拒绝启动。MUST NOT 回落其他任务或主工作库；未选择的服务不得隐式启动。

该判定 MUST NOT 修改任务记录或范围声明，MUST NOT 自动把服务写入范围。

组合 MUST 依赖单服务能力：对需要实际 URL 的前端声明，已选择对应后端时等待其就绪并注入实际地址，未选择时按原连接规则解析；对已声明的本地服务发现（Service Discovery）关系，MUST 先确定明确参与者的运行身份再启动进程，允许相互调用关系成环，不将发现关系的环直接解释为启动错误。尚未就绪的已选本地目标 MUST 显式不可用，不回落 QA。保留每项成功、复用或错误，局部失败不否定已成功实例。按本任务工作树启动的服务 MUST 使用该任务同一泳道：同一 `taskId` 的路由上下文与版本，服务数量不影响泳道身份。停止任务服务只影响明确选择的同任务实例。

#### Scenario: 工作树覆盖的服务不在任何项目声明里

- **WHEN** 任务工作树证据包含 `foundation/business-common`，而该服务没有登记在任务声明的项目内
- **THEN** 本地验证 MUST 列出并允许启动 `business-common`
- **AND** 与同任务其他服务 MUST 使用同一泳道

#### Scenario: 没有本任务工作树

- **WHEN** 选择的服务没有本任务工作树证据
- **THEN** 启动 MUST 拒绝并返回不可用诊断
- **AND** MUST NOT 借用其他任务的工作树或主检出

#### Scenario: 独立启动后端

- **WHEN** 用户只选择任务后端
- **THEN** 仅启动该后端，前端与其他任务不变。

#### Scenario: 独立启动远程连接前端

- **WHEN** 用户只选择前端并单选远程测试后端
- **THEN** 仅启动该前端，不启动本地业务后端。

#### Scenario: 前后端一组启动

- **WHEN** 用户选择同任务前后端及本地连接
- **THEN** 等待所选后端就绪，以实际端口启动前端；前端失败时保留后端及独立失败详情。

#### Scenario: 多后端组合启动

- **WHEN** 前端声明多个后端且用户同时选择其中部分或全部后端
- **THEN** 逐个所选后端等待就绪并注入各自实际地址；未被选择的声明后端按连接规则解析，逐项失败只影响对应前端启动，不否定已就绪服务。

#### Scenario: 本地后端缺失

- **WHEN** 用户只选前端的本地连接，且同范围没有匹配就绪后端
- **THEN** 明确返回缺失或歧义，不启动未选择的服务、不借用其他任务后端。

#### Scenario: 同任务循环发现

- **WHEN** 明确选择的本地 A、B、C 声明 A→B→C→A，且各自已验证的启动方式允许独立就绪
- **THEN** 各自获得一致任务身份及对应运行编号，不因相互发现等待而拒绝启动，真实请求按所选身份完成各跳。

#### Scenario: 循环中的一项启动失败

- **WHEN** 明确参与者 B 未就绪，而 A、C 已独立就绪
- **THEN** 保留 A、C 的成功事实，指向 B 的调用准确失败，不把 QA 当作 B 的替代，也不停止无关成功运行。

#### Scenario: 业务初始化存在真实前置条件

- **WHEN** 业务应用必须在初始化期间同步访问尚未就绪的本地伙伴
- **THEN** 准确展示该应用启动条件及失败，不用基本健康检查或其他探针成功宣称该业务应用支持循环启动。
