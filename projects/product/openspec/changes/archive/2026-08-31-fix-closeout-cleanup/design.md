## Context

现有默认清理仅从任务完成状态推导清理资格，再用提交祖先关系判断可删除性。旧内部路径可以接收贡献证明，但新公开清理入口没有表达智能体已核验交付的输入。两次提交编号不同就留下工作树，造成已交付任务无法正常收尾。

## Goals / Non-Goals

目标：智能体（Agent）核验完整交付，清理能力保护具体删除；必要补测发生在推进目标分支前。

非目标：不修改研发技能，不新增命令、证明文件、数据库、场景调度链或审批，不用任务完成状态直接授权丢弃工作。

## Decisions

1. 现有 `task environment cleanup` 增加可重复的 `--expected-source <selector>=<full-commit>` 与 `--delivered-ref <selector>=<full-commit>`。两组参数成对覆盖已有 Git 仓库范围，意味着调用者已经核验这些源成果完整交付；不能传可移动分支名或把目标存在当作成果等价证明。
2. 环境应用只对已完成且有交付的任务采用该输入，原内部授权参数保持兼容。它把逐仓输入交给原 Git 提供者，不保存第二份交付记录。无输入仍可走既有祖先包含检查。
3. Git 提供者核验既有工作树身份、当前源提交等于观察值、无未保存内容，以及指定交付提交仍由保留分支持有。删除前重验源、保留目标与工作树状态，分支用预期提交条件删除。不同源/交付提交不再触发原提交祖先或补丁等价要求；应用不声称已独立证明业务交付。
4. 任一未知范围、缺少配对或身份变化在删除前拒绝；已完成的删除不回滚，剩余工作保持可重试。既有动态资源继续由环境能力处理，远端分支永不删除。
5. `task-finish` 明确：内容与相关条件未变不补测；冲突或集成修改影响行为时，选最小充分的已有检查，在推进目标分支前执行。测试条数不作为成本或完整性的代理。

## Risks / Trade-offs

- 调用者可能错误声称交付：技能必须先核验实际成果再提交精确版本；应用明确该输入是调用者的交付核验，不把提交存在或completed状态冒充等价证明。
- 清理期间有其他写入：继续保留工作树身份与版本重验、干净检查及分支条件删除；失败只影响清理。
- 旧调用兼容：不改旧调用参数含义，不恢复旧收尾流程；新增输入与旧路径独立。
