## Context

当前 npm 入口直接加载完整命令行接口（CLI），开发来源则由 Buildr Web Dev 启动登记保存。工作空间（Workspace）的管理归属已存在，问题见 `proposal.md`。

## Goals / Non-Goals

以现有归属选择执行来源；不新增版本配置、不迁移登记或 SQLite，不改变业务命令目标语义，不从候选位置更新用户环境或发布 npm。

## Decisions

1. 以独立 `dispatchWorkspaceCli` 前置选择，在本包业务负载、Node 范围检查及安装环境注入前运行；源码模块编译为正式 npm 独立选择程序，显式源码入口保持绑定。放在业务解析后无法支持旧版未知命令。
2. `--target <dir>` 优先，否则从当前目录定位；联合真实根、身份与 Git 关系识别子目录、链接及工作树（Worktree），不能仅凭相同标识认领副本。`init` 新目标不继承父目录归属。
3. 只读管理记录与两版登记。开发来源从已校验启动登记发现源码根及 Node，npm 来源保持当前已验证安装；不要求网页运行，不写死目录。
4. 原样保留参数、当前目录和输入输出，传播退出状态与信号；清理父安装专用身份环境并防递归。显式开发入口、图形入口及规范列出的安装动作保留绑定；无目标的 `web` 保持目录列表。

## Risks / Trade-offs

- [登记损坏、冲突或来源失效] → 明确局部失败，不静默换版；充分证明归属时无关旧目录不阻塞。
- [副本或环境污染误认来源] → 核对真实关系与目标身份，并以子进程测试覆盖。
- [旧 npm 未含新能力] → 用隔离候选包验证集鲜，明确区分实现、安装采用及发布事实。

## Migration Plan

无需数据迁移。先完成直接测试与 npm 候选入口验证，再读取集鲜当前登记，对比候选默认入口和显式开发入口的 `version --json`，覆盖子目录。默认链接仍由 npm 管理；程序回退不改写归属或数据库。
