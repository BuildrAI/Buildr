现有规范已保护单一检查登记、准确原包、真实平台、独立公开授权及未知不重发。本变更加强消费边界和可解释适用性，不以代码目录或流程偏好建立新许可层。

## Goals / Non-Goals

**Goals:** 让发布不理解验证内部格式即可取得可信缺项；同一输入变化在不同验证入口得到一致的基础判断；恢复只触及未完成动作；准备和重复读取有可证明的有效期。

**Non-Goals:** 不改第一层产品 API、任务报告或用户项目要求；不改新候选完整执行、受保护主线采用、最低 Node 或两系统政策；不重写所有测试、不增加集中状态库、不预建通用发布平台、不承诺未经测量的提速。

## Decisions

### 1. 验证以窄门面交付能力，保留项目专用实现

在 `projects/product/services/buildr/test/verification/` 提供项目专用消费门面，优先由现有入口导出并组合，不默认增加多层转发文件。发布只调用三个职责组：计划（对象、检查与平台缺口）、执行/接续（沿用公开 wrapper 和现有执行器）、结果读取/核验（含来源和下一动作）。内部登记、分片、编码留在第二层。

对外结果保留准确对象、检查/成员、平台环境、真实来源、通过/失败/未执行和采用原因；不能只返回通过布尔值。现行命令及 JSON 消费者先保持兼容，门面复用它们，不另造长期结果存储。

拒绝把第二层执行器提到第一层：第一层已有技术栈无关入口和报告，Buildr 专用候选/原包不应成为用户项目的前提。也不将两个层次全部合并为一个工具目录，否则职责与权限仍然混合。

### 2. 产包是第三层能力，验证消费适配而非反向导入发布实现

`candidate-package.ts` 与原包生产继续随发布技能维护。发布或项目执行的组合入口向验证执行器提供显式的产包/读取原包适配；日常准确包检查仍能使用该适配，普通测试无需加载它。原包清单的轻量数据契约由产包责任方提供，验证只读和校验，不继承公开权限。

`candidate-source-binding.ts` 保留产品构建输入与受保护执行来源绑定；其中检查输入计算归第二层现有 `verification-source-inputs.ts`，由窄接口返回。`release-consumption.ts` 中共享覆盖定义与较重的包检查实现按职责分开；发布消费轻量契约及验证结果，不重新实现检查。

采用接口/适配而非复制产包逻辑或新建公共 npm 包，减少迁移面。是否需要独立文件以真实复用和导入闭包为依据，不以行数作为目标。

### 3. 共用事实判断，分别执行采用政策

以 `verification-source-inputs.ts` 的输入读取和 `verification-reuse.ts` 的内容/配方/环境身份为基础，将可复用的适用性判断与本机缓存读写分开。候选轮次和本机就绪接入同一判断，不能继续仅靠路径归属证明有效性。文件级完整性仍核对当前实际发现成员。

| 事实或政策 | 归属与规则 |
| --- | --- |
| 内容、配方、环境、成员、清理 | 第二层共用判断；未知仅使相关证明不可采用，保留实际执行结果。 |
| 日常跨执行复用 | 现有本机/可移植来源政策，不以提交编号单独失效。 |
| 候选轮次 | 只采用同轮有效成功；新候选完整执行，显式失效不读取旧文件成功。 |
| 原包与平台 | 必须同一原包字节及实际所需平台；通用检查政策不推导平台证明。 |
| 正式补验 | 对原包产品输入、验证输入和公开执行来源分别绑定；验证代码不取得公开权限。 |

归属映射和真实读取范围保持独立，未解析动态输入保守扩大或报告未知。结构化原因至少区分内容、配方、环境、成员、轮次/来源政策、显式失效及清理不明；不要求用户手工计算身份或拼接 JSON。

### 4. 发布总入口协调既有责任模块，不增加第二状态权威

保留 `prepare|inspect|publish|resume` 正常入口及受保护动作。将候选交接与接续从总入口收敛到候选协调职责；逐包公开继续由 `package-release-operation.ts` 及各包公开执行器持有；选择/Git与登记/清理仍使用现有责任模块。先将状态和返回类型写明确，再迁移分支，避免只移动大段代码而保留原耦合。

操作文件只保存不可重建的请求意图、准确执行指针和必要接续信息；已有效果日志继续是其动作记录。外部公开事实通过对应系统回读，生命周期/时间线只派生展示。不是删除全部持久化：丢失响应时所需的请求身份必须在写入前保存。

主包与插件共享协调和事实模式，各自保持受保护执行身份、原字节和恢复权限。登记、清理不改变已成立的公开结论。

### 5. 准备按产物依赖组织，性能调整晚于边界收敛

`source.ts`、`plan-runner.ts` 与 `candidate-environment.ts` 共用检查所需准备关系，逐步消除从分片反推粗档位及多入口重复准备；兼容现有准备档位入口。服务登记只拥有自己的检查，产品层保留跨服务/平台/发布政策，远端承载只消费计划，不复制完整成员清单。

内容观察在明确只读区间共享；生成、安装、源码修改等相关写入后失效。执行后核验及公开前实时核验保留。先记录实际读取次数、文件/字节数和阶段耗时，再决定是否优化扫描与调度；不新增常驻缓存守护程序。

## Risks / Trade-offs

- 旧候选证据缺少适用性字段 → 读取兼容层保留原记录，不重写历史；按可证明字段采用，缺项局部补验，未知公开请求只回读。新写入若需扩充闭合格式，升级格式并显式识别版本，不能静默加字段使旧验证器误用。
- 抽取门面只增加转发成本 → 验收发布调用方确实不再直接解释登记/分片/复用格式；删除旧路径后再收尾，不长期维持两套等价实现。
- 统一判断导致候选跨轮复用或误收窄读取范围 → 政策矩阵及未知输入反例独立覆盖，明确保持新候选完整执行。
- 发布重构破坏部分成功恢复 → 使用既有真实临时 Git/本地协议与受控远端替身，覆盖请求前后中断；不为验证重构执行公开发布。
- 并行发布修复任务可能修改相同脚本 → 已存在 `release-queue-recovery`、`release-skill-retry-approval`；实施前重读交付状态与当前源码，按实际重叠接续，不并发覆盖。本轮只写本变更规划。
- 边界更清楚但总成本增加 → 比较准备/执行/收束与全程成本；没有可解释收益的缓存和调度变更不纳入最终实现。

## Migration Plan

1. 固定当前对象和调用链，以现有稳定入口获取行为基线；补消费接口和关键事实类型，保留旧读取格式。
2. 迁移发布消费者及产包适配，清除直接解释内部格式的调用；本机与远端均接入同一消费边界。
3. 接入共用适用性判断，逐项验证日常、候选、文件补验及准确原包政策。一个旧入口迁移并通过后再退役其重复判断。
4. 收窄发布协调，回放最小恢复矩阵；随后整理直接相关声明和长期无用诊断分支，不扩大为所有工作流重写。
5. 在结构稳定后测量并优化准备/扫描；核销重复高层检查的独有证明后才迁移断言。校准现行说明及调用方。

每阶段必须可独立验证。未公开的代码可回退到上一有效提交；已发生的外部效果只能采用并恢复，不能通过回退代码撤销或重发。旧格式只读兼容，旧执行入口在消费者迁移完成后退役。

## 验收矩阵

| 场景 | 必须成立 |
| --- | --- |
| 普通项目 | 继续只使用自己的声明与命令，不引入 Buildr 专用候选依赖。 |
| 日常与发布消费者 | 同一检查定义和输入得到一致基础判断；各自执行自己的采用政策。 |
| 内容/配方/依赖变化，新增/删除成员 | 相关旧证明失效或成员重算；未受影响有效结果保留来源。 |
| 新候选、另一平台、另一原包 | 不越过轮次或对象边界采用旧成功。 |
| 同轮部分文件失败及显式失效 | 仅补必要成员；显式失效不采用旧文件；子集不冒充完整通过。 |
| 取消、清理失败、动态输入未知 | 不生成新的可信成功；独立既有成功与真实输出仍可报告。 |
| 请求已发但响应丢失 | 只回读同一准确执行，不重复派发或公开。 |
| 仅验证工具变化 | 保留原包，补验不能替代受保护公开来源。 |
| 联合发布部分成功、登记或清理失败 | 逐包效果保留，只恢复局部缺项。 |
| 首次准备、暖执行、局部修改 | 相同检查集合与环境测量；至少三次保留样本并报告中位数、范围、准备/观察/执行/收束，不混算远端等待。 |

正确性矩阵是实现验收，规划校验不能代替。性能无预设百分比；优化项必须证明目标开销下降且不引入更大总成本，否则保留证据并撤回该优化。真实跨平台运行在明确授权后执行，缺少环境按缺项报告，不从本机结果推导。
