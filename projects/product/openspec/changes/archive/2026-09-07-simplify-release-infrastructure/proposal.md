## Why

rc.30 已成功发布，但准备差异、同一提交的重复完整验证和部分成功后的恢复缺口，把正常发布变成连续修补与重跑。当前用户已确认统一构建与消费入口、正常只验证一次最终组合、按真实公开事实恢复，并授权在不公开发布的范围内完成实现与验收。

## What Changes

- 统一锁定依赖、产品 Node、生成代码、测试上下文、前端和产物准备；产物消费者使用独立的最小依赖边界。
- 候选验证（Candidate Verification）与发布消费者共享检查定义、参数和执行实现，覆盖真实平台启动；普通开发继续使用相关测试和低成本回归。
- **BREAKING**：取消失败修复必须执行“完整演练后再完整候选”的内部流程要求。同一精确源码、产物及相关执行输入复用同一完整结果；演练作为可选基础设施验收，不构成第二套发布状态。
- 统一引用解析、工作空间与执行位置，自动生成关联输入，减少独立绑定文件和人工复制证据。
- 跨本地 Git、远端 Git、npm 与 GitHub 分阶段报告已确认副作用和未知结果；相同目标可恢复，查询失败不能解释为不存在。
- 保留真实发布权限和不可覆盖边界；产品发布、登记、清理和本机自举各自报告真实结果。
- 合并发布检查清单、迁移验证框架说明到当前知识（Current Knowledge），更新全部相关引用和 npm 分发文档链接。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `release-collection-model`：单一冻结组合、证据复用、准备与恢复入口、部分写入和演练纳入。
- `open-source-release-governance`：统一发布消费配方、严格外部查询、有界恢复、文档与分发验证。
- `release-main-reconciliation`：根据实际源码变化决定候选失效，发布后允许可证明的正常 main 前进。
- `product-verification-quality`：共享准备与覆盖关系、独立失败收集、真实平台消费和行为故障注入。

## Impact

范围为 Product 的两个服务、`.github/workflows/verify.yml` 与 `publish.yml`、发布与验证工具、对应测试、发布技能及相关收尾/自举引用和当前文档。通过已有内部流程交付 `dev`，不创建新公开版本，不改变 rc.30 的标签、npm、GitHub Release、历史证据和仓库保护规则。发布专用内部入口可删并；对历史发布证据保留读取兼容。
