## Context

Buildr Core 是所有生成 Workspace 必读的基础规则，既要足够薄，又要承载跨 Workspace 一致的用户沟通方式和不可绕过边界。当前文件只有 40 行，但“产品哲学、规则边界、工作空间模型、工作空间硬边界”的分类把责任、表达、资产职责和安全约束交叉分散；部分愿景句不可判定，简明表达和下一步引导规范也没有完整落入模板。

## Goals / Non-Goals

**Goals:**

- 让每个章节都对应一种明确用途，Agent 能快速区分责任、沟通、资产职责与硬边界。
- 保留当前有效不变量，删除重复、模糊或接近默认行为的句子。
- 必读 Core 只保留所有用户 Workspace 普遍适用的行为，不保留只在设计新硬门禁时触发的分支规则。
- 将简明表达、强制中英文术语对照、下一步和按需 Mermaid 作为所有用户 Workspace 的共性表达。
- 让契约测试验证语义锚点，而不是依赖旧章节结构。

**Non-Goals:**

- 不把任务流程、命令序列、生命周期或专业状态写入 Core。
- 不列举架构图、时序图等 Mermaid 图表类型，也不规定每次回复必须画图。
- 不修改 runtime adapter、Rule 投射机制或能力绑定模型。

## Decisions

### 1. 以行为用途替代“产品哲学”分类

Core 改为“责任与治理、用户沟通、工作资产职责、不可绕过边界”四部分。开头保留 Buildr 的核心治理句，但不再将其包装成“产品哲学”；责任和门禁原则集中放置，避免同一含义散落在多个模块。

备选方案是仅重命名原章节，但无法消除“规则边界”和“工作空间硬边界”的职责交叉，因此不采用。

### 2. Mermaid 使用单条最小判断规则

采用以下规则：

> 输出环境支持时，关系、时序、分支或状态转换用文字不易准确理解，就使用 Mermaid，并用一句话说明结论；简单线性内容使用文字或表格。

该句同时给出能力前提、正向触发、图后结论和非适用情况。Core 不维护图表类型清单，避免把共性表达扩张为绘图手册。

备选方案是使用“适当使用图表”或枚举全部 Mermaid 图表类型；前者不可判定，后者会增加上下文负担并诱发过度绘图，均不采用。

### 3. 专业术语始终使用中英文对照

专业术语每次出现都使用“中文（English Term）”；没有稳定中文译名时使用“中文释义（English Term）”。这条规则不采用“优先中文”或“首次出现时双语”的宽松形式，因为中英文同时出现才能持续对齐术语 identity，并让用户在理解中文含义的同时识别真实英文概念。

代价是回复略长；相比术语漂移和理解成本，这个负担可接受。命令、代码标识、字段、接口、路径、错误原文和产品专名仍保留精确文本，但作为专业概念说明时必须补充中文或中文释义。

### 4. 契约测试验证保留与删除两类语义

测试分别验证责任分配、用户沟通、Rule/Skill authority 和不可绕过边界，同时明确旧章节标题、模糊愿景句及专业流程细节不应回流。这样后续仍能重排文字，但不能丢失关键行为。

### 5. 只修改产品权威模板

实现修改 `services/buildr/resources/workspace/rules/buildr/core.md`；当前 Workspace 的 `rules/buildr/core.md` 是 Buildr 管理的投射副本，不在任务工作区手工同步。产品交付后的自举同步由既有唯一流程负责。

### 6. 删除分支专用的硬门禁设计规则

“新增或收紧硬门禁”只在设计治理机制时触发，不值得占用所有用户 Workspace 每次必读的上下文。Core 删除该条目；现有产品架构与门禁分类文档继续保存 Buildr 产品设计事实，本变更不复制或迁移该流程。

## Risks / Trade-offs

- [Mermaid 规则可能导致过度绘图] → 同一句明确限制为“文字不易准确理解”，简单线性内容继续使用文字或表格。
- [强制中英文对照会增加少量篇幅] → 只约束专业术语，不要求命令、路径等精确文本机械重复解释；以持续术语对齐和用户理解为优先。
- [章节重写可能意外丢失有效边界] → 用现有规范、契约测试和逐条审查结果建立保留清单，再验证新模板。
- [Core 承载通用表达会扩大原测试定义的范围] → 同步修改 `workspace-first-runtime-projection` 规范，明确共性用户表达本来就是 required Core 的产品承诺。
- [用户 Workspace 受管副本暂时仍是旧内容] → 不手工改写；交付和自举同步后由 Buildr 正式投射。
