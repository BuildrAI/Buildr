## ADDED Requirements

### Requirement: 统一交互指引必须由服务拥有并适配全部执行方

Buildr 智能体服务（Agent Service）MUST 统一维护自主调查、专业取舍、必要提问及授权边界的指引。Codex、DSH、Qoder MUST 通过正式接入机制应用同一指引，不替换原生基础指令或写入用户全局配置。已授权范围内多个方案均可行 MUST 不单独构成要求用户选择的理由；可自行取得的信息 MUST 先调查。必要事实、授权和关键目标取舍 MUST 不由智能体编造。辅助标题与摘要 MUST 保持无工具隔离。

#### Scenario: 三家创建及恢复工作
- **WHEN** 使用任一家内置执行方创建或恢复工作上下文
- **THEN** 同一服务交互指引 MUST 生效，适配能力 MUST 如实声明，MUST NOT 仅在某一家程序中定义该产品行为

### Requirement: 问题生命周期必须独立于执行状态

统一问题契约 MUST 支持表达是否阻塞原执行，旧接入未声明时 MUST 按阻塞兼容。服务及界面 MUST 区分“仍有有效问题”和“执行正在等待”。运行观察 MUST NOT 单独删除仍有效问题；只有准确解决事件、明确待答快照或相关执行终态才结束相应可回答状态。MUST NOT 根据推荐标签或等待时长补造答复。界面 MUST 仅依据真实执行事实显示继续进行，未知 MUST 不显示为继续。

#### Scenario: 非阻塞问题与运行观察
- **WHEN** 有效非阻塞问题存在且原执行报告仍运行
- **THEN** 原问题 MUST 保持可答且执行 MUST 显示运行，不把整轮标成等待，也不因运行观察删除问题

#### Scenario: 准确结束及迟到回答
- **WHEN** 准确问题取消、已解决、明确快照移除或原执行结束，随后旧回答提交
- **THEN** 服务 MUST 结束对应卡片并拒绝旧回应，不移除其他有效问题、不记录虚构同意

### Requirement: 必要问题等待时必须支持用户明确发起讨论

用户 MUST 能在不回答必要问题的情况下明确发起“先讨论”，保留其反问及原问题。服务 MUST 复用准确停止及持久待发送机制，确认原执行与工具结束后以同一执行组合接续讨论。讨论 MUST 不回应旧请求、不构成同意、不自动更换执行方或重放旧工作；普通补充及草稿 MUST 继续保持原边界。并发回答、旧问题身份变化、停止未知及重复提交 MUST 按实时事实处理，不自动另起重复执行。

#### Scenario: 反问并接续
- **WHEN** 用户在必要问题等待期间明确选择先讨论并提交反问
- **THEN** 系统 MUST 保存原问题与反问，准确停止后接续同一执行组合，明确原问题未回答且相关动作仍需必要输入

#### Scenario: 停止未知或并发回答
- **WHEN** 讨论提交后原停止无法确认或其他入口已正式回答
- **THEN** 系统 MUST 保留输入及准确原因，MUST NOT 对旧等待继续分派讨论或重复提交

## MODIFIED Requirements

### Requirement: 必要用户决定必须通过问题卡片等待并接续原执行

工作对话 MUST 向支持提问的智能体（Agent）提供普通执行中可用的原生提问能力及使用指引。缺少无法自行取得的必要信息、新的授权或无法从已有目标推导的关键业务取舍时，智能体（Agent）MUST 发起明确问题并等待回答，MUST NOT 仅输出文字问题后继续依赖该答案的工作。Buildr MUST 复用现有问题卡片和准确本轮答复入口显示等待、选项或填写回答，并只把有效回答交回产生请求的原执行。完全访问 MUST NOT 自动回答业务问题；普通补充 MUST NOT 隐含解决待答请求。普通文字 MUST NOT 被推断为结构化请求（Structured Request）。

选项说明 MUST 随原生问题展示；原生允许其他回答时，卡片 MUST 提供可填写的其他回答，未填写有效答案前 MUST NOT 提交。有效问题 MUST 在页面重新读取后保持可见；原生取消、失效或停止后 MUST 结束该问题的可回应状态。迟到、重复或属于其他执行的答复 MUST NOT 继续原生工作。标题与交接摘要等无工具辅助生成 MUST 不获得工作对话的提问能力或等待用户决定。

#### Scenario: 普通执行中请求用户决定
- **WHEN** 智能体（Agent）在普通工作对话中确实缺少必要的用户输入
- **THEN** 原生提问 MUST 可用，页面 MUST 展示现有问题卡片，并按真实执行状态表达等待；收到回答前 MUST 不继续依赖该决定的工作
- **AND** 用户提交有效回答后 MUST 继续同一原执行，保存对应问题及回答，不另发一轮工作

#### Scenario: 等待期间刷新与补充
- **WHEN** 有效问题待回答，用户刷新页面或通过其他已有入口提交普通补充
- **THEN** 原问题 MUST 保留并可通过卡片回答，普通补充 MUST 不代替选择或清除等待

#### Scenario: 等待期间编辑草稿
- **WHEN** 当前有效业务问题待回答，用户刷新页面或编辑底部草稿及附件
- **THEN** 原问题 MUST 保留并可通过卡片回答，底部草稿 MUST 不自动发送、搬入回答或被当成选择

#### Scenario: 问题等待时普通发送不可用
- **WHEN** 当前有效业务问题待回答，用户查看底部普通发送入口或使用其发送快捷键
- **THEN** 界面 MUST 禁用普通发送并拦截快捷键，提示在问题卡片回答并提供定位入口及明确的“先讨论”动作，MUST NOT 因普通发送自动排队、停止原执行或另起一轮
- **AND** 底部草稿 MUST 保持可编辑和保留，定位 MUST 不自动选择或提交答案

#### Scenario: 其他入口提交普通补充
- **WHEN** 有效问题待回答，其他已有入口向原执行提交普通补充
- **THEN** 原请求 MUST 继续保留，普通补充 MUST 不代替正式回答或隐含清除等待

#### Scenario: 不回答问题而停止本轮
- **WHEN** 用户通过现有停止入口结束等待中的本轮
- **THEN** 系统 MUST 只在准确确认请求取消、失效或原执行结束后移除可答卡片，保存未回答事实，MUST NOT 伪造用户答复或同意
- **AND** 原执行与工具结束并满足既有发送条件后，新输入 MUST 作为新一轮处理；停止尚未确认时 MUST 保留准确状态与草稿，不自动重发或并行启动新轮

#### Scenario: 取消与迟到回应
- **WHEN** 原生取消问题、原轮停止或结束，随后旧卡片尝试提交回答
- **THEN** 系统 MUST 移除失效请求并拒绝旧回应，MUST NOT 影响其他问题或执行

#### Scenario: 辅助生成及文字询问
- **WHEN** 生成标题或交接摘要，或助手只输出含问句的普通文字
- **THEN** 辅助生成 MUST 继续禁止工具，普通文字 MUST 不自动形成问题卡片或执行许可
