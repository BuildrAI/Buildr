## Context

动机与范围见 [proposal.md](proposal.md)。原型工作树（Worktree）基线为 `6fab9694`；正式实现前已快进接入 `16ce3c36`。后者已增强项目、服务与代码库实例的关系、独立列表和共享服务文档解析；正式实现沿用这些身份与读取变化，保留已有探索成果，没有恢复旧身份模型。

当前 `current-knowledge-maintenance` v3 已支持按范围维护三类成果及按需术语治理，`code-architecture` 已指导代码职责。项目/服务文档接口和 `resolveProjectMarkdownHref` 以 `.md` 为主，尚无关联对象阅读、源码文本或图示安全展示。旧原型使用静态数据、直接按文件导航，不能证明来源变化后的维护行为。

## Goals / Non-Goals

目标是用一套轻量、可由文件工具维护的对象关联，把知识建设与维护能力本身从规范、代码和指导方法接到真实网页。首轮只建设必要内容和有界读取能力，实际维护仍由智能体（Agent）按授权执行。

不新增知识数据库、后台监听、自动语义决策、代码编辑器或全项目扫描；不把来源摘要一致等同业务语义正确。现有按方法解释的文档保留，本轮界面独立导航到文件为止。

## Decisions

### 1. 指导、制作、维护与展示分别负责

OpenSpec 指导规范，`code-architecture` 指导代码；新增 `code-map` 技能（Skill）负责代码地图（Code Map）制作，Archify 负责技术图（Technical Diagram），`terminology-governance` 负责含义与作用域。`current-knowledge-maintenance` 选择本次专业动作、维护必要关联并核对结果，Buildr Web 只读呈现。

`code-map` 作为随包普通技能（Skill）先交付主文与必要参考，不预建新的强制能力依赖。知识维护 v3 的 `Allowed Variations` 已允许选择分析、绘图和文档工具，本轮保留约定版本、输入输出、可选术语依赖及局部停止语义。已有绑定继续遵守，不将 Archify 或代码地图（Code Map）变成全部知识工作的前置。

### 2. 用局部关联文件支持确定性阅读

为启用知识阅读的范围提供 `knowledge/index.yml`，采用 `buildr.knowledge-index/v1`；普通文档维护不要求此文件。项目文件位于项目实际源根，服务文件位于服务自身工作资产根；服务代码由登记的代码库实例与模块路径解析。每个对象只有一个维护位置，项目引用共享服务的身份，不复制服务正文。

最小内容为范围身份、`objects`、`artifacts`、`sources` 和 `relations`：对象有稳定 `id`、标题、职责摘要及可选上级；成果有类型、文件引用和覆盖对象；来源记录对象根、相对路径、可选定位、已核对内容摘要；`link` 可将原生文档中的源文件路径连接到当前登记技能（Skill）详情。图源与展示分别记录已核对摘要；关系区分包含、指导、实现、依据和解释。`relations` 只保存有阅读用途的显式关系，不从同名或同目录推导调用。技能（Skill）引用使用当前来源身份；已绑定能力先解析已选提供者，未安装或不可用时明确说明。

正文保留在现有 Markdown、Archify 图源及展示中。索引只保存导航和来源观察，不复制正文、任务结果或另一套规范。相比解析自由 Markdown 链接，局部索引可稳定切换同一对象；相比知识数据库，它保留文件独立维护与版本控制能力。缺少索引仅表示该范围未启用新阅读方式，已有文档入口继续可用。

### 3. 代码地图先解释职责，再定位到文件

专业制作从已确认架构约束与实际代码出发，表达项目/服务组织、业务模块、模块内分层及真实目录文件；前后端按自身技术栈组织，不强制相同层级和命名。模块可以对应多个目录，多个服务可以共用一个代码库实例。

`code-map` 将地图正文与被纳入阅读范围的对象/文件关联一起维护，目录清单来自实际来源，职责说明经过核对；待确认处明确标注。代码变更后只更新受影响部分；推荐结构不得替代当前实现。方法可在文件说明中出现，本轮不建设独立方法对象导航或逐行索引。

### 4. 读取来源并显示实际核对状态

后端新增独立 `knowledge` 模块承载知识索引读取、关联校验与阅读结果，复用 Workspace 的身份/范围解析及 Agent Assets 的技能（Skill）解析能力；通用文件读取保持独立，不让 Workspace 或网页自行推断知识语义。

只读接口（API）为 `GET /api/v1/knowledge/:scopeKind/:scopeId`、其下 `objects/:objectId`、`artifacts/:artifactId` 和 `sources/:sourceId`。请求只接收已登记身份，服务器解析关联文件，禁止任意绝对路径。返回对象范围、实际工作副本、内容版本、正文/图示/源码类型及逐项诊断。服务入口兼容当前登记模型，旧路由与文档接口继续工作。

目录页只读有界索引；用户展开对象时核对该对象已声明的来源，不扫描整个代码库。摘要使用文件内容而非修改时间。返回来源一致、来源已变待核对、来源缺失或不可读等观察；摘要相同仅表示来源内容一致，语义结论沿用实际维护证据。来源变化时显示旧成果的限制，点击来源读取当前内容，不把旧图的结论说成已验证新代码。

只读访问先校验登记根和相对路径，再核对真实路径，拒绝路径穿越、符号链接越界、凭证类文件与非文本源码。初版单文件读取上限 1 MiB，超限明确提示；已有文档读取不因新增能力放宽。源码用转义文本加本地语法高亮，保留离线与会话边界。

### 5. 一个对象的多视角与上下文对照

完整进入路径为“项目主页 → 项目知识首页 → 架构解释文档 → 文中引用的独立图示或地图”。项目主页保留已有说明、服务与文档；项目知识首页按架构知识、技术图（Technical Diagram）、代码地图（Code Map）提供统一检索，当前收录两个真实主题与已有关联成果。知识建设与维护是一个能力主题，不等于项目知识的全部。

解释文档先说明目的、职责分工、实现位置以及事实变化后怎样维护表达，再在对应段落直接嵌入技术图（Technical Diagram）和代码地图（Code Map），同时提供独立查看入口；内嵌与独立展示引用同一成果，不维护两份正文。相关技能（Skill）、规范与文件按需展开。独立查看后可回到文档的阅读位置，不以去掉解释来实现精简。

点击技能（Skill）在副屏打开已有技能详情，保留主文档及阅读位置。正式实现通过现有资源副屏打开当前技能（Skill）页面 `SkillsPage` / `SkillHome`，沿用其正文、相关资料和维护信息；保留 `SkillDetailDrawer` 既有用途，不再为知识页维护另一套详情。原型使用真实文件快照演示相同结构，不连接真实修改操作。

代码地图（Code Map）以明确能力范围组织：工作方法与开发交接、文件读取与页面基础、维护后成果的位置。每个区域先说明职责，再呈现带说明的真实目录和关键文件，补充它们的协作关系；相关资料列表不能代替地图。已有实现与拟建设内容分开，技能（Skill）协作不能冒充运行时调用。引用保留真实位置，可点击阅读具体文件；只展开当前能力相关内容，项目级全景代码地图（Code Map）暂缓。

项目技术图（Technical Diagram）列表按范围与用途组织已登记图示，区分已有成果和本次草图。每个对象可以引用多种图，跨服务图在共同范围维护，不强制一对象一图或一图一目录。后续按真实内容扩充；代码地图区明确只有专题地图，全景建设继续暂缓。

节点到地图可能是一对多；有多个关联目标时明确选择，不能跳到同名近似文件。次阅读区复用技能（Skill）、规范、代码文件和证据阅读位置，保留当前对象、视角及阅读位置。来源版本、未建设及缺失状态具体到相关条目。反馈复用现有智能体（Agent）动作入口，携带对象、已观察版本和选定引用；形成上下文不等于发送或执行修改。

图示由受限框架独立展示，允许必要交互但不授予主页面同源权限，禁止网络连接和顶层导航，不放宽全站内容安全策略（CSP）。新图的可选节点事件只接受当前展示框架发出的已知对象标识；旧图保持可阅读，无法发出事件时由图旁对象列表进入对应内容。使用声明的图源/展示配对摘要验证本次产物，不能只核对二者文件名。

### 6. 开发内维护，不增加全局完成门禁

现有“必要技术图必须引用同一当前态事实”保持原文；其中不建立自动同步产品机制的约束继续适用。本次页面与接口只读观察，不在后台自动改写成果；实际维护由智能体（Agent）按授权执行，因此不需要与尚未归档的 `rebuild-current-knowledge` 重复修改该条规范。

OpenSpec 的已有 assess/reconcile 组合继续按真实影响使用知识维护。普通代码修改也在开发指引中加入条件化检查：仅职责、路径、关系或含义改变时维护相关已授权成果。是否需要新规范仍由原分流判断，不为维护文档创建无业务变化的变更。

新增来源补入必要关联；修改来源核对受影响陈述；删除来源先判断职责是否迁移，再更新或移除当前引用。历史结果保留，未受影响图不重建。写前重读文件与内容版本，保留并发修改；读页面不自动写知识。当前未确认的业务定义由相应事实源处理，不在地图中决定。

### 7. 首个建设对象与真实验收

建立“知识建设与维护能力”对象，关联 OpenSpec、`code-architecture`、`current-knowledge-maintenance`、`code-map`、Archify、`terminology-governance`、规范、实际实现与必要验证。完成后的图反映真实职责；规划项和已实现项分开。示范引用服务内相关代码和跨服务网页交互，避免把源技能文件冒充全部运行代码。

使用真实临时工作空间（Workspace）及受控样例，在明确授权的增、改、删中由智能体（Agent）执行维护，保存实际输入、修改与检查证据；另有无语义影响反例。自动测试证明读取、摘要、引用、保护与页面更新；人工/智能体走查证明职责解释，不能用关键词测试宣称模型必然遵循方法。

正式浏览器验收针对生产托管产物，验证对象切换、图示、技能（Skill）、规范、代码阅读、刷新和反馈上下文。用户是否看懂另收反馈；早期原型只复用已确认交互，内容模型和文件层边界以本次规范为准。

### 8. 用户引导的架构知识建设

知识首页（含未建设状态）提供“构建架构知识”，复用现有动作抽屉。用户填写主题，关注范围默认当前项目或服务，阅读问题可选；当前登记身份随上下文传递，不把选择技能（Skill）、查找目录或填写源码路径转交用户。文章页使用“完善这篇说明”，保留同一文章、对象与来源观察。

先生成可查看、复制的建设指令，明确尚未执行；复制后明确待交给智能体（Agent），不新增队列、运行状态、后台扫描或假文章。建设指令保留用户原话与范围，要求调查规范、代码和现有知识，复用既有正文，形成可支撑开发判断的文章，按需要使用技术图（Technical Diagram）和代码地图（Code Map）。当前事实、设计理由、推断与建议分清，专业能力在执行中按需采用。

`current-knowledge-maintenance` 补充用户引导建设的路径，不新建协调技能或升级 v3 协作约定。明确主题范围的请求即为该组成果建设授权；范围外主题或事实源修改单独处理。完成后维护当前范围的知识入口与必要索引，验证真实文件、引用和网页读取，返回文章入口；生成提示词不表示文章完成。以 Buildr 的项目、服务与代码库关系为真实建设主题，走通填写、接续、实际成文、关联、刷新阅读与完善的完整流程。

## Risks / Trade-offs

- [工作树基线落后] → 实现前接入当前关系模型及读接口，按真实冲突处理，不覆盖其他任务的已交付行为。
- [来源关联过细或过时] → 只登记实际阅读范围，摘要变化触发核对，不宣称全项目自动覆盖。
- [图示交互与隔离冲突] → 先保证安全阅读，按受限节点事件逐步增强；验证离线、脚本错误和主页面隔离。
- [把文件树当架构] → 每层先说明职责及对应范围，再显示真实目录文件；语义检查和路径检查分别报告。

## Migration Plan

先更新知识建设与维护能力的完整页面原型，根据用户试用反馈收敛阅读与上下文组织，再交付专业技能（Skill）与可独立维护的关联格式、实现只读接口和页面，最后接入真实示范与增改删验收。原型只验证阅读交互，不执行真实同步。资源清单、完整性摘要、投射和生成类型按实际影响同步更新；保持已有成果路径和旧文档入口。停用新入口保留源成果与原有阅读能力，不回滚业务事实或删除用户文件。实际交付、自举和发布分别按对应授权与既有责任执行。


### 9. 试用后的阅读与代码审查改进

采用组块化（Chunking）、认知负荷（Cognitive Load）和相似律（Law of Similarity）：项目主页以明显按钮进入知识，在同一项目主标签内逐层阅读；三类目录共享检索和卡片，搜索当前索引的标题、主题说明与路径。文件是唯一正文，当前有界索引足以检索，不增加数据库或另一套写入权威。

三类列表统一进入主屏详情，文内图与地图采用副屏对照，技能仍复用原详情。取消独立来源核对清单，仅异常就近提示；规范、技能和实现解释就近写入地图。地图以原生 Markdown 嵌套链接组织目录与文件，明确项目根相对范围，不重复使用路径宽表。

前端页面只编排范围、导航和异步读取，目录组件承担分类检索，成果阅读组件承担同一正文的内嵌与独立呈现。副屏请求取消和身份核对避免迟到结果覆盖当前上下文。后端保留现有模块与职责分层，在协议输出时剔除图示与图源正文，图示由现有隔离响应单独读取，保留摘要与失败诊断。

方法归属：`code-architecture` 指导真实代码职责；`code-map` 规定职责解释、规范与可点击树的表达；`current-knowledge-maintenance` 组织文章、图、地图及来源的一致性与阅读验收。技能行为只补充表达与验收方法，保持 v3 及现有绑定，不建立新契约。


### 10. 事实导航与完整详情

依据相似律（Law of Similarity）与工作记忆（Working Memory），分类列表保持同一进入方式：列表 → 主屏详情；正文引用 → 副屏对照。同一项目范围的副屏由打开的成果或来源身份保持，正文切换不自动清除。资源副屏只处理明确的打开、关闭和历史状态，不把缺少导航状态解释为清空请求。

文件树继续存为普通 Markdown 嵌套列表：加粗目录表示作者选定的业务范围，默认收起其内部，展开祖先；没有标记时默认到第二层。专用树组件提供目录和引导线按钮、键盘与紧凑布局。索引来源可带 `summary` 保存经过核实的文件总体说明；成果可带 `files` 引用它自己的源文件、展示及依据，不与 `sources` 事实依据混淆。两字段可选，旧索引仍可读，全部路径继续走现有有界读取。

独立图示去除嵌入参数，直接使用生成 HTML；只在文内预览采用已有 embed 模式。图示专用响应保持原内容，不剪掉标签或重建内部控件；仅为原生导出开放本地下载，原型响应策略不变，不开放同源、外部连接和顶层导航。窄副屏保留原生滚动并提供回主屏查看的入口。

取消独立“来源核对”栏目。文件与关联成果有明确解释及打开入口，观察信息仍用于变化或缺失提示与智能体接续，不作为阅读主线。


## 阅读细节与维护授权补充

独立图示采用有限高度、可滚动并可放大的原生 Archify 页面，保留外部展示文件与隔离边界。建设方法按技能身份归并为名称和职责；共享技能详情直接阅读 `SKILL.md`，参考文件折叠检索。

知识影响在开发开始时初判，最终增改删后复核。智能体主动说明实际受影响成果与建议校准范围；现有同范围维护授权连续有效，只有事实源修改授权时等待整组知识授权。主题建设以文章及必要图、地图、术语和阅读关联的整体准确性验收。此行为由工作方法执行，网页内容观察不冒充持续监听或后台调度。
