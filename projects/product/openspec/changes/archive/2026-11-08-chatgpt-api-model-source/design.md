## Context

Buildr Agent Service 已有统一的模型来源（Provider）、模型账号应用、本机模型网关和多协议转换。Codex 来源通过原生连接复用 ChatGPT 订阅账号，模型请求使用 ChatGPT 后端 Responses 协议；其他来源分别通过 OpenAI 兼容、Anthropic Messages 等协议接入。模型账号元数据保存在 `agent-service/model-access/accounts.json`，来源凭据由各来源在账号私有目录维护。

本 Change 需要在不改变现有 Codex 订阅来源、执行器协议和用户会话绑定的前提下，增加 OpenAI 官方 API Key 来源。GitHub 上 LiteLLM、One API、New API、LibreChat 等实现都采用“提供方注册表 + 各提供方协议适配 + 统一调用出口”的结构；Buildr 已具备后两部分的基础，因此只补提供方声明和 ChatGPT API 适配，不引入外部网关进程。

## Goals / Non-Goals

**Goals:**

- 新增固定官方端点的 ChatGPT API Key 来源，用户只填写 API Key。
- 让 API Key 来源与现有套餐账号共享模型目录、偏好、网关、租约和执行器选择，同时保持凭据完全隔离。
- 在账号界面和模型选择器中提供独立的“ChatGPT API”来源分类，并支持 API Key 的首次配置、校验、刷新、更换和断开。
- 订阅与 API Key 来源 MUST 可以同时启用和同时参与模型选择；API Key 的接入不得要求停用或替换订阅账号。
- 用提供方认证元数据支撑后续服务商扩展，而不是在 Web 或账号流程中按 ChatGPT 写死表单。

**Non-Goals:**

- 不实现其他厂商 API Key 来源。
- 不支持自定义 Base URL、代理地址、组织头或任意 OpenAI 兼容端点。
- 不引入 OpenAI SDK 或外部网关依赖。
- 不改变 Codex 原生登录、模型目录、租约和会话历史。

## Decisions

### 使用独立 ChatGPT API 来源并与订阅来源同时使用

新增来源 `openai`，显示名为 `ChatGPT API`，认证方式声明为 `api-key`，保留 `chatgpt` 厂商分组元数据用于描述来源归属，但不得把两个来源合并成一个模式开关。Codex 订阅来源继续使用 `codex` 与原生连接，声明认证方式 `oauth` 和模式标签 `订阅`。

两个来源拥有独立账号身份、模型目录、凭据目录和租约，可以同时处于可用状态。模型选择器分别显示订阅来源（现有 `Codex` 分类）与 `ChatGPT API` 分类，用户不需要停用其中一个才能选择另一个。替代方案是在 Codex 账号记录中增加可切换认证模式，但这会让原生连接、凭据续期和 API Key 生命周期耦合，无法同时使用，并增加既有订阅账号迁移风险。

### 使用 Responses 协议和固定官方端点

ChatGPT API 来源声明 `responses` 协议，固定使用 `https://api.openai.com/v1`，模型发现读取 `/models`，推理调用 `/responses`。选择 Responses 而不是 Chat Completions 是因为现有 Codex 与 DSH 工具流已经验证 Responses 转换路径，能保留工具身份、参数增量、推理恢复和不透明载荷语义。

提供方只在来源内部持有地址常量，HTTP/账号视图不接收 URL。后续服务商可以声明各自的固定端点与协议；若某服务商结构不同，应增加独立适配器，而不是在通用协议转换中加入供应商判断。

### API Key 由来源拥有并做原子校验后替换

新增来源在账号私有目录使用独立密钥文件保存 API Key，文件权限为 `0600`，目录沿用账号私有权限约束。普通 `accounts.json` 只保存非秘密账号元数据；来源检查返回由密钥派生的不可逆身份供账号修订与租约绑定，不返回密钥原文。

配置新密钥时先使用候选密钥读取官方模型列表，只有校验成功才原子替换旧密钥；失败时保留旧密钥与已有可用状态。更换成功后账号身份变化，旧租约立即失效。替代方案是把密钥写入 `accounts.json` 或统一凭据文件，但这会扩大秘密暴露面并混淆不同来源的写入责任。

### 模型目录采用官方返回与保守能力表达

模型目录只列出官方 `/models` 返回且可判定为文本对话用途的模型，并过滤嵌入、语音、转写、图片生成、审核和实时音视频等非对话模型。官方列表不提供完整能力元数据时，来源采用保守表达：不伪造上下文窗口、图片能力或推理档位；文本与工具能力按 Responses 对话模型声明。已知模型可后续在适配器内补充经官方确认的能力。

观察失败时沿用账号层现有规则：保留上次有效目录和观察时间，并标记本次读取未完成；首次读取失败不能冒充零模型或套餐耗尽。

### 通用账号流程增加认证元数据与配置动作

模型来源描述增加可选认证声明与来源分组/模式标签；账号视图携带来源认证类型和已配置状态，不携带秘密。账号应用增加通用 `configure` 动作，接收观察版本和候选密钥，并委托给支持 API Key 的来源完成校验与保存。HTTP、进程操作和 Web 客户端只传输该通用动作，不自行拼接 URL 或调用上游。

这比在 Web 中按 `provider === 'openai'` 写死输入框更可扩展；新增来源只需声明认证类型和实现配置动作。替代方案是每个来源增加独立 HTTP 路由，但会重复版本校验、错误映射和安全边界。

### 账号界面和模型选择器用独立分类表达两个来源

`modelSourceViews` 将订阅与 API Key 作为两个独立来源视图输出，不在前端合并成单一“ChatGPT”卡片或互斥模式。订阅卡片继续显示“订阅”标签，API Key 卡片显示名称 `ChatGPT API` 和“API Key”标签。没有 API Key 账号时提供可选择的 API Key 占位来源；用户提交密钥时先创建账号再执行配置。已有订阅账号和 API Key 账号同时存在时，两者分别保留模型、额度与偏好，并同时出现在模型选择器。账号来源列表按显示名称稳定排序，`全部来源` 固定在首位，使 `ChatGPT` 与 `ChatGPT API` 相邻；同名来源再按账号名称与标识排序，排序不改变账号选择或状态。

账号卡片根据通用认证元数据选择操作：`oauth` 使用现有登录流程，`api-key` 使用密码输入、保存、换密钥和断开动作。这样不需要为 ChatGPT 单独维护一套设置页面。

### 复用现有网关而不是代理到第三方网关

模型调用继续通过 `ModelAccessApplication` 的本机租约网关。来源适配器只负责上游认证、模型目录和 Responses 请求，网关继续负责模型绑定、协议转换、流式有界处理、工具参数核对、取消和租约撤销。LiteLLM 等项目的价值是验证提供方抽象与统一出口的可行性，但引入其运行时会增加部署、依赖和凭据旁路，不符合本次最小改动。

## Risks / Trade-offs

- **官方模型列表不提供完整能力** → 只暴露可确认能力，未知上下文和额度明确未知；后续按官方文档增量补充已知模型元数据。
- **API Key 泄漏到日志或响应** → 来源只在内存和私有文件持有密钥，错误映射使用固定诊断；测试覆盖普通读取和失败响应不含密钥。
- **无效新密钥覆盖可用旧密钥** → 先校验候选密钥，再原子替换；失败保留旧凭据和模型状态。
- **模型列表包含非对话模型** → 采用明确过滤规则并在测试中覆盖嵌入、图片、语音和实时模型。
- **不同执行器对 Responses 工具/推理支持不一致** → 复用既有跨协议转换与工具流保护；无法表达的能力按现有规则在发送前拒绝并保留草稿。
- **来源命名造成误解** → 账号卡片和模型选择器明确区分订阅来源与 `ChatGPT API`，不把 API Key 描述成 ChatGPT 套餐或订阅权益，也不要求用户停用另一来源。

## Migration Plan

1. 新增来源与认证元数据为可选字段，旧 `accounts.json` 和旧账号视图原样读取。
2. 新增 API Key 账号使用随机账号 ID 与独立目录，不迁移或改写既有 Codex 账号。
3. Web 在没有 API Key 账号时只增加占位来源；已有来源、选择和对话绑定保持不变。
4. 若需回滚，移除 API Key 来源注册和新账号即可；旧版不会读取新账号，但既有订阅账号和会话不受影响。新密钥文件保持在私有目录，可按账号目录清理策略处理。
