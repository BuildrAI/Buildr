## Context

独立 Harness 已有经过位置身份核验的目录宿主及受认证的同源网页。Development 的代码应用依赖仓库清单、任务和实际检出目录，已有成熟文件编辑、源代码管理和兼容路由。不能让 Harness 反向加载 Development，也不能把原生目录解释为 Development 登记。

## Goals / Non-Goals

- 普通本机目录提供可独立装配的资源管理器。准确获准的 Git 工作树提供可独立装配的源代码管理。两者可一起使用，无需开始对话或配置模型。
- 保持原有 Development 工程视图与操作；文件、Git 观察和通用 UI 的实现由 Harness 服务提供，宿主接入范围、工程操作及任务链接。独立入口不复制业务状态。
- 不移植 Development 的任务分配、跨库编排、远端同步、工程验证或发布流程。不扩展到动态插件系统或目录沙箱，不将可浏览的工作树自动绑定给对话。

## Decisions

1. 文件和 Git 操作按各自对象定位。独立网页将目录引用及其版本交给后端，每次重新核对真实位置。Git 写入只在明确选取该工作树根时开放；Git 识别到的上级/其他工作树不会被自动授权。Development 继续解析已登记范围，沿用工程读写约束；不把仓库/任务凭据转给浏览器。
2. 独立包和 Development 消费同一套文件与 Git 通用能力，以及相同的工作台视图。通用视图接收观察和动作适配，不访问任务 API。目录列表、查找和源码阅读沿用现有交互；可完整、安全读取的文件使用带版本保护的编辑。对话导航只交接明确的打开请求，不作为模块使用前提。
3. 独立 Git 状态来自当前工作树的实际 Git 观察。历史固定到提交，不写入；局部状态、差异和文件读取分别有界。手工暂存和取消暂存明确针对文件/比较层，提交仅包含已审阅的暂存区。写入核对来源、版本和作用范围，不隐式暂存全部、推送或重放未知结果。外部编辑不被陈旧请求覆盖。
4. 配置域、账号、对话数据库、Development 业务记录和现有兼容路由不迁移。DSH 仍是可选宿主与发行路径；运行配置和订阅只承诺实际支持的组合。产品层两者可独立，组合时通过公开入口依赖，不形成双向私有模块依赖。

## Risks / Trade-offs

- 避免只在独立入口复制已有 Git 界面而留下业务耦合。提取先保持 Development 上层现有语义，已有编辑历史、工程深链和专业操作由其适配器与回归测试保全。
- 同机的其他进程可在重核后继续改文件或 Git；版本保护、原生锁和效果回读缩小竞争窗口，不宣称全机事务或安全沙箱。路径别名、链接替换、陈旧索引、超限和失败按具体对象提示。
- 渐进迁移不删除在用的工程后端或网页路径。独立目录范围不可作为失效工程来源的回退；出现局部不可读时，其他可用模块与原对话保持可用。
