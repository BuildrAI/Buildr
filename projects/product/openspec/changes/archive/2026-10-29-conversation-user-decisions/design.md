## Context

见 [proposal.md](proposal.md)。现有 `ExecutorRequest`、`waiting-question`、`ConversationRequest` 和独立 `reply` 已覆盖请求保存、展示、版本与原轮身份校验。当前 Codex 使用默认执行模式（Default Mode）；本机程序 `0.165.0-alpha.1.2` 的 `default_mode_request_user_input` 默认关闭。该程序提供每个原生对话独立的 `config`、`developerInstructions`，并提供 `serverRequest/resolved` 取消通知。

## Goals / Non-Goals

**Goals:** 在普通执行中提供真正可等待的原生提问，复用现有卡片及回答路径，取消后拒绝旧回应。

**Non-Goals:** 不解析自然语言问句，不新增决定存储、执行器（Executor）或全局审批机制，不改变权限，不打断或重发已有活动执行。

## Decisions

| 责任主体 | 责任 |
| --- | --- |
| 智能体（Agent） | 判断缺少的必要决定，明确问题与选项，等待回答后继续依赖它的工作 |
| Codex 原生对话 | 提供普通执行可用的提问工具，持有原请求并接收准确回答 |
| Buildr 对话应用（Conversation Application） | 保存原请求与等待事实，核对答复身份，保留问题和回答 |
| 现有问题卡片 | 展示有效问题，提交回答并继续原执行 |

1. 在创建和恢复 Codex 工作对话时显式启用 `features.default_mode_request_user_input`，配套简短使用指引。选择每对话配置以隔离辅助生成；不切换到只规划的模式，不增加另一套动态工具。
2. 继续通过 `item/tool/requestUserInput` 产生现有请求，原生工具等待用户回答；必要问题不得超时默认选择。Buildr 只处理真实请求，不从回复或补充推测用户决定。
3. 消费同一原生对话中准确请求的 `serverRequest/resolved`，移除已取消请求并恢复仍适用的执行观察。已有轮次终态清理继续保留；未知请求通知不影响其他待答事项。
4. 原有卡片及状态流直接复用，保留选项说明和原生 `isOther` 对应的其他回答入口；在现有请求结构内增加可选字段，旧请求保持兼容，不新增页面或存储。

## Risks / Trade-offs

- 原生特性仍在开发中 → 使用实际安装程序核实特性及协议，以受控本机模型验证工具确实可调用和等待；程序不支持时保留真实失败，不退回文字推断。
- 智能体（Agent）可能不调用工具 → 提供必要决定的明确使用指引；检查工具可用性与真实阻塞行为，不把一次受控响应冒充所有模型的判断保证。
- 取消与提交并发 → 按原请求身份清理，保留现有版本校验及原生失效拒绝，不把取消当作用户回答。
- 既有活动对话采用旧配置 → 不修改活动执行；新创建及安全恢复后的工作对话采用新设置。

## Migration Plan

无持久数据迁移或依赖升级。实现先在隔离工作树（Worktree）验证；正式采用沿用后续交付与开发版更新入口，旧后台和活动对话保持原归属。
