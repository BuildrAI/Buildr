## Context

当前唯一执行器在同步前要求工作空间（Workspace）无未提交内容，随后同步、提交及推送。同步成功后若暂存失败，返回值已经列出自身变化路径，但再次调用会被同步前检查拒绝。原激活失败详情和当前 Git 仍是事实来源；任务状态不是恢复依据。

## Goals / Non-Goals

恢复经过智能体（Agent）核对的精确同步文件，使本次已授权激活完成。保留普通未提交保护、原交付参数与唯一执行器职责；不增加通用脏目录接管、自动清理、持久恢复状态库或外部接入功能。

## Decisions

- 采用显式临时 `--resume-sync` 输入。输入给出原交付身份、预期当前提交、文件路径与内容摘要；调用方先核对原成功同步返回及当前内容。临时输入是当次条件写入边界，不是第二份权威状态。
- 执行器逐项重新核对 Git、远端、全部变化路径和实际字节，只允许同步源资产区。任何多余或漂移文件都拒绝；不按名称猜测，也不隐去实际未提交内容。
- 通过后由原执行器接续精确提交和既有激活流程。手工提交绕过原所有者（Owner）、自动丢弃后重同步，以及修改测试执行包装器隐藏现场均不采用。
- 本次修复交付会推进保留提交，因此临时恢复输入分别保留原激活的交付身份与新鲜观察的当前提交；两者各自核验，不把原故障时的旧提交当作现在的身份。

## Risks / Trade-offs

恢复输入依赖调用方准确识别同步产物 → 使用显式参数、路径白名单、完整变化集合及字节摘要；未知、符号链接、版本变化和无法证明的对象停止。该输入不提供额外授权。

检查后仍可能有其他写入 → 提交前再次核对精确暂存与内容版本；已有 Git 和自举锁继续有效，不自动夺锁。原正常入口兼容，旧参数无需迁移。
