# asset-relation-editing 设计

## 关键取舍

- **代码库侧的所属服务只允许移入，不允许移出。** 不变量是「服务必须引用一个代码库」；若在代码库表单中取消勾选当前成员，服务将失去唯一代码来源。因此已引用服务在多选中锁定为必选，未选集合被拒绝；移出统一通过「在目标代码库勾选该服务」或「编辑服务的代码库」完成，不会留下悬空引用。代码库选择现有服务，不提供新增入口。
- **服务移入新代码库不重置模块路径。** 模块路径是否有效取决于新代码库的实际目录结构，系统无法推断；保留原值并由既有目录诊断报告「模块目录尚未准备」，由用户在服务编辑中修正，而不是静默清空造成「整个代码库即服务」的错误语义。
- **数据关系保持多对多，服务表单以单选维护归属。** 应用层与契约保留 `projectIds` 全量语义（编码到标识的解析在应用层完成），`projectCode` 继续承载目录位置与固定入口语义，向后兼容 `projectId`；项目侧可关联多项服务，服务侧表单单选一个项目且不带新增入口。已有多项目成员若只编辑服务的其他字段，必须保留完整现有关联；用户主动改变单选时再按单选结果更新。新建服务目录时，同一个「所属项目」选择同时作为目录位置，不再展示重复的项目下拉。
- **服务与项目编码可修改，代码库编码不可修改。** 代码库编码决定默认仓库目录等派生约定，改名容易让声明路径与既有目录语义错位；服务与项目编码只作稳定标识与历史定位使用，重名拒绝保证唯一性。项目改码时同步重写 `legacyRefs` 前缀，保持旧项目/服务定位仍可解析；服务改码沿用同样原则不重写既有 `legacyRefs`（别名按项目+服务组合保留原定位），仅对实际存在的 `services/<旧编码>/` 文档目录尽力重命名以维持服务文档优先查找路径。
- **项目编辑统一到目录编辑抽屉。** 旧 project HTTP 适配只支持名称与说明且与目录关系分叉；项目、服务、代码库统一经 `asset-catalog` 更新写入，维持单版本核对与引用一致性，不再维护第二套编辑语义。项目侧关联服务为可新增的多选；新增服务草稿和关联集合由一次项目更新事务保存。

- **项目编辑内联新增服务沿用同一提交。** `newServices` 只在项目更新中接受；服务草稿先由同一目录应用登记，再将新服务 ID 与已选择服务一起写回项目成员，任何校验失败都不写部分清单。
- **上一级项目固定展示而非隐藏。** 从项目页或新增项目流程打开服务抽屉时，上一级项目是已成立的业务归属；所有代码位置模式都展示为固定值并计入提交，避免「选了代码库就丢失项目」。独立入口中新建服务目录时，「所属项目」单选同时决定目录项目和业务归属，不展示重复的「所在项目」选择。

## 兼容与迁移

- 所有新字段可选，旧调用方与 CLI JSON 输入不受影响；HTTP 契约仍拒绝未声明字段。
- `assetUpdate` 扩展的字段与原字段互斥检查不变；`serviceIds`/`projectIds` 引用不存在对象或非法身份时以既有错误风格拒绝，不产生部分写入。
- 既有 `services/<code>/` 目录（人工文档）在服务改码后由尽力重命名保持可见；目录缺失或重命名失败仅影响文档优先路径，不否定登记修改。
