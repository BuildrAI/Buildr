## Context

参见 proposal.md 的需求。当前安装更新与网页生命周期分属两个模块；现有启动器（Launcher）可完成绑定交接，但普通命令会复用健康旧版。安装登记已经保留同槽位历史版本，生命周期已有启动锁、认证退出、退出等待和健康检查。

## Goals / Non-Goals

**Goals:** npm 更新后自动交接同一安装的旧网页；新版执行与旧更新调用方隔离，成功和失败均能准确说明；没有启动器（Launcher）也可完成。

**Non-Goals:** 不接管其他安装或开发版，不增加工作空间（Workspace）同步，不改变更新轨道，不建立调度系统，不强杀进程，不保证所有正在执行的生成不中断。

## Decisions

1. 安装模块编排软件包更新，随后调用窄网页交接端口（Port）；网页应用发起新版独立进程、核对结果，实际替换继续由网页生命周期唯一拥有。安装模块不反向引用网页实现，引导装配（Bootstrap）只连接端口（Port），不复制策略。直接在旧进程内执行新服务会复用更新前已缓存实现，且可能随旧服务退出，故不采用。
2. 从更新后的已验证安装登记取得精确 Node.js 与软件包入口，不从 PATH 选择、不复制可执行程序、不继承过时的安装或预览身份。独立进程复用现有数据目录与默认实例记录，不新建持久状态库。
3. 正常更新自动交接；没有运行实例不启动，当前版本已运行不重启。软件包已更新但网页遗留旧版时，再次更新可只恢复交接，不重复安装。
4. 以同槽位历史安装事实与当次旧实例观察作为交接范围；启动锁内再次核对。保留认证退出、归属冲突和并发保护，支持无启动器（Launcher）的旧命令行实例，不伪造绑定。
5. 有界等待并核对新版健康身份；区分包已更新、已发起交接、切换成功与失败。失败保留已成功的安装与必要诊断，不把安装状态降为失败，也不报告未证明的切换成功。
6. 尽量保持旧端口，避免原浏览器页面失去服务；不能保持时报告实际地址。更新不主动重复打开浏览器。

## Risks / Trade-offs

- 旧网页退出可能取消内部未完成生成 → 提前说明短暂中断，独立交接进程继续运行；原生宿主不在关闭范围内。
- 安装后来源或旧实例发生变化 → 重新验证安装登记与健康身份，启动锁内复核，外来实例保留。
- 退出、新版启动或就绪检查失败 → 分阶段报告，允许下一次更新恢复遗留交接，不回滚已更新的软件包。
- Windows 与 macOS 的进程机制不同 → 使用现有精确 Node.js 子进程与隔离测试；真实未运行的平台如实列出覆盖边界。

## Migration Plan

没有数据迁移；后续含本变更的版本采用新流程。开发版自举仍经既有唯一执行器。只交付候选，不更新真实本机安装或发布。
