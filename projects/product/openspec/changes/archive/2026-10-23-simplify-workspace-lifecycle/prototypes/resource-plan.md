# Buildr 添加与更新：资源管理方案（原型评审稿）

**目标：用户选一个目录并确认，或更新一次 Buildr，随后就能在工作空间（Workspace）使用。** “同步”和运行时投射（Runtime Projection）属于内部步骤，不成为用户必须理解或分别操作的事项。本文保留原型评审历史；资源布局已由后续确认改为固定 `~/.buildr/resources/`，完整替换官方资源并清理旧文件，失败空间按最新版恢复。当前权威方案见同变更 `design.md`，下文旧资源集保留方案不再适用。

## 原型评审时的基线事实

## 本轮推荐：共享随包资源，空间管理采用方式

将 Buildr 官方随包资源安装到本机共享资源库。macOS 以 `~/.buildr/resources/<资源集身份>/` 表达目标布局；该布局现已实施；验证使用隔离目录，尚未迁移用户本机资源。资源集身份包含版本及内容摘要，开发版与发布版按既有来源隔离，不原地改写已发布资源集。

安装包是版本交付物；共享资源库是本机安装后的标准内容。每个工作空间（Workspace）通过明确资源身份引用它，不再把同一份官方技能（Skill）源目录复制到自己的 `skills/buildr/` 并独立维护。

| 内容 | 共享位置与空间职责 |
|---|---|
| 官方技能（Skill）正文及全部附件 | 在共享资源库按资源集保留一份。空间清单记录选用、启停和方法选择；组织定制有独立归属，不改写官方原文 |
| `AGENTS.md` | 随包核心内容及项目初始化模板共享；根文件只更新受管区块（Managed Block），各目录自有内容保留。不另设官方 `rules/` 资源类别 |
| 组件（Component）定义、标准片段与随包模板 | 标准内容共享；安装、卸载、启停和空间参数归各空间，生成时只应用当前空间采用的内容 |
| 标准能力契约（Capability Contract）及默认选择定义 | 标准契约共享；实际能力绑定（Capability Binding）、组织契约与扩展由空间维护，默认选择不覆盖已有明确选择 |
| 命令（Command）目录与声明模板 | 产品定义共享；空间采用哪些要求由空间清单决定，不自动安装所有外部工具 |
| 初始化模板和数据迁移程序 | 随当前程序提供；各空间的数据、目录身份及迁移结果保存在各自范围 |
| `.agents/skills/` 等入口 | 按本空间的共享引用、自有方法、组件片段及当前选择装配。它们是可重建结果，不成为第二份可维护的官方源 |
| Buildr 程序、网页和启动器（Launcher） | 程序与网页属于本机安装；启动器属于对应安装的桌面入口，不复制进每个空间 |
| 组织自有技能（Skill）、规则（Rule）与业务内容 | 继续随空间协作，不因集中产品资源而变成本机个人资产 |

### 每个空间怎样管理共享技能

从任何空间都能浏览同一个官方技能（Skill）目录；在当前空间添加、启用、停用或取消采用，只改变当前空间的选择。准备结果也只生成当前空间适用的入口，不向用户级发现目录隐式安装全部方法。

官方正文随产品版本维护。用户为当前空间定制方法时，保留为有独立归属的组织自有内容；界面明确本次影响范围。空间不能删除其他空间仍在引用的共享版本。将来若需要用户级自有共享方法编辑，应另行明确其全局影响，不与修改官方资源混用。

清单中的逻辑资源引用与选用配置可以随空间协作；本机实际采用的资源集身份、内容摘要和生成回执（Receipt）记录在本机状态中，避免把个人绝对路径写进协作资产。在另一台机器打开时，由已安装的相应 Buildr 自动准备本机资源和入口。

### 共享内容与本地入口的关系

官方技能（Skill）的投射（Projection）来源，从各空间的 `skills/buildr/` 等随包副本，改为 `~/.buildr/resources/<资源集身份>/skills/`。组织自有技能（Skill）继续从本空间 `skills/` 读取；空间的采用选择、组件片段和能力绑定（Capability Binding）仍参与装配。

```text
~/.buildr/resources/<资源集身份>/
  AGENTS.md       随包核心内容
  skills/         官方技能及全部附件
  components/     组件定义与标准片段
  contracts/      标准能力契约

共享官方技能 + 当前空间自有技能 + 当前空间选择
                    ↓ 自动装配
<workspace>/.agents/skills/ 等宿主发现入口
```

`AGENTS.md` 仍在相应工作目录中准备并由宿主按目录作用域读取，不复制到 `.agents/skills/` 中。共享资源路径不再增加重复的 `buildr/` 层，资源集身份与来源校验继续防止发布版、开发版或不同内容互相覆盖。

同一官方方法在不同空间可能加入不同片段、契约引用及选定提供者，生成结果可以不同。统一后减少的是官方源的重复维护；各空间配置和可重建入口仍由 Buildr 自动处理。首轮沿用安全文件生成，不要求符号链接（Symlink）才能交付。

资源范围以[随包清单](/Users/chenjun/workspaces/BuildrAI/Buildr/projects/product/services/buildr/resources/manifest.yml)为准。新增共享库必须调整现有解析与所有权边界，不能只移动目录或让旧解析器按名称猜测来源。本轮先提供页面完整入口，由一个更新应用（Application）管理目标、执行记录和逐空间结果；不新增智能体（Agent）发起更新的专门联动。

### 一次添加

选择目录 → 确认名称和目录 → 自动准备 → 打开。普通目录自动初始化；已有空间登记并补齐；已登记目录直接接续准备或打开。名称默认取文件夹名，不要求先填写项目、服务或理解智能体运行时（Agent Runtime）。全新空间默认准备标准文件约定，已有接入按原有选择维护。

**完成标准：**目录身份与登记一致、适用资源及生成入口检查通过，才能显示“已准备好”。失败保留已完成内容和唯一空间身份，提供“重试”，不能要求用户重新添加或手工执行内部命令。成功提示：“在智能体中选择这个目录，新对话即可开始工作。”

### 一次更新与逐空间恢复

更新前说明“同时更新本安装管理的全部已登记工作空间（Workspace）”。下载校验和安装后，先确保新版共享资源完整，维护已有桌面启动入口并完成网页交接；再由新版程序逐一核对真实目录、为各空间采用新的资源集并生成入口，包括久未打开但仍可访问的目录。正式安装与开发来源遵守既有管理归属，不跨来源接管。

**完成标准：**新版程序可用，且本次管理范围内全部空间已检查通过，才能显示“更新完成，全部工作空间（Workspace）可使用新版”。软件已是最新版但空间仍待完成时，继续补齐，不能只返回“已是最新版”。

空间之间独立推进。部分失败显示“Buildr 已更新，3 个可用，1 个待完成”，提供“重试未完成”和单项“重试”；重试重新核对现场，仅接续必要工作。关闭页面、程序重启后仍能恢复结果。不可访问目录保持待完成，再次从 Buildr 打开时自动接续；不把将来重试冒充本次成功。若用户绕过 Buildr 直接打开仍未恢复的旧目录，不能保证其已经更新。

磁盘准备完成不证明已有对话已加载新版。需要时仅提示“新开对话即可使用新版”，不增加通用会话（Session）探测门禁。

### 诊断与自举

诊断（Doctor）核对当前安装的目标资源集、共享资源实际完整性、空间采用引用与自有内容，以及生成结果，使用内容摘要与身份关系，而非只比较版本号。同版本内容漂移也应发现；版本变化但适用内容未变则无需重复写入。现有[随包状态判断](/Users/chenjun/workspaces/BuildrAI/Buildr/projects/product/services/buildr/src/modules/agent-assets/application/package-maintenance/builtin-receipts.ts:64)需补齐“匹配旧回执但落后于当前包”的报告。

自举空间的正式激活只由 [`buildr-self-bootstrap-sync` 的唯一执行器](/Users/chenjun/workspaces/BuildrAI/Buildr/.agents/skills/buildr-self-bootstrap-sync/SKILL.md)编排。统一更新调度它并呈现实际结果，不拆跑内部步骤、不增加用户操作，也不将跳过标为成功。

## 迁移与实施边界

本轮将官方随包资源集中管理纳入正式方案，不再列作后续可选优化。现有规范仍要求空间技能源，正式实施前须将“官方产品资源来源”和“组织自有资源来源”明确分开，并调整解析、清单、所有权回执（Receipt）及诊断（Doctor）。

迁移时先校验并安装共享资源，再处理原空间副本：可证明未修改的官方副本迁为引用；已修改内容保留并按人的选择成为自有定制，不能直接删除。对应入口生成和检查完成前，不将该空间标为采用成功。

共享资源按身份保存，更新不原地改变旧版本。失败空间仍可引用旧资源；至少保留仍被空间或未完成更新引用的资源，不把集中存储变成强制同时切换所有空间。资源清理策略及正在使用内容的保留规则需要在正式设计中补齐，不能凭安装成功直接删除旧目录。

原型只演示目录选择、准备、安装、逐空间更新及失败恢复，不执行真实初始化或更新。正式实施需复用现有身份、归属、回执（Receipt）和安全写入机制，补齐统一执行能力与诊断（Doctor），并验证中断恢复及多空间失败隔离。

原型评审主要决定：添加与更新入口是否足够直接、部分成功与重试是否清楚、默认完成标准是否符合“更新后就能用”。正式实施应沿用确认后的交互与资源边界，内部准备步骤自动完成。
