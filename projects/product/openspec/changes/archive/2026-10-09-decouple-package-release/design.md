## Context

动机见 `proposal.md`。现有源码选择、执行绑定（Execution Binding）及操作文件均以主包版本定位；执行器（Runner）在任何候选（Candidate）前检查主包版本未公开。当前 `main` 与 `dev` 主包都为已公开 `0.1.0-rc.38`。插件（Plugin）已有独立可信发布（Trusted Publishing）工作流（Workflow），但完整检查直接读取相邻主包源码。主包候选（Candidate）不包含插件（Plugin）证明。

## Goals / Non-Goals

**Goals:** 同一入口表达三种目标；源码选择与包版本解耦；明确对端字节与能力；复用逐包发布及恢复；按实际影响验证，保留旧默认入口。

**Non-Goals:** 不建立跨包原子发布、不替用户决定无关开发范围、不复制第二套选择状态、不改变公开身份或绕过审批；本次不执行 `main` 激活及真实发布。

## Decisions

### 共享源码选择，目标单独固定

统一入口增加 `--packages buildr|dsh-plugin|buildr,dsh-plugin`、独立 `--plugin-version` 和按需 `--selection-id`。旧主包身份继续兼容；新身份由目标及版本稳定派生，不把内部字段交给用户决定。目标契约与来源链由既有选择所有者（Owner）固定，操作文件只保存恢复指针。选择、冻结、历史收敛和受保护源码纳入继续共用现有能力；仅选择插件（Plugin）时不调用主包版本未公开检查或主包发布就绪条件。避免新增旁路状态库或只跳过一个检查而留下身份碰撞。

### 实际差异决定检查，不用目标输入降低保护

既有 `verify.yml` 表达三种选择，固定准确源码及选择身份。已观察 `main` 与最终冻结源码的完整树差异包含基线（Baseline）自带变化、共享配方和生成输入；主包或网页产物（Artifact）输入变化仍运行完整主包候选（Candidate），即使不发布主包；纯插件（Plugin）路径运行独立完整检查与独立证明。首次启用的新发布基础设施明确验证主包影响。合入后的插件（Plugin）公开候选（Candidate）仍由 `publish-dsh-plugin.yml` 在准确 `main` 提交生成，不把源码载体产物（Artifact）当成已满足公开发布身份。

### 声明与真实消费分工

两个包使用入包 `buildrCompatibility` 描述具名公共契约与明确版本端点，不引入通用范围语言或未声明依赖。纯兼容模块核对声明与准确产物（Artifact）证明；适配器（Adapter）从官方公开元数据和完整性核验后的原包提取事实。旧包没有声明时仅真实消费可形成局部证明。主包同版本开发源码不补足公开包能力。插件（Plugin）基础打开能力必须可用，文件来源读取为可选能力；实际支持却发生错误必须失败。现有命令来源验证不因文件来源能力缺失被整体降级。

### 独立对端与安全顺序

插件（Plugin）完整检查增加显式主包对端清单，支持公开注册表（Registry）产物（Artifact）及联合候选（Candidate），核对原字节后在独占环境消费。移除私有源码入口及私有投射回执依赖，仍遵守工作空间（Workspace）冒烟检查（Smoke Test）隔离。联合核对新／新组合及两种旧／新中间状态，按可成立顺序执行；不存在与未知分开判断。主包没有插件（Plugin）运行依赖，因此公开插件（Plugin）不存在不阻塞主包独立发布。

### 各包继续拥有发布事实

主包保留原受保护事务和就绪上下文（Context）；插件（Plugin）保留独立工作流（Workflow）及发布日志（Journal）。统一执行器（Runner）保存逐包指针，准备不派发公开动作。每次公开前重新观察准确对端及兼容性；已有写入之后不得静默改变绑定顺序、目标或产物（Artifact）。联合部分成功后只恢复未完成项，未知请求先回读，不重打包或覆盖公开版本。共享选择引用只在全部已选择发布事实成立且用途结束后清理；纯源码交付按其明确目标与受保护历史保全判断，不等待不存在的主包发布。清理只处理已证明归属、保全及无活动用途的引用，保留所有公开标签（Tag）与发布证据。

## Risks / Trade-offs

- 旧身份兼容和同版本碰撞 → 旧默认路径原样派生，新目标使用独立命名空间；覆盖恢复漂移与两个包相同版本测试。
- 发布目标被用来绕过主包验证 → 来源门禁（Gate）核对准确实际差异与证明，不只信任输入。
- 公开旧包没有新兼容声明 → 用真实原字节消费证明，未知局部报告，不能从当前源码推测。
- 联合只成功一个包 → 保留逐包公开事实及原请求身份，只补未完成事项，不提供跨包回滚。
- 新工作流（Workflow）尚未进入默认分支 → 区分本机验证、开发分支持续集成（CI）与正式激活；不假称新模式已经在线可用。

## Migration Plan

在本任务隔离工作树（Worktree）正常实现、验证并交付 `dev`，保持包版本不变。现有主包默认命令继续工作。先报告实际 `main` 激活范围与保护变化，经用户决定后再沿正式源码纳入入口启用；首次激活不默认携入全部开发内容。实际公开发布时间确定后才配置 npm 信任，避免未验证绑定超时。本次只演练无公开副作用路径。
