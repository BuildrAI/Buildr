## ADDED Requirements

### Requirement: 遗留执行不得阻塞用户的新指示

系统 MUST 区分当前交互和保留执行。用户发送新要求、更换执行选择时，系统 MUST 允许接续，不以旧工具退出、原问题回答或未知结果消除为前提。系统 MUST 保留旧执行归属、状态、准确观察和停止能力，由智能体（Agent）判断保留、结束和清理。系统 MUST NOT 自动强杀、推断授权或重放未知操作。资源保护和版本冲突检查 MUST 保持。

#### Scenario: 遗留命令仍活动或结果未知
- **WHEN** 用户发送新要求或更换执行选择
- **THEN** 系统 MUST 将新要求交给所选执行方，保留原执行和控制，不要求用户先手工结束旧命令

#### Scenario: 原轮等待问题而用户改变方向
- **WHEN** 用户发送普通新要求
- **THEN** 系统 MUST 接收新要求，MUST NOT 把它当作原问题的正式回答或审批；原问题及未回答事实 MUST 保留

#### Scenario: 迟到结果与准确控制
- **WHEN** 新轮开始后收到原执行结果，或人和智能体请求停止原执行
- **THEN** 系统 MUST 按准确执行身份更新或控制原工作，MUST NOT 覆盖新轮、丢失控制或重复原操作；停止未知 MUST 只影响对应动作

#### Scenario: 已保存的新要求
- **WHEN** 待发送内容先前等待旧工具或问题结束
- **THEN** 系统 MUST 沿用原提交身份投递一次，MUST NOT 继续等待旧资源退出；页面 MUST 明确实际发送状态和仍保留的工作

## MODIFIED Requirements

### Requirement: 创建和发送必须保留尝试与接收事实

用户首次发送时，Buildr MUST 按需建立或恢复准确原生会话（Session），保存本次创建和发送尝试、输入身份及实际原生接收结果。重复提交同一已受理请求 MUST 返回其原有身份；并发或过期请求 MUST 明确冲突而非产生第二次执行。原生创建已成功而本地绑定未完成时 MUST 保留已知身份并重新观察。结果未知 MUST 不自动解释为未执行，也 MUST 不自动另建会话重发原指令。用户明确提交的新要求 MUST 使用独立输入身份；需要独立上下文时 MUST 保留原执行并交接现场，MUST NOT 将旧未知结果当作新要求的发送门禁。

#### Scenario: Codex 空会话尚未持久化
- **WHEN** 本次新创建的 Codex 原生编号尚未接收首条输入，历史读取明确报告未物化
- **THEN** 系统 MUST 仅对这个确知未发送的新建对象表达空历史，并继续准确记录创建与发送事实
- **AND** 已有绑定恢复失败 MUST NOT 被吞掉或显示为新空会话

#### Scenario: 发送超时但可能已被接收
- **WHEN** 发送返回前连接断开或后端退出，无法确认原生是否已接收
- **THEN** 系统 MUST 保留输入与未知结果，并先观察原生历史、本轮状态及必要工作现场
- **AND** 刷新、重连及用户重复提交同一请求 MUST NOT 自动造成第二次执行

### Requirement: 输入与执行反馈必须构成日常使用闭环

对话 MUST 支持文本输入、流式回复、基本工具进度、必要文件改动与错误反馈；必要图片 MUST 按所选接入及模型的真实能力提供有界输入和本机私有保存。不支持或超限时 MUST 在发送前说明并保留草稿。仍在运行且所选组合及权限未改变、支持同轮补充时，补充 MUST 使用当前执行身份与原配置；其他新要求 MUST 在保留原执行的同时独立投递，不等待旧工具或问题结束。未发送输入仍为草稿，MUST NOT 因输入或刷新自动交付。补充 MUST 不切换参与者、模型、权限或执行位置，不隐含回应原生授权和业务问题。

#### Scenario: 执行中主动补充图文
- **WHEN** 当前执行身份已确认且仍在运行，用户保持相同选择并主动补充文字、图片或图文组合
- **THEN** 系统 MUST 将该输入交付同一执行并独立保存其尝试与接收结果，原执行继续可观察及可停止
- **AND** 界面 MUST 沿用普通消息展示，不要求切换插入或排队模式

#### Scenario: 执行中继续编辑
- **WHEN** 用户只编辑输入而未提交发送
- **THEN** 系统 MUST 保留草稿，不自动发送；用户明确提交新要求时 MUST 按所选组合独立接收，MUST NOT 假称已送达或重发原未知操作

#### Scenario: 图片输入超过限制
- **WHEN** 图片不符合所选模型支持范围或超过已声明大小
- **THEN** 系统 MUST 提示受影响图片和原因，并保留可继续编辑的文本与材料
- **AND** MUST NOT 通过静默删图把请求显示成完整发送

#### Scenario: 等待明确授权时补充
- **WHEN** 原执行等待授权或业务问题，而用户发送普通补充
- **THEN** 原请求 MUST 继续保留，只有其独立回应才可以解决该请求
- **AND** 补充失败 MUST 不停止原执行或删除待回应事实

#### Scenario: 文件已被其他入口修改
- **WHEN** 智能体（Agent）继续读取或修改已有成果
- **THEN** 工作依据 MUST 是当前文件或外部系统事实，历史工具摘要不能证明内容仍未变化
- **AND** 工作页面 MUST 能继续使用原查询与刷新读取同一成果，不要求新增通用工作对象库

### Requirement: 控制请求必须及时作用于准确执行

同一内部对话（Conversation）MUST 维护唯一当前交互及可准确识别的保留执行；保留执行 MUST 继续由原参与者、原生上下文及准确后台控制，MUST NOT 覆盖当前交互。多个页面可以观察同一事实。发送准入与状态写入 MUST 使用有界短操作，不持锁等待整轮模型结束。停止、授权回复和问题回答 MUST 能独立及时处理，并核对连接、配置、参与者、本轮执行、原生请求及服务代次。原生未知交互 MUST 不默认批准；迟到或已失效回复 MUST 不应用到新执行。

#### Scenario: 权限选择绑定准确本轮
- **WHEN** 用户准备并发送默认权限或完全访问模式的输入
- **THEN** 系统 MUST 将实际权限模式纳入能力校验、发送预览、输入身份与本轮持久记录，模式变化后原预览 MUST 失效
- **AND** 刷新或重启 MUST 能读回本轮模式，旧记录缺失模式时 MUST 解释为默认权限而非推断完全访问
- **AND** 同一对话换家 MUST 保留明确选择；新对话 MUST 恢复软件级记住的权限选择，没有已保存选择的新草稿 MUST 初始选择完全访问，已有明确选择 MUST 优先且不改写旧轮次

#### Scenario: 模型正在等待授权
- **WHEN** 原生执行发出工具授权请求
- **THEN** 系统 MUST 展示原生动作、对象与实际可选决定，并将答复送回产生请求的准确执行
- **AND** 停止请求 MUST 不需要等待模型本轮完成

#### Scenario: 输入框已选择另一参与者
- **WHEN** 当前仍存在原参与者的授权或补充问题
- **THEN** 对该请求的答复 MUST 继续指向其原参与者及本轮身份，不随输入框选择改变

#### Scenario: 服务重启后收到旧回应
- **WHEN** 回应携带的服务代次或原生请求已失效
- **THEN** 系统 MUST 拒绝应用该回应并重新观察当前待回应事实
- **AND** MUST NOT 把其内容用于新的授权请求

### Requirement: 同一对话换家必须展示真实接续材料

用户 MUST 能手动选择同一对话（Conversation）的下一位智能体（Agent）和模型（Model），选择本身不创建执行、不发送输入、不改变任务或历史身份。用户明确发送新要求时 MUST 按所选组合接续，不等待原执行或工具结束；忙碌的原上下文 MUST 保留，新要求 MUST 使用独立上下文。系统 MUST 在同一对话中从本地原始记录组织交接，并允许查看实际发送正文、来源范围与执行位置。材料 MUST 不含秘密、隐藏推理或无关工作空间信息，不宣称迁移私有上下文。界面 MUST 只提示实际改变的执行维度，采用紧凑轮次列表，完整正文默认收起且与页面说明明确分开；详情 MUST 从对话所在一侧展开。正常发送 MUST 不强迫用户再确认一份交接清单。

#### Scenario: 首次切换到另一家
- **WHEN** 用户选择另一家并明确发送新要求
- **THEN** 系统 MUST 按该选择交接同一工作并保持同一内部对话，实际交接正文可在同侧详情查看
- **AND** 历史工具操作和授权 MUST 仅作有来源的参考，不作为可重放协议请求

#### Scenario: 原执行尚未确认结束
- **WHEN** 对话执行中、待回应、正在停止、仍有活动工具或状态未知
- **THEN** 系统 MUST 保留原执行及其准确控制，并允许用户发送新要求、更换选择及重新观察
- **AND** MUST NOT 因另一家可用而自动代选；独立执行新要求 MUST 以用户明确提交为依据，旧工作是否停止由智能体（Agent）按现场判断

#### Scenario: 查看发送内容
- **WHEN** 用户展开完整交接内容
- **THEN** 框内 MUST 仅展示准备实际发送的正文，框外解释 MUST 不混作发送文字
- **AND** 关闭重开 MUST 恢复正文收起，已发送回执 MUST 读取当次快照且区分确认接收与未知

### Requirement: 换回参与者必须恢复原生上下文并准确推进交付位置

换回曾参与的执行方时，原参与者没有未结束工作且归属可安全复用时，系统 MUST 恢复其准确原生会话（Session），补充其尚未收到的可见变化；原上下文仍活动、待决定或结果未知时 MUST 保留该绑定，并为新要求使用独立上下文，MUST NOT 冒充恢复或覆盖旧工作。交付位置 MUST 绑定实际输入身份、来源范围及接收事实，只有原生确认接收后才能推进；超时未知 MUST 保留尝试并先核对，不能凭本地已发送或界面显示推进。交付位置 MUST 不代替执行完成或成果正确的判断。

#### Scenario: Codex 经两家参与后返回
- **WHEN** Codex、DSH、Qoder 顺序参与且原上下文已空闲后，用户换回 Codex
- **THEN** 系统 MUST 恢复原 Codex 原生编号并仅补充其未收到的 DSH、Qoder 可见变化及本次要求
- **AND** MUST 保留 Codex 已有原生上下文，不新建同名会话冒充恢复

#### Scenario: 交付确认丢失
- **WHEN** 接续输入可能已被接收但确认未返回
- **THEN** 系统 MUST 保留原交付位置和未知尝试，按原生输入身份重新观察
- **AND** MUST NOT 自动重复提交整包历史或把未确认范围标记为已交付

### Requirement: 每轮模型来源必须固定并可追溯

系统 MUST 将模型账号、模型、档位及绑定版本纳入发送预览、本轮持久记录与真实请求。跨来源不兼容的原生上下文 MUST 在同一可见对话内准确接续，MUST NOT 搬运隐藏推理或静默覆盖旧恢复引用。

#### Scenario: 同名模型有多个来源
- **WHEN** 用户选择 Devin 账号的 GPT 而另有 Codex 账号提供同名模型
- **THEN** 本轮 MUST 固定使用 Devin，记录真实来源，失败时不自动扣另一套餐

#### Scenario: 原执行仍未结束
- **WHEN** 原执行、活动工具或受理结果尚未确认结束
- **THEN** 系统 MUST 保留原绑定，不重放未知输入；用户明确换源并提交新要求时 MUST 独立投递，旧工作保持原归属

### Requirement: 重新核对必须支持对话级安全接管

重新核对 MUST 先恢复准确原生观察。新后台 MUST 能按准确身份同步原执行结果，并独立接收已明确提交的新要求；原上下文的接管或资源关闭仍 MUST 取得准确持有者证明，MUST NOT 将此要求扩展为新输入门禁。系统 MUST NOT 为一条对话暂停整个旧后台，MUST NOT 因核对重发原要求或自动中断仍在运行的工作。身份、工具或释放不确定时 MUST 保留原因与原持有者。

#### Scenario: 原执行完成但旧观察失效
- **WHEN** 旧后台跟随连接丢失且同一请求的持久历史已经明确完成
- **THEN** 核对 MUST 同步最终回复和准确终态，并保留独占资源的准确归属，MUST NOT 因等待该资源释放而阻塞新版投递新要求

#### Scenario: 其他对话仍在执行
- **WHEN** 同一旧后台的其他对话仍运行
- **THEN** 核对 MUST 仅释放当前对话的可独立资源，不停止其他对话

#### Scenario: 原执行仍活动或状态未知
- **WHEN** 原执行仍运行、工具未知、有待决定或身份未匹配
- **THEN** 核对 MUST 恢复观察或保留明确原因，不自动重放原工作；用户明确提交的新要求 MUST 可以独立执行

#### Scenario: 旧后台不支持释放确认
- **WHEN** 旧后台没有返回精确执行的释放确认
- **THEN** 新后台 MUST 保留旧归属并沿用观察，不将请求成功当作接管成功

### Requirement: 必要用户决定必须通过问题卡片等待并接续原执行

工作对话 MUST 向支持提问的智能体（Agent）提供普通执行中可用的原生提问能力及使用指引。缺少无法自行取得的必要信息、新的授权或无法从已有目标推导的关键业务取舍时，智能体（Agent）MUST 发起明确问题并等待回答，MUST NOT 仅输出文字问题后继续依赖该答案的工作。Buildr MUST 复用现有问题卡片和准确本轮答复入口显示等待、选项或填写回答，并只把有效回答交回产生请求的原执行。完全访问 MUST NOT 自动回答业务问题；普通补充 MUST NOT 隐含解决待答请求。普通文字 MUST NOT 被推断为结构化请求（Structured Request）。

选项说明 MUST 随原生问题展示；原生允许其他回答时，卡片 MUST 提供可填写的其他回答，未填写有效答案前 MUST NOT 提交。有效问题 MUST 在页面重新读取后保持可见；原生取消、失效或停止后 MUST 结束该问题的可回应状态。迟到、重复或属于其他执行的答复 MUST NOT 继续原生工作。标题与交接摘要等无工具辅助生成 MUST 不获得工作对话的提问能力或等待用户决定。

#### Scenario: 普通执行中请求用户决定
- **WHEN** 智能体（Agent）在普通工作对话中确实缺少必要的用户输入
- **THEN** 原生提问 MUST 可用，页面 MUST 展示现有问题卡片，并按真实执行状态表达等待；收到回答前 MUST 不继续依赖该决定的工作
- **AND** 用户提交有效回答后 MUST 继续同一原执行，保存对应问题及回答，不另发一轮工作

#### Scenario: 等待期间刷新与补充
- **WHEN** 有效问题待回答，用户刷新页面或通过其他已有入口提交普通补充
- **THEN** 原问题 MUST 保留并可通过卡片回答，普通补充 MUST 不代替选择或清除等待

#### Scenario: 等待期间编辑草稿
- **WHEN** 当前有效业务问题待回答，用户刷新页面或编辑底部草稿及附件
- **THEN** 原问题 MUST 保留并可通过卡片回答，底部草稿 MUST 不自动发送、搬入回答或被当成选择

#### Scenario: 问题等待时普通发送不可用
- **WHEN** 原页面曾因有效业务问题待回答而禁用普通发送，用户继续在同一对话提交新要求
- **THEN** 界面 MUST 允许普通发送及快捷键，提交的新要求 MUST 独立接收并保留原执行；MUST NOT 自动回答原问题、批准权限或以问题未答为由无限排队
- **AND** 底部草稿 MUST 保持可编辑和保留，定位 MUST 不自动选择或提交答案

#### Scenario: 其他入口提交普通补充
- **WHEN** 有效问题待回答，其他已有入口向原执行提交普通补充
- **THEN** 原请求 MUST 继续保留，普通补充 MUST 不代替正式回答或隐含清除等待

#### Scenario: 不回答问题而停止本轮
- **WHEN** 用户通过现有停止入口结束等待中的本轮
- **THEN** 系统 MUST 只在准确确认请求取消、失效或原执行结束后移除可答卡片，保存未回答事实，MUST NOT 伪造用户答复或同意
- **AND** 停止尚未确认时 MUST 保留准确原状态，不自动重发原操作；用户明确提交的新输入 MUST 可以作为独立新轮处理

#### Scenario: 取消与迟到回应
- **WHEN** 原生取消问题、原轮停止或结束，随后旧卡片尝试提交回答
- **THEN** 系统 MUST 移除失效请求并拒绝旧回应，MUST NOT 影响其他问题或执行

#### Scenario: 辅助生成及文字询问
- **WHEN** 生成标题或交接摘要，或助手只输出含问句的普通文字
- **THEN** 辅助生成 MUST 继续禁止工具，普通文字 MUST 不自动形成问题卡片或执行许可

### Requirement: 等待回答时必须支持显式交接到新执行组合

原轮仅等待普通问题回答，用户切换模型或智能体（Agent）后，系统 MUST 提供两条明确路径：提交问题卡片的有效回答并交接，或提交输入框中的新指令并交接。无新增内容时 MUST 允许明确继续原目标。单独选择和查看交接 MUST 不停止、答复或发送。提交 MUST 先持久保存新内容、准确原轮及问题身份，保留原执行；系统 MUST 向所选新组合独立发送一次，不自动停止原轮，也不等待工具退出。执行未知、问题或原轮身份变化 MUST 保留具体原因及输入，MUST NOT 停止其他工作或推定成功。

交接资料 MUST 保留准确原问题；经卡片明确提交的回答 MUST 连同问题交给新组合，MUST NOT 先答复并唤醒旧执行。未提交的选项或填写内容 MUST 仍为未回答。交接动作本身 MUST NOT 被视为验收、选项答复或权限批准；实际业务回答 MUST 保持其明确范围。工具授权 MUST 继续归属原请求，不沿用本交接路径。普通原组合的卡片答复与补充 MUST 保持既有语义。

#### Scenario: 换模型后回答并交接
- **WHEN** 原轮等待问题，用户换模型并在问题卡片提交有效答案
- **THEN** 卡片 MUST 明确显示回答将交给新模型；系统 MUST 保存原问题与答案、保留准确原轮等待并向新模型交接，MUST NOT 把答案送回旧执行
- **AND** 其他未提交的输入草稿及未答问题 MUST 保留，实际回答 MUST 不扩大其授权范围

#### Scenario: 换模型后发新要求或继续
- **WHEN** 用户未提交原问题的回答，换模型后在输入框发送新要求或明确点击继续
- **THEN** 系统 MUST 交接已有现场与新要求，原问题 MUST 保留为未回答；选择了但未提交的选项 MUST 不作为答案

#### Scenario: 仅预览或取消交接
- **WHEN** 用户只切换模型、打开交接资料，或在实际投递前取消已保存的待发送
- **THEN** 原轮 MUST 继续等待，MUST 不自动答复、停止或投递新执行
- **AND** 如果另有明确停止操作，MUST 单独显示其事实；取消只撤回尚未发送的新轮，不改变旧停止的真实结果

#### Scenario: 停止未知或并发答复
- **WHEN** 原轮停止无法确认，或原问题被其他入口答复、原轮身份变化
- **THEN** 系统 MUST 保留交接内容和准确原因；停止未知 MUST NOT 单独阻塞新要求，已答复或身份变化时 MUST 拒绝过期问题的回答或交接，MUST NOT 重发原操作

#### Scenario: 重复提交和后台恢复
- **WHEN** 同一交接重复提交、页面刷新、接收后台重启或切换
- **THEN** 已持久保存的内容 MUST 能继续观察准确原轮并按原提交身份核对送达，MUST 不重复答复、重复发送或停止其他对话

### Requirement: 必要问题等待时必须支持用户明确发起讨论

用户 MUST 能在不回答必要问题的情况下明确发起“先讨论”，保留其反问及原问题。服务 MUST 复用持久待发送机制，以同一执行组合的独立上下文接续讨论并保留原轮，不以准确停止或工具结束为前提。讨论 MUST 不回应旧请求、不构成同意、不自动更换执行方或重放旧工作；普通补充及草稿 MUST 继续保持原边界。并发回答、旧问题身份变化及重复提交 MUST 按实时事实处理，不自动另起重复执行；原轮停止未知 MUST 只影响该停止，不阻塞已明确提交的新讨论。

#### Scenario: 反问并接续
- **WHEN** 用户在必要问题等待期间明确选择先讨论并提交反问
- **THEN** 系统 MUST 保存原问题与反问，保留原轮并在同一执行组合的独立上下文接续，明确原问题未回答且相关动作仍需必要输入

#### Scenario: 停止未知或并发回答
- **WHEN** 讨论提交后原停止无法确认或其他入口已正式回答
- **THEN** 系统 MUST 保留输入及准确原因，停止未知 MUST 不阻塞新讨论；已被正式回答的问题 MUST 不再按旧等待交接，MUST NOT 重复提交或重放原操作

### Requirement: 停止必须区分模型中断和活动工具退出

用户停止时系统 MUST 先发送原生中断并显示正在停止，自动观察本轮模型及相关活动工具的真实结果。中断请求成功或模型本轮结束 MUST 不单独证明命令退出。仍有活动工具时 MUST 显示准确未停项并提供可验证的针对性停止；状态无法确认时 MUST 明确未知。只有本轮相关执行已确认停止且不会继续延迟写入时，才可显示已停止。停止 MUST 不误停此前用户有意保留、与本轮无关的后台服务。

#### Scenario: 正常停止得到完整确认
- **WHEN** 原生确认本轮中断且相关活动工具均退出
- **THEN** 系统 MUST 自动显示已停止并保留历史和已发生的修改
- **AND** MUST 不要求用户为正常路径再手动核验一次

#### Scenario: Codex 中断后命令仍在运行
- **WHEN** 模型本轮已中断而本轮原生终端仍有活动命令
- **THEN** 系统 MUST 显示命令仍运行，并按准确原生终端身份停止与核对退出
- **AND** MUST NOT 用全对话清理或未经核实的操作系统进程号替代针对性处理

#### Scenario: 当前工具不支持单独停止
- **WHEN** 原生接入无法按准确工具身份单独停止某活动命令
- **THEN** 界面 MUST 不将该工具展示为可单独停止，仍保留活动事实与重新观察入口
- **AND** 单工具停止被拒绝时 MUST 保留原本轮状态，MUST NOT 先标为整轮正在停止或据后续空闲误标全部已停止

#### Scenario: 断线后结果未知
- **WHEN** 连接断开导致不能确认执行或工具终态
- **THEN** 系统 MUST 显示状态未知并允许重新观察，保留历史和草稿
- **AND** 未确认结束前 MUST NOT 自动重放或恢复原未知操作；用户明确提交的新要求或更换选择 MUST 能独立接收，保留原执行、未知结果及准确控制，MUST NOT 以旧工具结束为前提
