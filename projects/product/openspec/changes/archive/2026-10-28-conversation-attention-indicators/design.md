## Context

动机见 `proposal.md`。当前 `ConversationActivityEntry.tsx` 的 `total` 只绘制一个绿色角标；`conversation-activity.ts` 已按“未知、等待、执行、未查看”生成互斥主状态，但没有完整范围的分类汇总。`querySummaries()` 已在同一读取事务（Transaction）中完成分页与执行统计，可以沿用，不另建通知或待办数据库。

## Goals / Non-Goals

- 目标：一眼区分活动总数和需关注数量；展开后能找到待处理、待查看、执行中及状态待确认的准确对话。
- 非目标：不重画外围布局，不添加新对话状态，不改变排序、查看确认、权限与执行；不增加动画、桌面通知或自动处理。不制作未授权的界面原型（UI Prototype）。
- 本提醒变更不新增 Codex 档位语义。同一任务后续获授权的快速模式（Fast Mode）接入修复沿用既有模型能力规范，不包含真实付费验证。

## Decisions

### 1. 一个入口、两个静态数量

沿用现有列表图标和点击开合行为。图标右上角的柔和绿色数字继续表示全部活动；右下角以暖色实底角标显示“需关注”数量，为零不显示。两者置于同一按钮内部，不增加外部统计入口；预留互不遮挡的位置，不缩小点击区域。最大显示 `99+`，悬停说明和无障碍名称保留精确数量。

悬停说明示例：“活动 8，需关注 5：待处理 2、待查看 2、状态待确认 1”。不能仅靠颜色区分含义；浮窗内始终配中文分类标签。零活动保留图标但不显示数字。加载前和观察失败不能显示假零；已有观察失败保留原值并注明未更新，无旧观察时显示未知提示。

不选择只把现有角标改为待处理数：那会丢失原有活动总数含义。也不在窄轨道增加三到四个小数字，避免信息挤压。采用选择性注意（Selective Attention），让需要人关注的内容有克制强调；采用组块化（Chunking），把完整分类放在浮窗内。

### 2. 复用主状态，避免重复计数

以准确对话身份去重，依次判定：

| 分类 | 当前事实 | 计入需关注 |
|---|---|---|
| 状态待确认 | `run.status === 'unknown'` | 是 |
| 待处理 | `waiting-approval` 或 `waiting-question` | 是 |
| 执行中 | `starting`、`running`、`stopping`、`tools-active` | 否 |
| 待查看 | 不属于以上类别且 `activity.version > activity.seenThrough` | 是 |

活动总数等于上述四类之和，需关注等于待处理、待查看、状态待确认之和。执行中同时产生新消息仍仅归执行中，不额外叠加未查看；等待回应即使已经查看仍属待处理。状态待确认不是已经成立的授权请求，独立显示“查看状态”，不能伪装成待批准。

### 3. 完整范围汇总和分类定位

列表响应（Response）增加可选的 `activityCounts`，含 `active`、`running`、`waiting`、`unseen`、`unknown`、`attention`；新增可选 `activityState=running|waiting|unseen|unknown|attention` 筛选。服务端在空间身份约束及既有有效工作条件内汇总，置于分页、搜索、隐藏和分布筛选之前。浮窗覆盖全部已登记且可访问空间；完整列表跟随空间选择。保留既有 `total` 表示当前查询匹配总数，不用它代替汇总总数。

浮窗标题下增加“全部活动、需关注、待处理、待查看、执行中、状态待确认”紧凑分类按钮与数量。选择后沿用同一分组列表，只过滤不重排；重复选择恢复全部活动。分类筛选与既有智能体（Agent）/模型分布筛选互斥切换，避免隐藏交叉条件造成空结果。完整列表复用同一分类控件，切换空间清除分类筛选。分页游标（Cursor）包含分类参数，旧请求不得覆盖新筛选。

保留现有默认全部空间、按空间分组及最新消息倒序；不为待处理另建置顶规则。分类统计必须覆盖未加载页，分类筛选也在服务端完成。清空筛选后恢复全部活动，不能因为尚未加载匹配页而声称无待处理。分类为零时仍显示零，筛选后给出准确空态。

### 4. 交互、安全与无障碍

鼠标悬停与键盘聚焦显示相同分类和列表；键盘可选择分类、打开条目及按 Escape 返回入口。触屏通过既有点击进入完整列表，再选择分类。点击入口仍打开/收起全部对话，不突然改为直接跳到某一条。历史固定显示时不弹出浮窗。

筛选、悬停、展开统计与数量更新均不推进 `seenThrough`，只有原有可见最新正文确认流程可以推进查看位置。打开条目沿用 `workspaceId + conversationId`，不自动回答、不批准、不发送。数量随既有页面刷新/活动观察更新，不新增全库轮询通道。

## Risks / Trade-offs

- 双角标可能挤压：实施时在实际侧轨、窄屏、三位数及键盘聚焦态检查边界，保持原按钮尺寸和外围布局；必要时使用更紧凑字距，不把分类数量全部塞入轨道。
- 用户可能把需关注等同于待处理：完整说明及浮窗拆分三类，待查看仅表示新内容，未知仅表示需核实，不暗示必须授权。
- 服务端与前端主状态可能漂移：两侧使用相同判定顺序并以参数化测试（Parameterized Test）覆盖重叠状态；服务端提供权威数量，前端不从已加载行重算。
- 隐藏对话仍可能活动：沿用既有“不因隐藏移除活动”的规则。
- 接口为增量扩展，无存储迁移；旧服务无汇总时显示分类暂不可用，不由首屏伪造全量数字。回滚前端不影响执行或查看记录。

## Codex 排查依据与接续边界

起点 `bcb5089b26a1d0c11f858986fbfdc94161b92b33` 已观察到的实现链（以下为修复前事实）：

1. `ConversationOptions.tsx` 仅当 `selectedShared.serviceTiers.length > 1` 时启用闪电按钮，否则显示“该模型未提供可切换的快速档位”。
2. `model-access/providers/codex.ts` 的目录映射保留模型、思考深度与窗口，却没有生成 `serviceTiers` 或 `defaultServiceTier`；原生账号委托也走同一提供者。因此现状会将 Codex 的闪电按钮禁用，这不等于上游模型不支持。
3. 通用发送链已有 `serviceTier` 持久记录与租约（Lease）绑定，网关（Gateway）按绑定值设置 `service_tier`，`codexBody()` 没有主动删除该字段。因此不是所有调用能力都缺失，首先缺的是 Codex 档位能力发现和目录映射。
4. 原生默认路径显式拒绝未绑定共享模型来源的服务档位，不能仅删除前端 `disabled` 就认为完成接入。后续接入需核实该账号/模型允许的档位及上游真实请求值，再验证发送、恢复与偏好；不能根据模型名称批量猜测支持。

官方文档（2026-10-28 读取）：[Codex 速度配置](https://developers.openai.com/codex/agent-configuration/speed)。文档列出 GPT-6.1 Sol 支持快速模式（Fast Mode），并区分速度与用量：1.5 倍速度描述对应 GPT-5.6；当前支持模型的套餐内额度按标准的 2.5 倍消耗，购买点数及企业按量用量按 2 倍计费。该页面的 `service_tier = "fast"` 是 Codex 配置值，不能未经核实就等同于订阅响应请求的线值。

后续用户已同意提醒方案并授权快速档位接入修复；该修复沿用 `model-usage-controls` 的“基础模型和真实支持变体分别表达”要求，不改变本提醒变更的规范范围。本机非秘密目录已报告 GPT-6.1 Sol 的 `service_tiers: [{id: "priority", name: "Fast"}]` 及 `additional_speed_tiers: ["fast"]`，因此按明确目录映射快速请求，而非只解除按钮禁用。

尚未验证本机账号的实时推理权限和付费推理生效；未读取凭据、修改默认档位或调用收费推理。不承诺该账号必然拥有全部快速或超快档位。

## Migration Plan

先增量扩展列表汇总、分类筛选与公开操作，再接前端提醒；最后做真实浏览器验收。既有记录、查看位置与账号不迁移。实施后按已授权范围校准 `knowledge/docs/architecture/agent-integration.md` 对侧轨数字的说明，其余架构关系与代码地图（Code Map）无需重画；需要新增共享职责文件时再增量复核地图。
