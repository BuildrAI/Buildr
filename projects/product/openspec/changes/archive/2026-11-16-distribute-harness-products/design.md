## Context

前置分别交付[目录宿主、通用激活与 API](../2026-11-16-split-buildr-harness-product/design.md)和[完整 UI、网页发现与换代](../2026-11-16-extract-harness-web/design.md)。本变更交付真实安装与可点击入口，不重复实现前置能力。

当前 [`web-profile.ts`](../../../../services/buildr/src/modules/installation/contracts/web-profile.ts) 只接受 `npm/host` 与 `development/development`，profile 身份混入 runtime role；开发启动器硬编码 4458，实例替换以原产品约定判断。因此“复用启动器”只表示复用构建/安装技术，绝非只改两个显示名。

## Goals / Non-Goals

交付两个独立产品启动器和可独立消费的本机安装包；保持旧命令、数据、运行负载及活动执行。首个真实验收在当前本机平台完成，其他声明平台各自补证据。技术交付不包括公开 npm/GitHub 发布、代表用户接受厂商条款、强制迁移数据或另建全功能原生聊天应用。

DSH 插件属于后续交付，不是本次承载、依赖或验证前置。本次仍先完成 Harness 独立产品及默认集成 Harness 的 Development 独立产品，不增加新的模式交互或行业工作台。

## Decisions

### D1. 产品、渠道、共享数据域、入口身份分开

| 维度 | 作用与兼容策略 |
| --- | --- |
| `productId` | `buildr-development` / `buildr-harness`，决定壳、系统应用标识和安装所属 |
| channel/profile | 保留现有 released/development/隔离预览映射；产品 Development 不等于开发渠道 |
| 数据域 | 同操作系统用户、canonical dataRoot、profileId，共享 Harness 服务与资料；不包含 productId |
| 网页/启动器身份 | 产品、渠道、准确安装来源/负载和入口标识，区分两个网页实例；不是数据域身份 |

拆开现有 `webProfileName` 的数据定位与入口校验职责，旧身份只映射 Development。实例锁、发现记录、健康匹配、替换与退出检查均采用新入口维度；相同 channel 或端口不能成为“替换旧产品”的理由。预览额外钉住工作树/构建及隔离数据根，不能借用日常后台或凭据。

保留已有按渠道的数据根，以及 `agent-service/`、`programmatic-access/`。先发现并核验旧资料，不创建新 Harness Home 后要求用户再迁移。无法确认唯一数据域时局部拒绝接管，不按最近使用猜测。

### D2. 两个启动器，复用公共启动而非复制编排

| 启动器 | 行为 |
| --- | --- |
| Buildr Harness | 核验自身安装 → 通用准备/连接/明确激活 → 独立网页 ready 发现 → 单次登录引导 → 打开独立壳 |
| Buildr Development | 核验自身安装 → 启动工程现场 → 调用相同 Harness 公共能力 → 内嵌/专注走本身同源代理 |

Harness 不依赖 Development 运行；Development 不要求用户先开 Harness。重复点击只复用本产品入口，两个产品同开只共享执行后台，不互相关闭网页。独立网页端口、有效会话与代次交接按第二变更，不在启动器硬编码端口，也不复制一套登录机制。

macOS 使用两个 `.app` 身份，Windows 使用独立应用/快捷方式绑定；显示名之外，bundle/shortcut ID、日志与安装标识必须可区分。旧 Buildr 启动器仅在 ownership 可证时兼容映射 Development，不覆盖外部同名入口。真实点击、重复启动、同时打开和重装均需证据，不能只测 CLI 或生成文件。

### D3. 安装组合与版本采用

保留 `@buildr-ai/buildr` 和 `buildr`；独立包拟为 `@buildr-ai/buildr-harness`，命令拟为 `buildr-harness`。发布命名前核对名称可用性；内部源码 `buildr-harness` 不为品牌立即改名。

独立产品壳和安装包负责当前组合选择。工程业务本身按第一变更保持独立，完整路线表见[核心设计 D0](../2026-11-16-split-buildr-harness-product/design.md#d0-区分产品能力接入装配与交付宿主)。后续 DSH 生态分别提供原生执行＋Development 的组合，以及插件框架＋Harness＋Development 的完整组合；后者由 Harness 统一多执行程序、模型、对话和交互，Development 也可换成营销等专业环境。它们复用产品能力，不复制工程业务代码。本次不交付这些插件版本，也不因未来可替换而撤掉当前 Development 开箱即用的 Harness。独立安装验收不要求 DSH 桌面或插件系统；用户选择 DSH 原生执行器时仍按其实际依赖准备，这与作为 DSH 插件交付不同。

| 安装组合 | 预期 |
| --- | --- |
| 只装 Development | 内置兼容 Harness 负载，默认不开独立网页 |
| 只装 Harness | 自带目录宿主、完整 Web 和执行依赖，不读 Development 源码 |
| 两者同域 | 当前兼容实例优先；候选负载不同不等于自动更新，不能让 attach 顺序决定版本 |
| 协议/存储不兼容 | 保留当前工作和可用控制，明确等待或拒绝，不起第二写入者 |

产品版本、API/host/lifecycle 版本、数据兼容版本、运行负载摘要、UI 构建和原生程序版本分开观察。只有明确升级意图才调用公共激活，不能用“包版本大”跳过兼容判断。支持声明需含 API、页面会话及旧静态资源窗口，而不只有 npm major。

包消费与升级测试采用[核心设计](../2026-11-16-split-buildr-harness-product/design.md)中的真实 v1/v2 兼容矩阵，并包含 Harness 首先启动已有资料的情形；不能用两份从新源码重建的客户端证明旧版本兼容，也不能让首先安装或启动的产品改变历史来源解码。

### D4. 保留负载、卸载与恢复

把 Node、核心构建、生产 Web 资源及必要依赖纳入受保护的保留运行单元。运行不能依赖随后可能卸载的 npm 或任务工作树；独立安装用复制后的 tarball 验证。原生程序与 CLIProxy 的既有受管路径和模型装配保持，不趁拆分换实现。

普通卸载只移除自有安装与启动器。共享库、账号、程序凭据、原生资料和活动/另一入口仍需的负载保留；删除共享资料属于单独明确操作。另一入口不存在也不等于可以自动删数据。旧 Development 来源在其卸载后可按前置规则读/控原工作，新工作仍需原宿主，不能宣称独立 Harness 接管业务能力。

旧直接写凭据的宿主在采用新唯一维护者前须退出受影响写入路径；不支持的旧宿主组合明确拒绝。新格式不支持旧程序写入时禁止盲目降级；回退保全兼容负载与资料，并不撤销工作对外部系统的副作用。

Antigravity 的 `credentialScope: host-keyring` 需要核对真实密钥环边界，私有 HOME 不构成隔离证明。无法隔离的候选验证不能接管/清除日常凭据，只限制相关来源，其他组合继续验证。

### D5. 许可从第一阶段并行，发布决定由人负责

责任分工：Agent/工程维护者收集准确版本、许可证原文、二进制来源、分发方式及订阅调用路径；产品/发行负责人决定允许分发、允许的订阅用法及宣传范围，必要时请法律顾问判断。当前整体需求由用户验收，不能在没有实际答复时记录为已批准，角色可由用户另行委任。

从第一变更开始收集事实，不等代码拆完才查。每条记录区分 `已取得来源`、`待负责人决定`、`允许/限制/不允许`，保留依据及适用版本；不把包的 `private: true` 当许可豁免。技术可调用不证明“任意订阅接任意内核”。

本变更技术清单交付证据矩阵、许可证打包及拒绝未知/禁止项的发行检查，用允许、禁止、未知夹具验证门禁。实际许可批准、付费账号准备和外部平台证据是发行前依赖，不是一个由 Agent 打勾即可完成的实施任务。缺口只限制受影响发行物/平台；不能安全排除的依赖会限制整个对应发行物，不虚报可发布。真实产品验收按实际声明的平台与组合，不用替身或其他平台结果替代。

## Risks / Trade-offs

- 把新产品塞进旧 role 导致新数据根或抢 4458 → 数据域与入口身份分别测试，两个启动器并发验证。
- npm 卸载带走运行资源 → 保留负载不依赖安装目录，测试卸载任一入口后另一入口和原轮的真实可用性。
- 干净安装可用但原资料采用失败 → 覆盖只装两者、两种先后顺序、旧启动器、升级、卸载与重装矩阵。
- 许可或 Windows 证据延迟拖住全部拆分 → 三个独立变更，技术准备与外部批准分开；支持/发布声明不得超过证据。

## Migration Plan

先改身份解析与保留负载，再打独立包及两个启动器；真实安装消费必须晚于前两变更验收。版本管理、系统入口与许可检查只在本变更写一次，前置规范按引用消费。

退出证据：复制后的包无源码可启动；两产品各自及并发点击可用；同域复用与异渠道隔离；旧入口映射准确；卸载重装保全资料；升级不误停旧工作；在同一个 Development 工作空间可开发两产品并隔离预览。未验证平台保持缺口，不能在整体任务中记为全平台通过。

知识影响：入门、安装/发行流程、术语、启动器/自举入口、系统图与服务地图，以及 `preparation.yml`、`verification.yml` 和实际服务登记。只按实现成果更新；正式自举采用仍由既有唯一执行器完成，不创建另一同步流程。

## Open Questions

独立 npm 名称的实时可用性、各准确依赖/订阅路径的负责人决定、授权账号及其他平台真实证据尚需取得。它们不改变已选架构；会影响名称最终登记、某项分发/支持声明或对应平台的验收，不能被“无架构待决项”掩盖。

## 本轮边界修订

本变更涉及的核心与独立入口统一为 buildr-harness；buildr-harness-web 拥有完整唯一网页，buildr-harness-ui 退役。Development 在自己的 harness-ui 模块嵌套网页并准备工程上下文，不消费对话 React 组件。具体集成约束以同任务 extract-harness-web 的修订规范为准；不改变既有历史数据根、准确执行控制与独立发行批准边界。

## 最终验收范围（2026-11-16）

用户明确本机不能测 Windows，本轮不做 Windows 实机验证。当前技术交付按 macOS 已取得的两产品包消费与系统入口证据验收；其他平台适配和真实证据不纳入本次变更完成条件，不因归档获得支持或通过声明。公开发布、许可批准和未来 DSH 插件仍不在本次交付范围。
