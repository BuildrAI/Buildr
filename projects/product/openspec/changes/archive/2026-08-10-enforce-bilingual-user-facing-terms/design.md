## Context

Buildr 核心规则（Core Rule）是所有 Buildr 工作空间的必读资产。当前规则把中英文并列限定在专业术语首次出现时，并允许没有稳定中文译名的术语只保留英文；这与用户确认的目标不一致：中文术语可以单独使用，但任何面向用户出现的英文专业术语都必须同时提供中文名称或中文释义。

核心规则的产品源位于 `services/buildr/package/targets/workspace/rules/buildr/core.md`。工作空间根部的 `rules/buildr/core.md` 是同步产物，不是长期事实源。

## Goals / Non-Goals

**Goals:**

- 让中文专业术语可以单独使用。
- 让每次出现的英文专业术语都采用“中文（English Term）”形式。
- 保留必须逐字对应实现内容的英文原文，同时要求其用户可见标签或概念说明使用中文或中英文并列。
- 用正式规范和契约测试防止旧的“仅首次双语”语义回归。

**Non-Goals:**

- 不建立新术语表，不修改术语治理能力。
- 不机械翻译命令、代码标识、字段名、接口名、文件路径、错误原文或产品专名。
- 不修改运行时适配器（runtime adapter）的规则发现、加载或激活机制。
- 不扫描或批量改写历史变更、历史回复和归档证据中的英文术语。

## Decisions

1. **把约束从“首次出现”提升为“每次使用英文专业术语”。** 中文可以单独出现；英文专业术语不能单独出现。相比保留首次出现规则并追加说明，这一条判定更直接，也不会让智能体（Agent）把段落边界或上下文范围解释为裸用英文的许可。
2. **没有稳定译名时使用中文释义加英文原词。** 不强制创造规范译名；智能体提供能够说明含义的中文表达，并在需要保留原词时写成“中文释义（English Term）”。
3. **精确实现文本保持窄例外。** 命令、标识符、字段、接口、路径、错误原文与产品专名可以保留英文原值；只要智能体把它们作为专业概念解释，就必须补充中文名称或中文释义。
4. **只修改核心规则产品源并通过同步投射。** 不直接编辑任务保留工作空间中的同步副本；实现完成后由当前产品检出版本执行 Buildr 同步并运行诊断。
5. **不修改术语治理能力。** 本次改变的是通用用户表达格式，不新增或重定义领域术语，也不改变跨能力协作契约。
6. **保留既有规范场景标题。** 修改后的需求继续保留既有场景语义身份，只更新规范内容，并新增“英文专业术语后续再次出现”场景覆盖非首次出现的英文术语，避免确定性收敛把标题变化误判为场景删除与新增。

## Risks / Trade-offs

- [回复中中英文括注增多，文字可能变长] → 优先使用纯中文；只有确实需要英文原词时才采用中英文并列。
- [智能体把普通英文专名误判为必须翻译的术语] → 保留产品专名与精确实现文本例外，但要求概念性说明仍提供中文。
- [产品源与当前工作空间同步副本不一致] → 由当前产品检出版本同步，并以最终诊断确认投射结果。

## Migration Plan

1. 修改正式规范、核心规则产品源与契约测试。
2. 完成受影响验证并收敛变更。
3. 使用当前产品检出版本同步 Codex 工作空间运行时，再运行 Buildr 诊断。
4. 若新规则造成不可接受的表达问题，回退本变更对应的规范、产品源和测试提交后重新同步；不需要数据迁移。
