## Context

主体 `test:fast` 与其他三个服务的检查互不等价；智能体服务与插件入口混合构建、逻辑和真实进程，部分单元目录包含真实 Git 操作。既有登记、选择、执行、清理和证据应用可继续使用。现有正式规范存在要求旧档位和预算准入的条目，本次同步移除这些约束，不以新命令隐藏旧模型。

## Goals / Non-Goals

目标：四类唯一判定；两个技能（Skill）唯一职责；六条可见项目聚合命令；任务相关、用户显式与推送前全量的范围可解释；实际运行并如实报告。单元检查允许以替身隔离协作者后验证完整内部功能。

非目标：建立新的任务状态、审批或证据库；统一用户项目技术栈；取消真实系统/准确原包检查；设置耗时硬门槛；在未取得授权时推送、发布或激活共享安装。

## Decisions

1. 测试代码与辅助代码由服务拥有，稳定检查在唯一登记中表达身份、四类、执行入口、输入和环境。项目地图仅描述稳定能力，不复制文件成员。
2. `project-testing` 建设并登记能力；`project-verification` 读取、选择、执行并记录真实证据。应用中的 `task verification` 命令及兼容能力标识继续使用其原有任务报告语义，技能更名不触发无关报告迁移。
3. 项目聚合执行器由 `services/buildr` 的现有包装入口调用。`npm test` 运行全部单元，`check` 运行全部静态与单元，其他三类入口运行对应集合；`test:related --base` 解释变更选择，显式 `--check` 无需任务或基线。有基线时显式检查为追加，不能覆盖必要相关检查；`check` 不允许缩小覆盖。
4. 选择结果显示被测内容、检查类型、入选原因、环境及缺口。未知路径、缺少平台或依赖只使对应结论不完整，不清空其他独立可执行检查。
5. 准备是显式执行依赖，不是第五类。四服务类型检查与打包、加载器、模型账号分开；准备与运行耗时分别观察。失败后只补失败及实际输入变化项，有效成功保留真实来源。
6. 发布仍组合同一登记中的检查并消费准确原包，真实操作系统要求与字节身份保留；不再通过旧日常档位推导发布完整性。

## Risks / Trade-offs

- 文件迁移会影响测试、发布工具和源码字符串引用：建立完整旧新路径映射，统一更新现行消费者，保留历史材料。
- 旧类型检查没有覆盖全部测试代码：检查报告明确实际范围，不用 `noCheck` 宣称严格检查成功；不能在不修复的情况下掩盖缺口。
- 重型依赖或另一个系统不在本机：执行独立可用项，列出必要未执行及真实原因，不自动使用真实账号或替代准确原包。
- 删除旧技能（Skill）影响绑定：更名默认提供者并更新内置消费者；稳定协议无语义变化时保留，历史报告不改写。

## Migration Plan

先登记当前断言和入口，按实际行为迁移并消除混合分类，再接入四服务独立检查、统一选择与执行。同步命令、发布调用、技能源、声明和当前知识，最后运行新入口、审查覆盖及旧引用。未通过或环境未覆盖的检查保留诊断；不以路径移动或计划生成当作验证完成。

## 既有测试内容与并行

逐项核销源代码管理原有 60 个浏览器场景。将页面内来源优先级和尺寸计算分离为生产逻辑并直接以单元测试验证；真实 Git 与 HTTP 边界保留集成证明；已有充分低层证明的重复浏览器组合退役，必要完整页面流程保留。记录原场景的风险、低层证明与保留理由，审查材料不是第二份执行成员清单。

文件浏览与源代码管理使用两个明确检查。独立临时工作空间、随机端口、浏览器与清理责任成立的源码浏览器检查允许最多两个并行，仍服从全局进程与工作线程预算；共享可变资源的其他检查继续互斥。以真实执行重叠、隔离、清理和失败证据验证，不以无限并发掩盖重复场景。
