# 设计

## Context

现状见 proposal.md。实现层面的关键事实：Task `intent` 已存在于记录模型、编辑抽屉和总览头部（Markdown 渲染），前端已存在 `kind:'intent'` 的阅读目标但未接入需求节点目录；Task Review 与 Task Verification 的写入入口只接受 `active` 任务（`task_review_task_terminal` / `task_verification_task_terminal`），所以证据必须在完成登记之前落库；`brief.md` 的存在没有任何校验，只依赖 `openspec-propose` 增强片段的文字要求。

## Goals / Non-Goals

**Goals:**

- 每个正式任务的需求节点始终有可读正文（任务目标），变更 Brief 作为补充。
- 变更路径任务默认产出方案审查与实现审查记录，缺失时可解释；非变更路径不加默认动作。
- 已发生的验证/审查在任务 `active` 窗口内被登记，不被完成动作永久关在门外。
- `propose` 流程交付前能发现 `brief.md` 缺失。

**Non-Goals:**

- 不把审查、验证或 Brief 变成完成/归档门禁；不新增 Application、数据库字段或能力契约。
- 不为历史任务或历史变更补写 Brief、审查或验证记录。
- 不改变"用户确认"节点的机制（仍由 acceptance 待办事项填充），只澄清定位。
- 不实现风险启发式审查触发（如按改动文件数判断），避免引入另一种不稳定判断。

## Decisions

1. **任务级需求继续由 `intent` 承载，不新建产物。** `intent` 已是可编辑、可搜索、可直接展示的字段；新增一份独立需求文档会产生第二事实源和新的同步问题。代价只是写作指引与展示位置的调整。替代方案（Task 级 `requirements.md` 产物）被否决：与 `intent` 重复且需要新 Application 面。
2. **需求节点把任务目标作为默认正文，Brief 作为同层补充文档。** 节点语义本来就是"本次需要解决的问题、目标与范围"，`brief.md` 是"补充需求或说明"；让目录第一项始终是任务目标，节点在任何任务下都有内容，也使"需求 → 方案 → 实现"的阅读链有稳定起点。
3. **审查默认触发绑定 `change-flow`，不引入逐任务风险判断。** 语义治理分流本来就是每个实现任务必做的既有判断，绑定它得到的是可预测、可解释的覆盖（"code-only 没有方案材料所以无审查"），而不是让 Agent 每次重新决定。`Planning Review ⇒ Completion Review` 形成闭环：审过的方案成为实现审查的基线。范围外路径保持按需，人随时可要求。
4. **补登提醒放在 `task-finish` 的就近核对，不做应用层检查。** 应用层无法区分"没跑检查"与"跑了没登记"，硬检查只会把合法的空证据任务也拦住；技能层提示由知情的 Agent 执行，成本最低且符合"宽而薄"。
5. **`brief.md` 自查放在 `propose` 增强片段。** 只要求文件存在性核对，不做内容校验；缺失时补齐或如实说明，符合现有规范中"缺失必须如实报告"的语义。

## Risks / Trade-offs

- 默认审查仍多为 `self` 自审，独立性有限 → 如实记录 method，价值定位在为人的验收提供可读证据；高重要性变更仍可由人要求独立审查。
- 指引文本增加带来技能（Skill）体积膨胀 → 每个新增只写触发条件与边界，不复制专业手册。
- 需求节点默认内容从 Brief 变为任务目标，浏览器冒烟断言需同步更新 → 实现时核对 `browser-task` 相关用例。
- 已归档/已完成对象不回填 → 历史空缺保持历史事实，仅新任务适用。

## Migration Plan

纯指引与前端展示变化，随包发布生效；Agent runtime 重新发现技能后按新指引工作。无数据迁移。
