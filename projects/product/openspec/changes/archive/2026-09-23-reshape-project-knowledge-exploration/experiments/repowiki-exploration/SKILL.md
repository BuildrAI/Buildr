# 项目结构探索试用

这是从 RepoWiki 可见产物重建并收窄的试用方法，依据与推断见 [逆向证据](../evidence.md)。目标是让人能够理解和判断软件；实际事实来自当前规范、代码、配置及已确认决定。

## 选择当前问题

沿用用户给出的项目或服务范围。看全貌时从目的、主要职责与关键关系开始；跟场景时选择一个真实目标，沿参与者、过程和结果调查；深入某部分时关注它的责任、依赖和边界。用户只需表达问题，无需列出文件或先掌握术语。

区分只读理解与长期建设。普通提问以解释为成果；用户明确要求建设或完善时，才维护指定范围的知识文件。已有建设授权持续有效。

## 调查结构与依据

1. 读取已有导航和主要声明，按职责识别相关部分及代码范围；目录与旧文档用于定位，不自动视为正确模型。
2. 围绕当前问题检查关键关系：谁负责什么、谁调用谁、数据或结果由谁保存、哪些条件影响行为。用实际来源核实，会影响结论的疑点再深入。
3. 设计原因查找规范、决策或已确认材料。来源只证明实现时，将原因标为推断或未知；冲突分别保留双方依据。
4. 关键职责、关系与重要边界已有依据，未知明确且有进一步定位入口时，停止本轮展开。系统探索不要求读完所有代码；记录未覆盖范围。

调查可以深入函数，解释仍按人的当前判断选择粒度。不要把调查顺序或每个文件分别写成文章。

## 组织解释

围绕问题给出直接结论和有意义的结构。按实际关系选择职责表、对象关系图、流程或状态视图；简单线性过程使用文字即可。每条连线说明具体含义，引用可定位到实际依据。复用适用的现有视图。

优先保留目标、重要关系、行为约束及有依据的取舍。字段、具体函数和随时可查的步骤，在它们影响当前判断或具有反复参考价值时才展开。不设固定章节、篇数、层级或图数。

在当前主题旁给出少量具体的继续探索问题，让不熟悉项目的人能够选择下一步。来源和深入资料保持可达，不把完整来源清单挤进主线。

建设长期成果时优先完善唯一正文及必要导航。精简前核对独有事实和设计理由的去向；详细参考可以按需阅读。普通追问不会自动新增永久文章。

## 核对成果

逐项检查：解释是否足以说明当前目标、主要职责、关键过程及判断边界；关系是否与来源一致；未知是否明示；继续探索问题是否具体且能找到依据。实际修改文件时检查链接和适用展示。

交付实际解释或文件、重要依据、覆盖与未覆盖范围。区分静态核对、试用结果和人的验收，不用生成成功证明用户已经理解。
