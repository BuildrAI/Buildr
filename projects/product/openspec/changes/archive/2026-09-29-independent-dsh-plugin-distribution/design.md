## Context

现有插件源码位于 `services/buildr/resources/runtime/dsh/`，构建工具位于 `services/buildr/tools/dsh/`；生成包的 `private: true` 和禁用组合层使直接从 npm 安装无法得到可用按钮。Buildr 候选流程现将插件产物作为主包输入。DSH 官方管理入口能够安装预编译 npm 包及压缩包；Git 源码安装会触发需要额外授权的 `prepare` 脚本，因此首个公开路径选择预编译包。

## Goals / Non-Goals

**Goals:** 插件拥有独立 Service、版本和可复现候选；DSH 通过自身管理入口安装后自动启用；Buildr 主包发布无需每次重发插件；重启后复用可核验的插件标签。

**Non-Goals:** 不新增常驻服务进程，不要求 DSH 用户安装开发软件开发工具包（SDK），不绕过 DSH 配置档管理；不从私有浏览器存储认领手动标签。公开发布和真实桌面验收是分别取得的结果。

## Decisions

1. 在同一产品仓库新增独立 Service root，保留 Git 协作与 Buildr 服务登记，但用自己的 `package.json`、版本、构建与发布入口。不同服务不等于新增网络进程。Buildr 只暴露稳定的安装身份、健康查询和启动器接口；插件通过现有公开接口调用。
2. 构建时针对已核实 DSH 提交生成完整 `lib/`、准确 peer 兼容声明和默认启用的 `cordis.patch.yml`。发布候选从这份输出一次打包并核验内容；不把 SDK、源码工作树或本机绑定放入产物。正式包通过 DSH 管理工具安装，避免 Git 源码安装脚本的额外授权。
3. 将主包候选中的 DSH SDK 获取与插件强制输入移出正常路径。Buildr 发布准备读取上次插件发布标记与当前插件源范围，变化时给出待发布事实和候选；插件公开发布单独受控。未发布时不能因 Buildr 主包发布而声称插件已同步。
4. 标签身份只保存在插件客户端本机存储，复用前还要检查 DSH 公开标签清单及 Buildr 最新健康地址。正式版、开发版分别命名，存储损坏、标签关闭或地址变化时安全退回新开。

## Risks / Trade-offs

- [DSH 公开标签清单没有当前 URL] → 只复认插件创建且地址记录匹配的标签；手动标签与用户后来导航走的标签无法可靠确认，文档和验收如实说明。
- [不同 DSH 版本的接口可能不兼容] → 产物声明精确基线，新增基线须重新构建和验证；不以宽松 peer 范围掩盖未经验证的版本。
- [迁移期间旧 Buildr 包仍带插件准备命令] → 旧命令仅作为历史本地交付路径，公开安装文档与 Agent 指引不再要求它；等消费者确认后另行退役。
- [npm 产物与 GitHub 源码安装行为不同] → 首发只承诺 npm 或预编译压缩包；普通 Git 仓库 URL 不承诺免构建安装。

## Migration Plan

先在独立 Service 构建并通过隔离 DSH 配置档验证预编译包，再移除主包候选对插件产物的强制依赖和过时的安装承诺。已安装用户配置档保持不变；需要更新时由 DSH 管理入口安装新版本并按真实管理结果决定是否重启。公开发布停在精确版本、源码、压缩包和验收结果可审阅之后，取得对应授权再执行。
