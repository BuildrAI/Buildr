## Context

现有 `prepare` 将本机源码证明送到 GitHub，GitHub 生产原包，本机再下载验包，然后派发补验汇总。制包和验包身份绑定多个 run，旧分类器可能在最终消费时拒绝新验证器已接受的证据。本轮改为本地优先，保留原有检查执行器、npm 可信发布和真实字节核验。

## Goals / Non-Goals

目标：本机制包一次；通用及本机原包检查一次；对端系统为独立可选冒烟，不在发布关键路径；原包及原始证明全程可核对；失败不重打包；两种开发系统对称。

非目标：不保证每次发布前都有两系统通过证明；不将跳过检查或既有 Windows 失败伪装为成功；不修改 npm 身份或 main 保护，不启动真实发布，不改造业务功能。

## Decisions

1. 发布编排负责原包和交接，验证框架仍负责真实检查及复用。新准备采用本机原包模型；历史运行继续按原身份读取，不把旧失败改写为新成功。
2. 使用现有 `source.ts` 和 `artifact.ts` 在本机完成源码、通用原包和本机平台验包。新 handoff 固定平台策略；聚合器和正式消费者同样从该策略计算可选证据。仅移除另一系统的 runtime/host 必需证明，本机和通用缺项仍拒绝。无策略字段的旧 handoff 保持双平台要求。
3. 交接使用独立的不可变临时 Git 引用，只包含分块原包、manifest 和必要的验证证明。工作流从冻结产品源码执行，另行读取此数据引用，绝不执行交接引用中的代码。分块避免单文件大小限制；不把压缩包并入产品树或 main，不创建公开二进制 Release。
4. 本机证明保留原始执行来源；汇总采用现有验证器校验内容与范围，而不是虚构远端执行。本机和远端都核对原包摘要与清单，正式发布复用远端保全的准确字节。
5. 验包与公开发布解耦：正常 GitHub 作业只校验本机证明并保全原包，不安装产品或验对端；保全失败只补校验／上传。另一系统独立冒烟使用同包和准确最低 Node，一次安装、CLI 身份、Web 健康和进程清理；没有 SDK、源码轮、init/sync/Doctor/卸载或第二次安装。诊断记录源码与验证器的独立身份，不生成候选 aggregate，失败不影响新策略候选资格，但仍保留失败事实。公开仍须准确授权、同包和受保护身份。
6. 独立插件复用不可变数据交接和轻量远端保全，但不伪造主包或触发主包对端验收。SDK、正式／开发插件构建、加载器及准确双包兼容由本机专业验证器完成；真实桌面验收仍独立，历史运行继续按原路径恢复。
7. 本机自动准备准确 Node/pnpm 和 SDK。复用绑定上游、补丁、构建配方、工具、系统架构及实际依赖字节，回读原回执和生成物；失效时新建独占输出，不覆盖旧结果。准备命中不是插件测试通过，完整验证仍绑定准确原包。
8. 本机准备在交接分发前只读预演：主包由既有 plan/aggregate 采用真实源码与原包证明，再调用正式发布器的原包读取及覆盖校验；插件共用正式消费者的准确原包和完整验证读取。不虚构 Actions 身份、不额外执行测试或制包。预演失败保留原包，返回具体消费错误，不进入远端分发。
9. 分类策略成为版本化的稳定值；新来源绑定携带策略版本及定义摘要，校验按绑定版本执行，未来策略更新必须保留旧版本解释。交接另冻结验证配方、消费契约、范围及平台策略；校验发现漂移时明确报告不兼容，不覆盖已有交接或重跑碰运气。

10. 撤回只处理本机原包模型、尚无公开／主线采用意图且候选运行已终止的选择。默认只读；执行必须携带刚观察的计划摘要及独立授权，与 prepare/publish 复用同一操作锁。计划固定操作、原包、源码、运行 attempt、main、三个临时引用和准确附件 ID。
11. 首先在规范工作空间 `.buildr/local/release-withdrawals/` 保全完整交接原包／证明、源码与数据 Git bundle、运行日志及附件原 ZIP，逐文件保留摘要。完成之前不清理远端。每次接续先验证档案，删除前重新检查运行、PR、公开事实与引用；引用使用准确提交租约，附件仅删除原 ID。清理意图先落盘，未知结果只回读、不重放；完成及部分结果保留在原操作中。已进入撤回的选择禁止 prepare/resume/publish 重建资源，继续只能使用 withdraw。
12. 不取消活动运行、不回滚主线、不触碰正式 tag/Release/npm，不删除本机工作树或选择引用；其他轮次附件与未知归属资源继续保留。公开记录、历史候选和未知请求仍由原 owner 恢复。过期／缺失附件导致不能保全时停止对应撤回，不用“本机还有包”冒充完整证明已经保全。

## Risks / Trade-offs

- 临时 Git 引用产生压缩包对象存储开销，但无需新账户、外部存储或公开临时 Release；采用同一摘要避免重复传输，纳入现有发布引用清理。
- Windows 本机制包必须经执行路径测试；本机 macOS 检查不能证明 Windows 已实际通过，报告中保留该边界。
- 旧发布脚本与规范含硬编码 workflow/run 关系，需要同步调整所有消费者，不能仅替换生产入口。
- 已有范围声明继续表示未执行，不允许用新模型隐藏真实失败。
- 发布前另一系统可能未经过实测；汇总固定标明 `platformVerification.status=not-verified`，不能宣称跨平台通过。原 Windows Web 超时仍未修复，此次删除强制检查不改变该事实。

## Migration Plan

新选择默认走本机原包；已保存的旧选择按其原模型观察和恢复，不能悄悄转换原包或授权。先通过数据交接、两平台选组及消费反例检查，再使用本机实际检查；已获准提交前一批改动和不公开的 GitHub 验包，不执行公开发布或修改 main 保护。

## Open Questions

无需要用户决定的业务缺口。远端实际运行与 Windows 现场验收作为未执行边界如实报告。
