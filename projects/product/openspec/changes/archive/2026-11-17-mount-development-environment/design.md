## Context

保留的 `harness-shell-foundation` 已交付外壳接口但尚未集成。Development 的 `AppLayout` 同时装配工程页面和对话 iframe，后者通过 portal 放入工程布局，生命周期及布局主次仍由工程页面决定。

## Goals / Non-Goals

**Goals:** 使用真实工程页面证明工作环境可挂入 Harness 外壳；独立对话与环境开合保留状态，旧工程入口和交互继续使用。

**Non-Goals:** 本步不把对话组件搬出 iframe，不引入新的执行状态容器、通用插件管理或新后端协议。

## Decisions

1. **只共享通用外壳。** Harness 提供单独公开的 `src/shell.ts` 门面，Development 只导入这个门面，不通过聚合入口加载对话内部模块。现有 iframe 继续承载完整唯一对话。
2. **复用真实工程区域。** `AppLayout` 保留现有工程内容及提供者，在现有层级用 `DevelopmentHarnessShell` 组合固定对话区域和工程区域。工程节点通过局部 React Context 传入稳定的工作环境组件，避免每次 render 创建组件类型导致重新挂载。不复制页面、路由或工程数据。
3. **单一布局事实。** 外壳增加可选受控开合；组合入口把它映射到现有 `open/full` 偏好，不保存第二份布局状态。已有偏好优先；无偏好时根路径展示专注对话，工程直达路径展示工程区域并保留收起的对话窄轨，以免压缩原工程阅读布局。显式 `/?catalog=1` 继续作为工程目录直达入口，不能被专注偏好遮挡。后续工程导航展开环境，但普通刷新尊重已保存的专注选择。
4. **稳定对话位置。** 组合模式不再 portal 对话进工程区域。iframe 始终位于外壳固定子树；专注时只隐藏工程区域，收起对话时保留原 iframe 并显示既有窄轨。原有右侧停靠、拖动及键盘调宽移至外层装配，保留同一偏好与上下界。原坐标关联暂时保留，不宣称已消除该技术债。
5. **局部范围。** 工程区域仍有既有导航与标题栏，不在本步统一全部视觉设计。窄屏采用已有外壳上下布局并保持入口可达。工程抽屉经现有页面活动上下文及派生的环境可见上下文隐藏、恢复，不把 portal 浮层留在后台页面之外，也不清空草稿。工程渲染失败由已有环境边界承接，不宣称隔离同页副作用或外壳外层装配错误。

## Risks / Trade-offs

- 工程区域首次打开才挂载 → 现有工程页面的部分加载推迟，工作空间范围目录仍由外层取得。
- 工程区域可能较窄 → 保留收起对话及工程专注路径，不同时重画页面。
- 受控开合改变旧 fixed/portal 布局 → 补真实生产浏览器检查，保留 iframe 身份、草稿、任务关联、窗口来源核验及重启恢复断言。
- 当前知识中的壳方向会改变 → assess/reconcile 将建议局部更新双产品说明与代码地图；本轮不额外重画技术图或代写未授权知识。

## Migration Plan

先扩展通用外壳的受控模式及公开门面，再接现有工程区域，最后补根入口和工程直达回归。保留服务地址、认证及数据；不迁移浏览器草稿。回退只涉及本步源码，不触碰第一步成果与用户数据。本轮不安装或激活当前开发应用。
