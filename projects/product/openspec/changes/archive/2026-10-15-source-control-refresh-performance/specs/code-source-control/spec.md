## ADDED Requirements

### Requirement: 轻量登记观察与请求内复用

系统 MUST 提供只读 `source-control-inventory` 入口，使网页与智能体（Agent）能先取得当前全部登记代码库（Repository）的稳定身份和目录；该入口 MUST NOT 启动 Git 状态扫描或把尚未检查的来源表示为干净，未知文件数量和工作树（Worktree）数量 MUST 保持未知。完整状态读取 MUST 在单次请求内复用可确认的登记观察，并通过内容版本及真实来源检查发现期间变化，MUST NOT 用跨请求陈旧缓存替代当前事实或移除必要身份边界。

#### Scenario: 先取得登记清单
- **WHEN** 工作空间（Workspace）登记多个代码库（Repository），用户开始全量刷新
- **THEN** 系统 MUST 在逐库状态检查前取得全部登记身份，尚未确认的文件数 MUST NOT 为零，依赖真实 Git 身份的写入动作 MUST 不可用

#### Scenario: 读取期间登记或目录变化
- **WHEN** 状态读取期间相关登记内容、目录身份或 Git 成员关系发生变化
- **THEN** 系统 MUST 重新核对或明确拒绝该来源结果，保留真实诊断及其他来源，不得将旧观察标记为当前有效

### Requirement: 有界并行与逐库刷新

网页全量刷新 MUST 以有界并发检查各代码库（Repository），复用本机既有读取线程上限；每个来源完成后 MUST 及时发布该来源的状态，MUST NOT 等待全部来源完成才更新。一个来源慢或失败 MUST 不阻止其他已完成状态显示。刷新取消后 MUST 停止继续调度，失败或等待 MUST 保留可核对的旧结果和真实状态，MUST NOT 假装无改动。

#### Scenario: 快库先完成
- **WHEN** 两个来源并行读取，其中一个仍在等待，另一个已完成
- **THEN** 列表 MUST 立即显示已完成来源的新状态，保留等待来源的已有结果，并继续表达本轮尚未结束

#### Scenario: 局部失败与取消
- **WHEN** 一个来源读取失败，或用户取消旧刷新并开始新的刷新
- **THEN** 失败 MUST 只影响该来源，已完成来源 MUST 可继续查看；取消后的旧读取 MUST 不再继续调度或覆盖新结果

### Requirement: 渐进刷新顺序与阅读保持

同一次全量刷新的登记、逐库及最终结果 MUST 共享顺序边界，较旧进度 MUST NOT 覆盖较新的局部读取或已确认来源操作。只有完整登记观察与本轮收束后才可移除不再登记的来源。刷新 MUST 保留仍有效的来源及文件选择、展开、筛选、滚动、提交说明和未保存输入；任务预选 MUST 继续按确认的具体来源表达，MUST NOT 隐藏其他登记来源。

首次默认来源 MUST 按登记顺序选择可确认的具体来源，MUST NOT 取决于响应完成顺序；较早来源仍待查时 MUST 等待，确认没有可选来源后 MUST 可继续选择后续来源。用户显式选择和有效任务预选 MUST 保持优先。

#### Scenario: 局部读取先于旧全量返回
- **WHEN** 全量刷新尚未完成，用户触发较新的局部读取或确认切换分支（Branch），随后旧全量的该库结果才到达
- **THEN** 页面 MUST 保留较新的已确认状态，不让迟到进度回退该来源，也不清除其他已完成来源

#### Scenario: 更新期间继续阅读和输入
- **WHEN** 用户已有来源、文件、展开状态和提交说明，其他来源陆续完成更新
- **THEN** 仍有效的阅读、选择和输入 MUST 保持，MUST NOT 因逐项更新重建工作台或自动改选来源

#### Scenario: 默认来源与完成顺序无关
- **WHEN** 后续登记来源先完成，而首个来源仍待查，随后首个来源完成或确认没有可选工作树（Worktree）
- **THEN** 后续结果 MUST 可先显示，但默认详情 MUST 继续按登记顺序确定，首个来源无可选成员时 MUST 可继续采用后续已确认来源
- **AND** 用户已主动选择来源时 MUST 保留该选择，MUST NOT 被迟到结果抢回
