## Context

当前全量刷新同步读取全部登记库及实际工作树（Worktree），状态前后重复解析登记和核对身份。前端只接收最终结果。现有本机网页读取器已有两个工作线程，可用于真正并行执行同步 Git 读取。

## Goals / Non-Goals

目标是减少重复工作、限制并发、逐库呈现，同时维持准确身份、局部失败和新旧响应顺序。保留当前界面、来源选择、展开、筛选、滚动和输入；不增加文件监听器，不改写 Git 状态，不发布或激活共享开发版。

## Decisions

1. 新增 `source-control-inventory` 只读入口，返回既有状态清单结构的登记骨架。只表达已登记身份和目录，文件数量和工作树（Worktree）总数保持未知，以 `code_source_control_pending` 明确尚未检查。既有 `source-control` 完整入口保持兼容。
2. 前端在同一刷新序号内先取得登记清单，再最多并发两个现有单库状态请求。逐项完成时合并发布，全部结束后以已观察的完整登记清单处理删除；局部读取失败不阻断其他来源。已存在记录在等待时保留，首次等待不冒充干净。全量加载器（Loader）最多调度前 128 个库，其余保留身份、未知状态和覆盖诊断；每个单库请求仍独立遵守既有工作树（Worktree）及时间预算，不把原完整单请求的 128 个总检出及 12 秒解释为整批刷新预算。其他局部读取可能共同排队，真实并发继续由固定两个读取线程约束。
3. 后端单次状态请求复用登记解析，用原文内容版本发现变化。真实目录、Git 公共目录和成员身份仍在必要边界核对；不得跨刷新长期缓存可变状态。无轻量版本端口的调用保持安全的完整重读回退。
4. 渐进合并复用既有目录（Catalog）的请求取消与逐库序号。较新局部状态和已确认操作不受旧全量进度覆盖；登记骨架不推进正文版本，等待项和失败项不清空已有阅读结果。任务预选按实际单库读取合并，首次具体来源尚未确认时不提前消费空预选；不缩小全量展示范围。
5. 首次默认来源继续按登记顺序确定。较早来源待查时，后库可显示结果但不抢占默认详情；确认较早来源没有可选工作树（Worktree）后继续寻找下一项。用户显式选择和已确认任务预选保持优先。

## Risks / Trade-offs

- 多个本机请求增加少量协议开销，但复用固定线程池并避免一次阻塞全部来源；不另建工作线程池或无界子进程。
- 首次登记骨架没有 Git 身份，必须禁用依赖真实状态的动作，直到对应来源完成。
- 原文版本变化只使相关读取失效，不能将未经复查的数据宣称为最新，也不应阻止其他库。
- 活跃自动观察变更（Change）修改同一前端目录合并代码；保持加载器（Loader）的进度回调为可选参数，保留公共完整读取接口，避免复制其未提交成果。

## Migration Plan

无持久数据迁移；新入口附加，现有命令与响应不变。前端采用新入口，旧调用继续完整读取。测试验证轻量清单、身份漂移、失败保持、真实并行上限及乱序结果，再以真实集鲜只读观察作性能对比。
