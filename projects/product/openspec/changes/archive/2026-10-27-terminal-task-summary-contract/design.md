## Context

- 工作台任务行当前用 `context?.progress || record.result?.summary || record.intent` 选择主文案，不看任务状态：进行中任务与终态任务共用同一条优先级。
- 工作台列表接口已经同时提供任务记录（含 `status` 与 `result.summary`）与工作摘要上下文，前端无需新增请求即可判断状态。
- 工作摘要写入的应用层当前只对 `checks`（检查适用性结论）做终态拦截；`progress`、`nextStep`、`stage` 在终态仍可写入。命令行帮助却写"任务终态后不再修改"，与实现不一致。
- 任务详情页在"任务收尾"节点按任务记录呈现交付结果，不依赖工作台行的选择规则。

## Goals / Non-Goals

**Goals:**

- 工作台任务行按任务状态选择摘要来源：进行中显示工作摘要最近进展，终态显示任务结果摘要。
- 把终态工作摘要的真实写入边界（终态可补写进展类内容，且该写入不改变任务事实；检查结论的终态冻结沿用既有检查要求）写进规范与命令行契约。

**Non-Goals:**

- 不改任务四态、结果记录、工作摘要独立权威与 Agent 指令内容。
- 不引入新状态、门禁、审批或新的接口字段。
- 不改任务详情页的既有呈现。

## Decisions

1. **摘要选择放在前端纯函数，后端不变。**
   理由：列表接口已同时返回任务记录与工作摘要上下文，选择规则属于呈现层。后端新增 `displaySummary` 字段会把展示优先级固化进领域响应，让任务列表、Agent 指令与详情页共享同一个被展示污染的字段。
   备选：后端派生展示摘要 —— 否决，理由如上；并且会让终态判断散落到服务端多处。

2. **按记录状态判定，不比较写入时间。**
   理由：状态是任务记录的事实来源，直接可靠；时间戳比较在任一来源缺失时无法判定，且会引入"谁更新算新"的隐式规则。规则要求摘要来源不因工作摘要早于结果写入而改变，等价于"终态一律以结果摘要为准"。

3. **终态包含 `completed` 与 `abandoned`。**
   理由：两种终态都有结果摘要；放弃的任务同样需要向人展示结论而不是收尾前的旁白。

4. **命令行只改帮助文本，不改行为。**
   理由：应用层实现已经符合新契约（终态可补写进展类内容、拒绝改检查结论），不一致的是措辞。改行为会无谓扩大范围，并让"收尾前补最后一条摘要"重新变成必须恢复 active 的重路径。
   备选：终态整体禁止写工作摘要 —— 否决：那正是本次要消除的负担，且与"工作摘要是独立于任务核心的当前现场"语义冲突。

5. **补写终态最后一条摘要的实践要求保留在 Agent 指引中。**
   理由：即使终态可补写，Agent 仍在收尾前写入最终进展更自然；指引属于 `task-manager` Skill 的既有职责，不新增规范条款。

## Risks / Trade-offs

- [风险] 既有用户习惯在工作台行读"最近进展"，终态任务行改显结果摘要后措辞变化 → 详情页"任务收尾"节点仍按任务结果摘要呈现交付结果，行内同时保留任务标题与状态标识。
- [风险] 摘要来源变化可能掩盖"结果摘要缺失"的数据问题 → 两者都缺失时退回任务目标，与既有兜底一致。
- [权衡] 终态补写摘要让"已完成"任务的现场仍可变化 → 只允许进展类内容，检查结论与任务事实仍由各自权威冻结。
