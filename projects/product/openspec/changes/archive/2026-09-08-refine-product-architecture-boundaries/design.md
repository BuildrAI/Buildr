## Context

两个服务共用一个仓库；后端采用 Node 原生 TypeScript、显式模块装配与 CommonJS 发布负载，前端采用 React/Vite。生成物、每日演进、资产工程检查和部分客户端仍沿用旧归属；宽泛方法集合隐藏了真实依赖。前序 Web 回归已证明仅目录迁移和静态检查不足以验收。

## Goals / Non-Goals

目标：收窄跨模块协作者；每日演进归入任务子能力；分离源码、工程程序和生成物；以完整目录树连通模块、对象、方法和副作用。保持公开 CLI、HTTP、JSON、数据、版本冲突、安全和安装行为。

非目标：不改变单机版按 Git 提交汇总后关联任务的格式，不建设企业版汇总、自动知识生成或新测试平台，不发布版本或完成父任务。

## Decisions

1. 每日演进使用 `task/daily-progress/{domain,application,persistence,interfaces}`，由任务装配入口组合项目查询、任务查询和自身 Repository；不需要独立顶层模块。现有 YAML 文件位置与唯一 writer 保持不变。工作空间删除因此产生的任务晚绑定依赖。
2. 普通生成结果迁至各服务 `build/generated/`；Test Context 编译到 `build/test-context/`；`web-dist/` 保留单份前端构建兼后端托管输出。工程源仍在 `tools/`。生成文件不进入 Git，正式 npm staging 仍显式包含需要的生成物。测试库先在独立暂存目录编译；相同输出不替换文件，内容变化时逐文件原子替换，避免并行检查读取时因清空目录而丢失模块。这不是整个模块图的原子版本切换。
3. 公开 `@buildr-ai/buildr/test-context` 指向生成的公开入口，保持既有十个 JavaScript 导出与公开类型。实现内部索引与公共入口分开，防止移除 facade 后额外暴露内部 helper；兼容旧根物理入口时只在发布 staging 生成兼容文件，不保留手写根实现。
4. 工作空间给资产管理提供有真实消费者的具名 support 对象，不再提供全部业务/测试方法；移除无消费者常量、晚绑定和兼容包装。模块注册保持必要聚合，但具体依赖按命名对象传递并检查方法存在。
5. Buildr 自身包静态验证、测试执行等工程代码迁到 `tools/verification/`，保留公开命令入口的开发调度兼容；正式运行的资源同步、内置资产安装与业务校验留在资产模块。工程能力通过开发入口注入，不让发布运行依赖工具源码。命令入口启动工程进程时显式保留 `BUILDR_NPM_ENTRY_PATH`，直接运行工程程序也提供本服务 `bin/buildr.mjs` 默认值；后续子命令不得把检查程序自身作为产品入口。
6. 项目测试诊断复用其应用读取；`module.ts` 只装配。前端设置迁入工作空间；业务客户端归属功能，公共 `api/` 只保留传输、会话、请求上下文。
7. 原有代码地图就地改成总树、后端树、前端树、关键模块树与调用链，逐项标注手工源、生成物、业务/技术责任、主要对象和代表方法。技术图同步最终归属，不生成第二套地图。

## Risks / Trade-offs

- 生成路径影响打包、类型导入与干净检出 → 同步生成器、清单、构建配置、测试和 npm staging，检查导出集合及正式包。
- 工程检查外移影响公开命令 → 开发侧注入明确能力，检查源码入口与正式负载允许行为，不复制实现。
- 宽依赖收窄遗漏消费者 → 建立实际引用清单，运行真实生产装配、每日演进、资产与浏览器回归。
- 目录移动误改行为 → 先机械迁移后定向装配，保留数据与接口断言；不为目录对称拆小文件。

## Migration Plan

先迁移生成物与公开测试库，再迁移每日演进及前端客户端，随后收窄模块端口与工程检查；每块通过适用检查后更新当前认知。最终通过完整低成本、相关集成、真实浏览器与发布物验证，再收敛规范并交付。回退使用普通反向提交，无数据迁移。

## Open Questions

无待用户决定事项；发现实现兼容约束时保留现有契约并在当前范围内解决。
