# 接入形式、能力差异与第一版范围审查

日期：2026-10-23。审查对象为当前接入方案、已保存原型及对应候选源码；本轮没有修改被审方案、原型或正式功能。参考当前官方文档与已有固定版本实测，不能将新文档直接当作旧版本全部能力的实测。

## 结论

推荐保留三条已验证路线：Codex 的 `codex app-server`、DSH 的 `dsh web` 完整宿主（Host）、Qoder 官方软件开发工具包（SDK）管理配套 `qodercli`。它们都让 Buildr 使用厂家的真实智能体（Agent）执行程序，由厂家继续维护模型循环、工具、原生上下文与恢复。

“命令行还是桌面”不足以说明差异：还要看使用哪个程序入口、装载了哪些配置和工具，以及哪些能力属于桌面宿主。第一版应承诺在 Buildr 当前工作空间（Workspace）完成日常工作的完整对话链路，不采用“厂家桌面所有功能均等价”的开放式验收。

审查结论为需要修订：保留架构与已定布局，收紧范围并补齐原型的关键运行语义。详细问题见下文；这不是否定已有真实接续和恢复结果。

## 1. 实际接入什么

| 对象 | Buildr 实际运行或调用 | 谁执行工作 | Buildr 提供什么 |
| --- | --- | --- | --- |
| DSH | `dsh web --no-open --port 0`，使用官方客户端接口连接完整宿主（Host） | DSH 的模型循环、工具、原生权限与历史 | 自己的对话界面、历史入口、授权交互及工作页面连接 |
| Qoder | `@qoder-ai/qoder-agent-sdk` 调用库启动配套 `qodercli` 的程序交互模式 | 本地 `qodercli` 进程调用模型并执行工具 | 对话界面，以及对软件开发工具包（SDK）消息、控制和回调的处理 |
| Codex | `codex app-server --listen stdio://` | 独立 Codex 进程的原生执行能力 | 通过结构化双向协议管理登录、对话、消息、授权、停止与显示 |

这些进程运行在本机，模型服务仍通过相应账号或模型供应商访问；“本机进程”不表示模型权重必须在本机运行。三家都不要求打开原厂桌面窗口。实验复用某个桌面安装包内的可执行程序，只是程序来源，不等于连接或接管该桌面正在使用的会话（Session）。

### DSH

用户理解的主线基本正确。当前官方文档明确桌面版是在完整网页应用外包一层 Electron，并启动共享配置运行器及网页宿主（Web Host）；桌面再提供原生窗口、目录选择、麦克风和更新等能力。网页与桌面共用大部分执行和界面能力，但配置组合和原生宿主能力仍可不同。[官方桌面架构](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/apps/desktop/README.md)

本方案运行的就是 `dsh` 命令行（CLI）的网页服务模式。Buildr 使用它的后端接口，不嵌入整套 DSH 网页；对话显示由 Buildr 实现。因此接入后仍由 DSH 执行工作，界面由 Buildr 接管。

DSH 还有另一套软件开发工具包（SDK）协议。当前官方说明仍列出缺少单会话关闭、单提示取消和每条提示独立结果等限制；不能把名字相近的入口当成相同能力。已实测的完整宿主（Host）有 `session.cancel`，所以第一版继续采用这条路线。[SDK 协议边界](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/sdk/server/README.md)

### Qoder

软件开发工具包（SDK）是供 Buildr 开发者调用的程序库。官方文档说明它寻找包内携带或环境中的兼容 `qodercli`，也支持明确指定程序路径；实际模型循环、工具、权限与原生历史仍由该进程负责。安装入口可以是软件开发工具包（SDK），运行依赖仍包含配套命令行（CLI），无需桌面应用。[执行方式](https://docs.qoder.com/cli/sdk/how-it-works)、[快速开始](https://docs.qoder.com/cli/sdk/quick-start)

本次通过的是：在独立配置中完成 `qodercli login`，调用库通过 `qodercliAuth()` 使用这个账号，再选择该账号实际可用的模型。官方还提供 Qoder 个人访问令牌（PAT）和组织服务账号方式；它们都是 Qoder 身份，不是第三方模型供应商密钥。[官方认证](https://docs.qoder.com/cli/sdk/authentication)

Qoder 命令行（CLI）明确支持自带密钥（BYOK），通过 `/model → Custom` 官方向导配置，支持的供应商取决于实时目录及适用套餐；桌面也有自己的自定义模型入口。当前软件开发工具包（SDK）文档没有据此承诺“任意直接传入 `baseURL + apiKey`”；已配好的命令行（CLI）自定义模型能否被本次固定版本正确加载并执行，尚未实测。因此第一版先保留已通过的 Qoder 独立登录路径，不顺带开发通用模型配置中心。[CLI 自定义模型](https://docs.qoder.com/cli/custom-models)、[桌面自定义模型](https://docs.qoder.com/qoder/custom-models)、[SDK 模型选择](https://docs.qoder.com/cli/sdk/model-policy)

实际能力还有配置差异：项目技能需显式装配，部分工厂内置技能不保证在程序接入模式中继承。本次实测必须设置 `settings.skills.loadFromAgentsDirectory=true` 才能发现预期的工作空间（Workspace）技能。当前官方文档与固定版本的部分内置条目清单也不同，应读取真实清单，不笼统声称完全相同或完全没有。[官方技能说明](https://docs.qoder.com/cli/sdk/skills)

### Codex

应用服务（App Server）是 `codex` 可执行程序的一个子命令。`codex` 提供终端交互；`codex exec` 适合非交互工作；`codex app-server` 则启动供其他应用连接的本机进程。Buildr 实际已经在接命令行（CLI），只是选择其适合产品接入的启动方式。

应用服务（App Server）提供结构化双向消息，支持登录、持久对话、流式事件和授权处理；无需从终端显示文字中推断状态。当前选择的标准输入输出（stdio）连接也不要求另外运行一个网页服务。官方建议需要自定义完整客户端时采用此入口，批处理等程序工作可用 Codex 软件开发工具包（SDK）。[官方接入选择](https://developers.openai.com/blog/codex-as-a-platform)、[应用服务](https://learn.chatgpt.com/docs/app-server)、[软件开发工具包](https://learn.chatgpt.com/docs/codex-sdk)

桌面的内置浏览器、文件预览、可视化差异、项目管理及宿主扩展不会随该进程自动成为 Buildr 界面。比如官方明确内置浏览器不在 Codex 命令行（CLI）和编辑器扩展中；这与智能体（Agent）还能调用独立网页抓取或另行配置的浏览器工具是不同事实。核心读写和执行能力共用，不等于桌面全部工具、配置和界面自动继承。[内置浏览器边界](https://learn.chatgpt.com/docs/browser)、[桌面本地环境](https://learn.chatgpt.com/docs/environments/local-environment)

## 2. 哪些是交付方式，哪些是真实能力差异

| 层面 | 判断 | 对 Buildr 的含义 |
| --- | --- | --- |
| 模型和执行循环 | 多个入口常复用同一执行系统；显示界面不同不直接证明推理能力变弱 | 保留厂家执行程序，不重写智能体（Agent）循环 |
| 协议暴露 | 同一执行系统的不同接口可以只开放部分控制能力 | 选具体入口、固定兼容版本，不能按品牌名称保证等价 |
| 规则、技能与工具装配 | 默认加载范围、插件、权限和配置可能不同 | 展示真实发现与可用状态，不将登录成功当作能力全部就绪 |
| 桌面宿主能力 | 浏览器、原生窗口、麦克风、编辑器、通知等可能由桌面另外提供 | 需要 Buildr 提供或单独连接；第一版逐项取舍 |
| 用户体验 | 历史列表、消息、授权、工具进度和分屏由客户端组织 | Buildr 的界面实现质量直接决定能否达到日常桌面体验 |
| 账号与模型来源 | 相同品牌不保证账号权益、模型清单和密钥配置相同 | 官方登录、可用模型与真实执行分别核实 |

不能给出可靠的“与桌面等价百分比”。本项目已经证明的核心包括合成规则和技能、文件读写、跨目录权限、执行停止、原生恢复和跨家接续；没有证明所有桌面扩展、图片、长历史或任意运行中异常。当前官方资料与固定实测版本须分别保留。

## 3. 方案与原型发现

### R1 [P1] 第一版范围与原型入口尚未完全对齐

方案第 9 行仍列“配置来源选择”，而第 42–51 行已把首版限定为独立配置。`ConnectionSettings.tsx:120` 仍显示可选的共享本机配置，浏览器审查也观察到这一选项。`main.tsx:217` 把原“提出新目标”接到普通新对话；`RealWorkspaceSurface.tsx:38` 把旧工作动作代理到新对话，与旧接入保持的方向不一致。

建议：第一版每家一套独立配置，只增加明确的全局对话和内部任务入口；原有动作维持职责。任务零／一／多关联继续支持准确定位，但不交付跨任务关系管理器、批量绑定或任务移交。底层未来能扩展多对多，不等于首版要做这些界面。

### R2 [P1] 停止和失联缺少真实未知状态

`main.tsx:174–177` 定时转为“相关命令已退出”；`:229` 把断开接入的活动对话直接设为停止。浏览器中也观察到停止后显示这一结论。原型可以模拟成功，但必须另外演示已经实测可能出现的“模型已中断，命令仍运行”及“状态待确认”。

建议：保留正在停止、确认停止、仍有活动工具、失联未知四类就地反馈；失联不能推断停止，未确认原执行结束时不能启动另一家对同一现场继续写入。停止与授权回复不被整轮发送阻塞。这是首版基本可靠性，不是可延期的高级功能。

### R3 [P1] 三家能力不能由统一控件隐含保证

`main.tsx:181` 给所有执行方相同的“默认／只读／完全访问”，运行中也可调整；`:196` 和`:209` 统一允许补充指令。原生权限和操作系统隔离并不等价，运行中干预与排队也不是同一种行为。

建议：根据每家真实支持呈现权限、模型和追加方式；不支持的操作说明原因。第一版不建立第二套通用许可系统，也不为了同样的控件外观伪造等价能力。

### R4 [P2] 执行位置与接续内容仍有占位信息

`main.tsx:182` 的接续预览仅列类别并固定写 Buildr，`:211` 的底部位置标签也固定为 Buildr。浏览器将空对话起始目录改为 `/tmp/buildr-review-only` 后，设置里值已变化，底部仍显示 Buildr。当前为纯内存演示，没有真实文件操作。

建议：展示该对话保存的准确起始目录（CWD）、工作空间（Workspace）和可选任务；换执行方时可查看实际将交付的记录范围，不只是“将携带相关内容”。超容量时明确无法完整携带，保留原历史并允许继续原执行方；必要时由用户提供或确认可查看的精简接续说明，不先做自动记忆与通用摘要管理器。

### R5 [P2] 收起面板后的待回应状态需要最小提示

`main.tsx:217` 的全局入口始终是静态“对话”，待授权或待回答只在展开后的内容和历史中呈现。用户继续操作工作页面时可能不知道智能体（Agent）正在等待。

建议：全局入口保留状态点或待回应计数，点击准确返回对应对话即可；无需通知中心或自动弹窗。原工作页面继续保留可用的显式刷新，复用已有变化通知，不新增通用事件总线。

原型说明中的“跨家真实接续待验证”也已经落后于补充实验：应区分“隔离脚本已验证”与“原型仍模拟、正式产品未验收”。本轮只记录问题，没有修改原型。

## 4. 第一版建议边界

| 第一版必须形成闭环 | 范围限定 |
| --- | --- |
| 三家独立接入 | 每家一套独立配置、官方登录、实际模型选择；不做多账号池和共享桌面配置 |
| 全局对话和任务入口 | 保留已定布局、左右停靠、统一历史；普通咨询不依赖任务，从任务入口准确创建或打开 |
| 输入与反馈 | 文本和必要的图片输入、流式回复、工具及基本文件改动反馈；图片能力逐家验收，不扩成通用附件解析中心 |
| 授权、提问与停止 | 原生动作和准确请求身份、可及时回复、真实停止状态、必要的全局待回应提示 |
| 历史与恢复 | 准确原生编号，服务重启后继续；断线不盲目重发，未知结果先观察 |
| 手动切换执行方 | 同一可见主题、顺序执行、可查看的接续范围；换回恢复自己的原生上下文，再补增量 |
| 工作现场 | 使用现有规则、技能和权限，支持已授权跨目录操作；工作文件和业务对象继续为权威事实 |

后续再探索：自动页面／选区上下文、生成交互界面（Agentic UI）、成果导航、并行团队、自动分工、完整差异编辑器、桌面浏览器或语音、扩展市场管理、通用模型配置、长历史自动摘要，以及后端退出后继续执行的独立宿主进程。

自带密钥（BYOK）不应被宣布永久不支持；Qoder 官方路径存在，但其与固定接入版本的实际组合需要单独验证。首版不因这一扩展方向先增加一套供应商账户管理产品。

## 5. 为图形界面与对话界面（GUI＋Talk UI）保留的最小基础

1. 对话能力独立于任务详情组件；任意页面都能打开，页面浏览不会静默改变执行位置或发送内容。
2. 用户可见对话身份独立于各家原生会话（Session）；各条回复、工具和授权保留准确来源。
3. 延续已有任务身份、文件路径和系统链接作为对象引用，不创建一套新的工作对象库；历史记录不成为成果内容的权威副本。
4. 输入边界容纳显式提供的任务引用、文字、图片及以后用户选中的内容。第一版先由用户明确提供，未来再探索页面自动上下文。
5. 工具结果和状态保持结构化来源，前端当前呈现基本文字、进度和已有链接，后续可以增加具体视图；不提前建设任意界面生成引擎。
6. 人或智能体（Agent）修改对象后，原页面通过已有查询和刷新读取当前事实；接续执行重新核对实际文件，不依赖聊天里的旧副本。

这些边界为未来融合留出位置，首版无需把所有业务页面都改造成对话入口，也无需重做现有业务能力。
