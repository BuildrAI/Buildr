# Buildr 智能体接入分层架构说明

> 定位：本文是 [接入架构与实施方案](接入架构与实施方案.md) 和正式变更 `add-native-agent-conversations` 的认知补充，回答三个问题——Buildr 现在的设计方案、以后自研智能体要承担什么、为什么现在选择接入。具体行为以正式变更为准，本文不定行为规范。

## 0. 核心判断

"Agent 是工具"成立在**模型与内核层**；"产品是协作"成立在**编排、表面与集成层**。Buildr 接入成熟智能体，赌的是自己的编排与供给比厂家官方宿主在工作流里做得更好，而不是再发明一个智能体循环（Agent Loop）。

## 1. 分层模型：从模型权重到用户手感

| 层 | 名称 | 内容 | 归属 |
| --- | --- | --- | --- |
| L0 | 模型权重（Weights） | GPT、Qwen、swe-2 等参数本身 | 大模型厂家 |
| L1 | 推理契约（Inference Contract） | API 形态、推理强度档位、工具调用格式、缓存行为——模型训练时对齐的运行时约定 | 厂家，接入方只能按契约调用 |
| L2 | 智能体内核（Agent Kernel / Harness） | 智能体循环、工具目录与 schema、系统提示词、上下文组织、压缩（Compaction）、子智能体、护栏 | 厂家（黑盒或半开放），见 §3 |
| L3 | 编排层（Orchestration） | 会话/任务/工作区状态机、审批策略落地、并行与多智能体调度、后台与定时任务、失败恢复 | **Buildr**（替换官方桌面宿主） |
| L4 | 表面层（Host Surface） | 对话框、过程与产物呈现、与工作现场页面融合、引用与导航 | **Buildr** |
| L5 | 集成生态层（Integrations） | MCP、OAuth、CI、外部工具（browser-use、office、computer-use 类） | 部分厂家自带；**Buildr 自建/适配** |

经验证据：同一批模型权重在自家内核里手感更好（如 GPT-Codex 在 Codex 中优于在通用宿主中直接调用），说明"差一点意思"的主要来源是 **L1+L2 的模型-内核协同调优**，不是编排层；而"事情做得完不完整"更多取决于 L3 编排与 L5 生态。

## 2. Buildr 现在的设计方案：接入 = 保留 L0–L2，重做 L3–L5

### 2.1 三条接入路径（已验证，详见最小接入验证报告）

| 对象 | 入口 | 进程模型 | 工具/上下文注入口径 |
| --- | --- | --- | --- |
| Codex | `codex app-server`（JSON-RPC stdio） | 一服务多会话（Session） | thread/turn 生命周期、item 事件流、反向审批请求、dynamic tools、AGENTS.md |
| DSH | `dsh web` 完整宿主（Host）＋官方客户端（Client） | 一宿主多会话 | 原生客户端 API；内核插件化（技能/工具可按 profile 挂载） |
| Qoder | `@qoder-ai/qoder-agent-sdk` 驱动配套 `qodercli` | 每会话一进程 | SDK 自定义工具、权限、Hook、MCP、`.agents/skills` 发现 |

### 2.2 各层职责划分

- **L0–L2（借用）**：模型权重、推理契约、智能体内核循环整体保留——模型质量、循环行为、请求级上下文组装（排序、压缩、缓存命中）全部由内核负责，Buildr 不实现、不代理、不猜测。
- **L3 编排（自建）**：统一对话框承载多家执行者；任务上下文注入、模型/推理强度分配、统一审批落到 Buildr 权限预设、会话/工作树/产物归属、跨家接续。接入不是路由转发——是 Buildr 决定"谁、在什么上下文、用什么权限干活"。
- **L4 表面（自建）**：对话框只是入口；L4 的本职是把智能体过程与产物呈现在工作现场——diff、产物可独立查看、工具调用轨迹映射为任务进度、页面间准确引用。对话框是智能体的 UI，L4 是智能体在 Buildr 工作现场里的存在方式。
- **L5 集成（自建+适配）**：browser-use 等验收能力由 Buildr 提供实现，经各家注入口径（dynamic tools / SDK 自定义工具 / MCP / DSH 插件）挂入；内核只负责"看到 schema、决定调用、拿回结果"，实现永远在 Buildr 侧。

### 2.3 上下文供给原则：内核组装，Buildr 供给

Buildr **不做请求级上下文编排**，做"可检索供给"：

- **持久上下文**：工作现场 + AGENTS.md/规则/技能，整理得"可检索、可信任"——路标式组织（去哪找、什么边界），而非全量塞入；
- **场景上下文**：每次任务的目标、约束、验收标准、指向产物，由 Buildr 序列化成显式消息递入——这部分内核检索不到，必须显式给；
- **工具即供给**：Buildr 命令行与能力封装成工具，返回查询结果（任务状态、产物、技能正文）而非预打包提示词，匹配内核按需检索的模式（渐进式披露）。

## 3. 以后自研智能体，需要承担的责任

自研的本质不是"再写一个 Agent"，而是**自己承担 L2 内核 + 与 L0/L1 的协同调优**，具体责任清单：

| 责任 | 说明 |
| --- | --- |
| 循环正确性 | 智能体循环的每一步（工具选择、回合节奏、停止条件）正确、可恢复、可审计 |
| 请求级上下文组装 | 排序、压缩、prompt 缓存命中——这是内核质量的核心，也是目前接入免费获得的能力 |
| 工具目录与 schema 自维护 | 自建全部工具契约面与护栏；外挂工具的调用形态（图像输入、长产物、computer-use 回合模式）要自己实现 |
| 模型-内核协同调优 | 所选模型的推理契约、编辑格式、推理强度映射要与内核共同调优，否则重现"同一模型换个宿主就变差" |
| 会话与恢复语义 | 原生会话编号、上下文压缩、重启恢复的语义自己定义和保证 |
| 演进成本 | 跟随模型代际重调优；三家接入时协议升级只要改适配层，自研则全部自担 |

**触发自研的条件（满足其一才值得评估）**：需要审计/控制循环每一步（合规边界）；需要改变内核行为（压缩策略、工具语义）来服务 Buildr 任务模型；厂家内核质量或路线图成为瓶颈；成本或数据主权要求自有推理栈。除此之外，自研不产生差异化价值。

## 4. 为什么现在选择接入方式

1. **差异点在宿主不在内核**：内核正在商品化（codex-rs 开源、DSH 开源、Qoder 公开发 SDK），Buildr 的产品价值在任务/产物/权限/验收的组织，不取决于再发明一个循环。
2. **接入面足够完整**：三家协议已验证能提供 Buildr 需要的一切——会话生命周期、审批回调、工具注入、上下文加载、停止与恢复（见最小接入验证报告矩阵）。
3. **适配层做薄，内核当黑盒**：哪家协议变了只改适配层，不碰 Buildr 任务模型；损耗集中在各家协议差异（停止语义、技能发现开关、模型保存行为），已列入实施方案差异表。
4. **风险有界**：桌面专属能力（内置浏览器、自动化、IDE 补全、Quest 编排）本就不承诺等价；云端联动（codex cloud 等）经 CLI 命令仍可取回。
5. **可逆**：自研门槛清楚（§3），接入不锁定后续自研——届时 Buildr 的 L3–L5 资产（任务模型、界面、工具实现）全部保留可复用。

## 5. 遗留注意点（实施中继续验证）

- **供给质量是 Buildr 的真实质量变量**：AGENTS.md 路标、场景上下文翻译、工具返回的信噪比，决定接入后的实际效果下限。
- **L2 黑盒不可依赖其内部行为**：验收依赖产物与外部可观察事实，不依赖对内核内部上下文的假设。
- **协同调优损耗客观存在**：同模型跨内核有手感差异，属预期；模型选择时按"该内核原生搭配"优先，而非强行复用别家模型。
