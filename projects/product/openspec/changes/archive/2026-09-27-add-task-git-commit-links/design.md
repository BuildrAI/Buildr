## Context

动机见 [proposal.md](proposal.md)。当前 `TaskRecord` 保存任务目标、范围、关系和结果，没有提交列表；任务详情通过 `TaskWorkPath.tsx`、`TaskNodeContent.tsx`、`TaskReadingPane.tsx` 组织阅读。`git-operations` 已约定语义化主题，未要求任务尾注（Trailer）。历史收尾方案曾使用 `Buildr-Task`，对应执行应用已退役，本次只沿用该格式。

每日演进（Daily Progress）中的提交是按日保存的摘要，可关联多个任务，不是实时 Git 关系，不能充当本功能的数据来源。当前工作空间（Workspace）的产品与两个服务目录实际共享同一 Git 代码库（Repository）；实现必须按真实边界去重。

用户已确认[界面原型（UI Prototype）](ui-prototype/task-git-commits.html)并授权实施真实 Git 关联；该原型继续使用模拟数据。已完成的原型默认归入与发现修复一并保留，真实 Git 接入另用隔离代码库和正式页面验证。

## Goals / Non-Goals

**Goals:**

- 以实际提交说明（Commit Message）表达唯一任务归属，任务侧读取同一提交并显示完整身份。
- 命令行（CLI）和网页消费同一只读结果，局部读取问题不改变任务状态或否认提交成功。
- 沿用任务详情布局，提供独立阅读入口，保留原有四个工作阶段。

**Non-Goals:**

- 不建立人工关联维护台、提交台账数据库或每日演进（Daily Progress）的第二份数据。
- 不自动推送、抓取远端、改写历史、安装强制钩子（Hook），也不保证恢复 Git 已不可达或已清理的旧对象。
- 不处理跨工作空间（Workspace）的全局任务身份；编码在当前明确工作空间和任务范围内解析。

## Decisions

### 1. 用既有任务编码作为尾注

采用 `Buildr-Task: <taskId>`，主题继续表达改动内容，不把任务编码塞入标题。智能体（Agent）依据明确任务和已授权提交范围加入尾注（Trailer），提交后读取实际完整说明确认。无任务则省略；普通提交只有一个不同的任务编码。重复的同值尾注按一个值读取，但新提交只写一行；不同编码、空值或非法格式形成局部诊断，不静默选取或覆盖。

相比主题前缀，尾注（Trailer）保留标题可读性且有确定的解析边界。相比另外登记关联，任务页从 Git 读取可避免双方逐渐不一致。正文任意位置提及任务编码不算关联。

### 2. 明确双向关联完成的证据

实际提交含唯一合法 `Buildr-Task` 值，该值可解析为当前目标任务，且任务查询返回同一真实代码库（Repository）、完整哈希值（Hash）与实际说明时，双向关联才被确认。提交写入成功而查询失败时报告“提交已包含任务编码，任务侧暂未确认”，不撤销提交或冒称完成。任务状态、审查和验证结论不因关联存在而改变。

### 3. 读取当前可达提交，不保存新的权威记录

新增任务限定的只读应用，入口为 `buildr task commits <task-id> --target <workspace> --json` 和任务限定的 `/tasks/:taskId/commits`。命令行（CLI）和超文本传输协议（HTTP）使用同一应用结果及独立闭合契约，不扩展旧专业结果目录，也不往 `TaskRecord` 填入提交正文。

从任务登记的项目、服务位置及已知任务工作树（Worktree）解析真实代码库（Repository）。没有项目、服务和变更范围的任务沿用既有工作空间级任务语义，只读取其权威工作空间（Canonical Workspace）根自身的代码库，不从当前命令目录或上层代码库猜测范围。在同一代码库内读取本机分支、已存在的远端跟踪引用、标签及相关工作树当前 `HEAD` 的可达提交，因而覆盖尚未推送的本机提交；不遍历整个磁盘，不从最近使用的分支推断任务归属，不执行网络抓取。多个服务引用同一代码库或多个引用指向同一提交时，以“代码库身份 + 完整哈希值（Hash）”去重。

结果包含读取时间、实际覆盖的代码库与引用观察、已确认提交、局部诊断及读取是否完整。每条提交来自真实 Git 对象，提供主题、完整说明、完整及显示用短哈希值（Hash）、作者和提交时间；排序按提交时间从新到旧，并以完整身份稳定排序。超时、输出上限或分页未完成必须明确为部分结果，不把截断计数当作总数。访问时按需读取，缓存只能是可丢弃的加速结果，并随引用观察变化失效；第一版不要求持久索引（Index）。

与持久关联表相比，直接读取减少双写和历史重写对账成本。取舍是仅承诺当前覆盖范围：修改提交或变基（Rebase）生成新哈希值（Hash）后重新读取；旧对象仍可达则继续作为真实历史显示，已不可达则不冒充当前列表，不承诺永久留存。

### 4. 阅读入口与状态分离

在任务详情“任务收尾”后放置第五个阅读标签“提交记录”，四个原有阶段和当前阶段标记保持原义。进入标签按需读取，刷新只更新当前读取结果。列表展示主题、短哈希值（Hash）、作者、提交时间与代码库（Repository）；展开显示完整说明和完整值，复制完整值或说明。任务上下文已经明确，不再重复展示“关联当前任务”行；实际完整说明中的 `Buildr-Task` 尾注仍原样显示。单仓场景仍能识别来源，多仓同值不会混为一条。

成功读取且零匹配显示“当前检查范围内暂无关联提交”；仓库暂不可读、冲突或部分读取显示具体提示及重试，已成功部分继续可见。模拟原型的场景切换仅供演示，正式界面不出现这些控制，也不增加手工登记按钮。

### 5. 能力指引与当前知识影响

随包 `git-operations` 和 `task-finish` 技能（Skill）补充明确任务编码、实际说明回读及双向关联完成条件，继续遵守原有 Git 授权与归属边界，不把关联读取作为推送或任务完成的通用门禁。投射到工作空间（Workspace）的副本继续由既有更新方式生成，不手工修改。

自举同步执行器（Self-bootstrap Runner）已明确接收任务编码时，其生成的同步提交同样使用 `Buildr-Task`，保留原有激活身份及恢复尾注（Trailer）。未传入任务编码时保持无任务关联；该接入不增加任务状态查询或激活前置门禁。

## Risks / Trade-offs

- [历史提交没有尾注] → 保留历史，不自动补写或按相似说明猜测；第一版只确认符合约定的真实提交。
- [任务范围变化或代码库暂不可读] → 显示本次实际覆盖范围与局部诊断，不报告全历史完整性。
- [本机引用陈旧] → 结果说明来自本机当前观察，不把它当作远端最新状态；需要更新远端时由独立已授权 Git 动作处理。
- [大代码库读取耗时] → 有界读取、取消及显式部分结果，避免读取全部提交正文后才筛选；不把性能限制转成错误的空状态。
- [同一提交出现多个任务编码] → 显示冲突，不按第一行选定唯一归属；混合贡献应在提交前由智能体（Agent）核对范围。
- [并行原型保存规则变更] → `operation-trace` 工作树（Worktree）的 `add-buildr-operation-trace` 已调整原型和任务分流技能（Skill），并修改“原型成果必须随实施决定可靠接续”：已有任务及变更即可归入，展示不等于实施授权。本修复保留该语义并补充无变更任务、本机原型及统一阅读器，不修改对方现场。任一变更收敛前须合并该同名条目的完整最终文本，避免另一份增量规范写回无变更不支持的旧限制；本次预检仅代表当前可见工作根。

## 本轮已授权修复：已有任务默认能发现原型

任务已存在且原型属于当前任务时，智能体（Agent）默认把原型放入可被任务详情发现的位置。已有规范变更（OpenSpec Change）仍使用其 `ui-prototype/`；没有关联变更时，使用任务权威工作空间（Workspace）的 `.buildr/local/task-prototypes/<task-id>/`。不为放置原型伪造规范变更，也不以准备实施为保存条件。

读取先校验任务存在，再访问该任务的精确目录；复用现有 HTML 标记、文件大小和元数据约束。任务目录及从工作空间根到文件的所有路径层级都拒绝符号链接（Symbolic Link），不广扫其他任务目录。发现与读取正文零写入，失败仅影响相应文件或来源。返回来源明确区分 `task` 与 `change`，本机任务来源不伪填项目、变更或生命周期。

前端在任务“方案设计”中请求原型，不再以关联变更数量为前置；两个来源并存时清楚显示来源与稳定阅读身份。保留现有变更原型读取和安全限制。直接验证覆盖无变更任务、未知任务、不同任务隔离、祖先和文件符号链接（Symbolic Link）、超大与无标记文件、两来源并存，以及从任务详情进入原型的真实浏览器交互。

## Migration Plan

保留已经完成的原型归入与发现修复，按本轮实施授权完成真实 Git 只读能力和契约、接入页面并更新相关源技能（Skill），使用隔离测试代码库（Repository）验证真实双向关联。候选验证和当前安装状态分开报告。旧任务和旧提交不迁移，现有任务状态与结果保持有效；回退新能力不修改 Git 历史或任务记录。
