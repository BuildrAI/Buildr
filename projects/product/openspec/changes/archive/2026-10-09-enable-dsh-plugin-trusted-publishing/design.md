## Context

见 proposal.md。现有 `release.ts prepare` 已调用同一构建器和真实装载验证后打包，但记录本机绝对路径。主包发布器固定主包身份；现有 `verify.yml` 的归档软件开发工具包（SDK）输入不满足增强插件的真实 Git 检出要求。

## Goals / Non-Goals

目标是保持插件版本和候选独立，提供可验证、手动选择的准备与发布方式。实现不修改版本、不执行发布、不配置 npm 信任，不修改或输出现有令牌（Token），也不放宽主包发布器。

## Decisions

1. 独立 `.github/workflows/publish-dsh-plugin.yml` 使用 `workflow_dispatch`，默认 `prepare`。`publish` 必须消费明确 `candidate_run_id` 的成功准备运行；当前提交必须与候选及原工作流匹配。复用 `npm-production`，仅发布作业（Job）取得 `id-token: write`。需要平台设置时留待确认，不自动创建环境或降低保护。
2. 用固定上游 `deepseek-ai/deepseek-harness` 的已登记提交创建独占真实 Git 检出；先验证并应用入库补丁及逐文件摘要，再按补丁后的锁文件冻结安装并忽略安装脚本（Install Script），调用现有源码软件开发工具包（SDK）准备器。准备器仍从原提交归档重建并独立应用同一补丁；依赖链接匹配增强源码。旧 `fetch-sdk` 的归档和默认版本不能冒充本次来源。输入依赖安装与发布均隔离 npm 配置，避免隐含发送已有凭据。
3. 候选说明仅记录相对压缩包名、正式包身份、版本、源码、软件开发工具包（SDK）摘要、大小、SHA-256 及 npm 完整性（Integrity）；消费者有界读取普通文件并检查真实路径，不运行压缩包代码。服务的私有源码包不作为发布目标。
4. 插件专属发布器先检查 GitHub 托管身份及有效开放身份连接（OIDC），隔离用户／全局 npm 配置与认证环境，再发布固定 npm 注册表（Registry）的原包。复用主包可靠原则而非扩大主包授权元组。
5. 持久 `publication.json` 保存非秘密的请求身份和结果。新发布先完整查询同版本历史发布运行及所有尝试，证明未进入发布步骤的尝试不阻塞；已有可能派发的请求必须通过明确恢复运行编号取回原证据。证据缺失、取消或状态未知不得凭注册表（Registry）404 判为可重发，只能回读。未知响应禁止自动重试写入；发布失败同样上传该证据，已公开同字节直接复用。
6. 正式包模板补齐对应仓库 `repository.url`。插件独立标签（Tag）和公开版本保持原命名；本次工作流只负责 npm，标签（Tag）写入仍按现有精确版本授权单独处理。

## Risks / Trade-offs

- 已只读核验 `npm-production` 要求 `elevenching` 审批，`prevent_self_review: false`，未配置部署分支规则 → 工作流自身限定 `main` 身份，不修改平台保护，真实发布前重新核对。
- npm 信任保存不能证明有效 → 提供精确字段及允许动作，在后续真实发布授权内验证，不借用本机令牌（Token）。
- 上游下载或构建失败 → 固定身份和独占输出，失败不产生可用候选；无公开副作用测试使用真实临时文件／Git 与隔离外部协作者。
- 恢复证据缺失 → 不把未知状态当不存在；操作说明要求携带原运行证据，工作流禁止绕过已有未知发布尝试。

## Migration Plan

先交付代码和无公开副作用验证，再确认独立包的 npm 信任绑定，最后在另一次精确版本授权下准备和发布。新 npm 绑定有首次成功发布验证窗口，应在可发布时配置。不因本次代码完成撤销任何旧凭据。
