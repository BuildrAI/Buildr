## Context

背景见 `proposal.md`。当前随包核心规则已经要求约束局部化，并将规则（Rule）与技能（Skill）职责分开；产品入口 Buildr 技能（Skill）只在命中的资产维护动作中消费最终诊断（Doctor），已有结果可以复用。`task-finish` 按真实对象直接组合能力，不创建旧收尾运行（Finish Run）；现行 `agent-task-workflows` 与 `task-closeout-orchestration` 已明确该边界。

两个旧规范条款仍分别要求核心规则（Core Rule）的统一完成条件和旧收尾运行（Finish Run）不启动。这里只收敛这两项规范性冲突，主规范保持原文直至受保护的合流动作完成。已归档的退役资料、连续数据库迁移和遗留清单兼容事实保持原样。

## Goals / Non-Goals

**Goals:**

- 用同一目标、来源、运行时（Runtime）及相关条件说明诊断（Doctor）结果的适用性和复用边界。
- 让错误结果只影响消费它的具体动作和完成结论，同时保留身份、授权、版本及删除归属的保护。
- 将当前规范、实际技能（Skill）及长期完成说明对齐，避免再复制操作手册。

**Non-Goals:**

- 不修改诊断（Doctor）算法、命令、接口（API）、数据格式或业务实现，不降低具体能力的写入前保护。
- 不新建流程运行器（Runner）、许可位、诊断快照、收尾记录或自动状态传播。
- 不修改工作空间（Workspace）跨通道管理和登记锁行为，不触及 DSH 插件或发布。

## Decisions

1. **保留两个现有条款，以完整增量修订。** 只加解释会留下旧强制约束；直接修改主规范又不能独立审阅承诺变化。因此复制完整条款及场景到增量规范（Delta Spec），保留准备声明缺口场景，明确局部诊断、结果复用和当前收尾副作用边界。
2. **核验依赖事实，而非聚合健康值。** 与当前动作相关的身份、授权、版本和归属必须成立；无关诊断不能成为许可。资产维护结果失败继续保持未完成，其他已成立交付不撤销。此处依赖已有能力，不引入诊断分类器或统一自动放行机制。
3. **不新增技能（Skill）调用关系。** 当前 Buildr 与 `task-finish` 的实现指引已经具备局部处理和复用方法；本变更核对并保留它们。后续若发现实际指引缺口，应按能力协作边界明确提出，不能在知识维护中暗改绑定。
4. **区分证明类型。** 文档与严格校验只能证明材料结构和规范一致性；具体写入保护由既有能力测试及实现核对证明。静态技能（Skill）文本检查不能证明任意智能体（Agent）必然遵从指引，本变更不建立这种承诺。

## Risks / Trade-offs

- 把局部继续误解为忽略诊断（Doctor） → 增量保留相关错误不得冒充完成、身份或版本未知不得写入的场景。
- 用文档检查替代真实副作用证明 → 核对既有能力测试的断言对象与本次是否改变实现；保留检查事实与未覆盖范围，不新增镜像文本测试。
- 与同任务另一个变更合流相互覆盖 → 本变更只写上述两个条款；工作空间（Workspace）登记行为保持独立规范归属，并运行语义预检。
- 对旧清单和退休流程进行全局文字替换 → 只修订当前承诺冲突，保留历史、兼容迁移和仍有消费者的专属概念。

## Migration Plan

本次没有数据库、接口（API）或运行状态迁移。材料审查后，核对现行指引与必要知识说明，取得适用检查，再由唯一合流执行者更新这两项主规范并归档。若归档中断，使用现有合流恢复能力核对真实状态；不得手写恢复记录或回滚他人修改。源码交付、任务完成与自举激活仍由同任务分别依据实际事实处理。
