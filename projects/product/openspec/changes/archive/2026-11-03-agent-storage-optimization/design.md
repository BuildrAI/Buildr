## Context

见 proposal 与任务既有方案。当前存储版本 4，正文存在主记录与 read entries 两处，compact 又复制小正文；现有并行后台要求相同存储版本。搜索仅覆盖标题和可见消息，不能把工具日志加入命中。

## Goals / Non-Goals

目标是保留精确历史、修订、来源和控制语义，以单份正文与稳定工具压缩减少长期占用；保护版本升级及在途工作。非目标是原生会话归档、账号合并、全局附件去重、真实库清理、候选自举激活或新增页面。

## Decisions

- 使用版本 5：对话表只保存头和 main 条目数量，正文表按对话与原始字节摘要唯一保存，位置表区分 main／inherited 并引用正文。原有 read entries 成为权威位置，read states 仍可重建。相同小 compact 用 NULL 表示复用正文，不重复全文；必要有界预览保留。
- 原始字节摘要继续作为详情修订。仅对已完成／失败且超过 16 KiB、原始大小不超过 64 MiB 的工具条目尝试 zstd；只有变小才使用。可见消息保持 raw，普通检索直接读规范化可见消息；旧库读取保留原查询，不增加 FTS。
- 分页先读位置／大小后取内容；codec、原始长度、解压上限与摘要均验证。损坏只明确失败，不变成空消息、不请求原生模型补历史。流式与迟到更新生成新正文修订。
- 编解码、正文持久化与迁移分别封装在 persistence，应用仍组合 StoredConversation；减少读取模型的全文职责，不重建所有调用方。保留已发交接文件与附件引用。
- 复用同一连接的缓存根设置 NODE_COMPILE_CACHE，保持 HOME／TMP／账号隔离；仅声明 tmp/node-compile-cache 与受管共享编译缓存可按现有占用和身份规则回收。原生恢复日志及未知目录继续保留。

## Risks / Trade-offs

- 新结构不能兼容旧 body-only 写入 → 存储版本不同不得并行；新表保护触发器明确拒绝带全文的旧写入，不静默忽略。
- 备份暂时增加磁盘 → 在迁移前创建私有一致性备份并校验，报告包含备份的实际占用；不自动删除备份来虚报净收益。
- 冷正文损坏／超限 → 有界解压和原始摘要，完整错误而非截断。raw 大消息保持既有可读能力，不强行压缩超预算数据。
- 旧 read model 测试把正文表当派生表 → 保留旧版本只读测试，新增规范化存储测试；新的正文／位置不是可任意删除后恢复的缓存。

## Migration Plan

旧库普通读取不写入。新写入器仅在取得准确 owner 与 storage 保护、无其他存活原后台时迁移；未释放时保留旧库并明确推迟，不强停工作。以 SQLite 一致性备份保全旧库，逐条迁入正文／位置并核对往返内容，在事务中切换存储版本，失败回滚原记录。旧版数据库读模型只能从原 canonical body 重建，迁移不能相信可能陈旧的投射。

成功切换后尝试安全收缩空闲页；空间不足等回收失败不损坏有效新库。迁移提交后重新打开新库，完整性检查及与准确备份的逐条完整记录比对通过后，立即删除本次备份；失败保留，删除失败不否定新库，不扫描删除历史未知备份。备份不会自动覆盖新写入。尚未有新写入可在离线核对后恢复旧备份；有新写入时使用前向修复或另行验证的无损导出，不能自动降级覆盖。版本声明由现有 build 工具读取同一常量。
