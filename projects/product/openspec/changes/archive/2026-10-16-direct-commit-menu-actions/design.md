## Context

现有提交和同步分别拥有来源观察、写入互斥及明确结果。同步会获取固定上游，按需快进或变基（Rebase），再普通推送。提交内部临时索引（Index）和真实索引锁须清理后才能整合，公开同步入口自行持有同一公共目录锁，不能在提交锁内直接重入。

## Goals / Non-Goals

主按钮始终执行普通提交；菜单依次直接执行“提交并同步”和“提交并推送”。组合动作保护已成立提交和固定上游。沿用现有同步的权限、冲突及不确定结果边界，不新增自动冲突解决、暂存隐藏、强推或其他整合策略。

## Decisions

- 移除各来源主按钮模式记忆与菜单选中模式。主按钮固定 `commit`，菜单按 `commit-sync`、`commit-push` 排列；共用禁用条件并立即关闭菜单，旧事件仍由动作层读取最新状态和防重。
- 使用单次 `commit-changes` 请求的 `commit-sync` 模式，避免前端在两个请求之间失去提交事实或改读目标。
- 同步应用（Application）提供仅内部使用的准备能力，捕获提交前来源、分支（Branch）、完整目标配置版本及上游提交。提交外层持有一次公共目录写入锁；内部提交返回、索引锁清理后，核对当前提交等于本次新提交、原目标和上游观察仍成立，再执行既有同步核心。公开同步入口继续自己加锁，不开放 `skipLock` 参数。
- 同步准备失败不阻止合法本机提交；后续任何同步不可用、异常或未知都以已提交及独立同步阶段结果返回。原 `commit.hash` 保留初次提交身份，变基（Rebase）后最终身份由 `sync.head` 表达。
- 响应增加 `sync: CodeSyncResult | null`，旧提交和推送为 `null`；组合同步不使用顶层推送重试令牌。后续仅重新观察并使用既有同步入口，不重新提交、不自动重放未知结果。
- 继续使用已修复的局部箭头样式。详情按需展示真实阶段消息，避免把原提交标识误说成同步后的最终标识。

## Risks / Trade-offs

- 同一公共目录锁重入或索引锁未释放会导致同步失败 → 内部核心复用与外层单次锁，真实集成测试证明生命周期。
- 提交钩子（Hook）可以改目标、当前提交或留下新文件 → 同步前重新核对固定观察，保持已有脏内容保护；不能悄悄同步另一个目标。
- 变基（Rebase）改写本地未推送提交 → 分别保留原提交与最终同步头；冲突保留现场并停止推送。
- 部分成功被 HTTP 异常掩盖 → 已提交后的同步失败在正常结果中表达，不抛失提交事实。

## Migration Plan

无需数据迁移。后端接受新增模式并返回独立同步结果，前端随正常构建更新。旧动作语义与公开同步入口保持兼容；不改用户全局 Git 配置。
