## MODIFIED Requirements

### Requirement: 输入与执行反馈必须构成日常使用闭环

对话 MUST 支持文本、图文、流式回复与准确执行反馈。同组合执行中普通发送 MUST 优先使用原生追加能力并保持原轮和原生会话；MUST NOT 静默创建替代上下文。待回答问题、待授权仍属于原轮，普通消息 MUST NOT 自动回答、批准、释放等待或开启替代会话；不能安全追加时 MUST 保留输入并说明原因。确需更换原生会话时 MUST 先展示预览并取得明确确认，单独选择和普通发送不构成确认。未发送草稿和未知投递 MUST NOT 自动重放。Codex、DSH、Qoder MUST 遵守相同边界。

#### Scenario: 执行中主动补充图文
- **WHEN** 当前执行身份已确认且仍在运行，用户保持相同选择并主动补充文字、图片或图文组合
- **THEN** 系统 MUST 通过原生追加交付原轮，保留准确输入身份及接收结果，不创建新原生会话
- **AND** 界面 MUST 沿用普通消息展示，不要求切换插入或排队模式

#### Scenario: 执行中继续编辑
- **WHEN** 用户只编辑输入而未提交发送
- **THEN** 系统 MUST 保留草稿，不自动发送；用户明确提交新要求时 MUST 按原生能力保持会话连续性，MUST NOT 假称已送达或重发原未知操作

#### Scenario: 图片输入超过限制
- **WHEN** 图片不符合所选模型支持范围或超过已声明大小
- **THEN** 系统 MUST 提示受影响图片和原因，并保留可继续编辑的文本与材料
- **AND** MUST NOT 通过静默删图把请求显示成完整发送

#### Scenario: 等待明确授权时补充
- **WHEN** 原执行等待授权或业务问题，而用户发送普通补充
- **THEN** 原问题与授权 MUST 保持原轮及活动等待；新输入 MUST NOT 作为原请求的回答或批准，也不得触发新会话
- **AND** 不能安全追加时 MUST 保留草稿和原等待事实，不以预览或选择变更清理原问题

#### Scenario: 文件已被其他入口修改
- **WHEN** 智能体（Agent）继续读取或修改已有成果
- **THEN** 工作依据 MUST 是当前文件或外部系统事实，历史工具摘要不能证明内容仍未变化
- **AND** 工作页面 MUST 能继续使用原查询与刷新读取同一成果，不要求新增通用工作对象库

### Requirement: 同一对话换家必须展示真实接续材料

用户 MUST 能手动选择同一对话（Conversation）的下一位智能体（Agent）和模型（Model），选择本身不创建执行、不发送输入、不改变任务或历史身份。用户明确发送新要求时 MUST 按所选组合接续，不等待原执行或工具结束；忙碌的原上下文 MUST 保留，新要求 MUST 使用独立上下文。系统 MUST 在同一对话中从本地原始记录组织交接，并允许查看实际发送正文、来源范围与执行位置。材料 MUST 不含秘密、隐藏推理或无关工作空间信息，不宣称迁移私有上下文。界面 MUST 只提示实际改变的执行维度，采用紧凑轮次列表，完整正文默认收起且与页面说明明确分开；详情 MUST 从对话所在一侧展开。正常发送 MUST 不强迫用户再确认一份交接清单。

#### Scenario: 首次切换到另一家
- **WHEN** 用户选择另一家并在交接预览中明确确认发送
- **THEN** 系统 MUST 在用户明确确认后按该选择交接同一工作并保持同一内部对话，实际交接正文可在同侧详情查看
- **AND** 历史工具操作和授权 MUST 仅作有来源的参考，不作为可重放协议请求

#### Scenario: 原执行尚未确认结束
- **WHEN** 对话执行中、待回应、正在停止、仍有活动工具或状态未知
- **THEN** 系统 MUST 保留原执行及其准确控制，并允许用户发送新要求、更换选择及重新观察
- **AND** MUST NOT 因另一家可用而自动代选；独立执行新要求 MUST 以用户明确提交为依据，旧工作是否停止由智能体（Agent）按现场判断

#### Scenario: 查看发送内容
- **WHEN** 用户展开完整交接内容
- **THEN** 框内 MUST 仅展示准备实际发送的正文，框外解释 MUST 不混作发送文字
- **AND** 关闭重开 MUST 恢复正文收起，已发送回执 MUST 读取当次快照且区分确认接收与未知

### Requirement: 换回参与者必须恢复原生上下文并准确推进交付位置

换回曾参与的执行方时，原参与者没有未结束工作且归属可安全复用时，系统 MUST 恢复其准确原生会话（Session），补充其尚未收到的可见变化；原上下文仍活动、待决定或结果未知时 MUST 保留该绑定，未经用户在交接预览中明确确认 MUST NOT 为新要求创建独立上下文；待问题或授权 MUST 保留原轮，不通过新上下文绕过等待，MUST NOT 冒充恢复或覆盖旧工作。交付位置 MUST 绑定实际输入身份、来源范围及接收事实，只有原生确认接收后才能推进；超时未知 MUST 保留尝试并先核对，不能凭本地已发送或界面显示推进。交付位置 MUST 不代替执行完成或成果正确的判断。

#### Scenario: Codex 经两家参与后返回
- **WHEN** Codex、DSH、Qoder 顺序参与且原上下文已空闲后，用户换回 Codex
- **THEN** 系统 MUST 恢复原 Codex 原生编号并仅补充其未收到的 DSH、Qoder 可见变化及本次要求
- **AND** MUST 保留 Codex 已有原生上下文，不新建同名会话冒充恢复

#### Scenario: 交付确认丢失
- **WHEN** 接续输入可能已被接收但确认未返回
- **THEN** 系统 MUST 保留原交付位置和未知尝试，按原生输入身份重新观察
- **AND** MUST NOT 自动重复提交整包历史或把未确认范围标记为已交付
