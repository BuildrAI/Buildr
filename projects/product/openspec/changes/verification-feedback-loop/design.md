## Context

现有九组浏览器场景已隔离页面，但history内37个step共享夹具且遇错终止。现有统一CLI、timing诊断和源输入快照可继续扩展；不增加平行执行系统。

## Goals / Non-Goals

目标按二→三→一→四推进：独立场景、准确选组、已有修复交付、准备优化。不改产品业务规则、不绕过Windows证明，不承诺尚未实测的整体加速。

## Decisions

1. history导出带稳定英文id、名称与run(fixture)的单一成员源。每个独立场景新建浏览器上下文和夹具，保留原断言；真实顺序旅程内部不拆。场景筛选复用现有环境入口，新增精确id，未知id报错。使用现有Node子测试和分阶段诊断，同轮继续收集独立失败。选择完整组仍发现全部成员。
2. 测试路径自动标签不升级成产品全域标签；明确--tag仍取并集。测试本身保留直接归属与框架契约检查，产品实现仍覆盖跨服务边界。快照对同一检出目录的完整字节比较与交付基线分离，环境变化仍扩大必要覆盖。
独立场景证明在既有coverage中标记focused；失败接续保守保留父检查，旧证据无场景身份时不猜测子集。恢复组中原27秒真实退避文件单独登记，原组240秒预算保持，新组60秒，完整发现由唯一登记派生。

3. 原排序失败在独立场景定位；不把等待和重试当作根因证明。未知写入不重放，必要Windows证明不可替代。
4. 生产web-dist准备使用现有生成产物清单与缓存位置，内容摘要包括前端源码、依赖、构建配方、Node/平台和生成接口输入；缓存命中仍检查完整产物清单。结果记录准备来源和时长，输出损坏或输入变化时重建。跨轮复制到本轮隔离输出，不用在线目录。

## Risks / Trade-offs

- 每场景初始化成本增加：复用已建好的生产产物与服务，隔离浏览器状态，先测量总成本，不以并行淹没机器。
- 场景实际依赖前序：独立运行暴露后补必要setup，保留真实因果链，不能删除断言。
- 缩组选漏共享影响：固定测试文件、transport实现、网页准备配方三个选择矩阵与反例回归。
- 快照跨基线误用：仅同一检出目录且完整清单结构有效，逐字节校验，配方/环境改变不得假成功。

## Migration Plan

沿用任务工作树和既有组入口，先history迁移；其他组保持旧旅程。无新包依赖。结果和筛选增量兼容，旧证据缺场景信息时保守整组；产物缓存验证失败重建。本次变更与任务清单维护在同一工作树，不修改canonical规范直至合法收尾归档。
