## Context

参见 proposal.md。现有登记、执行器、源码结果库、候选分片和阶段时间线可以复用；当前复用范围多为整个后端/仓库，Git 身份包含全部引用，候选汇总又要求同一源码和登记摘要。诊断入口保留原包，但不能补齐正式候选。

## Goals / Non-Goals

目标是让完整覆盖由有效证明组成，修复影响决定返工范围，并在执行前解释成本。继续使用项目自己的验证程序，不新增通用测试平台、任务状态机或审批层。不操作已有发布选择及公开版本，不用本机通过冒充 Windows 或生产发布凭证。

## Decisions

1. 检查输入从候选覆盖与改动选择中独立出来。优先给已核验的源码运行检查声明稳定的产品输入、执行入口和辅助材料；配方包含实际测试文件、相关工具、共享执行器和环境。未知动态读取保留保守范围，不直接用 changed 路径集合充当完整输入。
2. 结果仍由执行器写入既有结果库。新增解释投影显示执行/复用原因、原执行时间、剩余工作量与最长依赖路径。执行方法变化只影响对应证明；全局调度或结果语义变化仍允许必要扩大。缓存读取和计划本身不成为成功证明。
3. 产包来源保持不可变，验证来源可以独立。受控补验必须比较原始构建输入与当前输入，校验原包全部摘要；只改测试或验证工具时保留原包。构建工具、依赖、产品源码变化不能借此绕过重建。补验继续使用正式检查及资源档位，不把任意诊断文件提升为完整候选。
4. 完整汇总保留每项原始来源及失败历史，只组合经身份和覆盖校验的成功结果；缺项、失败、未运行分别输出。原始记录足够时汇总修复只重新汇总。必要平台及真实包消费继续存在。
5. 发布请求先保存意图，随后保存准确返回或错误。确定未受理和可能受理分别恢复；未知只查询，明确拒绝可以在条件修复后重新请求。错误有界保存，保留退出码、信号、系统错误和诊断，不能吞错或伪造成功。
6. 六阶段职责使用现有准备/检查/发布/恢复入口表达，已有时间线展示实际等待与运行，不建立第二份发布事实。每次高成本补验先展示计划；同错不自动触发完整重跑。
7. 工具验收包含默认入口、真实文件大小、干净准备、采用/就绪、故障恢复及重复执行。基础设施变化验收一次，普通发版直接消费已经成立且仍有效的结果。

8. 正式补验使用原冻结工作流及承载引用，只更换精确验证检出；工作流定义也是不可变输入。验证提交须在 `origin/dev`，原包与原产包源码保持原身份。主包发布上下文绑定验证来源，受保护消费和公开动作使用该工具源码。首次采用新工作流需新的基础设施基线，不能对未支持入口的旧运行补发参数。
9. 当前先收窄已核验的后端运行检查。前端、DSH 服务及未知构建输入保持保守范围；未变化的插件及精确对端可保留整份完整验证。宿主环境与真正读取当前 Git 的检查重新观察，不按历史绿色状态跳过。

## Risks / Trade-offs

- 输入声明过窄 → 反例覆盖产品变动、测试变动、共享执行器、依赖、平台与 Git 漂移；未知保守，不用性能目标换覆盖。
- 旧成功记录缺新字段 → 保留读取与原来源，不自动赋予跨版本原包补验资格；新身份自然使受影响旧缓存未命中。
- 跨运行组合混入不同包或不可信结果 → 原包摘要、生产来源、验证来源、检查配方、实际环境和受控来源逐项核验。
- 静态证明无法代替真实 GitHub 条件 → 本地验收和真实远端验收分别报告，未运行项目保持未完成；不为演练公开无意义版本。
- 并发任务共享 Git → 只在本任务位置修改，检查自身确实依赖的引用或隔离临时仓库，不以工作树目录不同推断 Git 完全隔离。

## Migration Plan

先完善诊断与计划，再调整复用输入，随后接入原包补验及完整汇总，最后维护声明/说明并按代表场景验收。旧发布记录和已存在包不改写；新行为通过明确的新证明格式/字段启用。回退代码仍保留原记录，不能重标来源或重复公开。
