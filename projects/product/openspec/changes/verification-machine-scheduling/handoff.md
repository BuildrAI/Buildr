# 验证框架优化情况与后续接续

本说明面向新对话，汇总当前架构、已实施方案、收益证据、失败及后续方向。代码和真实执行是事实来源；本文件不授予新增优化、发布或跳过失败的许可。

## 当前结论

有明确的局部收益和共同调度收益迹象。旧集成与端到端顺序执行累计54分17秒，本轮四类共同执行33分24秒，运行器总耗时34分51秒。但两轮源码和集合不同，且两轮都存在失败，不能把原始约38%的时间差当作严格、稳定的优化收益。

当前最确定的剩余架构问题是：部分重型组申请当前全部I/O额度，额度调大时申请量也一起变大，因此仍然互斥。本轮有5分13秒只运行一个占满I/O的组，另有1分34秒只运行声明独占组。不能简单把这6分多钟视为可全部省下的时间，独占原因和稳定性仍须证明。

本轮完整验证结果：103组通过、3组失败、6组环境不可用。不能称全绿或已经完成集成。

## 整体验证架构

### 第一层：通用项目测试能力

这是Buildr产品能力。`project-testing`负责建设测试、登记及发现入口；`project-verification`依据用户目标选择并实际执行检查，交付证据；应用保存项目地图和可选正式任务报告。没有任务也可直接验证，用户项目保留自己的测试工具和执行入口。

Buildr自身也是受Buildr管理的项目。下面的内部登记、资源调度和发布候选机制属于Buildr项目，不能强加给普通用户项目。

### 第二层：Buildr自身的测试框架

覆盖`buildr`、`buildr-web`、`buildr-agent`、`dsh-plugin`四服务，只使用Static、Unit、Integration、E2E四种证明边界。

| 环节 | 实现与职责 |
| --- | --- |
| 声明 | `projects/product/verification.yml`与`preparation.yml`公开稳定能力、入口、范围和环境要求。 |
| 发现与选组 | `services/buildr/test/verification/registry.ts`汇集实际服务登记；`planner.ts`及相关选择模块组合类型、显式检查、路径、语义与失败范围。 |

四类可以进入同一计划；不保证四类在同一瞬间各占一路。本轮Integration与E2E实际重叠17分7秒，没有四类同时运行的区间。分类表达证明边界，并发由具体检查的依赖和资源决定。

本轮四类全集通过一次性启动器取得四个正式入口的精确并集，交给原`test:related`/`executePlan`执行；没有新增公开的“四类全量”命令。完整清单在本机`full-four-types/manifest.json`，不要凭旧112这个数字重建测试清单。

### 第三层：发布编排

发布由`buildr-release`消费第二层检查和仍有效的原始证明，冻结准确来源与原包，并核对真实平台及双包兼容。`release-verification.ts`、`release/release-consumption-contract.ts`和候选输入模块负责消费边界，不维护另一份业务测试清单。

源码测试通过不代表准确发布包或其他平台通过。相同有效包的证据可采用，但是否需要重测取决于内容与环境适用性。发布动作需要单独授权。本轮没有实施新的发布恢复编排优化。

### 并发设置位置与含义

`execution-capacity.ts`负责机器初始策略，`registry.ts`保有固定档位和组内预算。非CI默认`local-auto`，自动宽度取CPU/3与内存GiB/4的较小值并限制1至4；浏览器与I/O至少2以容纳现有双工作进程组。

`BUILDR_VERIFICATION_PROFILE=local`回退原固定预算：外层4、浏览器2、I/O3、工作进程8。CI默认固定档位保持。`BUILDR_VERIFICATION_JOBS=<正整数>`覆盖外层宽度并联合调整相关额度，组内并发及正确性锁不跟着放大。以计划和计时中的实际额度为准。

`localExecutionStep`仍把真实Agent进程、Archify、嵌套Git组的`workspaceIo`申请设为当前总额度。它是保守负载策略，不等于具名正确性锁，也不证明磁盘饱和；这是后续必须重点审视的策略。

### 已否定的共享服务方向

不要重新套用已撤回的共享服务器原型。文章与Change原先已经并行，关键路径约73.6秒；修正后的共享原型约79.3秒，未证明提速。它没有移除14至16秒的夹具初始化，还把两套服务的合计读/写能力各从4降为2；同步CLI/Git准备会阻塞共同Node事件循环。另一次身份冲突来自子进程私有数据根与宿主不一致。

这些结果说明该原型无效，不说明任何环境共享都不可行。后续应优先共享不可变准备、正确划分可写身份及阶段容量，而非直接合并服务。
