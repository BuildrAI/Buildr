## Context

见 proposal.md。DSH `packages/boot/plugin-manager` 的 `inspect` 已用于原安装页面，但只拒绝相同包名；`runProfilePnpm` 已在配置档（Profile）写锁中统一服务桌面与命令行（CLI），并在包管理器启动前检查兼容性。普通插件没有安装前拦截钩子。

## Goals / Non-Goals

在原安装页面预检时显示冲突，并在共用实际安装路径重新检查，确保接口直接调用不能绕过。保留旧插件、配置、会话和其它插件行为。不实现自动切换、通用冲突框架、安全卸载或历史数据迁移。

## Decisions

1. 使用确切包名集合：`@buildr-ai/buildr-dsh-plugin`、`@buildr-ai/buildr-dsh-plugin-dev`、`@buildr-ai/buildr-dsh-development-composition`、`@buildr-ai/dsh-plugin-dev`。从当前直接安装声明读取已有安装，包括禁用和旧开发入口，不靠活动服务判断。检查同包更新亦遵循用户要求先卸载。
2. 共用身份与冲突逻辑由安装模块负责。注册表（Registry）及目录沿现有真实清单读取；本地压缩包有界读取标准 `package/package.json`，不解包到磁盘、不执行代码。当前已有 Buildr 时，身份未知的远端安装源必须先取得可核验身份；无法取得则报告本次身份预检失败，不能误报 Buildr 冲突或静默继续。该失败只影响当前不可核验的安装请求，不禁用现有插件；已核验的无关插件继续原处理。
3. 原页面预检是反馈，配置档（Profile）锁内的执行检查才保护实际安装。拒绝允许记录本次诊断，不变更依赖、锁文件、选择层或用户配置。
4. 修订 DSH 安装模块源码，生成可复核补丁与独立候选，不把整个管理器塞入 Buildr 业务组合。后者会触发 DSH 管理保护，导致 Buildr 无法正常卸载。完整候选保留原安装模块身份及拥有者，原页面和候选官方命令行（CLI）使用同一实现；不手改现装应用归档，不猴补服务方法。补丁构建、受控原页面验证、完整候选启动及现装采用分别报告。

## Risks / Trade-offs

- 当前正式、开发入口已并存 → 不自动清理，后续 Buildr 安装将提示用户；保持原现场。
- 安装源身份变化或多个包同次安装 → 锁内以当次真实清单及本次待装集合检查，未知明确报告；不按名字猜测。
- 当前增强组合的普通卸载不恢复预设引用 → 独立保留缺口，本次不能声称安全卸载已实现。
- 当前应用的安装器是不可变运行时（Runtime）输入 → 普通 Buildr 包升级不能使此检查生效；验证候选实际入口，现装采用需要走受支持的完整 DSH 构建／更新，不回退受保护管理层替换。

## Migration Plan

保全原基线与事件来源补丁，在任务所属独立源码候选中实施。先验证原安装器测试、拒绝副作用与原页面，再构建采用新安装模块的完整 DSH 候选，使用独立数据目录核对启动与卸载后重试。候选或依赖无法准备时保存源码与验证事实，明确未完成的真实应用范围，不安装半成品或覆盖当前 DSH。
