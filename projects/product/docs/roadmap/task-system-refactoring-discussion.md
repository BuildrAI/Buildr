# 任务系统重构：讨论结论与推进方式

> 文档性质：历史讨论参考。本文整理 2026-08-28 至 2026-08-30 的讨论，其中关于模块是否保留的未决设想已被后续实现取代。当前行为见[任务生命周期架构](task-lifecycle-architecture.md)；本文不是规则（Rule）、行为契约或已批准的实施计划。

## 一、为什么重新审视任务系统

集鲜工作空间（Workspace）中的多个服务分别属于独立代码仓。使用反馈是：任务容易被环境、证据和交付链上的门禁卡住；智能体（Agent）花费大量时间读取指引、传递身份、登记结果和恢复内部状态，实际工作却未同比受益。

问题不只是某项检查过严，而是多个各自合理的模块组合后，是否形成了不必要的依赖与阻塞。继续为每次失败增加状态、门禁和恢复命令，可能使系统更完整，却不一定更好用。

本次重构希望降低无效阻塞和协作成本，而不是提前穷举所有未知场景。上述反馈是审查动机，不替代最新源码和真实案例的核验；历史任务状态、错误和耗时不能直接当作当前事实。

## 二、保留的核心思考

以下解释用于帮助后续审查，不独立增加规则：

- **正确性（Correctness）需要落到具体对象和动作。** 创建记录、运行验证、交付代码和清理环境保护的条件不同。应追问某个前置条件为何与当前动作有关；这不意味着命令永不失败或可以忽略必要授权。
- **确定性（Determinism）用于减少重复推理。** 能力明确对象、输入、输出和副作用；重复且稳定的组合可以固化为工作流（Workflow）。不应因此要求所有任务经过同一全局流程，也不能把业务取舍藏进自动化。
- **智能体优先（Agent-first）不等于人退场。** 人与智能体是不同用户：人侧重目标、认知、判断、授权和验收；智能体侧重理解与执行。界面和对话服务协作，真实工作对象及其状态才是继续工作的依据。
- **效率以可信完成为前提。** 时间、步骤、词元（Token）、工具调用、重复尝试和人工介入都值得观察，但更少调用不自动等于更好结果。没有可信测量时，不编造收益或把性能设想写成既有指标。

## 三、已经确认的决定

1. **先有最小原则，再以实践修订。** 六条原则已经确认；初版保持短小，不先建设完整的智能体时代软件理论。只有实践暴露现有原则无法判断的问题时，再讨论修订。
2. **原则正文只维护一处。** 本文仅引用[随包内联核心规则](../../services/buildr/resources/workspace/AGENTS.md)，不复制六条正文，不成为第二份规则权威。内联改造已通过[对应变更](../../openspec/changes/archive/2026-08-30-inline-workspace-core-rules/proposal.md)交付到 `dev`；进入开发分支不等于已经发布新的公开版本。
3. **先审查，不预定模块取舍。** 下一阶段先盘点模块、状态、权威来源（Authority）、流程和依赖，再判断哪些需要保留、简化、合并、改为可选或删除。
4. **从工作空间启动是本轮使用边界。** 不扩展独立服务仓库启动或新的运行时适配；工作空间内部的多项目、多独立 Git 仓库仍属于核心审查场景。

## 四、怎样推进

顺序是：最小原则 → 现状与依赖图 → 首个切片的目标边界 → 渐进迁移 → 用实际结果修订 → 继续下一切片。

依赖图不能只看代码导入，至少区分：

| 关系 | 要查清的问题 |
|---|---|
| 数据依赖 | 消费谁持有的什么事实，是否重复保存？ |
| 执行依赖 | 谁调用谁，哪些步骤确实必须先完成？ |
| 门禁依赖 | 缺少什么会阻止哪个动作，保护的具体不变量是什么？ |
| 只读投影依赖 | 谁为展示组合事实，是否误取得了写入或裁决权？ |

约定 `A → B` 表示 A 依赖 B。优先评估没有其他模块依赖、或容易与主链解耦的末端消费者；不是先改“不依赖别人、却被广泛依赖”的基础模块。实际顺序还要结合用户收益、风险和迁移成本；存在循环依赖时，先识别可拆开的边界。

一个切片通常先迁移或移除消费者，再收缩被依赖模块，最后删除不再使用的状态、命令和恢复逻辑。允许为迁移先补齐最小兼容能力，但不为此预建通用框架。

审查门禁时，核心问题是：**如果放行，当前哪个动作会产生什么具体伤害？** 能回答的安全约束应保留；仅为满足内部流程而存在的条件应重点审查，不能预设所有门禁都应删除。

## 五、当时尚未确认的设想

- 采用“日常任务与受控任务”两类模型，还是“一个任务、多种可选动作”，尚未定案。
- 任务研发（Task Development）、任务候选（Task Candidate）、研发交接（Development Handoff）及固定审查阶段当时尚未定案；这些内部模型现已退役。
- 是否需要通用动作模型、执行引擎、统一结果存储，尚未定案。
- 首个改造模块、迁移顺序、兼容期限及量化收益，需由实际审查提出。

前文讨论中的模块删除建议和架构草图都只是候选，不能直接当作实施清单。一次审查也不等于完整的新任务系统已经设计完成。
