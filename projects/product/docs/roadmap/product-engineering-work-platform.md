# Buildr 产品里程碑与产研工作平台（Product and Engineering Work Platform）架构

> 文档性质：产品路线图（Product Roadmap）。本文给人阅读，用于统一产品目标和重构方向，不是当前能力说明、正式规范或实施任务。具体改造仍需独立评审和规范变更系统（OpenSpec）变更。

## 一页结论

Buildr 已经完成从工作资产管理工具到本机工作平台的建设，但任务系统（Task System）过于复杂，正在拖慢智能体（Agent），并增加任务缺陷、执行时长和词元消耗（Token Consumption）。

下一阶段的目标是：

> **建设以智能体和人为核心用户的产研工作平台，维护产研工作资产，让任务管理从可用变得好用，同时显著提高智能体执行效率。**

下一阶段只抓三条主线：

1. 在整体产品与架构约束下重构任务系统；
2. 减少智能体执行时长、重复调用和词元消耗；
3. 重新审查全部技能（Skill），该保留的保留、该合并的合并、该简化的简化、该删除的删除。

## 一、产品建设关键里程碑

| 阶段 | 主要建设 | 阶段结果 |
|---|---|---|
| 1. 工作资产原型 | 在集鲜工作空间中使用清单文件（Manifest）管理项目、服务、规则和技能 | 验证了“工作内容和工作方法可以成为长期资产”，但尚未形成独立产品 |
| 2. Buildr 产品化 | 建立独立工作空间（Workspace）、命令行界面（CLI）和 Buildr 技能；支持初始化、更新、项目/服务管理，并发布到 npm 软件仓库（npm Registry） | Buildr 成为独立产品，能够为不同组织创建和维护工作空间 |
| 3. 智能体运行时适配 | 将规则、技能和命令投射到不同智能体运行时（Agent Runtime），适配 AGENTS.md、.agents/skills/ 等共同约定 | 同一套工作资产可以被不同智能体发现和使用 |
| 4. 任务平台建设 | 建设任务记录（Task Record）、任务工作树（Task Worktree）、任务环境（Task Environment）、任务研发（Task Development）、任务验证（Task Verification）、任务收尾（Task Finish）、任务复盘（Task Retrospective）和 Buildr 网页界面 | 任务不再只存在于聊天列表，Buildr 从资产管理工具进入本机工作平台阶段 |
| 5. 治理与架构收敛 | 重构 Buildr 核心规则（Buildr Core），确立“约束智能体不要做错事，而不是要求智能体必须通过 Buildr 才能做事”；建立宽而薄治理、模块化单体（Modular Monolith）、本机结构化数据库（SQLite）和结果对账（Reconciliation） | 产品边界和技术分层更加清晰，但任务生命周期和内部协作成本仍然过高 |
| 6. 当前阶段 | 产品已进入候选发布（Release Candidate）阶段；主要功能已经完整，正式任务、验证、收尾和发布能力较强 | Buildr 进入产品减法和任务系统重构阶段 |

本次梳理时的代码与任务数据快照说明，复杂度已经集中到任务领域：

- 工作空间已有 377 个任务记录；
- 仍有 113 个待处理任务复盘；
- Buildr 运行源码约 5.7 万行，其中任务模块约占 45%；
- 命令行已有约 40 个主要命令和 40 个智能体机器命令。

## 二、下一阶段产品目标与定位

### 产品目标

Buildr 要建设产研工作平台，支持产品、设计、研发、测试和发布团队的日常工作。

平台主要维护两类内容：

- **工作资产（Work Asset）**：项目事实、服务关系、产品知识、规范、文档、规则、技能、命令和验证方法；
- **工作状态（Work State）**：任务目标、进展、决策、风险、授权、证据和结果。

### 产品定位

Buildr 是产研工作的资产与协作基础设施，不是另一个智能体，也不是所有工作必须经过的流程许可层。

~~~text
人：提出目标、业务判断和授权
智能体：理解、推理、执行和交付
Buildr：管理工作资产、任务状态和必要安全边界
~~~

### 核心用户

| 用户 | 最关心什么 | Buildr 应提供什么 |
|---|---|---|
| 人 | 目标、进展、结果、风险和需要决定的事项 | 简单清晰的任务与工作资产界面 |
| 智能体 | 当前范围、相关上下文、可用能力、真实状态和安全边界 | 结构清晰、可发现、可检索的上下文来源，稳定接口和少量确定性操作 |

### 产品边界

Buildr 负责：

- 长期工作资产；
- 可接续的任务状态；
- 来源、身份、范围、关系和完整性；
- 智能体运行时投射；
- 结果对账和必要安全边界。

Buildr 不负责：

- 替智能体理解用户目标；
- 组装上下文窗口（Context Window）；
- 通用规划、智能体调度和固定岗位路由；
- 强制代码、测试、版本控制（Git）和拉取请求只能通过 Buildr 执行。

Buildr 通过组织工作资产、范围、关系和来源，让智能体（Agent）更容易从正确范围找到可信信息，提高请求上下文（Request Context）质量。

## 三、产品架构

Buildr 只有一套产品架构，但面向人和智能体呈现为两种不同视角：

- 对人来说，Buildr 是产研工作平台（Work Platform），用于理解、管理和优化工作内容；
- 对智能体（Agent）来说，Buildr 是上下文（Context）基础，用于从正确范围找到可信信息并完成具体任务。

~~~text
            人的视角                          智能体的视角
          产研工作平台                          上下文
       理解 / 管理 / 优化                 检索 / 判断 / 使用
                 └──────────────┬──────────────┘
                                ▼
┌─────────────────────────────────────────────────────────┐
│                    Buildr                               │
│                                                         │
│  工作内容                                               │
│  ┌──────────────────────┐  ┌────────────────────────┐ │
│  │       工作资产       │  │          任务          │ │
│  │ 工作事实 / 工作方法  │  │ 目标 / 进展 / 决策     │ │
│  │ 项目 / 服务 / 知识   │  │ 风险 / 授权 / 证据     │ │
│  │ 规则 / 技能 / 命令   │  │ 结果 / 当前状态        │ │
│  └──────────────────────┘  └────────────────────────┘ │
│                                                         │
│  治理基础                                               │
│  范围 / 来源 / 身份 / 关系 / 权限 / 诊断 / 安全边界   │
└───────────────────────────┬─────────────────────────────┘
                            ▼
          代码 / 文档 / 测试 / 版本控制（Git）/ 外部系统
~~~

产品架构由两层基础构成：

1. **工作内容**：包括工作资产（Work Asset）和任务（Task）。工作资产主要包括工作事实（Work Fact）与工作方法（Work Method）；任务承载日常工作的目标、进展、决策、风险、授权、证据、结果和当前状态；
2. **治理基础**：维护范围、来源、身份、关系、权限、诊断和必要安全边界，保证人和智能体看到的工作内容可信、可理解、可操作。

上下文不是独立模块，而是全部工作内容与治理信息面向智能体的组织和使用方式。工作平台也不是独立模块，而是同一套工作内容与治理能力面向人的产品形态。

任务是人和智能体最常使用的日常协作对象。任务会使用工作资产，也会产生新的事实、方法、决策和证据；其中需要长期复用的内容可以继续沉淀为工作资产。

## 四、技术架构

~~~text
projects/product/
├── 产品文档、当前认知、正式规范和路线图
└── services/
    ├── buildr-web
    │   └── Buildr 网页前端
    └── buildr
        ├── 接口层
        │   ├── 命令行界面（CLI）
        │   ├── 应用接口（API）
        │   └── Buildr 网页运行时
        ├── 应用层
        │   ├── 工作空间与工作资产
        │   ├── 任务系统
        │   ├── 验证与交付
        │   └── 安装与诊断
        ├── 基础设施层
        │   ├── 文件与版本控制（Git）
        │   ├── 本机结构化数据库（SQLite）
        │   └── 进程、网络与运行时
        └── 智能体运行时投射
~~~

技术架构继续保持：

- projects/product/ 管理产品事实和规范；
- buildr 服务（Buildr Service）承载命令行、应用、数据、网页运行时和产品实现；
- buildr-web 服务承载网页前端；
- src/bootstrap/ 保持唯一进程组装入口；
- 继续使用模块化单体，不通过拆分更多服务掩盖领域复杂度。

下一阶段技术架构的核心不是大规模搬目录，而是重新划清任务系统边界：

- 通用日常任务能力留在任务核心；
- 正式验证和自动交付成为可选受控能力；
- Buildr 自举、候选验证和发布逻辑从通用任务核心抽离；
- 能从真实事实派生的状态不重复持久化；
- 内部模块保持独立责任，但不把所有内部接缝暴露给智能体。

## 五、当前核心问题

### 1. 任务系统太复杂，缺陷频发

当前任务系统包含任务记录、环境、计划、研发、内容目标、候选、审查、验证、研发交接、收尾、激活、清理、诊断和复盘。

这些模块分别合理，但组合后产生了三个问题：

- 日常任务容易进入完整正式流程；
- 模块之间身份和状态很多，任何漂移都可能触发缺陷；
- 修复一个恢复问题时，往往又增加新状态、新命令和新恢复逻辑。

因此，下一阶段最重要的产品任务是：

> **在整体产品和架构边界内重构任务系统，而不是继续修补现有长流程。**

### 2. 智能体执行效率太低

智能体接入 Buildr 后，经常需要：

- 读取大量规则、技能和能力契约；
- 多次查询任务、环境和验证状态；
- 在多个模块间传递身份、摘要和临时文件；
- 通过“失败—修复—重试”发现正常前置条件；
- 为小改动承担候选、审查、正式验证、收尾和自举成本。

直接结果是：

- 任务耗时变长；
- 词元消耗增大；
- 重复调用增多；
- 智能体更容易在过长或失焦的请求上下文中犯错；
- Buildr 内部工作超过真实产研工作。

智能体执行时长、Buildr 调用次数和词元消耗必须成为正式产品指标。

### 3. 全部技能需要重新梳理

现有技能覆盖工作资产、任务、验证、收尾、发布、规范和运行时，已经形成较大的技能体系。

每个技能都需要重新回答：

1. 它服务哪个明确用户意图；
2. 它是否与其他技能重复；
3. 它应该是规则、技能还是应用能力；
4. 它是否读取了过多前置内容；
5. 它是否把推荐步骤变成了强制流程；
6. 它是否应当默认触发；
7. 它的输入、结果和停止条件是否足够简单；
8. 它应该保留、合并、简化还是删除。

技能梳理的目标不是重新命名，而是减少触发歧义、重复职责、跨技能交接和上下文开销。

### 4. 产品复杂度缺少统一预算

当前新增功能通常强调完整性和安全性，但没有同时要求删除旧复杂度。

后续每个改造都必须说明：

- 增加了什么；
- 删除了什么；
- 减少了多少状态、命令或交接；
- 对人是否更容易理解；
- 对智能体是否更快、更省词元。

## 六、下一阶段重构重点

### 1. 重构任务系统

日常任务默认路径应收敛为：

~~~text
目标 → 任务记录 → 智能体工作 → 进展/决策/证据 → 完成
~~~

日常路径不默认要求任务环境、正式验证（Formal Verification）、任务候选（Task Candidate）、完成审查（Completion Review）、研发交接（Development Handoff）和自动任务收尾。

只有发布、部署、隔离环境、正式证据或自动交付等高风险任务，才进入受控路径。

重点改造：

- 任务记录与版本控制（Git）基线、任务环境解耦；
- 减少持久状态，优先使用只读派生状态；
- 合并重复的当前性判断；
- 用一个面向结果的入口完成确定性内部步骤；
- 把发布和自举专用逻辑移出通用任务核心；
- Buildr 网页界面优先展示目标、进展、风险、证据和结果。

### 2. 提高智能体执行效率

重点改造：

- 只加载当前动作真正需要的规则和技能；
- 提供一个紧凑任务入口，避免重复读取完整结果；
- 正常路径一次发现完整前置条件；
- 正常路径不以失败作为流程分支；
- 输出默认紧凑，详细证据按需展开；
- 已经匹配当前内容的验证不重复运行；
- 恢复同一任务时不重新创建任务、环境和执行；
- 持续统计执行时长、调用次数和词元消耗。

### 3. 重审全部技能

建立统一的技能清单，逐个标记：

| 结论 | 含义 |
|---|---|
| 保留 | 职责清晰、用户意图明确、成本合理 |
| 简化 | 能力有价值，但正文、依赖或流程过重 |
| 合并 | 与其他技能存在重叠或只能共同完成一个目标 |
| 可选 | 只服务正式、高风险或低频场景 |
| 删除 | 没有独立用户价值，或已被应用能力替代 |

优先检查任务分流（Task Triage）、任务环境、任务研发、任务验证、任务收尾和产品入口 Buildr 技能，因为它们直接决定智能体的日常执行成本。

### 4. 加强工作资产和上下文组织

在任务系统收敛的同时，逐步建设：

- 工作资产目录（Work Asset Catalog）；
- 按范围、类型、来源和关系查询；
- 内容读取和来源追踪；
- 新鲜度与漂移诊断；
- 任务引用的工作资产；
- 跨会话、跨智能体的任务接续。

Buildr 组织广义上下文中的范围、关系、来源和工作资产，智能体继续负责检索、判断相关性，并形成任务上下文和每次请求上下文。

## 七、推进顺序

1. **形成共同基线**：以本文明确里程碑、目标、架构和问题；
2. **设计目标任务模型**：先定义日常任务和受控任务的边界；
3. **梳理全部技能**：按照目标任务模型决定保留、合并、简化和删除；
4. **重构日常任务路径**：优先降低缺陷、耗时和词元消耗；
5. **抽离高风险专用能力**：收敛正式验证、发布和自举；
6. **加强工作资产与上下文**：支撑完整产研协作；
7. **再评估多人共享形态**：模型稳定后再建设服务端（Server）或云端（Cloud）能力。

## 八、成功标准

重构取得效果时，应该看到：

- 人能够直接理解任务目标、进展、风险和结果；
- 普通任务不再默认进入完整正式生命周期；
- 任务系统缺陷和恢复分支明显减少；
- 智能体开始真实工作的时间更短；
- Buildr 调用次数、任务耗时和词元消耗明显下降；
- 技能数量、重复职责和跨技能交接开始减少；
- 发布、部署和安全删除等高风险边界仍然严格；
- 工作资产和任务状态可以被后续会话与不同智能体接续；
- Buildr 从“复杂的任务治理系统”收敛为“日常好用的产研工作平台”。
