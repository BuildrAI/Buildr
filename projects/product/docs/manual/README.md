# Buildr + Agent 日常操作手册

这是一份面向团队成员和 Buildr 协作者的简明手册。它只介绍我们日常怎么使用 Buildr 和 Agent，不展开命令行（CLI）、内部架构和完整产品能力。

第一版先把已经跑通的工作方式写清楚，后续根据大家的实际使用反馈继续迭代。

## 一句话工作方式

**在 Buildr 中组织工作，通过 Agent 开展工作。**

Buildr 管理可长期复用的工作事实、工作方法和任务过程；Agent 负责理解目标、查找相关信息、使用工具并推进任务；人负责提出目标、补充业务判断和确认重要决定。

日常使用时，不需要先学习 Buildr 命令。进入正确的工作空间（Workspace），直接告诉 Agent 你想完成什么。

## 开始一项工作

一次完整表达通常包含四件事：

1. **目标**：想解决什么问题。
2. **已有信息**：相关资料、项目、服务（Service）、代码仓或线索。
3. **期望结果**：先要结论、方案，还是直接实现。
4. **边界**：哪些内容不要改，哪些决定需要先确认。

例如：

> 检查支付退款失败的问题。先查清业务流程、历史约定和代码入口，给我原因、依据和修复方案，暂时不要修改。

如果不知道工作属于哪个项目或代码仓，也不用先猜：

> 我想处理支付退款问题，请先根据当前工作空间帮我确认相关项目、服务和资料范围。

## 日常最常用的说法

| 你想做什么 | 可以直接这样说 |
|---|---|
| 查业务或代码事实 | “查一下这个业务规则从哪里来的，给我结论、依据和不确定项。” |
| 先审查，不修改 | “先检查现状和问题，给我方案，暂时不要改。” |
| 讨论和收窄方案 | “基于刚才的结论，给一个窄方案，说明影响范围和取舍。” |
| 开始实施 | “按这个方案实现，保留无关改动，完成后告诉我改了什么。” |
| 验证结果 | “验证当前改动，说明覆盖范围、结果、耗时和没有覆盖的部分。” |
| 正式收尾 | “收尾。” |
| 复盘执行过程 | “复盘这个任务，重点看耗时、令牌（Token）消耗、重复尝试和人机协作。” |
| 更新工作空间 | “更新 workspace，并检查同步后的 Buildr 状态。” |

这些不是固定口令。自然语言说清目标和边界即可，Agent 会根据工作空间中的规则和技能选择具体流程。

## 五种常见场景

### 1. 有问题，先问 Agent

当你想知道某个业务口径、历史决定、表结构或代码行为时，先描述真实问题，不必先知道文件名、表名或代码位置。

Agent 会在当前权限范围内，从项目事实、历史记录、规范、代码和其他已授权来源中查找依据，再给出结论和不确定项。Buildr 的作用，是让这些信息和查找方法不只停留在某个人的记忆或某一个代码仓里。

### 2. 先审查，再决定是否修改

当问题还没有查清时，明确说“先不要改”。Agent 应先确认事实来源、当前实现、影响范围和风险，再给出建议。

你确认方案后，再单独授权实施。这样可以把调查结论、业务决定和代码修改分开。

### 3. 从需求持续推进到交付

对需要持久交付的工作，Agent 会在 Buildr 中建立或恢复正式任务（Task），准备隔离的任务环境，并根据变更性质选择直接修改当前事实，或先建立窄的 OpenSpec 变更（Change）。

你不需要手工维护这些过程信息，只需要在关键节点确认目标、范围、业务语义和风险。Agent 应持续报告当前阶段、已经成立的证据、阻塞项和下一步。

### 4. 验证与收尾分开

“实现完成”不等于“已经验证”，“验证通过”也不等于“已经交付”。

- **验证**：证明当前内容是否符合已有要求，并说明覆盖缺口。
- **收尾**：在验证和审查完成后，执行安全可确定的提交、集成、推送和任务环境清理。

“收尾”不授权强制推送、丢弃改动、改写共享历史、删除远端分支或替你决定语义冲突。遇到这些情况，Agent 必须停下来说明影响并请求决定。

### 5. 任务结束后复盘

任务完成或放弃后，可以让 Agent 复盘本次执行效率，重点关注：

- 总耗时和可见的令牌（Token）消耗；
- 重复检查、重复运行和失败重试；
- 哪些信息反复由人补充；
- 哪些流程让 Agent 绕路；
- 哪些经验值得沉淀为工作资产或后续任务。

如果只想先保留复盘内容，可以说：

> 先记录复盘，处置保持待处理，不创建后续任务。

复盘中的改进建议不会自动改变产品、规则或技能；是否处理、如何处理，需要再次确认。

## 几个重要的授权边界

- “检查一下”默认是只读调查，不等于授权修改。
- “按方案做”授权当前方案内的实施，不自动包含提交、推送和清理。
- “验证一下”授权验证当前目标，不等于接受风险或正式交付。
- “收尾”只包含当前流程可以安全确定的常规交付动作。
- “先记录复盘”只记录复盘，不自动处理建议或创建关联任务。
- 涉及删除、覆盖、强制推送、共享历史改写或业务语义取舍时，Agent 必须单独说明并取得确认。

## 并行工作与任务接续

- 一个独立目标使用一个独立 Agent 对话，避免在同一对话中混入无关工作。
- 同一个目标尽量在原任务中继续，让 Agent 复用已经形成的任务事实和证据。
- 多个目标可以并行，但每个目标应有独立范围和任务环境，避免共用未确认的改动。
- 大任务需要拆分时，先让 Agent 给出子任务边界、依赖和最终集成方式，再决定是否并行。
- 恢复历史工作时，优先提供任务 ID 或让 Agent 从 Buildr 中查找正式记录，不要只凭聊天标题猜测。

## 在 Buildr Web 中查看进展

不需要打开 Buildr Web 才能工作；它是任务和工作空间事实的人类查看入口。

常用路径：

1. **工作空间**：打开 Buildr Web，选择目标工作空间。
2. **项目 / 服务**：查看项目范围、服务关系和当前 Git 观察事实。
3. **任务**：进入任务列表，打开目标任务。
4. **任务详情**：通过“概览、研发、证据、复盘、环境”查看当前过程信息。

Buildr Web 当前主要用于查看和有限维护。正式任务由 Agent 创建和执行；Buildr Web 不启动或管理 Agent 会话，也不会替 Agent 执行开发、验证、收尾或环境清理。

## 当前需要知道的限制

- Buildr 仍处于预发布阶段，Buildr Web 和部分工作流会继续迭代。
- 工作资产可以通过文件系统和 Git 协作；当前任务过程信息保存在各工作空间的本机结构化存储中，不会自动跨机器同步。
- Agent 的结论仍受当前资料质量、可访问范围、工具和权限影响；重要业务结论应要求给出依据，并由合适的人确认。
- Buildr 不替 Agent 思考，也不会自动把所有资料塞进模型上下文。Agent 仍需根据任务主动发现和选择相关信息。

## 如何反馈

使用过程中遇到问题，可以按下面的最小格式反馈：

```text
工作场景：
我对 Agent 说了什么：
实际结果：
哪里卡住或重复了：
希望 Agent 或 Buildr 怎么改进：
```

我们重点收集三类反馈：Agent 是否找到了正确事实、过程边界是否清楚、哪些经验值得沉淀为团队共享的工作资产。
