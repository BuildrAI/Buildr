# Buildr 整体认识

Buildr 把组织的工作事实和工作方法沉淀为可共享、可追溯的工作资产（Work Asset），让不同成员和智能体（Agent）能从同一份依据开始，并把工作持续推进到交付。

任何人进入组织都可以从一句自然语言指令开始，由智能体（Agent）准备工作环境并进入任务。你可以请它理解已有业务与代码、推进一次改动，或把做成的工作方法留下来供下次使用；无需先学会全部内部模型和命令。

**在 Buildr 中组织工作，通过智能体（Agent）开展工作。**

## 为什么需要它

一次工作做成之后，背景和方法往往仍散落在聊天、个人经验、文档和不同工具中。换一个人、换一种智能体（Agent）工具，或者改动涉及多个实现时，这些信息就需要重新解释和拼接。

Buildr 让值得复用的部分成为共同维护的基础：业务目标能连接实现职责，工作方法能进入不同工具，进行中的成果能被其他参与者找到并接着做。它带来的价值是减少重复理解和环境漂移，而不是保证所有信息已经齐备或所有工作都会自动完成。

## 谁负责什么

| 参与者 | 主要职责 | 人如何参与 |
|---|---|---|
| 人 | 表达目标、约束和业务取舍，给予必要授权并验收成果 | 在对话中说明意图，在页面中查看材料、填写意见和作出明确选择 |
| 智能体（Agent） | 查阅当前事实，选择方法，形成方案、实施、验证并推进交付 | 在已有授权内持续工作，需要新决定时解释影响 |
| Buildr | 治理长期资产，连接范围与来源，保存可接续结果并保护具体写入 | 通过 Buildr Web 查看同一份成果，通过确定性能力维护它 |

能由智能体（Agent）在现有工具和权限内完成的动作，默认由它直接执行。人的手动操作是主动选择或无法代办时的兜底。Buildr 的约束保护对象、授权、内容保全和真实结果；内部登记或辅助信息不足，不应扩大成无关工作的阻塞。完整依据见[核心规则](../../services/buildr/resources/workspace/AGENTS.md)与[产品定位规范](../../openspec/specs/agent-first-product-positioning/spec.md)。

## 三组关键关系

### 从业务目标找到真实代码

| 对象 | 负责回答 | 与其他对象的联系 |
|---|---|---|
| 工作空间（Workspace） | 我们共同工作和发现资料的范围在哪里？ | 容纳组织的资产与登记入口；其中的所有文件不都属于受管资产 |
| 项目（Project） | 我们要实现什么业务目标或长期工作？ | 引用目标所需的实现职责，可以先于具体代码建立 |
| 服务（Service） | 哪一部分实现承担这项职责？ | 可被多个项目（Project）引用，指向一个代码库实例（Repository Instance） |
| 代码库实例（Repository Instance） | 实际使用哪份代码，来源和位置是什么？ | 可以承载多个服务（Service），声明与当前检出状态分别观察 |

因此，一个业务目标可以跨多个实现，一份实现也可以被多个目标共用。目录嵌套不决定业务归属，也不决定 Git 边界；没有服务（Service）的项目（Project）仍然可以开始工作。具体关系和修改影响见[项目、服务与代码库如何协作](architecture/project-service-repositories.md)。

### 从工作方法到可发现入口

规则（Rule）保存边界，技能（Skill）提供可复用方法，规范（Specification）描述业务与产品承诺。命令（Command）声明可使用的外部工具，组件（Component）把相关源资产组织起来统一维护。这些是当前形式，工作资产（Work Asset）仍是开放概念。

Buildr 保留受管源文件，再适配到不同智能体运行时（Agent Runtime）的发现入口。这样，同一套工作方式可以复用，生成入口也能重建；发生内容或归属冲突时，需要先核对，不能静默覆盖。实际工具、登录态和个人凭证属于使用者的环境，不放入组织源资产。来源、组合与适配边界见[Buildr 技能体系](architecture/buildr-skill-system.md)。

全部潜在来源组成工作信息空间（Work Information Space）；其中被治理的长期资产及发现入口，形成共享工作环境（Shared Work Environment）。上下文（Context）表示当前范围内可能相关的信息；智能体（Agent）结合代码、数据库、网页、用户输入和工具结果，选择形成任务上下文（Task Context），再把本次需要的请求上下文（Request Context）放入有限的上下文窗口（Context Window）。Buildr 组织来源与关系，相关性仍由智能体（Agent）判断。概念区别见[术语表](glossary.md)。

### 从当前目标到可接续成果

正式任务（Task）保存目标、范围、关系和结果；工作摘要（Work Context）保存当前进展、下一步及需要人处理的事项。审查（Review）和验证（Verification）保留各自的结论与未覆盖部分，代码、规范、文件和业务系统继续承载实际成果。

Buildr Web 让人查看这些材料并参与判断。人的答复保存后，智能体（Agent）在继续时重读当前事实；答复本身不启动执行，任务状态也不能代替实际交付证据。完整过程见[从需求讨论到任务收尾](architecture/task-system.md)。

## 当前边界与进一步探索

当前 Buildr 以本机使用为主。长期源资产可通过文件与 Git 协作，任务等本机记录不会自动跨机器同步；浏览器页面、命令入口和智能体（Agent）使用同一组产品能力，不各自保存一套业务事实。安装、适配、诊断和具体实现按需查阅[架构与专业参考](architecture/index.md)。

企业云服务、完整权限系统、托管网站服务、多用户协作、代码托管平台集成、跨机器自动恢复、系统级钩子（Hook）和全部智能体适配器（Agent Adapter）仍不属于当前完整承诺；独立桌面内嵌界面与自包含安装器也属于未来方向。设想与当前能力分开，后续方向见[产品方向汇总](../../docs/roadmap/product-directions.md)。
