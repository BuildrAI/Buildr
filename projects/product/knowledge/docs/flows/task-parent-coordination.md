# 父任务协调（Task Parent Coordination）

父任务（Parent Task）组织一个整体目标和多个可独立交付的成果。智能体（Agent）负责规划、推进和核对成果；人负责目标、关键决定与明确完成授权；Buildr 保存各自状态、关系和完成依据。子任务（Child Task）全部结束，只说明可以核对整体结果，不会自动完成父任务（Parent Task）。

本文说明怎样协作、怎样完成以及如何处理变化。完整工作链路见[任务系统架构](../architecture/task-system.md)，实现位置见[任务系统代码地图](../../code-map/task-system.md)。

## 谁负责什么

| 参与方或内容 | 职责 | 留下的事实 |
| --- | --- | --- |
| 人 | 明确整体目标、约束，审阅成果并授权完成 | 可回查的原始指令或页面明确确认 |
| 智能体（Agent） | 拆分独立成果、判断依赖、推进工作、核对总体验收 | 当前计划、真实成果和逐项处置说明 |
| 父任务（Parent Task）与子任务（Child Task） | 分别承载目标、范围、状态和结果 | 已有任务记录及直接父子关系 |
| Buildr | 读取同一当前事实，检查记录版本、关系和完成输入，安全保存 | 当前记录、完成时间、验收与授权依据 |

简单计划直接写在目标说明中；复杂计划使用已有文档，并从任务说明链接过去。计划说明分工、依赖、验收标准和剩余范围，不另建一套计划数据库。代码、文档和业务系统中的实际成果，仍以各自当前内容为准。

## 如何组织和推进

1. **按独立成果拆分。** 例如后端能力、前端体验、跨服务业务验收可以各自交付；同一成果内的调查、编码和测试步骤不必各建一个子任务（Child Task）。
2. **按现场判断下一步。** 智能体（Agent）重读计划和实际成果，在已有授权内选择可推进的工作。每项工作按自身需要选择工作位置、规范、审查和验证，不能继承其他任务的通过结论。
3. **把变化写回当前成果。** 新增范围、提前覆盖、被替代和剩余工作要写清楚。整体目标或验收边界改变时由人决定，不能因为当前一批工作结束就缩小目标。
4. **用工作摘要（Work Context）接续协作。** 进展、待处理事项和人的答复可保存在当前摘要中。答复可供智能体（Agent）理解授权，但保存答复不会自动执行完成动作。

任务管理（task-manager）技能（Skill）提供具体操作方法；Buildr 没有把上述判断固化成统一执行链。嵌套父任务（Parent Task）逐层独立，一层完成不会递归结束其他层。

## 从总体验收到完成

完成包含三个不同事实：**直接子任务（Child Task）均已结束、整体目标已核对、指定父任务（Parent Task）已有明确完成授权。** 三者齐备后，调用者才能提交当前完成依据；应用还会在写入时重新检查记录。

![父任务完成：当前观察、明确授权与安全写入](../../archify/flows/task-parent-coordination.html)

图中通过与拒绝是互斥分支，日常进展和人的答复不会自动触发完成。

总体验收必须覆盖整体目标及全部直接子任务（Child Task）。对已完成项说明真实成果，对已放弃项说明替代、删减或遗留处置；放弃不等于交付。测试通过、子任务（Child Task）终态和记录数量，都不能独立证明整体目标已经实现。

明确授权可以来自本次对话中仍有效的用户指令，也可以来自 Buildr Web 的明确确认。已经获得的授权不因阶段切换重复索取；“继续开发”或“完成这个子任务（Child Task）”不能推导为完成整个父任务（Parent Task）的授权。

调用者通过一次 `task parent inspect` 取得当前目标、直接子任务（Child Task）和同一次观察的 `recordDigest`、`snapshotIdentity`。随后提交总体验收、逐项处置、真实授权来源以及已观察版本。网页和命令行（CLI）共用完成应用；成功后只更新指定记录，保存 `parentCompletion`，并不执行 Git、发布或资源清理。

## 变化和失败如何处理

| 当前情况 | Buildr 的行为 | 调用者应怎样继续 |
| --- | --- | --- |
| 仍有 `todo` 或 `active` 的直接子任务（Child Task） | 拒绝完成，保留原状态 | 先处理剩余工作，不自动放弃或完成其他记录 |
| 观察后目标、范围、关系或结果发生变化 | 拒绝陈旧版本或观察身份 | 重新读取、核对成果和授权适用性，再形成当前输入 |
| 授权、总体验收或逐项处置缺失 | 拒绝不完整输入 | 补齐真实依据，不能编造授权或遗漏被放弃项 |
| 一次写入失败 | 保留已保存的记录 | 根据具体错误恢复，不用旧输入盲目覆盖 |
| 历史计划不可读或旧完成依据缺失 | 局部提示，当前关系和结果仍可读 | 保留历史事实，不回填授权、不据此重开任务 |

完成观察身份覆盖父子记录中与完成相关的当前事实，不锁定外部代码、文档或业务系统。智能体（Agent）仍需在验收时核对这些真实成果；Buildr 校验授权声明的结构和记录一致性，不独立认证自然语言指令的真实性。

如果已经误把阶段成果当成整体完成，在用户明确更正后使用既有状态更正动作。当前记录恢复为进行中，原结果和更正原因保存在 `resultHistory`；已经交付的独立成果不会被撤销。更正不能绕过下一次完成所需的依据与版本检查。

## 实现、依据与维护

[任务系统代码地图](../../code-map/task-system.md)按职责定位父子关系读取、完成输入、事务写入和页面入口。关键事实依据是[父任务记录规范](../../../openspec/specs/task-record/spec.md)、[父子观察](../../../services/buildr/src/modules/task/application/parent-coordination-application.ts)、[完成应用](../../../services/buildr/src/modules/task/application/task-command-application.ts)与[工作摘要应用](../../../services/buildr/src/modules/task/work-context/application/work-context-application.ts)。

代表性行为由[父任务应用回归](../../../services/buildr/test/integration/parent-coordination-application.test.ts)与[页面完成输入检查](../../../services/buildr-web/test/parentCoordination.test.mjs)核对。这里解释它们证明的职责，具体执行结果以对应实际报告为准。

旧父计划仅用于历史展示，不建立当前父身份，也不参与完成判断。父身份由显式 `isParent` 或真实直接子关系确定；建立后不会因解除最后一个子关系而取消保护。退役过程的背景见[历史审计](../../../docs/archive/2026-08-30-parent-child-task-audit.md)，它不替代当前规范和实现。
