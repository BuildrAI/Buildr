# Buildr 发布

日常修改使用既有受影响检查，源码包检查不等发布时才发现问题。发布同轮集中收集独立失败，运行中不改源码；经用户同意修复后，同轮只补失败及尚未执行检查；完整成功节点继续按本轮已观察结果采用；失败 Node 节点保留的文件成功须校验真实输入，仅补失败、新增或失效文件，共享实现／夹具变化扩大补验范围。新候选轮次完整执行。定位具体检查时通过公开入口显式选择准确检查，或使用 `test:related` 按当前请求选择，正常执行保留详细用例诊断和有效证明，通过后不再为取得正式结果重复执行。原包失败仍用原验包入口恢复同一原包。

验证范围是用户决定，不是发布器自行加严的门槛。用户声明不跑某类检查时，用 `--excluded-boundaries E2E --scope-statement "<决定>"` 一次性传入本地源码轮和 GitHub 候选：该执行边界下的检查不进入执行矩阵，聚合以 `declaredScope` 与 `notRun` 如实记录，发布消费接受这些声明未执行项。打包步骤 `candidate-artifact` 是发布前提，不按测试边界排除。声明只减少执行范围；任何真实失败、未声明的缺项或原包字节不一致仍使发布停止。

**固定候选 → 本机源码验证 → 本机制包一次 → 本机通用及本机系统验包 → GitHub 校验保全原包与证明 → 获准公开原包。** 本页是唯一发布流程入口；准备候选不自动公开。

新主包候选使用 `buildr.local-package/v1`。独立插件发布继续由插件自己的发布所有者处理；主包候选所需的插件构建与兼容检查在本机完成，远端只采用其原字节和证明，不再构建插件。

## 谁负责

发布编排拥有原包与不可变交接；验证框架拥有检查与内容适用性；GitHub 是数据校验保全、独立可选冒烟和受保护公开的执行环境，不是整条发布链的控制中心。

智能体（Agent）按 `buildr-release` 协调本机与 GitHub，人决定目标和公开授权。发布流程、打包及公开代码归 `buildr-release` 的随附脚本；检查定义、执行、结果复用、环境准备及汇总归验证框架。

## 怎么发布

根据真实本机系统对称分工，不固定维护者必须使用 macOS。

| 步骤 | 本机做什么 | GitHub 做什么 |
| --- | --- | --- |
| 1 固定候选 | 固定包、独立版本、分支（Branch）、准确提交（Commit）、比较基线及对端；先核对版本与发布说明，后续 `dev` 不自动进入 | — |
| 2 源码验证 | 通用功能和发布工具检查只跑一次；另跑本机系统的源码节点 | 不重复源码检查；另一系统源码专项按开发改动另外选择，不是每次发布自动全量前置 |
| 3 打包 | 在干净冻结检出目录生产一份主包原包，保留摘要与来源 | 不制包 |
| 4 验包 | 通用原包检查与本机系统验包；保留真实本机证明 | 只校验并保全本机原包和证明；不安装产品或执行重型验包 |
| 5 获准发布 | 核对准确原包及授权，发起发布 | 经受保护入口公开已验原包，回读 npm 与 GitHub；不重新打包 |

本机完成适用验证，不再强制等待对端系统测试。新 handoff 冻结 `buildr.local-required-remote-optional/v1`；汇总只要求本机和通用证明，并固定显示另一系统 `not-verified`。没有平台策略字段的历史候选保持双系统要求，不能为绕过旧失败静默降级。**没有对端证据，就不能宣称跨平台验证通过；此次流程重构没有修复此前的 Windows Web 超时。** 本机验包使用实际 Node `24.15.0`，不另跑当前版本。插件桌面仍按实际影响验收，见[插件说明](dsh-plugin-release.md)。

正常 `prepare --wait` 在本机源码证明齐备后自动制包和验包，再从已登记的 `verify.yml` 入口以 `preserve_only=true` 调用 `verify-package.yml` 校验并保全数据（可在中立系统执行，不构成该系统产品验收），无需为首次派发先把新工作流合入 main。本机缺项由智能体按既有入口补齐，不让人搬运文件或拼命令。等待期间只校验保留原包、读取同一远端运行，不重复启动本机检查。

独立插件与联合候选均在本机自动准备 DSH SDK、构建并完整验证插件原包。SDK 的固定源码、补丁、配方、工具、系统架构、实际依赖与生成物校验一致时复用；否则在新目录重建。独立插件远端只校验并保全同一插件及证明，不执行主包对端验收；完整源码差异需要主包 QA 时仍按真实影响保留。真实 DSH 桌面验收不由 SDK 或加载器检查替代。

SDK 下载缓存不随工作树隔离：使用所选 pnpm 在真实用户主目录下发现的标准 store；自定义位置可通过 `BUILDR_DSH_PNPM_STORE` 指定绝对目录。发现过程仍使用空认证配置，不加载用户凭据；各次源码、`node_modules`、补丁和输出保持独立。固定上游 Git 对象缓存在用户缓存目录 `buildr/sdk-git`，按仓库地址区分并串行更新；准确提交命中后无需联网，缺失时仅从官方仓库拉取固定 tag 并核对提交。缓存不是验证证明，异常锁不自动抢占。

本机准备可设置 `BUILDR_DSH_NPM_REGISTRY=https://registry.npmmirror.com/` 使用国内镜像，默认仍为 npm 官方源；仅用于 SDK 工具与依赖下载，不改变正式发布或版本回读。锁文件和完整性检查保持不变，明确的网络或缺包错误最多回退官方源一次；认证、证书、锁文件及完整性错误不换源重试。不修改全局 npm、Git 或 Clash 设置；Clash 路由优化以真实请求和对照测速为依据，TUN 已生效时不叠加未经证实的代理设置。

## 分发前的正式消费预演

本机必要检查通过后，准备自动只读预演原包和证明：主包采用已有源码／原包证明并调用正式发布器的读取与覆盖检查；独立及联合插件共用正式消费者的原包、完整验证与准确对端检查。不额外打包或执行测试，不伪造远端运行。每次预演隔离派生证据并保留成功／失败回执；失败返回 `local-consumption-preflight-required`，不分发、不重制包。

冻结候选的消费代码需要修复时，可为同一原包追加独立验证来源，不修改产品检出或原始证明。`preflightLocalConsumption` 显式接收 `verifierRepo` 与准确 `verificationSource`；执行前按交接中冻结的输入策略核对两份干净检出及完全相同的构建输入，仅允许 `plan`、`aggregate`。检查配方和证明输入继续来自原产品，汇总保留独立验证来源。非公开保全从 `verify.yml` 的 `local_package` 传入准确 `product_source`、`verification_source` 并设置 `preserve_only=true`；工作流先用原产品的绑定校验器核对构建输入，再加载独立验证代码。该绑定不授权测试重跑、制包或公开发布。

`verificationRules` 随交接冻结输入分类策略、配方、消费契约、平台策略及范围。新来源绑定 v2 显式携带分类策略版本及定义摘要；旧绑定 v1 保持兼容读取。已保存规则与新默认不同就报漂移，不覆盖旧选择。只有相同实际规则才采用既有证明，不能靠重复派发解决结构性不兼容。

普通开发反馈 CI 不准备 DSH SDK、不下载准确主包对端，也不构建插件集成输入；保留轻量源码检查，依赖这些环境的检查如实报告不可用，不作为已通过的发布证明。

新主包交接在本机正式消费预演通过后，将汇总随原始证明一起冻结；相同输入接续时复用该汇总。GitHub 的保全模式只核对冻结输入、规则、实际原包和必要消费覆盖，并标明证明来自本机，不再重复执行证明的 `plan/aggregate` 推导。没有该汇总的旧交接、显式对端检查和独立验证源仍使用既有推导路径；公开时的实时权限、来源、原包完整性检查不变。

## 可选对端冒烟

本机 macOS 时可另验 Windows，本机 Windows 时可另验 macOS；未选择时不自动派发，不成为准备或公开门槛。复用同一原包交接，从 `verify.yml` 设置 `purpose=local-package`、冻结 `local_package` 数据及 `diagnostic_only=true`（`preserve_only=false`）；工作流使用独立验证器检出目录，不执行数据引用内的代码。原包源码与工作流修复提交不同时，显式传原包的 `diagnostic_source_commit`，保留两者身份。

隔离入口 `node tools/development/run-isolated-workspace-check.ts --script test/verification/release/package-smoke.ts -- --artifact-dir <准确原包> --output <报告>` 只做一次安装、CLI帮助与身份、一次Web健康检查、进程清理，使用实际最低Node。没有SDK、源码全集、workspace init/sync/Doctor/卸载和第二次安装。`buildr.package-smoke/v1` 报告精确失败阶段及耗时，只作诊断、不生成候选 aggregate。保全或受保护公开仍需要 GitHub 服务；此次取消的是对端重型验包依赖，不是删除 GitHub 的全部职责。

## 不可变原包交接

原包、清单、本机源码及原包证明和范围声明按摘要绑定，通过独立、不可变的临时 Git 数据引用传输；分块避免单文件大小限制。产品源码引用保持原样，数据引用不进入 main，远端不检出或执行其内容。GitHub 核对摘要与本机证明后保全 `candidate-package` 与 `candidate-aggregate`，正式发布仍消费这份准确字节。交接不创建正式标签或 GitHub Release Assets，不替代 npm 正式分发。

数据引用使用原发布的临时候选命名空间，按发布结果及准确身份清理；未确认传输、验收或保全时保留并说明，不能仅凭“候选成功”假定已清理。旧运行使用原模型观察，不把旧失败转换成新候选。

`prepare --stop-after candidate` 停在验包：保全原包和证明，登记验证报告和结果材料，关联本轮过程报告，结束准备任务，并逐项清理或说明保留的临时资源。记录或清理失败只补相应动作。后续可明确接续同一冻结候选，再核对同树 `main`、准确对端、顺序及公开授权；纳入新源码仍须恢复活动准备。发布代码位于工作空间根的 `skills/buildr-release/scripts/`，检查明细和入口见[验证框架](../architecture/verification-framework.md)及[工具地图](../../code-map/product-verification-tools.md)。

正常运行使用 `--wait` 由程序等待远端终态，默认只输出摘要及变化的状态；完整结果用 `--output <file>` 保存，需要诊断时再选 `--detail full`。超时保留同一运行身份，继续原命令，不重新派发。缺少本机证明时按返回缺项调用现有检查入口，完成后接续。

主动停止本机等待时，保留最近观察的运行身份和已发生效果，返回 `waiting.status=cancelled`，不取消远端、不开始下一次恢复动作。已在执行的属主动作先收束其结果，再退出；后续依据保留结果接续同一请求，不把停止等待当作重新发布的授权。

主包和插件共用同一发布传播等待：正常最多查询24次、间隔20秒，版本可见即结束。命令退出码、每次回读结果与耗时写普通日志；短暂不可见继续等待同版本，不重新上传。插件原运行在回读阶段失败、随后同一原包已公开时，直接采用官方公开结果与原始运行记录补登记，保留失败历史，不为改写登记再派发一次远端恢复运行。

等待联合发布的下一包时，已确认成功的包不重复查询运行、下载记录或读取公开原包。声明完整时只下载当前待写入包的候选；新的公开写入仍核对当前对端，旧包缺少兼容声明时仍做必要的真实配对检查。登记与清理各完成一次，按实际返回值接续失败项；不为重复展示成功再跑检查或收尾。

相关开发检查在改动交付前完成；发布阶段集中处理实际失败，不在运行中修改冻结源码。README 固定标题、章节与编辑表达不检查。文档链接、架构和规范静态检查放在相关开发检查中，不再是候选必跑项。真实功能、数据保护、安装启动、核心页面及系统和 Node 兼容继续保留。发布完成不附带本机开发应用更新；登记以实际保存返回值核对，不反复进行界面验收。

## 失败从哪里继续

- 一轮集中收集互不依赖的失败，经用户同意修复后只补失败及未执行检查。先采用本轮普通日志中的成功结果，只准备、执行剩余缺项；平台失败只补对应节点，汇总失败只补汇总。源码检查正常中断后，确认子进程和共享环境已清理才保留完成项；强制杀死或清理不明不能冒充成功。
- 本机与 GitHub 使用冻结的同一比较基线；等待合并保护检查时保留原合并请求（Pull Request），继续同一 `prepare`，不重测或重建候选。
- 测试或工具修复不默认重打；只有产品或真实构建输入变化才使相关原包失效。共享不可变准备，不共享案例改过的数据。
- 请求结果未知先回读，保留已成立的公开事实；登记、清理分别恢复。本机开发应用更新是另行工作，由 `buildr-self-bootstrap-sync` 唯一执行器负责，不阻止发布完成。

## 历史远端制包模型的交接与耗时诊断

以下只用于接续已经保存的旧模型；新主包准备不进入这条远端制包、下载再补验链。旧 `prepare --wait` 观察到同一 run 的 `candidate-package` 已上传后校验准确字节，再交给本机验包。网络未知只观察，不重打包。旧候选失败及已发生的公开事实保持原样，不用新模型覆盖。

候选仍运行时只读同一运行、作业和原包，不重复 `git fetch` 或重新选择源码；进入真实主线采用仍刷新引用。工作流对已复用源码的 `skipped` 显式处理，原包与 Host Node 作业只在 plan/bootstrap 成功且确有缺项时运行，不创建零检查源码传递作业。

等待覆盖补验派发未确认、补验回读和主线采用中状态。摘要中的 `waiting.pollWorkMs` 是本机调用工作，`sleepMs` 是实际休眠；远端初始排队使用 run 创建至启动边界，作业／步骤时间分别列出。缺少边界为 `null`，进行中不估算总耗时；这些观察不改变候选通过条件。源码普通日志的 phases 另含准备、执行、清理与复用收束，结构化文件失败会在慢文件结束前输出；先据实际失败诊断，再决定修复及失效范围，不先反复修改超时。

## 验证消费与等待职责

发布编排经项目的 `release-verification.ts` 取得覆盖集合、证明传输及候选能力，检查输入计算由验证框架的 `candidate-check-inputs.ts` 维护。共享覆盖定义已从真实包检查实现中分开，生产和公开仍属于发布所有者；验证执行器通过明确适配消费产包能力。通用项目测试能力不承担本项目的发布模型。

正常入口保留 `prepare|inspect|publish|resume`；有界等待由 `release-operation-wait.ts` 执行，总入口提供准确操作，不增加状态库。逐包公开、请求日志、主线保全、登记和清理仍各由既有责任模块维护。前次公开请求结果不明时只回读同一准确版本和原包，注册表返回404不单独授权重发。


### 未公开新候选撤回

`release-orchestration-runner.ts withdraw` 默认只读计划；准确授权后携 `--authorized --plan-identity <摘要>` 执行或接续。只处理已终止、未公开且未主线采用的新模型选择；公开历史、活动 PR／运行或未知请求交回原恢复路径。先在规范工作空间 `.buildr/local/release-withdrawals/` 保全原包／证明、源码 bundle、日志及附件 ZIP，再清理当前选择的三个临时远端引用和当前运行准确附件 ID；运行历史、本机工作树／选择引用和其他轮次附件保留。意图先落盘，未知删除不重发，档案漂移就停止；撤回后的选择不能再次 prepare/resume/publish。此工具不承担主线回滚或撤销已公开版本。
