# Buildr DSH 插件发布流程

Buildr 在 DSH（DeepSeek Harness）里提供一个侧栏入口。本文说明这个插件的产物如何构建、随什么发布、由谁维护，以及它与 Buildr 正式版、开发版的关系。

## 责任边界

| 事项 | 归属 |
|---|---|
| 插件源码 | Buildr 服务：`services/buildr/resources/runtime/dsh/` |
| 插件产物（可安装包） | 单独构建，不随源码目录发布 |
| 正式包是否带产物 | 发布时以 `--dsh-plugin` 显式传入；不传则不承诺包含 |
| DSH 内的安装、启用、卸载 | DSH 自己的插件管理，不属于 Buildr |
| 真实桌面验收 | 独立结果，不与文件投射或构建通过混为一谈 |

插件不是 Buildr 的必需组件：不装它，Buildr 一切照常。

## 正式版与开发版

面向用户发布的是**正式版插件**：一个入口，打开本机的正式版 Buildr。它可以通过 npm 包名或代码仓库地址安装，不需要用户做任何渠道选择。

面向开发者的是**开发版入口**（包名 `@buildr-ai/dsh-plugin-dev`）：在本机已有 Buildr 开发版源码时，额外提供一个独立入口打开它。它只在开发者机器上构建，随源码工作空间存在，**不进入正式发布**。

两者各自独立：正式版插件只认正式版安装，开发版入口只认开发源码，互不回落。这样任何一方都不需要为另一方增加选择或判断。

## 构建

在 Buildr 服务的源码目录执行插件构建，产出未绑定本机信息的产物目录：

```
node tools/dsh/build-plugin.ts <sdk-dir>          # build/dsh-plugin（正式版）
node tools/dsh/build-plugin.ts <sdk-dir> --dev    # build/dsh-plugin-dev（开发版入口）
```

两种变体是同一份代码加不同构建期身份（包名、入口标识、标签、补丁层）。产物包含主机侧与客户端侧两半，以及生成的远程接口描述。构建会针对已核对的 DSH 基线逐个校验，基线变化时重新构建，不猜接口。

## 随正式包发布

正式包构建接受一个显式输入：

```
--dsh-plugin <built-bundle-dir>
```

提供时，逐文件校验同一清单后放入包内 `product/build/dsh-plugin`；未提供时不隐式扫描旧构建目录，也不让 DSH 软件开发工具包（SDK）成为普通构建的前置条件。

包内**不包含插件源码目录**：用户拿到的是可安装产物，不需要 clone 仓库自行构建。

## 从产物到可用入口

装进 DSH 之后没有额外步骤：插件需要知道的“Buildr 在哪里”由它自己发现。

1. 插件安装后即可加载；找不到 Buildr 时明确说明，而不是留下一个点不动的入口。
2. 插件第一次打开时**自己发现**本机 Buildr：先读 Buildr 自己的安装登记表，读不到再从运行本插件的 Node 推出 npm 全局模块目录。两条都不成立才报告“没有检测到 Buildr”。
3. 用户在 DSH 里完成安装与启用，重启后看到入口。

用户侧因此只有“安装插件 + 重启 DSH”两步，没有登记命令、没有渠道选择。发现结果不写盘，Buildr 升级或换位置都不需要重新登记。

## 变更与恢复

- DSH 升级导致席位或接口变化时，重新核对基线、重新构建产物，再按上面的流程更新。
- 入口失效时，先核对本机 Buildr 是否可用，再核对产物是否为当前基线构建。
- 卸载插件不触碰 Buildr；Buildr 卸载后插件入口应给出明确说明，而不是静默失败。

## 验证分层

以下都是**相互独立**的结果，任何一项通过都不代表其他项已通过：

1. 插件单元与集成测试；
2. 针对官方基线的构建成功；
3. 集成夹具通过（真实加载器、客户端挂载、渲染与卸载）；
4. 正式包内确实包含产物；
5. 真实桌面验收：入口位置、点击行为、对话保留、启动与重复点击、禁用与卸载。

第 5 项必须在真实桌面版执行一次，不能用前四项替代。
