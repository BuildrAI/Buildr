# 从需求讨论到任务收尾

范围：Buildr 的任务协作，依据 `dev` 提交 `1e353c9e`。本文讲清人、智能体（Agent）和 Buildr 的职责、交互与授权；图示展开完整过程，代码地图（Code Map）连接真实实现。

## 从讨论需求开始

人提出目标、约束和预期成果，智能体（Agent）先核对当前事实，再判断怎样推进。需要修改持久文件时，默认创建或复用本任务的独立工作树（Worktree）；改变产品承诺时，通过 OpenSpec 写提案、设计、规格和实施清单。纯调查、事实维护和已有契约内的小改动按实际需要选用这些能力。

方案审查检查准备做什么；实现结果审查检查实际做成什么；任务验证（Task Verification）说明真实运行过哪些检查。审查与测试由智能体（Agent）执行，Buildr 保存对应结果。具体方法见[任务分流](../../../services/buildr/resources/workspace/skills/buildr/task-triage/SKILL.md)和[任务审查](../../../services/buildr/resources/workspace/skills/buildr/task-review/SKILL.md)。

## 人、智能体和 Buildr 怎样协作？

| 参与者 | 职责与授权边界 |
| --- | --- |
| 人 | 表达目标、决定业务取舍、授予实施或交付权限并验收成果；可以在对话中表达，也可以在网页查看材料并答复。 |
| 智能体（Agent） | 读取现场和工作方法，讨论需求、分流、写方案、审查、实现、验证及收尾；在已有授权内持续推进，需要新决定时才请人处理。 |
| Buildr | 连接人与智能体（Agent）：治理规则（Rule）、技能（Skill）和能力绑定，管理工作空间（Workspace）、项目及隔离位置；通过工作台（Workbench）和任务页呈现关键过程成果、接收人的意见，并支撑具体操作、交付与自举。授权决定仍由人作出。 |

Buildr 把目标、方案、进展、审查、验证、人的意见和交付结果组织成可查看、可接续的成果；结构化记录链接实际文件，完整对话及逐次工具日志仍由智能体（Agent）的会话承载。需要人处理的事项由智能体（Agent）明确登记到工作摘要（Work Context）。Buildr Web 展示同一方案、进展或成果；人保存意见后，智能体（Agent）在继续前重读答复与当前文件。网页答复不会自动启动执行，也不会自动完成任务。直接对话中的授权同样有效；进入下一阶段不意味着重新索取已有授权。

## 职责怎样落到实现？

工作方法由技能（Skill）指导；任务、工作摘要（Work Context）、审查与验证各有自己的应用（Application）和当前版本。网页与命令行（CLI）共享这些事实，代码、规范和 Git 仍保存实际成果。代码地图（Code Map）先解释职责，再从规范与实现树下探到文件，最后连接专业方法和成果位置。

## 怎样完成收尾和自举？

[收尾与交付](../flows/task-closeout.md)把成果交到约定位置，保存已有任务结果，并由原所有者处理可安全释放的资源。任务记录为完成、代码推送成功、应用已激活是不同事实。父任务还需总体验收和明确指向它的完成授权，详见[父任务协调](../flows/task-parent-coordination.md)。

Buildr 自举只处理适用的已交付改动：唯一执行器核验交付范围，按需同步受管资产、提交并推送同步结果、更新开发应用，再核验开发入口及最终 Doctor。没有命中输入就不触发；局部失败保留已成立的交付，按当前事实接续。具体调用、成功标准与[现有表述差异](../../archify/flows/task-system.md#现有表述差异)放在图示依据中，主文不重复操作手册。
