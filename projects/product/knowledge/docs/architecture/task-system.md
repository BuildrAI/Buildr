# 从讨论到交付

一次工作完成，意味着约定成果达到目标并到达约定位置。人表达目标、约束和判断，智能体（Agent）依据当前事实推进，Buildr 保存可查看、可接续的材料。纯调查可以止于解释，小改动可以直接实施，不需要每次走完固定流程。

![完整过程与角色职责](../../archify/flows/task-system.html)

图示以涉及正式任务（Task）和 OpenSpec 的完整实现为例。走 OpenSpec 变更（change-flow）的任务默认有一次方案审查与一次实现审查，其他路径按需；是否需要收尾、自举或清理取决于本次目标、风险和工作现场，箭头不构成所有工作必须经过的阶段。

## 从目标形成可继续的工作

| 当前问题 | 要留下什么 |
| --- | --- |
| 要做成什么？ | 已确认目标、范围、限制与完成标准 |
| 如何推进，哪里需要决定？ | 实际进展、下一步、明确待处理事项及人的答复 |
| 怎样判断做到了？ | 实际成果、适用的审查（Review）与验证（Verification）、未覆盖范围 |
| 怎样结束本轮工作？ | 约定位置的交付、已有任务（Task）结果及可安全完成的善后 |

任务记录（Task Record）说明“这项工作是什么”，工作摘要（Work Context）说明“现在到哪里”，变更材料解释“准备怎样改”，实际成果证明“做出了什么”。当前工作节点不扩展为任务顶层状态，完整聊天和工具日志仍由会话系统保存。

页面展示已经保存并关联的材料，不会自动把对话整理成需求和方案。任务目标（`intent`）保持一句话级定位，关联变更的 `brief.md`（需求）作为需求正文优先展示；没有需求文档时如实显示任务目标。需要人在 Buildr 中接续时，智能体（Agent）保存目标和重要进展，并链接真实成果。小任务的方案可以直接写在目标说明里；采用 OpenSpec 时，任务（Task）关联变更并读取其中材料，不再复制正文。

## OpenSpec 变更怎样推进

改变产品承诺时，智能体（Agent）核对当前规范、实现与活跃变更，再形成提案、设计、规范增量和实施清单。已有同范围授权继续有效；涉及新的业务取舍或扩大副作用时，先给人可审阅的具体方案，再取得必要决定。方案存在或审查通过都不自动等于实施许可。

实施时按授权修改成果，运行适用检查并维护受影响知识。归档只在目标包含、材料已完成且相关规范一致时进行；归档成功不证明代码已交付，也不附带额外知识写入授权。中断时先核对当前文件与恢复现场，不凭旧记录重复写入。

工作位置、授权和具体操作分别由[任务分流](../../../services/buildr/resources/workspace/skills/buildr/task-triage/SKILL.md)、[OpenSpec 提案](../../../services/buildr/resources/workspace/skills/openspec/openspec-propose/SKILL.md)、[实施](../../../services/buildr/resources/workspace/skills/openspec/openspec-apply-change/SKILL.md)和[归档](../../../services/buildr/resources/workspace/skills/openspec/openspec-archive-change/SKILL.md)方法维护；行为承诺见[开发变更规范](../../../openspec/specs/buildr-development-openspec/spec.md)。这里不再维护第二份命令与执行清单。

## 人怎样看成果、作决定

Buildr Web 的“等我回应”显示已经明确登记的决定、验收或补充信息请求。人可以在网页或对话中答复；智能体（Agent）继续前重读事项与成果，判断答复是否仍适用。保存答复不会自动启动执行、完成任务（Task）或发布产品。Buildr 保存答复原意，不独立认证自然语言授权。任务收尾节点的“用户确认”展示同一来源：成果确需人验收确认时登记 acceptance 事项，没有登记时如实为空，不新增默认确认环节。

较大的界面变化可先制作经授权的界面原型（UI Prototype），普通小改动直接实施。原型可从任务（Task）相关材料按页面和状态查看，也可独立打开；它表达预计结果，不能代替真实数据接入与正式页面验收。归入阅读位置不代表批准实施。

原型可以属于关联变更，也可以是主工作空间（Canonical Workspace）中的本机成果。本机原型不会随代码提交交付，移交或长期保留时需要同时保全实际页面与构建来源。来源、隔离与读取边界见[原型阅读实现](../../code-map/task-system.md#原型阅读怎样落到实现)。

审查（Review）判断方案或成果的正确性，验证（Verification）记录真实检查及未覆盖项。正式审查与验证报告目前只在任务（Task）进行中时写入，这是记录操作的局部条件，不是所有工作必须先建任务的理由；收尾登记完成前先补登已发生但尚未保存的审查或验证。构建通过、测试通过、人的验收和实际交付是不同事实；检查选择见[测试建设与使用](workspace-testing-and-verification-framework.md)。

## 提交怎样关联到任务

有明确正式任务（Task）时，智能体（Agent）按 [Git 操作指引](../../../services/buildr/resources/workspace/skills/buildr/git-operations/SKILL.md)将任务身份写入提交说明。没有任务时继续普通提交，不为此补建记录。旧提交保持原历史，不为了补关联而改写。

任务详情的“提交记录”从明确范围读取当前可达的真实 Git 对象，包含尚未推送的本机提交；不自动抓取远端，也不扫描任意目录。页面显示读取范围、上限与局部诊断，部分结果不能用来断言没有其他提交。具体归属规则、命令与前后端实现见[提交记录地图](../../code-map/task-system.md#提交记录怎样落到实现)。

提交成功和任务关联分别核对：查询失败不否定已成功的提交，关联存在也不证明任务完成。查询不新增关联数据库，不改任务、审查或验证结果。

## 收尾：把成果交到约定位置

用户明确要求“收尾”时，[收尾方法](../../../services/buildr/resources/workspace/skills/buildr/task-finish/SKILL.md)指导智能体（Agent）完成当前范围内的实际交付、已有记录更新和安全善后。该指令覆盖可核验的常规 Git 提交、集成与普通推送；强推、改写共享历史、丢弃内容、发布、语义冲突取舍以及远端任务引用的创建或删除仍需相应授权。具体对象的持续授权以适用规则（Rule）为准。

有 Git 就核对提交及约定交付位置，有已有任务（Task）就保存结果；没有这些对象时交付成果本身，不为收尾补建记录。多仓库分别核对；约定目标包含部署时，推送代码不足以证明目标完成。

内容和相关运行条件未改变时，复用仍适用的检查。冲突处理、集成修改或未解决问题影响行为时，才补相关验证。登记失败不撤销已经成立的交付，清理失败也不自动表示成果未交付；必要成果尚未到位时，不能报告整个目标完成。

## 父任务怎样确认整体目标

父任务（Parent Task）组织整体目标，子任务（Child Task）承载可独立交付的成果。Buildr 保存关系和各自结果，不从子项数量推断完成比例，也不自动传播完成状态。

**普通完成入口**要求：直接子任务（Child Task）均已结束、总体验收覆盖整体目标与每个子项、指定父任务（Parent Task）有明确完成授权。已放弃项须说明替代、删减或遗留处置，不能当作交付。已有同范围授权持续有效，不要求每次提交重新询问。

**网页组合结束入口**允许人明确处置每个未结束的直接子任务（Child Task）：解除关联后独立推进、确认完成，或放弃。处置与父项结果一起保存；嵌套父任务（Parent Task）须先独立验收，或解除关联，不能从外层递归代为完成。人的一次网页确认不扩大为智能体（Agent）自行批量关闭其他工作。

两种入口都核对已观察版本和当前成果，变化后拒绝旧输入并要求重读。保存完成不执行 Git、发布或清理。误完成可用状态更正保留原结果和原因，已经交付的独立成果不会撤销。[父任务完成图](../../archify/flows/task-parent-coordination.html)只展开普通完成；输入、冲突和组合结束的实现见[父任务地图](../../code-map/task-system.md#父任务协调怎样落到实现)。

## 资源清理、自举与发布分别判断

资源由明确负责本次工作的智能体（Agent）核对后清理，接手者承担继续核验的责任。缺少 Buildr 历史登记时，可以提供明确的当前工作树（Worktree）对象，从真实 Git 身份重新核验，不补造创建历史；已有记录与现场冲突仍须停止相关删除。删除前确认归属、未保存内容和成果保留位置，不能证明安全时保留现场。任务完成、提交存在或端口相同都不能单独证明资源可删；具体操作由[工作树管理方法](../../../services/buildr/resources/workspace/skills/buildr/task-worktree/SKILL.md)及对应资源所有者负责。

Buildr 开发自身时，已交付内容可能还需同步到保留的工作空间（Workspace），更新开发应用并核验实际入口。仅安装了自举组件（Component）且改动适用时，由 `buildr-self-bootstrap-sync` 唯一执行器处理；任务编号可选，普通使用者不承担这项开发流程。[自举图与完成边界](../../code-map/task-system.md#自举图的适用条件)说明为什么同步、应用安装和完整激活须分别核实。

正式发布另行核对版本、源码、完整候选（Candidate）、唯一产物和授权，不能用任务完成记录代替，详见[发布流程](../flows/open-source-release.md)。旧数据保全属于[数据设计](buildr-data-design.md)，不是收尾清理许可。

更细的职责、来源和接口定位见[任务系统代码地图](../../code-map/task-system.md)。
