# 从需求讨论到任务收尾

一次工作完成，意味着约定成果达到目标并到达约定位置。人表达目标并作出重要决定，智能体（Agent）依据当前事实推进，Buildr 保存可查看、可接续的材料和结果。

本文跟随一次产品改动说明主要过程。纯调查可以止于解释，小改动可以直接实施；图中展示较完整的场景，各步骤按实际需要组合。

## 从目标走到成果

| 当前要解决的问题 | 谁参与，留下什么 |
|---|---|
| 到底要做成什么？ | 人说明目标、限制和业务取舍；智能体（Agent）核对现状，形成有依据的范围、方案和完成标准 |
| 怎样推进，哪里需要决定？ | 智能体（Agent）实施并获得反馈；Buildr 保存进展、下一步和明确待处理事项，人据同一材料答复 |
| 怎样判断做到了？ | 智能体（Agent）检查实际成果，说明审查（Review）、验证（Verification）及未覆盖范围；人按目标验收 |
| 怎样结束本轮工作？ | 智能体（Agent）核对实际交付、登记已有结果；资源所有者确认内容保全后安全善后 |

方法由目标与当前现场决定：工作位置和方案选择见[任务分流](../../../services/buildr/resources/workspace/skills/buildr/task-triage/SKILL.md)，检查范围见[测试建设与使用](workspace-testing-and-verification-framework.md)。已有授权继续有效，出现新业务取舍或需要扩大副作用时才请人决定。完整对话和工具日志仍由智能体（Agent）的会话承载，不必逐条复制到 Buildr。

## 三个不能混淆的边界

**人的决定保存后，仍需据当前事实执行。** 工作摘要（Work Context）保存进展、下一步、待处理事项和答复。人可以在对话或网页作出决定；智能体（Agent）继续前重读答复与成果。保存答复不会自动启动工作或完成任务，事项已经变化时需要重新判断。依据见[摘要与答复实现](../../../services/buildr/src/modules/task/work-context/application/work-context-application.ts)。

**完成记录与实际交付分别成立。** 完成状态保存成功、代码推送成功和应用已经采用更新，是不同事实。Buildr 检查当前记录版本并保存结果，交付仍从 Git、文件或实际系统核对。登记或清理失败不撤销已经成立的交付；必要成果未交付就不能报告整个目标完成。没有对应记录的普通工作直接交付，不为收尾补建记录。具体交付、验证复用与适用自举见[收尾与交付](../flows/task-closeout.md)。

**组合结束需要明确处置。** 子任务完成不自动表示整体目标已达成。普通父任务完成要求直接子任务已结束，并保存总体验收、逐项处置与明确授权。网页的显式组合结束还允许人对未结束的直接子任务选择“独立推进”“完成”或“放弃”，再一并确认结束；独立推进只解除关系，保留原状态。嵌套组合需到自身页面核对结束，或解除关系独立推进，不递归代为验收。

相关目标、关系或结果在观察后改变时，旧组合请求会被整体拒绝；成功也不生成测试通过或成果已交付的证明。当前依据见[任务记录规范](../../../openspec/specs/task-record/spec.md)与[任务结果写入](../../../services/buildr/src/modules/task/application/task-command-application.ts)。上方总图未展开这一显式组合分支。
