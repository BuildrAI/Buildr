# Buildr 怎样实现

本文帮助开发者判断改动属于哪里、会影响哪些事实，以及需要分别验证什么。Buildr 由三个服务（Service）协作：`services/buildr` 负责命令、业务能力、文件与 SQLite、本机网页托管和 Buildr npm 分发；`services/buildr-web` 负责 React 页面与交互；`services/dsh-plugin` 独立构建、验证和发布 DSH 桌面插件。三者共用一个 Git 代码库（Repository），各自维护版本与构建边界，沿用同一[产品术语表](../glossary.md)。

整体组成见[系统全景图](../../archify/system/buildr-system-overview.html)，下面按调用与写入职责展开。

## 一次操作怎样到达真实数据

![调用、数据与副作用责任](../../archify/flows/capability-data-responsibility.html)

一次写入从命令行接口（CLI）或网页进入所属应用用例。入口解析输入、展示结果；应用核对对象身份、已观察版本与业务条件；数据访问层（Persistence）读写所属文件或 SQLite。网页和命令入口使用同一应用，不各自保存一份任务状态或业务规则。诊断读取当前结果，不取得业务写入权。

开发入口 `projects/product/buildr` 委托服务（Service）的薄入口；正式 npm 命令进入同一产品。开发检出不能覆盖 PATH 上的正式 `buildr`。网页由功能客户端发起请求，本机宿主处理会话（Session）、静态文件及分发，业务协议仍由所属模块维护。

请求分发前，主机（Host）必须与本机服务实际监听的地址和端口一致；页面、静态文件和业务读取共用该边界。写入另外校验来源与会话（Session），不能用一项校验代替其他保护。入口及模块定位见[服务与工程地图](../../code-map/system-services-assets.md)。

## 职责怎样划分

后端启动装配、业务模块、本机网页宿主和通用技术机制各有边界。接口进入应用，再到领域判断或数据访问；领域层（Domain）不依赖上层或输入输出，应用层（Application）不解析终端参数，也不直接导入其他模块内部文件。模块只在存在真实职责时建立相应层次。

模块装配核对依赖顺序和提供者唯一性，以具名能力协作；确实需要延后连接时使用一次性绑定器（Binder），不恢复一个随处可写的全局业务对象。具体模块、连接点和一例完整调用见[模块内部地图](../../code-map/technical-layers.md)，本章不重复成员清单。

登记、资产同步、任务记录与个人偏好各有写入者。资产同步可以组合登记维护，却不取得登记的第二写入权；工作台（Workbench）聚合已有事实，也不因此拥有它们。用户项目测试声明用于发现与选择检查，不是 Buildr 的通用测试执行引擎。数据归属和本机状态见[数据设计](buildr-data-design.md)。

前端按功能维护页面、业务请求和完整交互，应用壳只组合导航及真正跨页共享的状态。缓存页面、筛选或草稿不表示数据一直最新；编辑前仍需核对当前事实，保存时比较已观察版本。工作摘要（Work Context）中的答复不自动启动智能体（Agent），界面原型（UI Prototype）不能继承正式页面的写入能力。具体状态与隔离边界见[前端技术层](../../code-map/technical-layers.md#前端技术层)。

智能体（Agent）生成由 `agent-operations` 统一管理登记、默认与单次选择、运行（Run）、取消和结果。Codex 使用 Buildr 按需启动、复用和回收的专用应用服务（App Server）；DSH 连接已运行桌面的 Buildr 插件，调用同一宿主（Host）的当前模型服务，每次读取当前默认配置并记录实际采用值，不启动独立 DSH 生成进程。两者按登记身份串行排队；DSH 空闲回收、取消与退出只释放本次请求和连接。提交说明由 `code` 准备有界材料并校验来源及结果，提交、推送继续直接调用 Git。

原生会话（Session）关联由 `native-session-links` 聚合 Codex 与 DSH 的多对多关系；`codex-desktop` 保留原有文件和深层链接（Deep Link），`dsh-desktop` 核验桌面范围并确认准确导航。原生程序继续保存对话与持续执行；一次生成不继承已有聊天的内容、工具或记忆。两条链路见[智能体（Agent）接入架构](agent-integration.md)。

既有外部连接（Connection）由 `connections` 维护本机工作空间（Workspace）SQLite 中的身份、配置和观察版本；密码独立加密并绑定真实目标。MySQL、旧 Nacos、Kibana 和 XXL-JOB 保持原入口与提供者（Provider），MySQL 查询工作区继续使用原工具。Kibana 网页只管理连接和数据视图（Data View），日志发现、只读搜索和统计由命令行接口（CLI）提供；应用不保存日志或固定故障流程。专业结果的完整性、字段、保护范围与账号权限按每次实际返回判断。职责见[既有连接专业能力](../../code-map/technical-layers.md#外部连接的公共身份与专业操作)。

技能声明的接入由 `connection-skills` 独立维护。它通过 `AGENT_ASSETS_SOURCE_READ` 读取技能（Skill）身份及安全源文件，重建声明目录并精确绑定实例；不导入资产模块的内部持久化实现，不新增技能加载器。新团队实例与团队认证在当前目录的逐实例文件保存，个人整组覆盖在本机加密存储；网页和 `buildr connection-skill` 共享该应用。类别（Category）只帮助发现，声明只渲染受限字段及槽位，页面不会自动安装程序或访问真实系统。

共享认证的程序接收方仅使用稳定声明；目录当前观察同时包含本机解析位置，变化时拒绝旧观察。程序状态逐项返回，测试与发现按其槽位（Hook）引用的程序判断，不因次要依赖缺失扩大失败。Nacos 专业结果通过显式受限本机文件接续，不要求通用模块解释发布、授权或业务产物。

新连接技能源统一位于 `skills/connections/<skill-id>/`，由同一技能清单（Skill Manifest）登记；Nacos 产品源在 `resources/workspace/skills/connections/nacos-connection/`，新安装按此映射。本轮是尚未发布的新模块，不提供开发期旧目录迁移层。页面展示系统与类别，接入声明以有序区块组织地址、团队账号和业务范围，高级字段及个人账号默认收起；同系统存在多种方法时才选择接入方式。

声明的 `presentation.groups` 只引用已有配置及认证字段，规定区块顺序与折叠；`categoryLabel/methodLabel` 只提供纯文本展示名。只读发现的 `hooks.inputs` 允许先以地址和完整认证获取业务范围，所有给定配置仍校验，连接测试不因此放宽完整配置检查。主测试使用团队候选，个人账号在次要区独立测试和保存；声明不会注入任意界面代码。

唯一已登记工作空间（Workspace）来源是新连接的配置入口；相关代码目录通过 Git 公共目录证明关联，独立副本和多源冲突不静默选取。资产取消登记和内置卸载复用既有影响披露结果，通过只读回调列出绑定实例并保留配置与认证；局部连接读取故障不阻止合法源操作。

Nacos 自带专业程序属于完整技能源，由通用入口独立启动；帮助及专业参数仍由程序解释，配置认证经私有子进程通道交接，标准输入（Standard Input）保持给业务数据。通用模块只校验本机身份、来源和观察版本；Nacos 负责远端对象、并发保护、生产逐次授权和成功失败未知结果。程序可执行、请求受理、回读一致、服务加载及业务验证不能互相替代，进程隔离不宣称安全沙箱（Sandbox）。调用链见[技能声明接入](../../code-map/technical-layers.md#技能声明接入与私有上下文)，数据位置见[两条连接路径](buildr-data-design.md#两条外部连接路径分别保存事实)。

MySQL、Kibana 与 XXL-JOB 也通过完整内置连接技能（Connection Skill）交付。MySQL 接入程序 `buildr-mysql` 随主包安装，仅负责连接测试和数据库发现；独立 `mysql-query` 模块提供查询、结构读取及本机偏好，经通用连接应用的内部 `useSelected` 端口核验明确实例和观察版本，不公开认证。新旧连接页复用 `features/mysql-query/` 的同一查询工作面。Kibana 与 XXL-JOB 的专业程序随技能源携带，后者的服务关联和逐次授权记录保存在实例隔离的专业私有状态；这些专业动作不进入通用连接模块。

## 写入保护和失败边界

| 对象 | 当前保护 | 不能据此推断什么 |
| --- | --- | --- |
| 任务记录与关系 | 同一 SQLite 事务（Transaction），写入比较记录摘要 | 数据库提交不证明 Git 或外部系统已经交付 |
| 多个受管源文件 | 管理锁、操作记录、修改前镜像和恢复 | 不是跨进程、数据库和外部系统的全局事务（Transaction） |
| 智能体（Agent）派生入口 | 文件清单、完整性和所有权回执（Ownership Receipt），冲突显式处理 | 内容相似不赋予覆盖或删除权限 |
| OpenSpec 主规范 | 锁定上游生成、校验并写入，Buildr 回读并保留恢复依据 | 不承诺整个上游归档为原子写入 |
| 本机实例与启动器（Launcher） | 产品身份、运行配置（Profile）及进程归属 | 名字或端口相同不证明属于当前安装 |

文件访问核对真实路径和作用范围，恢复前重新观察当前对象。局部失败只影响依赖它的动作；已经从 Git、文件或实际系统核实的交付，不因内部登记失败而被否定。数据位置与恢复条件集中在[数据设计](buildr-data-design.md)。

## 一次构建怎样成为同一份产品

后端协议定义生成两端数据传输对象（DTO）；前端源码构建为后端托管的 `web-dist/`；文件资源按清单选入运行负载。正式安装消费打包后的运行文件、网页和资源，不要求完整源码树或 Vite 开发服务器。更新 Buildr 因而包含网页，但正在运行的旧实例和工作空间（Workspace）采用结果仍需分别确认。

工程工具属于 `tools/`，普通生成结果属于被 Git 忽略的 `build/` 和 `web-dist/`。正式用户命令不加载开发工具；`buildr package check` 需要开发检出，不能作为安装后健康检查。测试库、协议生成与打包来源见[构建与消费地图](../../code-map/system-services-assets.md#构建与消费)，资源边界见[命令架构](../../../services/buildr/docs/cli-architecture.md#文件型交付资源)。

开发环境由[准备声明](../../../preparation.yml)、[Node.js 版本](../../../.node-version)和对应服务（Service）的包清单确定。类型检查、逻辑测试、真实页面交互、安装包消费和目标平台证据分别证明不同边界；构建通过不能替代其他验收。日常按改动选择已有检查，正式发布另行固定源码、完整候选（Candidate）和唯一产物，见[产品验证](verification-framework.md)与[发布流程](../flows/open-source-release.md)。
