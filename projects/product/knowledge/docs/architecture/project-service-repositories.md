# 项目、服务与代码库如何协作

这篇文章回答：三类对象分别负责什么，怎样从业务目标找到真实代码，以及修改关联或分支声明会影响哪里。依据当前规范与实现，不描述部署实例或运行中的服务进程。

## 从业务目标走到代码位置

| 对象 | 帮助你作出的判断 | 关键联系 |
| --- | --- | --- |
| 项目（Project） | 我们在实现什么目标，需要哪些实现职责？ | 用 `serviceIds` 引用所需服务 |
| 服务（Service） | 哪一部分实现承担这项职责？ | 用 `repositoryId` 指向唯一代码库实例，可用 `modulePath` 限定代码位置 |
| 代码库实例（Repository Instance） | 使用哪份代码、什么来源和集成分支，位于哪里？ | 声明来源及位置，实际检出状态另行观察 |

目录的物理嵌套不决定业务归属。一个实现可以被多个目标复用，一份代码基础也可以承载多个实现职责。正式定义见[项目术语表](../glossary.md)，引用基数见[对象关系规范](../../../openspec/specs/workspace-asset-relationships/spec.md)。

![项目、服务与代码库的引用关系](../../archify/flows/project-service-repositories.html)

图中的 A、B 是规范允许的共享关系示意，不表示当前工作空间必然登记了这两个名称。两条引用都指向同一个身份，不会因为第二个使用方出现就复制服务或代码。

## 怎样找到实际代码？

先从当前目标的 `serviceIds` 找到全局服务身份，再按 `repositoryId` 找到对应代码库。最后把实例实际目录与 `modulePath` 合并；没有模块路径时使用实例根目录。这个过程依据登记身份与位置，不按名称猜同一个 Git 地址下的任意目录。

例如，Buildr 的前后端实现分别在 `services/buildr/` 与 `services/buildr-web/`。这些子目录承担不同职责；它们是否共用代码库，以当前登记和真实 Git 根为准，不因目录名看起来独立即认定为独立仓库。

[代码库实例规范](../../../openspec/specs/repository-instance-registry/spec.md)区分声明与现场：登记可以先于代码准备，本地目录缺失时应提示待准备；集成分支是协作目标，不等于本地当前分支。需要并行维护同一远端的不同分支时，要保留不同实例身份及各自位置，不能把两个实例自动合并。

## 改动时，先判断影响范围

| 你想做的操作 | 当前行为与需要核对的范围 |
| --- | --- |
| 移除项目登记 | 保留项目目录、服务、代码库与历史任务，仅移除项目及其服务引用 |
| 登记已有项目 | 从工作空间 projects/ 下的未登记目录中选择，核对名称及服务关联，只保存登记，不补写原文件；不自动恢复原身份 |
| 解除一方关联 | 只移除当前引用；其他使用方、服务身份与代码保留 |
| 移除服务登记 | 解除所有项目对该身份的引用；保留文件、代码库和历史任务 |
| 调整服务职责或代码位置 | 核对所有引用方及模块路径，保证仍指向存在且允许访问的代码范围 |
| 修改代码库目录或分支声明 | 改变后续解析依据；保存声明本身不搬文件、不克隆、不切换分支 |
| 多人或多入口同时修改 | 保存时必须核对当前版本；陈旧修改被拒绝，需要重读现场 |

这些是[规范承诺](../../../openspec/specs/workspace-asset-relationships/spec.md)和[当前应用实现](../../../services/buildr/src/modules/workspace/application/asset-relationships-application.ts)中可核对的行为。删除登记与删除源码是不同动作，不应把其中一个推导成另一个。

## 哪些边界不能混淆？

**当前约束：** 一个服务身份只引用一个代码库实例，模块路径必须留在该实例内；项目引用可共享，反向关系由引用派生；写入必须保留其他对象与并发修改。这些约束由[领域校验](../../../services/buildr/src/modules/workspace/domain/asset-relationships.ts)及应用事务共同落实。

**设计依据：** 当前规范明确把业务引用、代码来源与本地检出状态分开。由此可以分别调整业务组织和核对代码现场，而无需把目录迁移、分支切换与业务登记混成一次隐式操作。这里说明规则带来的效果，不推测没有记录的历史设计动机。

**建设建议：** 修改共享职责前先查看全部引用方；调整代码位置时先核对实际 Git 根、分支与模块目录，再决定迁移或修改声明。建议本身不代表已执行。多方共享还应依据本次任务明确的项目范围、服务规则与实际代码规则协作，不自动合并所有引用方规则，见[作用域规则](../../../services/buildr/resources/workspace/AGENTS.md)。
