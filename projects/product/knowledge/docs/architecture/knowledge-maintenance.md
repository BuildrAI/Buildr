# 怎样建设和维护项目知识

知识帮助人和智能体（Agent）理解当前工作：文章解释目标、职责与取舍，技术图说明关系，代码地图（Code Map）把解释落到真实文件。规范说明应该怎样，代码反映已经怎样；发现差异时要把两边事实讲清楚，不能只改文章让它们看起来一致。

## 从一个阅读问题开始

可以先问“这个项目怎样工作”“一次请求经过哪里”或“哪些服务负责这个目标”。智能体（Agent）核对规范、代码和已有说明，再选择合适的解释粒度。普通提问先回答问题，不自动新增长期文档。

需要保留长期知识时，明确主题、关注范围和阅读问题。Buildr Web 的“构建架构知识”“构建技术图”“完善当前内容”等入口会准备可查看、复制的工作指令；还需交给智能体（Agent）实际执行。生成指令不等于调查或建设已经完成。

当前知识维护方法（`current-knowledge-maintenance`）组织这项工作，按需要使用图示、代码地图（Code Map）或术语维护。已经授权的主题应连同必要来源、引用和阅读关联完成；无关新主题、业务取舍或事实源修改另行判断。具体方法见[建设指引](../../../services/buildr/resources/workspace/skills/buildr/current-knowledge-maintenance/references/architecture-knowledge.md)。

## 正文、图和来源怎样放在一起

| 成果 | 适合回答什么 |
| --- | --- |
| 解释文章 | 为什么这样组织，各部分做什么，有什么重要边界？ |
| 技术图（Technical Diagram） | 对象、调用、数据或状态之间怎样联系？ |
| 代码地图（Code Map） | 职责由哪些真实目录和文件实现？ |
| 阅读索引（Knowledge Index） | 哪个主题关联哪些成果和来源？ |

正文保存在独立文件，`knowledge/index.yml` 只关联主题、成果与来源，不复制正文、不维护另一套历史。图源与展示放在一起；源码位置与说明应能相互核对。文件组织见[数据设计](buildr-data-design.md)，代码与页面实现见[知识实现地图](../../code-map/knowledge-maintenance.md)。

Buildr Web 按主题组织阅读，也提供全部资料检索。正文按打开的内容读取，文中登记的图和地图可以在旁边对照；某个文件缺失时局部报告，保留其他可读内容。阅读和刷新不改写知识成果；最近访问及收藏另存工作台（Workbench）偏好。

目录续页失败会保留已读内容，索引版本改变时提示刷新。页面不把旧摘要变化转成人的“确认已读”任务；当前没有知识编辑、历史对比或自动同步事实源的功能。

## 改动后维护什么

| 变化 | 需要核对的内容 |
| --- | --- |
| 文件移动或删除 | 找到替代来源，修正正文链接和索引关联；不保留只为占位的旧文章 |
| 职责、关系或行为改变 | 校准解释与相关图示，区分已实现行为和建议 |
| 新增有价值的主题 | 组织必要正文、图和实现入口，避免重复描述同一事实 |
| 代码变化但文章仍然成立 | 核对后保留，不为文件有改动就重画图 |

普通代码开发应先识别已有知识受到的影响。只有代码修改授权时，提出具体维护建议；已有同范围文档维护授权时，继续完成必要调整，不逐文件重复确认。验收看内容是否准确、关联能否打开以及阅读是否顺畅，链接检查不能代替正文审阅。

开发预览（Development Preview）可从已登记工作树（Worktree）读取那份代码及资料，并显示来源说明。预览启动时的分支与提交不是文件的实时版本；修改后仍需刷新。当前没有主应用内的“当前版本／开发中”切换，开发渠道标志也不代表所读文章正在开发。

依据见[维护规范](../../../openspec/specs/current-knowledge-maintenance/spec.md)、[读取行为测试](../../../services/buildr/test/integration/knowledge-query.test.ts)及[职责图](../../archify/flows/knowledge-maintenance.html)。这些是实现与检查入口，不代表当前会话已验证全部页面。
