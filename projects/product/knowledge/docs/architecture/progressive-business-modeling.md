# 渐进式业务建模

本文记录 Buildr 产品开发中的业务建模共识。它是一份持续演进的设计方法文档，不是产品行为规范、Rule 或 Skill。

## 基本原则

所有系统和产品都是迭代形成的。业务设计从当前需求所需的最小模型开始，随真实业务逐步扩展，不预先构建缺少需求支撑的完整模型。

## 数据模型

数据模型面向数据存储。它以业务的基本事实字段为基础，逐步设计数据主体、字段和数据关系，并最终用于建表或建立其他存储结构。

## 领域模型

领域模型是数据模型在应用系统中的业务映射。核心事实字段和关系应与数据模型保持一致，但允许根据应用表达需要，在字段命名、对象结构、集合和派生信息上存在适度差异。

## 广义业务建模

广义业务建模同时抽象业务数据和业务行为，包括静态的数据模型、领域模型，以及动态的业务流程和行为。

在系统架构中，广义业务建模主要对应：

- `domain`：表达业务数据及其在应用中的领域模型。
- `application service`：表达业务行为和业务流程编排。

## 与服务分层的关系

业务建模形成的主要业务分类，可以进一步成为服务源码中的业务模块。服务顶层优先按业务模块组织，业务模块内部再按技术职责分层。

业务模型与服务分层的基本映射如下：

| 业务建模内容 | 服务架构表达 |
|--------------|--------------|
| 数据模型 | 数据库表、文件结构或其他存储结构 |
| 领域模型 | `domain` |
| 业务行为与业务流程 | `application service` |
| 数据模型与领域模型的存取和转换 | `persistence` |
| CLI、HTTP、Job、MQ 等访问协议 | `interfaces` |

`persistence` 和 `interfaces` 是业务模型进入应用系统所需的技术适配，不代替数据模型、领域模型和业务行为本身。具体目录、依赖与运行时组装方式见[服务分层与模块组织](service-architecture.md)。

## 演进方式

本文只记录已经达成的共识。后续通过真实任务逐步补充具体推进方法；稳定且必须遵守的约束可以提炼为 Rule，形成明确触发条件、执行步骤和结果要求的方法可以进一步沉淀为 Skill。
