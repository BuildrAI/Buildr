# 数据保全

[阅读目录](../README.md) · [排查问题](troubleshooting.md)

Buildr 的资料文件与本机工作记录分别保存。只提交 Git，不能备份全部任务（Task）历史。更新或换机器前，可以把下面的话交给智能体（Agent）：

> 先核对当前 Buildr 版本、工作目录和已有数据，保留一份可恢复的副本，再进行更新。告诉我备份在哪里、检查过什么；不要覆盖原资料或把直接降级当作恢复。

你重点确认三个结果：**原版本和目录明确、备份位置明确、重要资料与记录可读**。下面的路径与检查细节供智能体（Agent）或维护者使用。

## 需要保留的内容

以下路径相对实际工作空间（Workspace），不是 npm 安装目录。

| 内容 | 保存位置 | 保全要点 |
| --- | --- | --- |
| 业务资料、规则（Rule）、技能（Skill）、代码 | 实际来源文件及各自 Git 仓库 | 同时保留未提交成果与外部仓库 |
| 任务（Task）、审查（Review）、验证（Verification）记录 | `.buildr/local/workspace.sqlite` | 停止全部写入后复制，保留当时仍存在的 `-wal`、`-shm` |
| 复盘正文 | `.buildr/local/task-retrospectives/` | 与数据库一起保留，数据库没有正文副本 |
| 每日演进 | `.buildr/daily-progress/` | 保存原文件，重新生成不等于恢复 |
| 未完成操作 | `.buildr/mutations/` 及相关恢复记录 | 保留记录、备份与当前文件 |
| 安装和目录归属 | 应用数据目录及管理记录 | 核对实际位置；不当作跨机器通用配置 |

数据归属及更多路径见[数据设计](../architecture/buildr-data-design.md)。副本可能含业务内容或凭证，应放在受保护的位置。

## 维护者执行顺序

1. 记录当前版本、程序入口、目录和目标版本，检查未完成操作。
2. 停止相关命令与应用写入。关闭浏览器不等于退出 Buildr。
3. 复制到新的受保护目录，核对文件清单及重要记录；外部仓库、未提交成果和独立工作树（Worktree）分别处理。
4. 在副本上检查数据库完整性，再按[命令参考](../../../services/buildr/docs/cli-reference.md)更新并检查一项代表工作。
5. 保留副本直到新版本已实际使用。失败时先保留现场，再判断继续修复或从副本恢复。

运行中的数据库需要一致备份能力；不能用普通文件复制假定得到完整快照。当前没有统一备份或跨机器自动恢复工具。

## 较早版本的数据提醒

当前迁移会退役旧执行、研发、环境、收尾聚合和部分复盘数据。可写打开数据库时会执行待迁移项，也会清理旧 `.buildr/asset-review/`、`.buildr/local/task-execution-records/`；有价值的旧内容需在新版首次写入前另外保存。

每项迁移分别提交，后续失败不会自动撤回前面已经完成的迁移。安装旧程序也不会降级数据库。因此，报错时不要假定数据完全没变，不要直接覆盖唯一现场。

换机器时，先迁移明确可移植的资料，再准备工具；本机记录和实际路径单独核对。实现依据：[数据库维护](../../../services/buildr/src/infrastructure/sqlite/workspace-sqlite.ts)。
