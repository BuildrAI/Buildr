# 文档维护

[阅读目录](../README.md)

把文档当成一本持续修订的书：读者能找到答案，每个主题只保留一份有效正文。智能体（Agent）负责随变化维护，人判断产品承诺和重要取舍。

## 放在哪里

| 内容 | 位置与边界 |
| --- | --- |
| 首页和目录 | 仓库首页、根 `docs/README.md`、`knowledge/README.md`；只介绍和导航 |
| 使用与开发说明 | `knowledge/docs/`；按读者问题分章 |
| 实现定位与图示 | `knowledge/code-map/`、`knowledge/archify/`；图源与展示共同维护 |
| 当前阶段的审查结果 | `knowledge/reviews/`；用于处理具体问题，不复制为长期产品手册 |
| 服务目录参考 | 暂存 `services/buildr/docs/`，只维护一份正文；当前正式包仅复制 `bootstrap-guide.md`。普通参考应归入知识目录，程序消费的必要文本归入 `resources/`，迁移时同步实际读取与打包路径 |
| 已发表文章 | `docs/publications/`；属于产品读取的内容数据，保留文章身份与发表记录 |
| 行为规范与单次变更 | `openspec/`；不是用户手册，不套用普通文档删除规则 |
| 可执行规则（Rule）与技能（Skill） | `services/buildr/resources/`；是产品资产，修改时核对消费者与实际行为 |

除以上职责外，不再新增平行文档区。源规则（Rule）和技能（Skill）的附件也不是手册副本；两者以链接连接。

## 写什么，怎样写

- **简约**：先回答读者的问题。删掉重复背景、过时过程、空模板和没有下一步作用的口号。
- **易懂**：首次使用以目标和例子展开；内部字段、命令参数和复杂限制放到参考章节，不能把维护过程转交普通用户。
- **图文配合**：关系、分支、状态适合用图；操作外观适合真实截图；比较适合表格。简单步骤直接写文字，不为“每篇有图”增加装饰。
- **高信息密度**：每段提供一个有效结论、操作或解释。专题保留必要深度，不把复杂内容压成读不懂的术语串。
- **有依据**：保留关键实现或规范链接。截图注明真实环境与用途，原型不能冒充已实现界面。

GitHub 可直接渲染 Mermaid。当前 Buildr Web 的普通正文不直接渲染 Mermaid，也不把图片路径当普通截图加载；交互图通过已登记成果展示。选择形式时核对实际入口，不能只确认文件存在。

## 更新、合并和删除

1. 优先更新现有章节。只有需要独立回答一个持续存在的问题时，才新增正文。
2. 多篇重复时，保全独有的有效事实，合并到最合适的一篇，删除旧正文并修正引用。
3. 过时说明、已实现的规划、无用模板和一次性旧审计直接删除，不再为普通文档建立归档目录。Git 保留修改历史。
4. 持续有效的设计理由留在相关章节；尚未实施且仍值得讨论的方向集中在一篇方向说明。
5. 删除前核对真实消费者。发表文章、运行时（Runtime）恢复说明、规范或仍被使用的成果，不能仅因扩展名相同就删除。
6. 本次改动结束时检查目录、相对链接、关键陈述与 `knowledge/index.yml`，并从读者入口走一遍受影响路径。

无需每次全库重写，也不要求人通读全部文档。内容变化只校准相关正文；阶段审查结束后，仍有用的结论进入对应章节，已经失去行动价值的报告可以删除。
